# HOP：面向人类编程

一个项目写出来不是只跑一次。它会被反复打开、修改、加功能、删功能，而每一次打开它的，都可能是一个对它一无所知的接手者：第一次来的新人，三个月后回来的作者，被打断后重新拾起的自己，一个刚开新会话、上下文被压缩过的 AI，或者你派出去、完全没有上下文的子智能体。

他们要的是同一件事：**零背景下打开项目，就能很快找到要改的地方，放心地改；想加东西直接加，想删东西直接删，不用大动干戈。**

所以写的时候，始终偏向两边：

- **为人类考虑。** 读代码的人会累、没耐心、视野窄、记不住、怕出错。
- **为未来的自己考虑。** 未来的你，上下文已经被压缩过；你派出去的子智能体，压根没有上下文。他们看不到你现在想了什么、试过什么、为什么这么选，只能靠项目本身。没写进项目的想法，等于没发生过。

## 怎么用它

下面十二条，是这两件事落到具体情况时常见的样子。它们是**例子，不是清单，也列不全**：真实项目千变万化，你遇到的形状（库、命令行工具、界面、跨进程的服务）可能一条都没提到。各条写到对应位置时再用，不需要提前全部过一遍。

**拿不准时，回到那两件事。** 遇到没写到的情况，或者某一条套上去反而更别扭，就跳过它，问自己一句：哪种做法让读的人更容易找到、更敢改，也让未来的自己少重新猜一遍？选那一种。两种都说得通，就选更简单、文件更少的那种。不要为了对齐某一条，做出实际上对人和对未来的自己更差的选择。

**判断不出来，就直接问人。** 几种做法各有明显的好处、你判断不了哪个对用户和未来的自己真的更好时，不要硬猜。涉及用户自己的数据、习惯和实际用法，或者每条路的代价都不小时，问一句比猜错强。另外有两件事必须先问：会影响项目外面的事，比如改接口、动已经存下的数据；在已有项目上做大范围的结构调整（见第 12 条）。

**边想边写，想定一件就写进文件。** 做一个新项目或一次大改动时，不要在动笔前把整个项目想完，也不要先在脑子里把代码起草一遍。想和写交替着来：

1. 定下项目由哪些主体组成、各叫什么名字，哪些东西会不断增加（第 1、2、9 条）。定下就马上把这些文件建出来，每个文件先只写一句话说明它管什么。建好的这些文件就是整个项目的目录。
2. 从主体文件开始，一个文件一个文件地写，入口最后写。写到哪个文件，才去想这个文件里的事：数据放哪（第 3 条），用户输入在哪检查（第 8 条），代码怎么写（第 5 到 10 条）。代码直接写进文件，边写边加注释。
3. 一个文件写完，补全它的文件头：怎么调用，调用示例长什么样（第 5 条）。
4. 全部写完后，把项目跑起来，每个功能都真的调用一遍，包括填错的情况，看结果对不对。钱算出一长串小数、数据文件建错了位置，这类问题读代码不容易看出来，跑一次就能看到。实在跑不起来，就告诉用户哪些没有验证过。
5. 最后扫一遍"常见信号"那张表，看到类似的就改。

已经写进文件的决定，不要回头反复比较；写到后面发现前面确实选错了，直接改掉就行，照这个思路写出来的项目本来就好改。

**数字是参考刻度，不是考试线。** 下面出现的"5 个左右""十来个"这些数字，是告诉你大概到什么程度该停下来想一想，不需要精确卡住，也不要为了凑数字去改结构。

**它管的是项目，不是回复的格式。** 给用户的回复怎么写，照用户或环境本来的要求来，这件事它不管，也不用在上面花时间。

## 接手者是什么样的

HOP 不按"聪明人认真读"来设计，而是按接手者真实的弱点来设计。

人**容易疲惫**，理解力随时间下降；**不想多动手**，改一处要动五个文件就不想改了，也不想为了加一个东西先去研究框架内部；**没有耐心**，找一会儿找不到就会放弃或者乱猜；**视野狭窄**，一次只看得到眼前几行，看到大段密集代码会直接跳过；**记忆容量小**，同时只能记住四五个东西；**容易遗忘**，看完这个文件再去看那个，前一个已经忘了一半；**不擅长抽象**，脑子里模拟不了多层嵌套、回调和跳来跳去的调用；**词汇量有限**，遇到生僻术语要停下来查；**推理消耗大**，每多想一步都在消耗力气；**害怕出错**，不确定影响范围的代码就不敢动；**讨厌不确定**，名字和行为对不上、改完不知道有没有问题，是最消耗人的状态。

AI 的弱点几乎一样，还多一条人没有的：**它看不见自己上一次的思考**。思考不进下一次上下文，所以同一段代码，AI 每次接手都要从头推导一遍，既烧输出，也占掉它本就不多的注意力。把判断和原因写在代码旁边，是唯一能跨会话留下来的地方。

所以设计基准是：**假设接手者只看得到几行，只记得住几秒，不愿意多推理，没有编程背景也要能看懂名字，而且第一次打开这个项目。在这种状态下还能找到、看懂、改对，项目才算合格。**

下面从项目整体开始，再到文件，再到每一行，最后是日常维护的方式。

## 一、项目层

项目层决定接手者能不能"找得到"。代码写得再清楚，如果接手者在目录里迷路，也等于看不到。

### 1. 按主体组织

接手者没有耐心、容易遗忘，所以找东西必须靠猜就能猜中，而且一件事的全部内容只在一个地方。

项目按业务里真实存在的东西（主体）来组织，比如订单、用户、会话、预算。每个主体一个文件，文件名就是这个主体的名字；这个主体的全部操作都写在这个文件里，方法名是动词。一个主体如果大到一个文件装不下，说明主体划分得太粗，应该拆成几个更小的主体，而不是把同一个主体拆成"定义文件、处理文件、工具文件"散落各处。

怎么判断一个东西要不要单独成为主体：它有自己的数据，或者接手者会专门来找它，就是一个主体，单独一个文件；它只是拿另一个主体的数据算点东西，就写成那个主体的一个方法。拿不准时，放进已有的主体文件里，不新建。比如一个网店项目，"订单"是主体，放在 `order.js`；"订单合计金额"只是把订单里的价格加一加，写成 `Order.total()`；"支付方式"会不断增加新的，是一类会增长的东西，按第 2 条放进文件夹。

主体叫什么：用用户自己描述需求时用的那个词，翻成最常见的英文单词，想到一个能用的就定下来，不要列一排近义词挑。比如用户说"下订单"，主体就叫 `order`；用户说"预约"，就叫 `booking`。避开和项目结构撞名的词，比如 `entry` 容易和"入口"混在一起。

文件夹的作用是把同一类东西放在一起好找。名字要让接手者不打开就能猜到里面是什么。判断一个文件夹该不该有，看两件事：里面是不是只有同一类东西；名字是不是一个日常词。两个都满足，这个文件夹就是对的。

分清两种归类，它们看起来像，其实相反：

- **同类归在一起，对**。几个小工具、几种导出格式、几种支付方式，各放一个文件夹，接手者知道"那张纸在那一摞里"。跨主体共用的小东西有专门一个文件夹，是有好处的，见第 4 条。
- **同一个主体按层切开，错**。把"会话"拆进 `controllers/`、`services/`、`repositories/`，接手者要找一件事得跑好几个文件夹拼起来。错的不是这些文件夹的名字，是把一件事劈成了几段。

不同的主体本身不是同一类东西，小项目里直接平铺在最外层，看文件名就知道是什么；主体多到一眼扫不过来时（参考：十来个），再按业务分成几个文件夹，比如 `shop/`、`user/`。同一类东西只有一两个时也直接平铺，不单独建文件夹，否则多一层要点开、还会让人怀疑"这个文件夹是不是快没用了"。

看的是每一层能不能一眼扫完：名字猜得到、同类在一处，就是对的。深一层浅一层不是重点，为了"更浅"把已经分好的东西拆散反而更糟。

比如一个 AI Agent 服务，好的结构是这样的，接手者看目录就能猜到每样东西在哪：

```
server.js        入口：接收请求，交给对应的指令
store.js         会话和配置：好几个主体都会改，所以集中放在这里
session.js       会话：创建、读取、删除
agent.js         对话：发送消息、停止任务
tool.js          工具扫描器：启动时登记 tools/ 里的每个工具
tools/           会不断增加的工具，一个工具一个文件
  read.js        读文件
  shell.js       执行命令
utils/           不属于任何单个主体、大家都用的小工具，两个以上才建
  fail.js        做一个带状态码的错误
  http.js        读请求内容、把结果写成 JSON 回复
```

坏的结构按技术角色分层，一个"会话"的逻辑被拆进四个文件夹，接手者要拼凑才能看懂：

```
controllers/SessionController.js
services/SessionService.js
repositories/SessionRepository.js
models/SessionModel.js
workers/execution_worker.py
```

### 2. 加删只动一处

接手者不想多动手，也害怕出错。如果加一个功能要去三个地方登记，他会漏掉一处；如果删一个功能要去三个地方清理，他不敢删。

会不断增加的那一类东西，比如工具、插件、导出格式、支付方式，放进同一个文件夹，每个文件按统一的格式写，由上层在启动时自动扫描、自动导入、自动登记。加东西只需要往文件夹里放一个文件，删东西只需要把文件删掉，任何中央文件都不用改。改一个功能只改它自己的文件，不需要去别处同步。

这条只管"会不断增加"的东西。数量少、很少变化的东西，比如一个小服务里的几条路由，直接写在一个文件里就好，不用为它做扫描，自动化本身也是要人看懂的代码。

比如 `tools/` 文件夹里每个文件都导出同样的三样东西：说明、参数、执行方法；文件名就是工具的名字，不在文件里再写一遍，这样名字只有一个来源（第 3 条）。`tool.js` 启动时扫描这个文件夹，按文件名把每个工具登记进来。想加一个"写文件"工具，只要新建 `tools/write.js`；想去掉"执行命令"工具，只要删掉 `tools/shell.js`。

自动化要有统一的、看代码就能预测的规则。像 Vue 响应式那样，只改数据界面就自动更新，规则永远一样，看代码就知道会更新什么，这是好的自动化。事件总线、魔法字符串分发这种，谁会响应要运行起来才知道，出了问题也找不到是谁触发的，这不是自动化，是藏起来的依赖。

### 3. 数据一个来源

接手者容易遗忘。同一份数据如果在两个地方定义，他改了一处一定会忘掉另一处，而且读代码也发现不了。

一份数据只定义一次。下游需要它时从来源提取或推导，不各自再定义一份。数据结构保持相近，扩展时只加字段，不改已有结构，这样下游的提取逻辑不用跟着改。

数据放在哪，看谁会改它：只有一个主体会改它，就由这个主体自己保管，比如 `order.js` 自己读写 `orders.json`，别的主体要用就调用它的方法，比如 `Order.list()`；好几个主体都会改它，就集中放进 `store.js`，让人一眼看到全部数据长什么样。不管放在哪，都不在别处再存一份。

数据文件的位置要固定，按代码文件所在的位置去找，比如 JavaScript 里写 `new URL('./orders.json', import.meta.url)`。只写 `./orders.json` 的话，程序会按启动时所在的文件夹去找，换一个文件夹启动，就会在那里新建第二份空的数据文件，看起来像数据丢了。

但要分清两种数据。**项目自带的**（初始数据、示例数据）跟着代码走，用上面的写法。**用户自己产生的**（对话记录、日志、用户存下来的东西）属于用户，放在用户的目录里（`%APPDATA%` 或 `~/.程序名`），不要写进代码目录——代码目录可能只读；升级、重装、或者干脆把项目删掉时，不该把用户的东西一起带走。

比如 `history` 保存完整的对话记录，发给模型的 `messages` 由 `Context.build()` 从 `history` 提取出来，两者结构几乎一样。以后给 `history` 加一个 `time` 字段，`messages` 的提取逻辑一行都不用改。

这里说的"只定义一次"，指的是需要保持同步的数据和逻辑。注释里为了让读者看懂而重复说明一下调用方式或数据格式，不在此列。

### 4. 流程一条线

接手者不擅长抽象，推理消耗大。一个功能的执行路径如果绕来绕去，他就追不下去。

所有业务都走同一条路：**入口 → 指令 → 数据 → 反馈**。

**入口**接收触发（HTTP 路由、命令行、界面事件、子进程发来的消息），把外面的东西变成指令需要的参数，交给对应的指令。入口不做业务判断。入口还负责一件事：整个项目只有这里统一接住错误，并把错误分成两种送出去。一种是**用户能自己改的**，比如填错了、要找的东西不存在，指令抛出它时带一个标记（HTTP 服务上就是一个状态码，比如 400、404），入口照这个标记把原因发回去；另一种是**程序自己的故障**，入口按"程序出错"处理（HTTP 上就是 500），也带上原因，方便定位。用户发来的内容格式不对，比如不是合法的 JSON，算用户填错了，不算程序出错。

**指令**是业务的主线，读数据、处理、改数据、返回结果都在这里，一个主体的全部指令在一个文件里。被入口直接调用的指令，在开头检查一次用户输入（见第 8 条）。

**数据**按第 3 条决定放在哪，要一眼能看出存在哪、长什么样。**反馈**是结果的出口，比如返回值、界面更新、推送消息。

**通用工具**是不属于任何单个主体、被好几个主体一起用的小东西，比如做一个能带原因和标记的报错、记一条日志、把 JSON 读写包一层。业务主体和会不断增加的同类东西都不算，它们是业务本身。通用工具放哪，看它有几个：

- 只有一个，平铺在最外层就行，名字说清它是什么（比如 `fail.js`），不用建文件夹。
- 到了两个以上，集中放进 `utils/`。理由和会不断增加的东西一样：同类东西一多，散落在主体文件之间就找不到了，接手者看目录分不清哪些是业务、哪些是零件。放进 `utils/` 之后，加一个工具就是往里放一个文件，主体文件一个都不用改。

判断一个小工具够不够格进 `utils/`，用三句话问它：名字里有没有业务词；它有没有自己的数据文件；业务规则改了它要不要跟着改。三句的回答都是"没有、没有、不用"，才放进去。`fail.js`、`log.js`、`http.js` 合格；`bill.js`、`export.js` 不合格，它们是业务主体，本来就该各自站在最外层；`orderTotal.js`、`userCheck.js` 不合格，业务词写在名字里了。

这条是在防 `utils/` 变成第二个主体目录。一旦业务逻辑也塞进去，接手者就得在两个地方找同一件事，第 1 条和第 3 条同时被破坏。

一件事只服务一个主体时，不要为了"看起来整齐"把它挪进 `utils/`。跟着那个主体待在同一个文件里，或者就在它旁边，找的时候在一个地方就能看完。

最后看整条路径通不通：从入口顺着调用往下读，每经过一个文件都在做实事，没有只转手、不干活的中间层，比如 controller 转给 service、service 再转给 repository。一般两三个文件就能读完一个功能；加上一个"会不断增加的东西"里的那一个文件，比如某个导出格式，也很正常。

## 二、文件层

文件层决定接手者打开一个文件后能不能马上看懂。

### 5. 打开就懂

接手者视野狭窄、没有耐心，打开文件的前几秒决定了他会不会继续读。

每个文件开头都有一段文件头注释，用大白话说清三件事：这个文件管什么，怎么调用，调用示例长什么样。示例要能直接复制去用。

接下来是业务本身，业务步骤占据文件的主体位置，读起来就是这件事的流程。类型定义、格式转换、兜底处理这些不是业务的东西，要么交给库和框架，要么做成通用工具，不堆在业务前面挡住视线。

文件头写多长，看这个文件对外承担多少：别人会 import 的库模块，文件头要写全——调用示例、每个参数的取值、为什么这么设计，写长了是对的；只是内部一个环节的文件，文件头保持短，让人尽快看到业务步骤。

```js
/*
工具扫描器：读取 tools 目录，把每个工具文件登记进来，再按名字执行。
调用示例：
  await Tool.scan('./tools')
  const schema = Tool.schema()
  const result = await Tool.run('read', { path: './a.txt' })
*/
```

打开一个发送消息的指令，看到的应该就是"保存用户消息 → 请求模型 → 保存回复 → 推送给界面"这几步，而不是先看到一屏参数检查。

文件内用空行分段，每个函数前用段落标题 `// --- 添加任务 ---` 隔开。注释的具体形态见第 10 条：一段里每行代码的右边配一条短注释，对齐到同一列，形成"左边代码、右边解说"的两栏，让接手者只扫右边一栏就知道流程。

## 三、函数和行

这一层决定接手者读每一段代码时要花多少力气。

### 6. 装得下

接手者记忆容量小，同时只能记住四五个东西。

一个函数里同时要记住的变量和概念要少（参考：5 个左右），一屏能读完。超过了，先想能不能换一种数据组织让它变简单；还是太大，就按业务步骤拆开。一行只做一件事，链式调用不要太长，不为了"结构好看"引入中间层概念。

什么样的函数可以拆出来：拆出来的那一块是一个完整的业务动作，能用一句大白话说清它做什么，比如"算出这个月每个分类各花了多少"，而且拆完以后原来的函数一眼就能读完。这样的函数即使只用一次也可以拆。说不清业务、只是把几行代码挪走的小函数不要写，比如 `validateInput`、`processInput`、`formatHelper`，它们逼接手者跳过去看、再跳回来；这样的几行就写在原地，用段落注释标明。被多个主体反复用到的逻辑，才提取成通用工具，放进 `utils/`（见第 4 条）。只服务一个主体的逻辑，留在那个主体里。

### 7. 平铺直叙

接手者不擅长抽象，脑子里模拟不了多层结构。

代码从上往下顺序执行，读到哪里就执行到哪里。不用继承，不套设计模式，条件嵌套尽量不超过两层，用提前返回代替层层 if。不用回调套回调，不用事件总线在背后传话，不用字符串拼出要调用的方法名。一个东西依赖谁、数据从哪来到哪去、会改动什么，都直接写在调用的地方。

比如要清空已完成的任务，就在 `clear()` 里直接调用 `remove()`，而不是继承一个 `BaseTask` 再重写方法。要停止任务就直接调用 `Agent.stop()`，而不是发一个 `'stop'` 事件等别处去响应。

### 8. 信任内部数据

接手者推理消耗大。每一行防御代码都在逼他想"这是在防什么情况"，业务反而被淹没。

项目内部的函数之间互相信任，拿到数据直接用，不检查类型，不判断是不是空，不包 try-catch，不写"以防万一"的兜底。数据真的有问题，让程序直接报错，报错信息会指向问题所在。

检查只在系统边界做一次：用户输入、对外提供的接口、外部系统返回的数据。用户输入的检查写在被入口直接调用的那个指令开头，发现不对就抛出一个说明原因、带标记的错误，入口会把它发回给用户（见第 4 条）。输入要先整理再检查：先去掉首尾空格，再看是不是空的，否则只填了空格的标题也能存进去。

几个指令要用同一种输入时，检查放在它们共同调用的那一层。比如"列出账单""月度汇总""导出"都要用月份，而后两个都会调用 `Bill.list(month)` 取账单，月份写得对不对就只在 `list` 里检查一次。找不到共同的一层，就写一个检查方法让它们一起用，不要各写一遍。数据过了边界，里面所有代码都信任它。

要区分的是：业务里本来就会出现的情况要写，比如按 ID 找不到这条记录、第一次运行还没有数据文件；能从结构上消掉的就消掉，比如启动时先建好数据文件，读的地方就不用再判断。为了防"不应该发生的情况"而写的代码不要写，比如检查一个内部传进来的参数是不是字符串。

有一类问题不是防御，而是业务本身要做对：钱、时间、数量这些东西的计算。比如金额是小数时直接相加会得到 `0.30000000000000004`，要按"分"来加，最后再换回"元"；这属于业务规则，写在算钱的那一行，加注释说明原因。

比如 `Agent.send()` 是被入口直接调用的指令，开头检查一次用户输入不为空。它内部调用 `Loop.run()`，`Loop.run()` 再调用 `Context.build()`，这一路都直接传、直接用。

### 9. 说人话

接手者词汇量有限，也会被名字误导。

名字用普通人日常就认识的词，标准是没有编程背景也看得懂。`summary`、`export`、`report`、`format` 这类日常词可以用；`repository`、`dispatcher`、`middleware`、`handler` 这类只有程序员才懂的词不用。业务或行业里本来就这么叫的名字直接用，比如 `csv`、`markdown`、`http`。

**同时，在达到"看得懂"这个前提下**，如果一个词恰好也是同类库或框架里的标准说法，就直接用那个词——不要换。接手者在其他项目见过这个词就认识，比如 `maxTokens`、`schema`、`callback`；换成"更白话"但生态不用的词，反而让他在多个库之间切换时多花力气做映射。判断标准是：**这个词能不能让一个完全陌生的接手者（包括不懂这门语言的人）光看名字就明白这是什么东西**。`maxTokens` 能猜是"最大 token 数"，`schema` 能猜是"结构定义"或"格式"，即使你从没见过这个库也能推出来。只有名字推敲不出来、像自造的黑话（`procData`、`doStuff`、`xfrm`），才改成白话。

文件名就是里面那个东西的名字。业务主体的名字是名词，比如 `order.js`、`budget.py`；一类会增加的东西里的一个，文件名就是它自己的名字，比如叫 `read` 的工具就是 `tools/read.js`，叫 `alipay` 的支付方式就是 `payments/alipay.js`。不用"动作加技术角色"拼出来的名字，比如 `execution_worker.py`、`recall_services.py`。

要避开的词，标准是它描述的是"在架构里扮演什么角色"，而不是"这是什么东西"：`repository`、`dispatcher`、`middleware`、`handler`、`controller`、`service`、`manager`、`processor`、`factory`、`adapter`。接手者不知道一个项目分了哪几层，看到这些词猜不出里面是什么。反过来，`utils`、`helpers` 这种词说的是"一堆杂用小工具"，谁都知道里面是那种随手能用的小东西，可以给放通用工具的文件夹用（见第 4 条）。但它们不能用来给业务文件起名，`orderHelper.js` 不行，因为名字没说出它到底干什么。

能用一个词说清就用一个词。名字里不重复上下文已经说过的信息，归属关系靠 `主体.方法` 来表达。名字说什么，代码就做什么。

```
sandbox.py            对：一个主体，一个名词
execution_worker.py   错：动作加技术角色

Context.build()          对
Context.buildContext()   错：context 说了两遍

messages      对
messageList   错：List 是多余的类型后缀

users            对
UserRepository   错：概念太重，还是术语

tools/           对：谁都看得懂
utils/           对：谁都看得懂，里面是杂用小工具
repositories/    错：技术分层词
orderHelper.js   错：用一个含糊的词盖住业务文件，没说清它干什么
```

几个主体都有构建方法时，都叫 `build()`，靠 `Context.build()` 和 `Agent.build()` 区分。缩写只用行业里本来就这么叫的，比如 id、url、api、http、json、csv、html、css、ui；不用为了少打几个字母自己造的，比如 usr、cfg、mgr、btn、msg、err、cb、fn、ctx、req、res。

### 10. 注释讲业务

接手者推理消耗大、容易遗忘。他需要有人在旁边告诉他三件事——**这一步在干什么、别人怎么调用、当时为什么这么写**。注释就是干这个的，按这三件事分成三种。

**第一种，步骤注释：最常写、密度最高的那种。** 一行代码，右边配一条短注释：一句话说清这一步在干什么，压在一行内，同一段里的注释对齐到同一列。整段读起来就是"左边代码、右边解说"的两栏。

```js
tools.push(item)       // 将 item 推入数组              ← 复述语法，没用
tools.push(item)       // 把新工具加入待登记列表         ← 说业务，有用
```

这样写是为了那两件事：人（尤其是非英语母语的人）可以**只扫右边一栏**就把流程读下来，不用逐行去理解代码；未来的自己和子智能体拿到这段代码，扫右栏就能恢复"当时这一步在干什么"，不用重新推。

**所以要密。** 一段里大多数代码行的右边都该有一条；连续三行以上没有注释，差不多就是漏了。别因为"这行一看就懂"就跳过——对第一次打开这个文件的人，没有哪一行是一看就懂的，`const total = items.reduce((a, b) => a + b, 0)` 也要说一句"把所有条目的价格加起来"。import 说明引入了什么能力，export 说明导出了什么，提前返回说明为什么返回，都算在内。检验办法：把一个文件的代码全删掉、只留注释，读的人仍然能知道这个文件的实现步骤和细节。

一整段连起来应该长这样——右边一栏单独读下来就是这件事的流程：

```js
// --- 记一笔账 ---
const text = await readFile(file)              // 把账单文件整个读出来
const list = JSON.parse(text)                  // 文件里存的是一个 JSON 数组
const good = list.filter(b => b.amount > 0)    // 金额为 0 或负数的当没填，丢掉
total += good.length                           // 记进去几条，回给界面显示

// --- 算这个月的总额 ---
const cents = good.map(b => Math.round(b.amount * 100))  // 先换成"分"再算：小数直接相加会得到 0.30000000000000004
const sum = cents.reduce((a, b) => a + b, 0)             // 加完还是"分"
return { count: good.length, total: sum / 100 }          // 最后换回"元"交回去
```

**第二种，接口说明：别人怎么调用。** 别人会调用的函数（导出的、跨文件用的）属于接口，要用这门语言标准的文档格式——JS/TS 用 JSDoc（`@param`、`@returns`），Python 用 docstring，Go 用紧挨函数上方的注释——这样编辑器、LSP、`help()`、AI 的符号搜索才能取到。

**第三种，为什么注释：当时为什么这么选。** 这种只在**真的有原因**时才写。值得写下来的原因有这些：

- 看起来多余、甚至反直觉，但必须这么写的（换个写法就会坏）
- 试过别的写法不行的：写清试过什么、为什么不行
- 特殊的数字、特殊的顺序、非默认的取值：说清为什么是这个值
- 从别处抄来的做法：写清抄的哪里、为什么抄它而不是自己写
- 实测踩过的坑和量到的数字（多少倍、几次成功几次失败）原样写下来，下次不用重新踩
- 这个文件或函数的职责边界：它负责什么，什么交给调用方

```js
// 压缩用的消息原样当 messages 发，不要 JSON.stringify 塞进一条 user 消息：
// 引号会被二次转义，实测请求膨胀到目标上下文的 1.51 倍，157011 token 直接 400。
// 本该救命的压缩，反而第一个把上下文窗口撑爆。
const result = await LLM.chat({ ...llm, messages })
```

```js
const SMOOTH = 0.3   // 新样本占的权重。越小越稳，越大越快跟上；0.3 是实测够用又不抖的值。
```

**宁缺毋滥，只限这一种。** 没有取舍的行硬编一个理由，是在凑字数，凑多了会让人连真的理由也不信——步骤注释反过来，一条都不能省。原因写在旁边，未来的自己才不会把有意为之的写法当成错顺手改掉。

注释用接手者读得最快的语言写，跳读最省力——语言本身不强制，清楚、能一眼扫过去就行。

## 四、维护方式

项目的大部分寿命花在维护上。维护时的做法决定了项目是越来越轻，还是越来越重。

### 11. 修问题做减法

接手者容易疲惫、讨厌不确定。补丁会让代码越来越多，每个补丁都是一个新的"这是在防什么"。

出了问题，先找它为什么会发生，然后改代码或者改结构，让这个问题不可能再发生，而不是在出错的地方加一个判断把它盖住。只有增加功能才应该增加代码，修问题通常应该让代码持平或者变少。如果一次修复让代码变多了，停下来想想有没有让它变少的改法。

比如一个函数偶尔收到 `null` 就崩溃。加一句 `if (!data) return` 是补丁。找到上游为什么会传 `null`，让它不再传，或者把数据设计成本来就不会有 `null`，这才是解决。

### 12. 改到哪里整理到哪里

接手者会在旧代码上继续工作。旧代码如果没有注释、名字难懂，下一个人会遇到同样的困难。

修改已有代码时，被改到的那一片要同时达到上面这些要求：补上注释，改掉难懂的名字，去掉不需要的防御代码。不只在新写的代码上加注释，改动过的旧代码同样要有。

整理时分清里外。别人依赖的东西默认保持原样：接口的路径和字段、返回的数据格式、已经存下来的数据文件。这些一改，调用它的程序和旧数据就坏了。

只在一个文件内部的改动（比如换个写法、拆个函数）可以直接做。要移动、改名已有文件或重排目录，属于结构改动；发现结构层面的问题（比如加一个功能要改好几个地方）也一样，先告诉用户问题在哪、打算怎么调，得到确认再动。

觉得对外的部分也该改，比如字段名不好懂，就作为建议告诉用户，说清会影响谁。改之前先把相关功能调用一遍，记下结果；改完再调用一遍对照，除了有意修掉的问题，对外的结果应该和原来一样。

## 常见信号

写完或改完代码后，可以扫一遍下面这些信号。它们不是验收清单，只是"这里可能对读的人不友好"的常见样子。看到类似的情况，回到那两件事想想怎么改。

| 看到这个信号 | 对应哪条 | 可以怎么改 |
|---|---|---|
| 加一个会不断增加的同类东西，要改两个以上文件 | 加删只动一处 | 做约定文件夹加自动扫描 |
| 删一个功能后还要去别处清理 | 加删只动一处 | 去掉手动登记，让位置决定是否存在 |
| 为很少变化的东西做了扫描和登记 | 加删只动一处 | 直接写在一个文件里 |
| 文件名是"动作加技术角色"，或带 service、manager、handler、worker | 按主体组织、说人话 | 改成里面那个东西的名字 |
| 一个主体的逻辑分散在多个文件夹 | 按主体组织 | 合并到以主体命名的一个文件 |
| 为只装一两个文件的同类建了文件夹，或者把同一个主体按层拆成几个文件夹 | 按主体组织 | 平铺出来，或改回按主体命名的一个文件 |
| 项目已有能正常工作的目录结构（`tests/`、`scripts/`、按能力分的模块目录），却为了"层级更浅"去拍平 | 按主体组织 | 保留原样，只有明确发现问题时才改 |
| 两个以上通用小工具散落在各个主体文件旁边 | 按主体组织 | 集中放进 `utils/` |
| `utils/` 里出现带业务词的文件，比如 `orderTotal.js` | 数据一个来源 | 挪回对应的主体文件 |
| 同一个字段或配置在两处定义 | 数据一个来源 | 保留一处，另一处从它提取 |
| 好几个地方都能直接改同一份数据 | 数据一个来源 | 交给唯一的主体保管，或集中到 store |
| 追一个功能时经过只转手、不干活的文件 | 流程一条线 | 去掉中间层，让入口直接调用指令 |
| 文件开头没有调用示例 | 打开就懂 | 补文件头注释和可复制的示例 |
| 打开文件先看到一屏定义和检查 | 打开就懂、信任内部数据 | 把非业务代码移走或删掉 |
| 读一个函数要同时记住很多东西，一屏读不完 | 装得下 | 换数据组织，或按业务步骤拆 |
| 说不清业务、只是挪走几行代码的小函数 | 装得下 | 写回用它的地方 |
| 嵌套很深、回调套回调、事件总线 | 平铺直叙 | 提前返回，直接调用 |
| 内部函数里有类型检查、空值检查、try-catch | 信任内部数据 | 删掉，检查移到边界指令的开头 |
| 同一种输入在好几个指令里各检查一遍 | 信任内部数据 | 放到它们共同调用的那一层，只查一次 |
| 所有错误都按同一个方式返回，或者把错误原因藏起来 | 流程一条线 | 区分"用户能自己改的"和"程序故障"，都带原因 |
| 钱直接用小数相加 | 信任内部数据 | 按分来加，最后换回元 |
| 输入没去掉首尾空格就检查是不是空的 | 信任内部数据 | 先整理，再检查 |
| 数据文件路径只写了 `./data.json`，换个文件夹启动就找不到原来的数据 | 数据一个来源 | 按代码文件所在的位置去找 |
| 用户的数据（配置、对话记录、日志）写进了代码目录 | 数据一个来源 | 挪到用户目录，比如 `~/.程序名` |
| 名字里同一个词出现两次 | 说人话 | 删掉重复的部分 |
| 没有编程背景就看不懂的名字 | 说人话 | 换成日常词，或同类库通行的叫法 |
| 连续三行以上代码没有注释 | 注释讲业务 | 每行右边补一条，说这一步在干什么 |
| 只有"这一步干什么"，看不出为什么这么写（特殊数字、反直觉的做法没写原因） | 注释讲业务 | 把原因和试过的做法写在旁边 |
| 修一个 bug 后代码变多了 | 修问题做减法 | 找到原因，从源头消除 |
| 改过的旧代码没有注释 | 改到哪里整理到哪里 | 给改动的那片补齐 |
| 整理完，接口的路径、字段或返回格式和原来不一样了 | 改到哪里整理到哪里 | 改回原样，想改就先问用户 |

## 接手已有项目时

每次接手一个项目，包括新会话继续开发时，先按接手者的视角走一遍，再开始写代码：

1. 只看目录和文件名，试着说出每个文件管什么。说不出来的地方，就是"按主体组织"的问题。
2. 挑一个功能，从入口追到数据，看看有没有只转手、不干活的文件。有，就是"流程一条线"的问题。
3. 设想加一个会经常增加的同类东西，数一数要改几个地方。超过一处，就是"加删只动一处"的问题。
4. 打开几个核心文件，看有没有文件头调用示例，注释是不是在讲业务。
5. 把项目跑起来，把现有功能各调用一遍，包括填错的情况，记下结果。有些问题读代码看不出来，比如数据存到了别的文件夹、只填空格的标题也能存进去，跑一次就能看到。
6. 把发现的问题按项目层、文件层、行的顺序告诉用户，项目层的问题影响最大，优先处理。

不要依赖"我记得之前是这么写的"。新会话的 AI 和第一次来的新人一样，只能相信眼前看得到的东西，所以项目本身必须把一切写在明处。报告一个问题之前，尽量先让它真的发生一次。做不到的，要说明这是推测，以及是根据什么推测的。

## 最后的判断

写完之后，把自己想象成那个最弱的接手者：刚打开这个项目，很累，只看得到几行，记不住前面，不想推理，看不懂术语。问自己五个问题：

**能不能很快找到要改的地方？能不能放心地改？加一个同类的东西，是不是放一个文件就行？删一个东西，是不是删一个文件就干净？一个丢了全部上下文的自己（或者子智能体），只看项目本身，能不能接着往下做？**

五个都能回答"能"，这个项目就是面向人类的。有哪一处拿不准，就选让这些问题更容易回答"能"的那种做法，然后继续。项目再大，也要让每一个局部读起来像一个小项目。

## 示例

**一个完整的小项目**：[examples/ledger/](examples/ledger/) 是按这份思路写的记账服务，可以直接运行（`node server.js`）。看它的目录就能对上大部分条目：

```
server.js          入口：把请求交给指令，统一接住错误，按状态码发回去
bill.js            主体"账单"：记账、列出、删除、月度汇总，账单数据只有它读写
export.js          导出：启动时扫描 formats/，按格式名导出
formats/           会不断增加的导出格式，一种格式一个文件
  csv.js
  markdown.js
fail.js            做一个带状态码的错误，好几个文件都用它
```

想加一种导出格式，只要往 `formats/` 里放一个文件，其他文件一个都不用改。

**同一个机制的三种语言写法**：一个"工具系统"，都做到了"工具文件放进 `tools/` 就生效，删掉就消失"：

- JavaScript：[examples/js/tool.js](examples/js/tool.js) · [examples/js/tools/read.js](examples/js/tools/read.js)
- Python：[examples/py/tool.py](examples/py/tool.py) · [examples/py/tools/read.py](examples/py/tools/read.py)
- Go：[examples/go/tool/tool.go](examples/go/tool/tool.go) · [examples/go/tools/read.go](examples/go/tools/read.go) · [examples/go/main.go](examples/go/main.go)

**反面写法**（同一个工具系统，逐处标注违反了哪条）：[examples/wrong.js](examples/wrong.js)
