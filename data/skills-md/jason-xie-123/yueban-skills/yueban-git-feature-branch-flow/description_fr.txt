Dans un dépôt qui utilise des sous‑modules git, créez une branche portant le même nom selon la spécification /feature — le dépôt parent et chaque sous‑module actuellement maintenu (découverts dynamiquement à partir de .gitmodules, en excluant les modules historiques préfixés par deprecated/) se ramifient uniformément à partir d’une branche <change-id> à partir d’une branche de base sélectionnée par l’utilisateur (toute branche réellement utilisée par le projet convient, pas de valeur codée en dur). Pendant le développement, utilisez sync pour aligner cette branche sur plusieurs machines (sans toucher à la branche de base elle‑même). Lors du commit, orchestrez yueban-git-commit pour commettre chaque dépôt dans l’ordre « sous‑module d’abord, dépôt parent ensuite ». À la fin, fournissez un rapport prêt à être fusionné mais ne fusionnez pas automatiquement (l’utilisateur fusionne manuellement / via PR). Après la fusion, nettoyez éventuellement la branche.  

Différence avec yueban-git-safe-sync : cet outil gère le pull/push de la branche courante elle‑même et les deux actions isolées « fusionner la base dans la branche courante » et « ouvrir une PR pour la branche courante », alors que celui‑ci gère tout le cycle de vie d’une branche de fonctionnalité détachée de la branche de base.  

**Déclenchement explicite uniquement** : il n’est invoqué que lorsque l’utilisateur saisit explicitement `/yueban-git-feature-branch-flow` ou nomme explicitement cette compétence ; les énoncés génériques comme « créer une branche », « checkout d’une branche » ou « comment développer cette spécification » ne doivent pas être automatiquement liés ici—traitez‑les comme des opérations git normales ou posez des questions de suivi à moins que l’utilisateur ne fasse référence explicitement à la compétence.  

Veuillez toujours répondre dans la langue de l’utilisateur.
