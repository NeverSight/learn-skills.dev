В репозитории с git‑подмодулями создайте ветку, названную в соответствии со спецификацией/фичей — как в основном репозитории, так и в каждом поддерживаемом подмодуле (динамически найденном из .gitmodules, исключая исторические модули с префиксом deprecated/) — одинаково ответвляются от выбранной пользователем базовой ветки (подойдёт любая ветка, действительно используемая в проекте, без жёстко заданных значений) для создания ветки `<change-id>`.  

Во время разработки используйте sync, чтобы синхронно поддерживать эту ветку на разных машинах (не изменяя саму базовую ветку). При коммите оркеструйте `yueban-git-commit`, чтобы коммитить каждую часть в порядке «сначала подмодуль, затем основной репозиторий». В конце предоставьте отчёт, готовый к слиянию, но не выполняйте автоматическое слияние (пользователь сливает вручную или через PR). После слияния, при необходимости, очистите ветку.  

Отличие от `yueban-git-safe-sync`: тот инструмент управляет pull/push текущей ветки и двумя одношаговыми действиями «слить базу в текущую ветку» и «открыть PR для текущей ветки»; этот инструмент управляет полным жизненным циклом ветки‑фичи, отделённой от базовой ветки.  

**Только явный вызов**: инструмент вызывается только когда пользователь явно вводит `/yueban-git-feature-branch-flow` или явно указывает эту функцию; общие фразы вроде «создать ветку», «переключить ветку» или «как развивать эту спецификацию» не должны автоматически связываться с этим инструментом — обрабатывайте их как обычные операции git или запросите уточнение, если пользователь не упоминает их конкретно.
