En un repositorio que usa submódulos de git, crea una rama con el mismo nombre según una especificación/característica: el repositorio principal y cada submódulo actualmente mantenido (descubierto dinámicamente a partir de `.gitmodules`, excluyendo los módulos históricos con el prefijo `deprecated/`) se ramifican a partir de una rama base seleccionada por el usuario (cualquier rama realmente utilizada por el proyecto, no una codificada) para crear una rama `<change-id>`. Durante el desarrollo, usa `sync` para mantener esta rama alineada en múltiples máquinas (sin afectar la rama base en sí). Al confirmar, orquesta `yueban-git-commit` para enviar los cambios uno por uno en el orden “submódulo primero, luego el repositorio principal”. Al final, genera un informe listo para fusionar, pero no realices la fusión automáticamente (el usuario fusiona manualmente o mediante un PR). Después de fusionar, opcionalmente limpia la rama.

Diferencia con `yueban-git-safe-sync`: esa herramienta gestiona pull/push en la rama actual y las dos acciones únicas “fusionar la base en la rama actual” y “abrir un PR para la rama actual”. Esta habilidad gestiona el ciclo de vida completo de una rama de característica que es independiente de la rama base.

**Disparo explícito únicamente**: Se invoca solo cuando el usuario escribe explícitamente `/yueban-git-feature-branch-flow` o menciona de forma explícita esta habilidad. Frases generales como “abrir una rama”, “cambiar a una rama” o “cómo desarrollar esta especificación” no deben invocarla automáticamente; trátalas como operaciones git habituales o formula preguntas de seguimiento a menos que el usuario mencione explícitamente la habilidad.
