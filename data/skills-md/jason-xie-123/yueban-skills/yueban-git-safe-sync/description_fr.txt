Dans un dépôt qui utilise des sous‑modules Git, lors d’un pull, d’un push, de la fusion de la branche de base dans la branche courante, ou de l’ouverture d’une PR GitHub pour le dépôt parent ainsi que tous les sous‑modules, assurez‑vous que chaque sous‑module actuellement maintenu (découvert dynamiquement à partir de .gitmodules, en excluant les modules historiques ou gelés avec le préfixe deprecated/) reste toujours sur sa branche d’origine (le nom exact suit les conventions réelles du projet) et ne se retrouve jamais en état de HEAD détaché ou forcé au SHA enregistré dans le dépôt parent par ces opérations. Le pull/push est approprié pour les scénarios où le même projet s’exécute sur plusieurs machines et où les états des branches des sous‑modules doivent rester cohérents d’une machine à l’autre ; le merge‑base/PR est approprié pour les scénarios où vous êtes sur une branche de fonctionnalité découpée à partir de la base et devez fusionner les nouveaux commits de la base, ou ouvrir une PR pour fusionner cette branche dans la base. **Activation uniquement explicite** : la compétence n’est invoquée que lorsque l’utilisateur saisit explicitement `/yueban-git-safe-sync` ou indique clairement qu’il veut utiliser cette compétence ; des remarques occasionnelles comme « pull a bit », « push a bit », « sync the code », « merge develop » ou « open a PR » ne doivent pas déclencher automatiquement cette compétence — traitez‑les comme des opérations Git normales ou demandez une clarification à moins que l’utilisateur ne nomme spécifiquement la compétence.
