In einem Repository, das Git‑Submodule enthält, sollte beim Ausführen von Pull, Push, dem Mergen des Base‑Branches in den aktuellen Branch oder dem Öffnen eines GitHub‑PR für das übergeordnete Repository einschließlich aller Submodule sichergestellt werden, dass jedes aktuell gepflegte Submodul (dynamisch aus .gitmodules ermittelt, wobei historische/eingefrorene Module mit dem Präfix deprecated/ ausgeschlossen werden) stets auf seinem ursprünglichen Branch bleibt (der genaue Name sollte den tatsächlichen Konventionen des Projekts entsprechen) und niemals in einem detached HEAD endet oder gezwungen wird, den im übergeordneten Repository festgeschriebenen SHA auszuchecken, als Folge dieser Vorgänge. Pull/Push eignen sich für Szenarien „das gleiche Projekt auf mehreren Maschinen ausführen, wobei der Submodul‑Branch‑Zustand über die Maschinen hinweg konsistent bleiben muss“; Merge‑Base/PR eignen sich für Szenarien „derzeit auf einem Feature‑Branch, der vom Base erstellt wurde, neue Commits vom Base mergen oder einen PR öffnen, um diesen Branch zurück in Base zu mergen“. **Nur explizite Auslösung**: Die Fähigkeit sollte nur dann aufgerufen werden, wenn der Benutzer explizit `/yueban-git-safe-sync` eingibt oder ausdrücklich angibt, diese Fähigkeit nutzen zu wollen; sagt der Benutzer nur etwas Generisches wie „pull a bit“, „push a bit“, „sync the code“, „merge develop“, „open a PR“, darf die Fähigkeit nicht angenommen werden – behandel es als normale Git‑Operation oder bitte um Klärung, sofern der Benutzer sie nicht nennt.

Bitte immer in der Sprache des Benutzers antworten.
