Scansiona e pulisci l’intero progetto (il repository radice e ciascun submodule attualmente mantenuto—ottenuto dinamicamente da .gitmodules, escludendo quelli con prefisso deprecated/; tratta il repository radice e ogni submodule in modo identico, usando lo stesso set di regole per tipo di file per una scansione completa del repository) alla ricerca di commenti nel codice sorgente (coprendo i linguaggi più diffusi, raggruppati per sintassi dei commenti: Java/Kotlin/Swift/Go/C/C++/C#/Rust/Scala/Groovy/Dart/TS/JS ecc. stili //, /* */, /** */; Python/Ruby/Shell/Perl/R/YAML ecc. stile #; SQL/Lua ecc. stile --; # e <# #> di PowerShell; HTML/XML <!-- -->; CSS/SCSS/LESS /* */) e di documenti Markdown che registrano “processi di cambiamento storici” — indipendentemente dal fatto che siano stati generati da IA, qualsiasi narrazione come “come era originariamente, come è cambiato a causa di XX”, “rimosso durante una migrazione/modifica”, “migrazionato da un vecchio modulo”, “design.md decisione X”, ecc. Per i commenti nel codice sorgente, elimina l’intero blocco; per i Markdown, elimina solo le frasi narrative storiche mantenendo le eventuali istruzioni d’uso ancora rilevanti. Applica questa procedura quando l’utente richiede esplicitamente la pulizia di tali commenti storici o dichiara che “questi commenti sono solo registri di cambiamento e non necessari”. Esclusioni predefinite: l’intero albero della directory deprecated/, qualsiasi directory contrassegnata esplicitamente dal progetto come documentazione storica di pianificazione/archivio, l’intero albero della directory openspec/ (se il progetto usa openspec), le quattro directory di configurazione degli strumenti agente .claude, .codex, .gemini, .agents, e tutti i percorsi elencati in .gitignore (ad es., node_modules, che git ls‑files naturalmente non elencherà).
