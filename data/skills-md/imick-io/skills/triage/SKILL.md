# Triage

Triage is the **front desk** for work that arrives raw: bug reports, feature requests, anything a person files. It decides what each issue is and who acts next. It never builds anything, and it never closes anything: a human closes.

It runs in two modes:

- **Manual**: a maintainer invokes `/triage` and directs the work. This file.
- **Unattended**: the triage workflow, or the agent loop with `AGENTS_TRIAGE=1`, runs it on each new issue, with nobody to ask. Read [UNATTENDED.md](UNATTENDED.md) when invoked that way.

If this repo treats external pull requests as a request surface (see the issue-tracker config), triage covers them too: **a PR is an issue with attached code**, with the same roles. Resolve a bare `#42` to an issue or PR per the tracker config.

Every comment posted during triage **must** start with:

```
> *This was generated by AI during triage.*
```

## Roles

A triaged issue carries exactly one **what** role and exactly one **who** role, from these pairings and no others:

| What | Who | Meaning |
| --- | --- | --- |
| `bug` | `ready-for-agent-debugging` | Something is broken; an agent reproduces it next |
| `enhancement` | `ready-for-agent` | A small, fully specified improvement; an agent builds it from the brief |
| `enhancement` | `ready-for-human` | A small improvement a person must build (judgment calls, access, manual testing) |
| `needs-scoping` | `ready-for-human` | Too big for one brief; a person runs `/scope-decomposer` on it |
| `needs-info` | `ready-for-human` | Can't be classified yet; the reporter answers the triage notes |
| `wontfix` | `ready-for-human` | Already built, a duplicate, or rejected; a person confirms and closes it |
| `bug` | `ready-for-human` | Set by `/debug-and-fix`: diagnosed, but the fix needs a person; the diagnosis is on the issue |
| `bug` | `ready-for-review` | Set by `/debug-and-fix`: fixed, the PR waits for review and closes the issue on merge |

**`enhancement` means small**: one brief, one agent session. Almost any real feature ask is bigger than that and is `needs-scoping`.

`needs-triage` is transient: triage hasn't finished on this issue yet. An untriaged or half-triaged issue carries it; a triaged one never does.

`split` marks an issue that bundled several separate asks, a pasted client email for example, and was split into one issue per ask (see [Split a bundle](#split-a-bundle)). Like `backlog`, it carries no **who** role and sits in nobody's inbox: its children carry the work. A person closes it once they're done.

`backlog` parks an issue for later. It keeps its **what** role and carries no **who** role, so it is in nobody's inbox: no agent builds it, the loop never plans it, and triage leaves it alone. Taking it out of the backlog means removing the label and giving it a **who** role again (or sending it back through triage with `needs-triage`).

These are canonical role names. The actual label strings are mapped in `docs/agents/triage-labels.md`. If it doesn't exist, tell the user to run `/setup-imick-skills`. If an issue carries roles outside the pairings above, flag it and ask before doing anything else.

`ready-for-agent` and `ready-for-agent-debugging` are the agents' inbox; `ready-for-human` and `ready-for-review` are the people's inbox, and `who` is about who acts next, not who builds. Triage itself never sets the two pairings marked as set by `/debug-and-fix`.

## Areas and assignment

Read `docs/agents/team.md`. Unless it says the repo has a single area:

- Add the issue's **area** label (`area:<app>` or `area:<app>:<part>`), judged from what the issue touches and the areas' code folders.
- **Assignment means claimed.** On `ready-for-human`, assign the person who acts next: the area's default person, except on `needs-info`, where it's the reporter when they are a repo collaborator, and the area's default person otherwise. Leave `ready-for-agent` and `ready-for-agent-debugging` unassigned so an agent can claim them.

## Skip

Issues the other skills created are already shaped and never go through triage: anything labelled `initiative`, `epic` or `wayfinder:*`, and any issue under an epic. Neither do issues labelled `backlog`, unless the maintainer asks to take one out. Tell the maintainer and stop.

## Invocation

The maintainer describes what they want in natural language. Examples:

- "Show me anything that needs my attention"
- "Let's look at #42" (issue or PR)
- "Move #42 to enhancement / ready-for-agent"
- "What's ready for agents to pick up?"

## Show what needs attention

Query the issue tracker and present three buckets, oldest first:

1. **Unlabelled or `needs-triage`**: never triaged, or triage didn't finish (often an unattended run that failed).
2. **`needs-info` with reporter activity since the last triage notes**: needs re-evaluation.
3. **`wontfix`, still open**: waiting for a person to confirm and close.

When PRs are in scope, include external PRs and tag each line `[PR]` or `[issue]`. Discovery surfaces only *external* PRs (the tracker config defines who counts as external); an explicitly named PR is always triaged regardless of author.

Show counts and a one-line summary per item. Let the maintainer pick.

## Split a bundle

One issue gets one pairing, but an issue can carry several separate asks: a client's email pasted as is, the notes from a test session, feedback mixed with requests. Check for that first, before classifying, and split such an issue into one issue per ask.

- **When to split.** The issue asks for two or more things that would each be fixed, built or decided on their own, and none needs the others to make sense. Two sentences about the same problem are one ask. If you're unsure whether two things are separate, keep them together. A single big ask is never split: that's `needs-scoping`. Neither is a PR.
- **One child per ask**, ten at most. With more than ten asks, don't split: classify the whole issue `needs-scoping`. Triage each ask exactly as you would its own issue: the redundancy, prior-rejection and duplicate checks, then one pairing, its area and its assignee. Create the child already triaged, in one command: `gh issue create --title "<the ask, in the codebase's terms>" --body "<body>" --label "<what>,<who>,<area>"`, plus `--assignee <login>` per the assignment rules. The body starts with the disclaimer, then `Split from #<n>.`, then the ask in the reporter's own words, quoted (`>` lines). Then post the child's triage comment per the outcome list, as for any issue. For `needs-info`, the reporter is the original issue's author.
- **Feedback with nothing to act on** (praise, an impression with no request in it) gets no child. It goes in the summary.
- **The original** gets a summary comment: one task-list line per child (`- [ ] #<child> <title>: <what> / <who>`), so GitHub tracks them, then the feedback lines. Then label it `split`, remove `needs-triage` and every other triage role, and leave it unassigned. Create the label first if the repo lacks it: `gh label create split --color c5def5 --description "Split into one issue per ask"`.

In manual mode, recommend the split with the children you would create, and wait for direction like any recommendation.

## Triage a specific issue or PR

1. **Gather context.** Read the full issue or PR (body, comments, labels, author, dates; for a PR, the diff too). Parse prior triage notes so you don't re-ask resolved questions. Explore the codebase using the project's domain glossary, respecting ADRs in the area. Run two checks: (a) **redundancy**: search for an existing implementation of the requested behaviour by domain concept, not just the request's wording, and report where you looked; found means `wontfix`, already built. (b) **prior rejection**: read `.out-of-scope/*.md` and surface any that resembles this request.

2. **Recommend** a split when the issue bundles several asks ([Split a bundle](#split-a-bundle)); otherwise a pairing from the Roles table with your reasoning, the area, and a brief codebase summary relevant to the request. Wait for direction.

3. **Verify the claim.** For a PR, confirm the diff does what it claims: check it out, run the relevant tests. Report what happened. (Reproducing a bug is the job of whatever picks up `ready-for-agent-debugging`, not triage.)

4. **Grill (if needed).** If the request needs fleshing out, call the Skill tool twice, for "grilling" and "domain-modeling", and grill it into shape a round at a time.

5. **Apply the outcome**, then swap `needs-triage` for the pairing and the area, and assign per the rules above:
   - `enhancement` / `ready-for-agent`: post an agent brief ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `enhancement` / `ready-for-human`: same structure as an agent brief, plus why it can't be delegated.
   - `bug` / `ready-for-agent-debugging`: post what's known: expected vs actual, the reporter's steps, and the code paths that look involved.
   - `needs-scoping` / `ready-for-human`: post why it's bigger than one brief, and the next step: `/scope-decomposer #<issue>`.
   - `needs-info` / `ready-for-human`: post triage notes (template below).
   - `wontfix` / `ready-for-human`: post why, and leave the issue open for the maintainer to close:
     - **Already implemented** or **duplicate**: point to where it lives or the issue it duplicates. Do **not** write to `.out-of-scope/`.
     - **Rejected enhancement**: write to `.out-of-scope/` and link it ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
     - **Rejected bug**: a polite explanation.

## Quick override

If the maintainer says "move #42 to enhancement / ready-for-agent", trust them and apply it directly. "Backlog #42" adds `backlog`, removes its **who** role and `needs-triage`, unassigns it, and posts one line saying it is parked; it keeps (or gets) its **what** role. Confirm what you're about to do (labels, comment, assignment), then act. Skip grilling. Moving to `ready-for-agent` without a grilling session: ask whether they want an agent brief written.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved so far under "established" so the work isn't lost. Questions must be specific and actionable, never "please provide more info".

## Resuming

If prior triage notes exist, read them, check whether the reporter has answered any outstanding questions, and present an updated picture before continuing. Don't re-ask resolved questions.
