# Verify epic

An epic's PR to `main` is up: every ticket in its milestone is closed. Before a person reviews and merges it, check that the epic actually does what it promised, **in the running app**, and turn every gap into a ticket the agent loop can pick up.

The agent loop runs this after it opens an epic PR, and again whenever fixes land on that epic. A person can run it too: `/verify-epic <pr>`.

Read the tracker doc, `docs/agents/triage-labels.md`, `docs/agents/preview.md` and `docs/agents/team.md`. If they don't exist, tell the user to run `/setup-imick-skills`. Every comment starts with:

```
> *This was generated by AI while verifying this epic.*
```

## Run

1. **Load the epic.** From the PR (`gh pr view <pr> --json number,headRefName,headRefOid,body`): the epic is the issue in "Closes #n", its milestone holds everything else. Gather:
   - the closed tickets in the milestone, with their acceptance criteria,
   - the spec and the UI spec (issues in the milestone with the spec template),
   - the agreed screenshots: the epic's Design section links them on the `design/NN-<slug>` branch,
   - the API contracts in the spec's Implementation Decisions.

   Mark the PR's head commit pending: `gh api repos/{owner}/{repo}/statuses/<sha> -f state=pending -f context=verify-epic -f description="Verifying"`.

2. **Reach the app**, as `preview.md` says:
   - **GitHub deployments**: the newest successful deployment for the head commit (`gh api "repos/{owner}/{repo}/deployments?sha=<sha>"`, then its statuses' `environment_url`); wait up to 10 minutes for it.
   - **URL pattern**: fill in the PR number, and wait until it answers.
   - **No preview**: start the app from the PR's head as the project runs it locally.

   Credentials for a protected preview come from the environment variables `preview.md` names. Sign in only with test accounts from the project's seed or fixture files. If the app can't be reached, stop: the status goes red with the reason.

3. **Check, in this order**, driving the app in a browser (Claude in Chrome when present, else `agent-browser`, else Playwright) and recording a verdict and evidence for each:
   1. **Smoke**: the app loads; no console errors or failed requests on the epic's pages.
   2. **Each ticket's acceptance criteria**, one by one.
   3. **The spec's user stories** not already covered by a ticket's criteria.
   4. **The API contracts**: call each endpoint the spec describes, check status codes and response shapes.
   5. **The screens** against the agreed screenshots: same layout, content and states, judged by looking at both, not pixel by pixel.

   A verdict is **pass**, **fail** (the behaviour is clearly wrong or missing, and you can show it), or **unsure** (you can't tell: a visual difference that might be intended, an ambiguous criterion, a missing test account).

4. **File the gaps**, after checking open issues in the milestone so nothing is filed twice:
   - each **fail** becomes its own ticket: title the broken behaviour, labels `bug` + `ready-for-agent-debugging`, the epic's milestone and area, the evidence (steps, starting URL, what happened vs what the criterion says), and "Found by verify-epic on #<pr>". Unassigned, so the loop claims it.
   - all **unsure** verdicts go into one ticket, "Verify-epic: needs a person's call", labels `ready-for-human`, assigned to the area's default person, one checklist line per item.

   File every gap from this run at once, and leave them independent: link one as **blocked by** another only when it really can't be fixed first. The loop works independent tickets side by side; a chain is fixed one at a time, with a check between each.

5. **Report and set the status.** Post or update the PR's verification comment (edit the earlier one with `gh api` when it exists, so the PR keeps a single report):

   ```markdown
   > *This was generated by AI while verifying this epic.*

   ## Verification: <passed | N failed | needs a person>

   Tested <preview URL or "locally"> at <short sha>.

   | Check | Verdict | Ticket |
   | --- | --- | --- |
   | Smoke | ✓ | |
   | #31 Sign-up form: rejects a taken handle | ✗ | #52 |
   | Story 4: password reset email | ? | #53 |
   | Screen: settings page | ✓ | |
   ```

   Then set the status on the head commit: `success` only when every verdict passed; otherwise `failure`, with a description such as "2 failed, 1 needs a person". The `epic-gate` check reads it.

   **Leave CI to the fixes.** Don't push to the epic branch yourself, and don't re-run the PR's failed CI jobs by hand while fix tickets are open or building. Every push and every re-run runs the project's whole suite again. The loop (or `/run-epic`) lands the fixes as one batch: the pushes before the last one say `[skip ci]`, so CI runs once, on the branch with every fix in.
