# dpgk

説明を、読むより速く分かる「動く図解」にするスキルです。出力はアニメーション付きSVGか、単一ファイルのHTMLです。

最優先ルールは「**動きが意味を運ぶこと**」と「**正確さを演出より優先すること**」です。ドーパミンが出る見た目は、理解が速くなる結果として出すもので、目的ではありません。

---

## 1. コア原則

1. **1つの図で1つの問い**: 図を作る前に「見終わった人が答えられるようになる問い」を1文で決めます。問いが2つあるなら図を分けるか、HTMLのステップに分けます。
2. **動きは意味に対応させる**: 動かしてよいのは次の5種類だけです。
   - 順序（何が先か）: 段階的に出現させる
   - 流れ（何がどこへ行くか）: パス上を粒子・パケットが移動する
   - 因果（何が何を起こすか）: 原因が動いた後に結果が反応する
   - 変化（何がどれだけ変わるか）: 量・状態・形が遷移する
   - 注目（今どこを見るか）: 1か所だけを強調し、他は落とす
   どれにも当たらない動き（常時の回転、ふわふわ、意味のないバウンス）は入れません。詳細は [`references/motion-patterns.md`](references/motion-patterns.md) を参照します。
3. **最終フレームだけで成立させる**: アニメーションを止めても、最後の静止画だけで説明が成り立つようにします。順序は ①②③ の番号や、到着した矢印を消さずに積み上げることで静止画に残します（最初と最後のフレームが同じに見えるなら、動きに頼りすぎています）。`prefers-reduced-motion` のときは最終状態を表示します。
4. **読める速度で動かす**: 文字が出てから読み終わるまで最低1.5秒、ループの終わりには1.5秒以上の静止を入れます。全体は1ループ4〜15秒を目安にします。
5. **正確さ**: 説明対象の事実（プロトコルの手順、アルゴリズムの計算量、状態遷移の条件）を省略しても、嘘にはしません。単純化した点は出力時に明記します。
6. **自己完結**: 外部CDN・フォント・画像を読み込みません。1ファイルで開けば動くようにします。参考資料への `<a href>` リンクは構いません。
7. **「派手に」は「キレよく」と読む**: 派手・かっこよく・映える、と頼まれたら、コントラスト、テンポ、メリハリのある出現で応えます。グロー、ネオン、回り続ける枠、流れ続ける背景は理解を遅くするので入れません。その判断は出力時に一言伝えます。
8. **仕組みの図には「なぜ」を1ビート入れる**: 「どう動くか」だけでなく、その設計である理由（例: なぜ3回やりとりするのか、なぜフレーム番号で描くのか）を1ビート使って示します。読者が一番知りたいのは多くの場合そこです。

避けるべきパターンは [`references/anti-patterns.md`](references/anti-patterns.md) にまとめています。

## 2. 形式の選び方

| 条件 | 形式 |
|---|---|
| README・Markdown・Slack・ドキュメントに埋め込みたい | **SVG** |
| 1つの概念を1ループで見せられる（ビート5個以下） | **SVG** |
| ステップ送り・一時停止・倍速・巻き戻しが必要 | **HTML** |
| 読者に値を変えて試させたい（入力・スライダー） | **HTML** |
| ビートが6個以上、または図が2枚以上要る | **HTML** |

ユーザーが `--format` を指定した場合はそれに従います。迷ったらSVGを選びます。

### SVGの制約
- GitHubのREADMEなどでは `<img>` として描画されるため、`<script>` は動きません。アニメーションはCSS `@keyframes` かSMIL（`<animate>`, `<animateMotion>`, `<animateTransform>`）だけで作ります。
- `<img>` 埋め込みのSVGには一時停止も倍速も付けられません。読者が一時停止・倍速したい場面では HTML にします。README 用のSVGと、じっくり見る用のHTMLの両方が欲しそうなら、両方作るか提案します。
- ルート要素に `viewBox` を付け、`width`/`height` は固定しすぎないようにします。
- `<title>` と `<desc>` を入れ、`role="img"` と `aria-labelledby` で関連付けます。
- フォントは `system-ui, -apple-system, "Hiragino Sans", "Noto Sans JP", sans-serif` のようなシステムフォントを使います。

### HTMLの制約
- [`assets/player.html`](assets/player.html) をコピーして作ります（`cp <スキル配置ディレクトリ>/assets/player.html <出力.html>` から始め、図の部分だけを書き換える）。プレイヤーは画面全体を使い、見出しと操作ボタン以外の高さはすべて図（`#scene` の SVG）に渡します。図は `viewBox` の比率のまま画面いっぱいに拡大されるので、PC では大きく、スマホでは縦に余白が出るだけで済みます。
- 書き換えるのは次の4か所だけです。
  1. 図のスタイル（`/* ここから図のスタイル */` 以降）
  2. `<header>` の見出しと「問い」（ページ冒頭に問いを1行で書く）
  3. `#scene` の SVG。ビートで出し入れする要素には `data-k="名前"` を付ける
  4. 図のスクリプト: `beats`（各ビートの最終状態）と、必要なら `render(b, i)`（位置や文字など、出し入れ以外の見た目）と `BEAT_MS`
- スマホを縦に持つと、横長の図は小さく縮んで上下が空きます。HTML の図には必ず縦向きの配置も用意します。375×667 のスマホでプレイヤーが図に渡せるのは約 343×440px です。縦向きの `viewBox` は幅 340〜380、高さ 440 前後までにし、図中の文字は 13 以上にすると、画面上で 10〜12px 以上になります（画面上の大きさ = 文字サイズ × 343 ÷ viewBox の幅、高さで詰まるときは × 440 ÷ viewBox の高さ）。入りきらないときは、縦向きでは補足の文字を省くか、要素を減らします。`#scene` に `data-viewbox-portrait="0 0 幅 高さ"` を付けると、図が大きく映る方（横向き / 縦向き）をプレイヤーが選んでその `viewBox` に切り替え、`<html data-orient="portrait">` を立てて `render` を呼び直します。図の側では次の3つで縦向きの配置を作ります（ひな形に例があります）。
  - `[data-orient="portrait"] [data-k="…"] { transform: translate(…) }` でグループを動かす
  - 向きで形が変わる線は、横向き用に `class="only-landscape"`、縦向き用に `class="only-portrait"` を付けて2本用意する
  - `render` の中の座標は `document.documentElement.dataset.orient` で切り替える
- `dpgk-player:start`〜`dpgk-player:end` で囲まれた3ブロック（CSS / 操作ボタン / プレイヤーのスクリプト）は編集しません。プレイヤーを改善したときに `scripts/dpgk_sync_player.py` で全ファイルに反映できるようにするためです。プレイヤーで足りない動きは、図のスクリプト側（`render`）で作ります。
- プレイヤーには次の操作が入っています。読者は自分のペースで見たいので、どれも消しません。
  - 開いたら自動再生する（動きを減らす設定のときだけ、自動再生せず最終ビートを表示）
  - 縦型動画と同じ操作: 図をタップ（クリック）で一時停止 / 再開、長押ししている間だけ 2×。押したまま上下にドラッグすると速度が変わる（上で最大 10×、下で最小 0.1×）。離すと元の速度に戻る
  - 画面の上辺に再生バー（全体のどこまで進んだかだけを示す。時間表示はなし。ビートごとの長さの違いも反映）
  - 再生 / 一時停止（Space）、前へ / 次へ（← / →）、ステップの点から直接ジャンプ
  - 倍速 0.5× / 1× / 1.5× / 2×（`<` / `>` でも切り替え）。ビートの間隔と遷移の長さが両方縮む
  - 全画面（ボタンか F キー。対応ブラウザのみ）
  - `#beat=3` のような URL で特定のビートを遷移なしで開く（共有リンクとスナップショット用）
- 各ビートは「その場面の最終状態」を宣言的に書き、どのビートにジャンプしても同じ見た目になるようにします（直前の状態に依存しない）。Remotion の「フレーム番号から見た目が決まる」発想と同じです。ビートごとに長さを変えたいときは `ms` を指定します。
- 配色はプレイヤーの「自動 / ライト / ダーク」ボタンで切り替わります（選んだものはブラウザに記憶されます）。図のスタイルでダーク用の色を足すときは、次の2つをセットで書きます。`@media (prefers-color-scheme: dark)` の中で `:root` だけを上書きすると、ボタンでライトを選んでもダークの色が残ります（lint の `W-THEME`）。

  ```css
  @media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) { --edge: #78716c; } }
  :root[data-theme="dark"] { --edge: #78716c; }
  ```
- 外部ライブラリは使いません。CSS トランジションと `render` で足ります。

## 3. 入力の種類

何を元に図を作るかで、Step 1 の進め方だけが変わります。Step 2 以降は同じです。

| 入力 | 例 | Step 1 の進め方 |
|---|---|---|
| お題 | 「TCP の3ウェイハンドシェイクを図解して」 | 一般的な知識から問いを決める。事実は確かめてから使う |
| 会話のまとめ | 「今の話を dpgk でまとめて」 | 会話で決まったこと・分かったことから問いを決める |
| 資料 | 記事、設計書、README、URL、ファイルのパス | 資料を最後まで読んでから問いを決める |

### 会話や資料を元にするとき

読者は「その資料（会話）に書いてあること」を図で確かめたいので、図の中身は元の内容に忠実にします。

- **何を伝えるかを先に決めます。** 図を考える前に、次の2つを書き出します。
  - 主張: 書き手（会話なら、その会話で決まったこと）がいちばん言いたいことを1文で。話題の説明ではなく、言い切りの形で書きます。
  - 持ち帰ること: 読者が見終わったあとに、判断や行動が変わるような具体的な1文を1〜3個。

  問いは、この主張と持ち帰ることを伝えるために立てます。データの出どころや周辺の細部など、主張から外れたことを問いにしません。最初のビートで主張を示し、最後のビートで持ち帰ることを言い切ります。最終フレームだけ見ても、持ち帰ることが分かるようにします。
- **元にない事実を足しません。** 手順、数値、条件、コンポーネント名は、元の資料や会話にあるものだけを使います。一般的な知識で補いたくなっても補わず、足りない点は出力の「単純化したところ」か、末尾の「確かめたい点」に書きます。数値や名前は、元の表記のまま使います。
- **省くのは構いません。** 1つの問いに関係しない部分は図から外し、外したことを「単純化したところ」に書きます。
- **問いを1〜3個に絞ります。** 資料の全部を1枚に詰めると、どの問いにも答えられない図になるためです。資料が複数の話題を含むときは、図にする問いを1〜3個選び、選ばなかった話題を出力に挙げます。問いが2つ以上なら、図を分けるか、HTML のビートで区切ります。依頼の時点で問いを選べないほど長い資料なら、作る前に候補の問いを示して選んでもらいます。
- **出典を書きます。** 図の中（HTML なら header の下や注記、SVG なら `<desc>` と図の隅）に、元の資料の名前か URL を書きます。会話が元なら「この会話のまとめ」と書きます。
- **元の内容と食い違いそうな単純化はしません。** 例えば、元の資料で並行して進む処理を、図で順番に描く場合は、その単純化を図の注記に書きます。

## 4. 実行手順

### Step 1: 問いとビートを決める（ストーリーボード）

入力が会話や資料なら、先に「3. 入力の種類」の決まりに沿って、元の内容から問いを決めます。

コードを書く前に、作業メモとして次を決めます。

```text
問い: TCPはなぜ3回やりとりしてから通信を始めるのか
形式: SVG（ビート4つ、READMEに貼る）
ビート:
  0.0s  クライアントとサーバーを表示
  1.0s  SYN がクライアント → サーバーへ移動（流れ）
  3.0s  SYN-ACK がサーバー → クライアントへ移動（流れ）
  5.0s  ACK がクライアント → サーバーへ移動、両端が ESTABLISHED に変化（因果）
  7.0s  静止（最終フレーム）〜 9.0s でループ
単純化: シーケンス番号の値、再送、タイムアウトは省略
```

ビートは3〜7個に収めます。8個以上になったら問いが大きすぎるので分けます。

例外は、過程そのものが主題のもの（探索・ソートなどのアルゴリズム、1命令ずつの実行）です。この場合は「説明のビート」は3〜7個に保ったまま、その中で1操作ずつ進められるようにします（例: 比較を1回ずつ進める「次の比較」ボタンや、ビート内の自動ステップ）。途中を飛ばすと、読者が一番見たい「1回で何が起きるか」が見えなくなります。この例外でも、ビートの数そのものは増やしません（1命令ごとにビートを作ると、ビートが 10 個を超えて全体像が見えなくなるため）。それでも8個以上のビートが必要だと判断したときは、その理由をビート表の下（出力フォーマットの「ビート」）に1行で書きます。

### Step 2: 静止画として組む

まず最終フレームを静止画として完成させます。配置・ラベル・色・凡例がこの時点で読めることを確認してから動きを付けます。

- 色は意味ごとに1色（例: 送信側、受信側、エラー）で、3〜4色以内に抑えます。色だけで区別せず、ラベルや形でも区別します。
- 種類の違うもの（問い合わせ / 途中の応答 / 最終的な答え、成功 / 失敗、元のコミット / 作り直したコミットなど）は、文字の内容だけでなく見た目（色と線の種類・形の両方）で区別します。止めた画面で、文字を読まなくても種類の違いが分かるようにします。
- テキストは12px相当以上にします。ラベルが図形と重ならないようにします。
- 図は画面幅に合わせて縮むので、`viewBox` の幅が広いほどスマホで文字が小さくなります（幅 860 の図を 375px で表示すると、15px の文字が約 6.5px になる）。横に長い図は避け、`viewBox` の幅は 640 前後までにします。HTML では、狭い画面（`@media (max-width: 480px)`）で縦並びのレイアウトや幅の狭い `viewBox` に切り替えて構いません。
- ライト・ダークどちらの背景でも読めるよう、背景色をSVG/HTML自身に持たせます。README に貼る SVG は `@media (prefers-color-scheme: dark)` でダーク用の配色も用意します（GitHub のダークモードで白い板が浮かないように）。

### Step 3: 動きを付ける

Step 1のビート表どおりに `animation-delay` / `begin` を振ります。

- 同時に動く主役は1つだけにします。
- イージングは `ease-out`（出現）、`ease-in-out`（移動）を基本にし、`linear` は流れ続けるもの（破線の流れ）だけに使います。
- 無限ループは「全体を1本のタイムラインで回す」形にし、要素ごとにバラバラの周期で回しません（周期がずれて意味が崩れるため）。
- `@media (prefers-reduced-motion: reduce)` で `animation: none` にし、最終状態を表示します。

### Step 4: 静的検査（リンター）

ファイルを保存したら、同梱のリンターを実行します。

```bash
# スキル配置先（${CLAUDE_SKILL_DIR}等）を基準にスクリプトの絶対パスを解決して実行
python3 <スキル配置ディレクトリ>/scripts/dpgk_lint.py <出力ファイル>
```

`ERROR` は必ず直します。HTML で `E-PLAYER` が出たら、プレイヤー部分がひな形と違っています。`assets/player.html` をコピーし直して図の部分だけを移すか、`python3 <スキル配置ディレクトリ>/scripts/dpgk_sync_player.py <出力.html>` で揃えます。`WARN` は意図があれば残してよく、その場合は出力時に理由を書きます。Python 3 が使えない環境では、[`references/anti-patterns.md`](references/anti-patterns.md) の表を上から目で確かめ、出力の「検査結果」に「lint 未実施（Python なし）」と書きます。修正と再実行は最大2回までとし、警告を消すためだけの改変ループはしません。

### Step 5: 止めて目で確かめる

リンターは重なりやはみ出しを見られません。同梱のスナップショットスクリプトで、動きを止めた画面を撮って見ます。ローカルの Chrome をヘッドレスで使うので、ブラウザ操作ツールがなくても、他の作業と並行していても動きます。

```bash
python3 <スキル配置ディレクトリ>/scripts/dpgk_snap.py <出力ファイル>
```

1回の実行で、次のものがそろいます（数秒で終わります）。
- **HTML**：全ビートを並べた一覧画像（シート）が2枚です。PC 幅（`sheet-w1200.png`）と、スマホ縦持ち 375×667（`sheet-w375.png`）です。あわせて、スマホでの図中の最小文字サイズをビートごとに表示します。ビート数はページから自動で読み取ります。動きを減らす設定の見た目は最終ビートと同じなので、別には撮りません。
- **SVG**：ループを 6 等分した時刻と終わり際を並べたシート（`sheet.png`）と、動きを減らす設定の静止画です。

確認の往復を減らすため、まずはこの2枚（SVG は2枚）だけを Read で見ます。1枚ずつ撮って1枚ずつ見る方法は、見る回数が増えて時間がかかるので使いません。シートで気になったコマだけ、実寸で撮って確かめます。

```bash
python3 <スキル配置ディレクトリ>/scripts/dpgk_snap.py <出力.html> --beat 4 --width 375 --height 667
```

見るところは次の4つです。
- 動く要素（パケットなど）が、止まった位置でラベルや文字に重なっていないか。停車位置は文字の外に置きます。
- スマホ幅で、図の文字が小さくなりすぎていないか、横にはみ出していないか。最小文字サイズは全ビートで 10px 以上にします。足りなければ、縦向きの `viewBox` と文字サイズを直します（`--measure` を付けると、画像を撮らずに数値だけ測れます）。
- 動きを減らす設定（HTML は最終ビート）だけで、説明が成り立っているか（原則3）。
- 最初と最後のフレームで、何が変わったかが見て分かるか。

直したあとは、もう一度同じコマンドを実行してシートを見直します。画像は `<出力ファイル名>.snaps/` に保存されます。確認が済んだら削除して構いません。Chrome が無い環境ではこの手順を省き、省いたことを出力に書きます。

## 5. 出力フォーマット

ファイルを保存したうえで、次の形式で返します。絵文字は使いません。

