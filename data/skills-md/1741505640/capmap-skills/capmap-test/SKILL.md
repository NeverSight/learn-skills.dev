# capmap-test — 测试计划与记录

原则：[lifecycle](../capmap-system/reference/lifecycle.md) · 模板：[templates](../capmap-system/reference/templates.md) · Tag：[status-tags](../capmap-system/reference/status-tags.md)

## 启动

1. 读 `.agents/skills/capmap-system/capmap.yaml` → `docs_root`
2. 确认主题、能力名、相关方案/底图
3. 方案宜已是 `已开发`（由 [capmap-dev](../capmap-dev/SKILL.md) 收尾后用户同意转测，或用户直接点名本 Skill）

## 路径与命名

```text
<docs_root>/测试/<主题>/测试-<功能可读名>.md
```

例：`测试/权限-abac/测试-三级目录权限.md`  
图谱靠文件名区分，禁止 `README.md`。

## 两拍节奏（降卡顿）

| 拍 | 谁做 | 文档/Tag | 不要做 |
|----|------|----------|--------|
| **拍 1 · 交测试文** | Agent（用户确认转测后） | 写满范围/影响面/用例步骤与期望；结果列默认 **未测**；测试文 `测试中`；方案 `验证中` | 不要等「测过再说」才写文；不要空等用户回「测完了」才开工 |
| **拍 2 · 记结论** | 人测后告知，或用户明示免测 | 填结果；通过/免测 → 测试文与方案 `已验证` | Agent **禁止**无证据自评通过 |

入口：`capmap-dev` 标完已开发后会**询问**是否转测；用户同意（或本回合已点名）再执行拍 1。  
拍 1 结束后回复可附 **3～7 条建议自测要点**，然后停住等人填结果——**文档与 Tag 已就位**。

## 文档必备节

1. **背景**：对应能力 / 方案 / 底图链接  
2. **测试范围**：要测什么（功能点列表）  
3. **影响面与回归**：改动可能波及哪里、建议回归哪些路径  
4. **用例与记录**：步骤 / 期望 / 结果（通过/失败/阻塞/**未测**）/ 日期 / 执行人  
5. **结论**：是否可发布；遗留问题；免测说明（若有）  

首次落地拍 1 时：1～4 写全，结果一律「未测」，结论写「待人测」。

## Checklist

```
- [ ] 1. 解析 docs_root；创建或更新 测试-<功能>.md
- [ ] 2. 测试文：`测试` + `状态/测试中`；对应方案标 `验证中`（拍 1）
- [ ] 3. 写清范围 + 影响面/回归 + 可执行用例；结果可先「未测」
- [ ] 4. 拍 2 通过或免测：测试文 → `已验证`；方案 → `已验证`；底图 §1 可写已验证（无 Tag）  
  **未通过前禁止**把方案标成 `落地中` / `已落地`
- [ ] 5. 失败：测试文保持 `测试中`；方案保持 `验证中`
```

## 与开发的关系

- 通常在 [capmap-dev](../capmap-dev/SKILL.md) 标完 `已开发` **并经用户确认转测**（或用户直接点名本 Skill）后执行拍 1  
- 用户说「免测/仅冒烟」→ **必须**在测试文档结论写明免测范围与日期，测试文标 `已验证` 后，方案才可 `已验证`；**禁止**无测试文直接已落地  

## 硬约束

- 测试文仍为 `测试中` ⇒ 方案不得 `落地中`/`已落地`（见 [status-tags](../capmap-system/reference/status-tags.md)）  
- Agent 不得把冒烟自述直接写成「全部通过」除非用户确认或明示免测  

## 不做

- 不代替自动化测试框架配置  
- 不把长期调用手册写进测试文档 → [capmap-norm](../capmap-norm/SKILL.md)  
- 不因「还没测」回退方案的 `已开发`  
- 不在用户未确认转测时擅自从 dev 静默开写测试文（用户已点名除外）
