# japanese

## 原則

英語で組み立てた文を日本語に置き換えない。何を伝えたいのかを先に決め、それを日本語の話者が普段使う言い方で書く。

直訳が不自然になるのは、英語の比喩や句動詞をそのまま日本語の動詞に移すと、日本語ではその動詞がその意味を持たないからである。「寄せる」は日本語で PR を取り込む意味を持たないし、「確実にする」は確認するという行動を指さない。読み手は字面から意味を復元しなければならず、読む手間が増える。

下の変換表に載っていない表現も、次の手順で見分ける。

1. 書いた文の英語の原文を頭の中で復元してみる。英語の単語や句動詞が一語ずつ日本語に置き換わっているなら、直訳を疑う。
2. その文を、日本語の話者が職場や日常でそのまま口にするか想像する。口にしないなら書き直す。
3. 動詞が比喩になっていないか確かめる。倒す、落とす、回す、焼き込むのような身体の動作を表す動詞が抽象的な作業に使われていたら、実際の作業を表す動詞に置き換える。
4. 述語が欠けていれば補う。
5. 同じ語尾が三回以上続いたら、文の形を変える。

変換表は、よく出る直訳を先回りして止めるための一覧である。表にあるかどうかではなく、上の手順で判断する。

## 記号

文の中で丸カッコ、コロン、ダッシュ、区切りのためのスラッシュを使わない。これらを使うと、読み手は本文と補足を行き来することになり、文章が読みにくくなる。

補足をカッコに入れたくなったら、独立した一文にするか、不要なら削る。候補をスラッシュで並べたくなったら、「か」や「または」でつなぐか、一つに決める。項目名や見出しの後ろにコロンを置いてラベルのように書かず、述語のある文にする。

コード、コマンド、パス、コミットメッセージの書式の中の記号は対象外とする。

## 体言止め

本文、説明文、会話文を名詞で終えない。述語を補う。

- 対応。 → 対応しました。
- 修正。 → 修正しました。
- 確認。 → 確認してください。
- 未対応。 → まだ対応していません。
- 要確認。 → 確認が必要です。
- 認証エラーの修正。 → 認証エラーを修正しました。
- 詳細はドキュメント参照。 → 詳細はドキュメントを参照してください。

見出し、ラベル、UI のステータス表示、ごく短い箇条書きでは名詞で終えてよい。

## 文末と依頼

「〜どうぞ」は、相手に何かを勧めたり差し出したりするときの言葉である。依頼には使わず、「〜ください」か「〜をお願いします」と書く。

- ご確認どうぞ。 → ご確認ください。
- お試しどうぞ。 → お試しください。
- よろしく。 → よろしくお願いします。
- 以上。 → 以上です。

「〜まで」は後ろに述語が続く言葉である。それだけで文を切らず、述語を補う。

- リリースまで。 → リリース予定です。
- 対応まで。 → 対応中です。

## 技術スラングの直訳

英語の句動詞や比喩をそのまま訳さず、実際に何をするのかを書く。

- land を寄せる、着地させると訳さず、マージする、取り込む、反映すると書く。
- drop を落とす、ドロップすると訳さず、削除する、廃止する、提供を終了すると書く。
- knock down や take down を倒すと訳さず、修正する、解消する、取り除くと書く。
- ship や push out を出すと訳さず、リリースする、公開すると書く。
- roll out は段階的に展開する、順次提供すると書く。
- spin up を回すと訳さず、起動すると書く。
- wire up を配線すると訳さず、接続する、組み込むと書く。
- bake in を焼き込むと訳さず、組み込む、標準で備えると書く。
- bubble up は表面化する、上位に伝わると書く。
- nail down は確定する、詰めると書く。
- call out は明示する、指摘すると書く。
- follow up は追って連絡する、後日対応すると書く。
- circle back は改めて検討する、後で戻ると書く。
- unblock は妨げを取り除く、作業を進められるようにすると書く。
- green-light は承認する、着手を許可すると書く。
- make sure を確実にすると訳さず、確認する、必ず〜すると書く。
- it's worth noting を注目すべきはと訳さず、補足すると、なお、と書くか、そのまま本題を書く。
- leverage を活用すると訳すのが不自然なら、使うと書く。

「〜きる」は finish 〜ing や 〜 out の直訳になりやすい。最後までやったことを伝えたいなら、完了した、書き上げた、最後まで確認したと書く。

- 仕様を書ききる → 仕様を書き上げる
- タスクをやりきる → タスクを完了する
- 一覧を読みきる → 一覧を最後まで確認する

## 冗長な構文

意味を変えずに短くできる言い回しは短くする。

- 〜することができます → 〜できます
- 〜となります → 〜です
- 〜に関して → 〜について
- 〜していきます → 〜します。続けて行う作業なら順次〜しますと書く。
- 〜を実施する → 〜する。定着した業務用語なら実施してよい。
- 〜という形になります → 〜です

「〜の方」は、方向や比較を表さないときだけ削る。「こちらの方が速い」「東京の方へ向かう」の「方」は必要なので残す。「資料の方をお送りします」のように、ぼかすためだけに付いているものを削る。

「問題なく動作します」や「ご不明点がございましたら」のように、自然で定着した言い回しは直さない。読み手や場面に合っているかだけを確かめる。

## カタカナ語

カタカナ語そのものは悪くない。日本語で十分に伝わるなら日本語を選ぶ。

- インプリメンテーション → 実装
- レファレンス → 参照
- コンフィグレーション → 設定
- バリデーション → 検証、入力チェック

リファクタリングやデプロイのように定着した言葉はそのまま使う。

## トーン

ユーザーへの説明や報告は、です・ます調で、簡潔でも述語のある文にする。技術ドキュメントもです・ます調にし、名詞で終えてよいのは見出しだけにする。

コミットメッセージは常体で書き、動作を表す言葉で終える。

UI のボタンやラベルは短くてよい。「保存」「削除」のように動作が明確な名詞か、「保存する」のような動詞形にする。一つの画面の中ではどちらかに揃える。

敬体と常体を混ぜない。意図して混ぜる場合は除く。

## 例

作業報告。

```
バグの修正。テストの実行。問題なし。
→ バグを修正し、テストを実行しました。問題はありませんでした。
```

次の手順。

```
次は PR のマージまで。
→ 次は PR をマージします。
```

依頼。

```
ログの共有どうぞ。
→ ログを共有してください。
```

コミットメッセージ。

```
認証まわりの修正。
→ fix: 認証エラーのハンドリングを修正する

不要な依存関係を落とす
→ chore: 未使用の依存関係を削除する
```

PR 説明。

```
この PR では変更を寄せます。レビューどうぞ。
→ この PR で変更を取り込みます。レビューをお願いします。

既知の問題を倒す対応。
→ 既知の問題を解消しました。
```

UI 文言。

```
エラー。再試行。
→ エラーが発生しました。再試行してください。
```

記号の多い文。

```
設定ファイル（config.ts）を更新しました：タイムアウト値を変更／ログ出力を追加。
→ config.ts の設定を更新しました。タイムアウト値を変更し、ログ出力を追加しています。
```

長い文の分割。

```
今回の変更では認証フローを更新し、トークンの検証ロジックを修正し、
エラーハンドリングを改善し、テストを追加することができます。
→ 今回の変更では、認証フローを更新し、トークン検証とエラーハンドリングを
  修正しました。あわせてテストを追加しています。
```

## 出力前に確認する

1. 本文が名詞で終わっていないか。
2. 「〜どうぞ」や「〜まで。」で文が終わっていないか。
3. 英語の原文を復元すると一語ずつの置き換えになっていないか。
4. 身体の動作を表す動詞が抽象的な作業に使われていないか。
5. 文中に丸カッコ、コロン、ダッシュ、区切りのスラッシュが残っていないか。
6. 一文が長すぎないか。長ければ分ける。
7. 敬体と常体が意図せず混ざっていないか。
8. 同じ語尾が続いていないか。
