Crea una mappa di revisione HTML di una pull request — cosa è cambiato, i giudizi che il revisore deve fare con le linee esatte che li risolvono, l'ordine in cui leggere il codice e a cosa il cambiamento arriva nel codice che non ha toccato — così un revisore può spiegare il cambiamento prima di giudicarlo. Targetta Rails e Elixir/Phoenix — un'app Phoenix LiveView o un'API JSON Rails o Phoenix, con o senza un client separato come Next.js. Usalo ogni volta che qualcuno deve comprendere un cambiamento piuttosto che valutarlo: quando si chiede cosa fa una PR o un branch, da dove cominciare in un diff grande, quali file sono davvero importanti, cosa il cambiamento potrebbe rompere, se frontend e backend sono ancora allineati, o quando è necessario aggiornare un revisore sul lavoro di qualcun altro — anche se non usano mai i termini “review map” o “walkthrough”. Invocare con /accountable-review:review-map in Claude Code o $review‑map in Codex, opzionalmente passando un numero di PR, URL, branch o intervallo di diff. C'è un unico formato di pagina e nessun flag lo seleziona. Un livello di sforzo è separato: --effort high è il valore predefinito e tenta di falsificare l'analisi eseguita prima che la pagina venga scritta, --effort low salta quel passaggio. --mentor è per un revisore nuovo allo stack piuttosto che al cambiamento: aggiunge un'introduzione al framework all'interno dei checkpoint che ne guadagnano uno e non modifica nient'altro della pagina. Fornire --output <dir> rende l'esecuzione non interattiva: la pagina viene scritta in <dir>/index.html come HTML statico portabile invece di essere pubblicata, che è il modo in cui CI ne genera una. Non è destinato a pubblicare commenti di revisione o verdetti di approvazione.
