# 安卓设备移植主线 Linux

## 这份 skill 怎么组织

- **外层框架**（本文件和 `references/`）：先做什么、后做什么，工作纪律，技术选型，怎么判断通过。相对稳定。
- **经验库**（`experience/`）：按领域写的推荐路线、完成标准和具体的坑（现象、原因、怎么确认、怎么解决、怎么预防）。随项目不断追加。

经验来自高通平板移植到 Ubuntu 26.04 + GNOME 的过程。硬件和内核部分基本通用；Ubuntu 相关部分换发行版时按 `references/ubuntu.md` 最后一节调整。版本号和接口名有时效性，使用前核对上游现状；上游已经解决的问题，直接用更简单的办法。

## 怎么用

- **新项目**：按下面的流程从第 0 步开始，每一步先读 `references/process.md` 对应小节，再读相关的 `experience/` 文件。
- **中途接手**：先读项目自己的 AGENTS.md、状态表和技术债表，再定位到流程中的哪一步。
- **做技术决策**：先读 `references/decisions.md` 对应一节的默认做法和规则。
- **排查故障**：先按 `experience/patterns.md` 判断问题属于哪一类、按通用步骤排查；再用日志里的错误码、函数名、配置项在 `experience/` 里 `grep` 找具体案例。
- **只做评估**：完成第 0 步，输出评估报告和决策清单。

### 顺序上最容易出错的地方

下面这些顺序错误代价最大，通常一次就是数天：

1. **先看同类项目再设计。** 安装方式、切换方式、调试通道、打包结构，同 SoC 或同类设备的项目往往已经有成熟做法和复盘。
2. **先建调试通道和自动恢复，再做任何实验。** 默认启动路径在通道建立前不碰外设寄存器。
3. **先取证，后写设备树。** 每个数值来自本机原厂证据，不从参考设备抄。
4. **借用固件画面只用于首次点亮。** 原生显示接管从第 4 步就开始并行，亮度、熄屏、休眠、外接显示都依赖它。
5. **桌面在内存里能跑就尽快持久化。** 不要等外设做全。持久化之后才能做冷启动验证，迭代也更快。
6. **新功能先单独测，再合并。** 不要把多个未经真机验证的改动塞进一个候选。
7. **日常迭代在设备上装包。** 只在发布时完整构建根文件系统。
8. **发布前按公开文档完整走一遍全新安装。**

## 工作纪律（必须做到）

细节见 `references/discipline.md`。

1. **必须写文档，并在固定时刻写。** 开始功能前写路线和完成标准；上机前写预期和判据，上机后当天写结果和证据位置；结论变化时更新状态表和工作日志；会话结束前写清唯一的下一步、阻塞和设备状态。下一个接手的人或 agent 只看文档就能继续。
2. **临时做法必须登记技术债。** 为了快速点亮或跑通可以先用临时做法，但每一个都要记进**统一的一份技术债表**：做了什么、放在哪、为什么需要、影响、去掉的条件。链路跑通后回来集中还债。
3. **目录结构固定，一份代码只放一个地方。** 内核仓、集成仓公开；私有工作区放记录和内部脚本；本机唯一数据和密码不进任何仓库。
4. **每条结论带版本信息。** 源码提交、镜像哈希、场景、证据位置。换内核、换系统、换驱动后旧结论要重验。失败记录不删。
5. **分清"跑起来了"和"能用了"。** 驱动加载、服务运行、节点存在、Fastboot OKAY、模拟器通过都只说明某一层没问题。标准见 `references/verification.md`。
6. **每一步都能退回去。** 只读 → 内存启动 → 写分区 → 改 bootloader 状态，风险逐级升高。往上走之前先确认退路可用。A/B 槽状态只用 bootloader 自己的命令改。
7. **一次只改一个变量；同样的失败第二次出现就停下来。** 从物理层往上找最早出错的层，写下已排除的假设和下一个能证伪的实验。
8. **不用全局开关掩盖问题。** 关资源回收、屏蔽部分模块、固定延时、无条件重试都会把问题推到更难查的时候。
9. **改启动路径必须冷启动验证。** unit、socket、udev、initramfs、启动参数的改动，用冷启动加对照验证，运行中切换不算。
10. **设备同一时刻只有一个操作者。** 每条命令带 serial；离开 Android 前读电量；对状态不明的设备不发破坏性命令；正式镜像永远保留一条可打开的调试通道。
11. **测试尽量全自动，用户参与尽量少。** 上机、采集、判定、恢复由脚本完成；截图和输入注入走调试通道自动化。用户只做看、听、按、摆放、插拔这类必须由人做的事，合并成一份清单，提前通知时间，一次做完。能用只读手段测量的不用提问代替。
12. **按版本推进。** 每个版本先定范围和验收方式，开发、测试、发布、清理之后再继续；不堆积未发布的候选。
13. **效率优先。** 超过 5 分钟的步骤要计时、找瓶颈、按输入缓存；长期 OUT 加足够大的 ccache；见 `references/build-environment.md`。

## 技术选型原则

每个重要选择用同一组问题判断，并记录理由和重新评估的条件。约 40 个关键选型点的默认做法和"遇到什么情况怎么做"的规则，见 `references/decisions.md`。

- 离上游越近越好：上游 > 在审补丁 > 同 SoC 社区 > 厂商代码 > 自己写。
- 可逆优先：不改 bootloader 状态、不碰原厂关键分区、失败能自动恢复。
- 有真机证据的优先于"声称支持"的；别人的结论在本机验证前只算线索。
- 能复用就整组复用；复用前先比较两边的"地基"（设备树路线、资源管理、安装方式）。
- 自己维护的部分越少越好；不引入通用框架和常驻"管家"服务。
- 硬件层不绑定发行版和桌面，换发行版只换集成层。
- 临时方案可以先用，但要同时开始长期方案并登记技术债。

## 需要用户决定的事

评估完成后一次性列出，每项给选项、代价和建议，用提问工具确认，确认后写进 AGENTS.md，不再重复问：

1. 数据能不能清除，备份哪些分区。
2. 单系统还是双系统，是否保留 Android。
3. 分区大小（给 2 到 4 个具体方案；Linux 根分区 60 GiB 通常足够，home 放最后方便扩容）。
4. 发行版和桌面环境。
5. 调试通道默认开还是关，是否预置账户。
6. 发布用的账号、仓库名、许可证，原厂固件是否随仓库分发。
7. 预计工作量、主要风险、还缺哪些前提条件。
8. 用户不在场时可以做哪些操作。

## 维护这份 skill

完成一个项目或解决一个新问题后，把经验写回 `experience/` 对应文件（格式见 `experience/README.md`）。流程或纪律有变化时才改外层。不写设备型号、序列号、个人信息和项目内部代号。
