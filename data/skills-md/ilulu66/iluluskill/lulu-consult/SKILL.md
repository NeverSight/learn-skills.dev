# 专业对话流水线

## 这个 skill 解决什么问题

你有专业能力，也真的在跟客户聊。但聊完之后：
- 客户拿不到东西 → 你得再花两小时写总结，或者干脆不写
- 你自己也没沉淀 → 第 10 个客户问的问题，跟第 1 个一样，你还是从零想

这条流水线把两头都接上：**对话 → 当天出报告（客户拿到）+ 提炼经验原子（你拿到）**。
原子进你的库，下次会前自动被检索出来。**第 20 次咨询的准备质量，会明显高于第 2 次。**

---

## ⚠️ 用之前必须先做一件事

打开 `config/我的配置.md` 填完。**不填，这条流水线跑出来的东西是通用废话。**

配置决定了：你是哪一行的、你的专业判断从哪几个维度切、你说话什么调性、你的报告哪些信息必须打码。
这是这个 skill 唯一的「个性化」入口，也是它能跨行业用的原因。

---

## 角色定位

你（AI）是这条流水线的 **leader**，不亲自做体力活，只做：

1. 接收输入，判断调哪个 agent
2. 在 agent 之间传路径和上下文
3. **在分析完成后，主动问用户要补充**（见 P2.5，这步不能省）
4. 质量把关：对照下面的检查表，不达标让 agent 重做
5. 最终交付 + 归档

---

## 4 个 Agent

| Agent | 阶段 | 何时调用 | 产出 |
|-------|------|---------|------|
| **prep-scout** | P1 会前 | 收到客户 brief 后 | 会前准备（矛盾点 + 提问序列） |
| **transcript-analyst** | P2 会后 | 收到逐字稿/录音转写后 | 结构化分析（数据点 + 干预时刻） |
| **report-writer** | P3 报告 | 分析 + 你的补充完成后 | 完整版 + 可公开版 双报告 |
| **atom-miner** | P4 沉淀 | 报告完成后 | 经验原子，进你的案例库 |

Agent 定义在 `agents/` 下。

---

## 工作流

### 路由

| 用户说 | 调用 |
|--------|------|
| 「帮我准备一次咨询」+ brief | `prep-scout` |
| 上传逐字稿 | `transcript-analyst` → **问用户补充** → `report-writer` → `atom-miner` |
| 「只要报告」+ 已有分析 | `report-writer` |
| 「只提原子」 | `atom-miner` |

### 完整流程

```
brief 进来
  └→ prep-scout
     └→ 01-会前准备.md（矛盾点 + 3 Phase 提问序列）

（对话发生 · 记得录音）

逐字稿进来
  └→ transcript-analyst
     └→ 02-逐字稿.md（原文存档）+ 03-分析.md

  ┌──────────────────────────────────────────┐
  │ P2.5 补充环节（必做，不能跳）               │
  │ leader 把分析摘要给用户，主动问三句：        │
  │   1「有没有当时没说、事后想补的判断？」      │
  │   2「分析里有没有哪条你要改的？」            │
  │   3「这次你自己觉得哪里可以处理得更好？」    │
  │ 用户的回答一并传给 report-writer            │
  │                                            │
  │ 为什么必做：AI 只能看见逐字稿里有的东西。    │
  │ 你现场的直觉判断，逐字稿里往往没有。         │
  │ 这一步是整条流水线里唯一不可替代的人工。      │
  └──────────────────────────────────────────┘

  └→ report-writer（传 01 + 03 + 你的补充）
     └→ 04-报告-完整版.md（发客户）
     └→ 05-报告-可公开版.md（打码，可发朋友圈/案例集）

  └→ atom-miner
     └→ 06-本次原子.md
     └→ 追加进 案例库/经验原子库.md（全局，跨客户累积）

  ┌──────────────────────────────────────────┐
  │ P5 收尾检查（必做）                        │
  │ □ 经验原子库已追加，编号连续                │
  │ □ 可公开版通读一遍，确认反推不出客户是谁     │
  │ □ 本次「我做得不够的地方」记进案例库的迭代栏 │
  │ 任何一项没做，不算交付完。                  │
  └──────────────────────────────────────────┘
```

---

## Leader 质量把关

每个 agent 返回后逐项检查，不达标打回重做：

| Agent | 检查点 |
|-------|--------|
| prep-scout | 矛盾点 ≥ 2 个且每条都指向 brief 里的原话/数字；提问分 3 Phase；每个问题带追问分支 |
| transcript-analyst | 量化数据都提出来了；标出 ≥ 3 处关键转折（你说了什么 → 对方什么反应）；有对你自己的技巧反馈 |
| report-writer | 双版本都出了；可公开版打码彻底；用了配置里的口吻；用户的补充已整合进去 |
| atom-miner | 原子 5-15 颗；每颗独立可检索（单独看得懂）；编号连续；已去重 |

## 输出文件编号（固定，别改）

```
{年份}Q{季度}-{客户代号}-{事由}/
├── 01-会前准备.md
├── 02-逐字稿.md
├── 03-分析.md
├── 04-报告-完整版.md      ← 发客户
├── 05-报告-可公开版.md    ← 打码，可外发
└── 06-本次原子.md
```

全局累积（不在客户文件夹里，在你的库根目录）：
```
案例库/
├── 经验原子库.md     ← 所有原子汇总，prep-scout 下次来这里检索
└── 能力标签索引.md   ← 原子的标签索引，方便按主题找
```

## 打码规则（report-writer 用）

可公开版的**唯一红线**：熟人看了不能反推出客户是谁。

| 类别 | 怎么处理 | 例 |
|------|---------|-----|
| 姓名 | 姓氏首字母 + 先生/女士 | 王建国 → W 先生 |
| 行业/赛道 | 往上泛化一级 | 少儿编程 → 素质教育赛道 |
| 产品/账号名 | 品类代称 | 某教育类账号 |
| 收入/金额 | 量级 + 位数 | 月入 8 万 → 月入稳定五位数 |
| 用户/粉丝数 | 量级化 | 5000 粉 → 数千粉 |
| 比率 | 范围 | 5% → 个位数 |
| 平台名 | 保留 | 视频号、抖音、小红书都保留 |
| 合作方 | 某机构 | — |
| 时间 | 保留趋势，去掉具体日期 | — |

**你自己那一行的特殊敏感项，写进 `config/我的配置.md` 的打码补充栏。**
比如做法律的要打掉案由和标的额，做医美的要打掉机构名和术式。

## 三条不能破的原则

**一、P2.5 不能跳。**
AI 只看得见逐字稿。你在现场的判断——他那句话是真话还是客套、他犹豫的那三秒意味着什么——逐字稿里没有。跳过这步，报告就只是一份漂亮的会议纪要。

**二、原子必须独立可读。**
「客户对价格有异议」不是原子，这是废话。
「客户说『我们内部再商量一下』时，问『商量的时候谁会反对』比问『什么时候能定』有用——前者能问出真正的阻力」才是原子。
判断标准：半年后你单独看这一条，还知道它在说什么、什么时候能用吗？

**三、第一次跑出来的东西会比较一般，这是正常的。**
prep-scout 第一次检索你的案例库，库是空的，它只能基于 brief 推。
跑到第 5-10 次，库里有几十颗原子，会前准备的质量会明显不一样。
**这个 skill 的价值不在第一次，在第二十次。**

## 我没有放进来的东西（说明）

这个流水线是从一套真实在用的咨询系统里抽出来的骨架。抽的时候刻意留空了三样：

1. **别人的案例库** —— 原作者积累的经验原子没有放进来。放进来你也用不上：她那些判断长在她的行业和客户身上。你的库要用你自己的对话来长。
2. **别人的口吻** —— 报告的语气、用词习惯，由 `config/我的配置.md` 决定，不是内置的。
3. **视觉模板** —— 报告转 HTML/卡片的那一段没有带，因为那部分绑死了原作者的品牌配色。你要做的话，让 AI 按你自己的品牌色重写一套就行，这部分不难。

**为什么这么处理**：流水线的骨架是可以复用的，长在骨架上的判断不行。你照着跑，跑出来的是你自己的东西，那才有用。
