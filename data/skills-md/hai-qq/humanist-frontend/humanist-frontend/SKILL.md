# Humanist · 设计执行 Skill

本 Skill 将设计指南、案例与访谈的研究提炼应用到当前项目。完整解释在 references 中；这里负责选择规则、实施与验证。仓库和调用名保持 `humanist-frontend`。

## 先判断这次需要什么

读取相关页面、共享组件与项目规则，确认是实现、改版、局部修复还是只审查。只审查不写代码；局部任务不重建设计系统。当前需求与已有设计系统优先于主题预设，外部参考不构成安装、上传或发布授权。

把“像 Anthropic / Kimi”转成具体需求：阅读节奏、品牌表达、信息组织还是交互方式？从已有材料能判断就继续；只有不同解释会实质改变结果时再询问。不要仅凭品牌名选定颜色和字体。

## 按任务选择设计判断

| 需要解决的问题 | 要落实的判断 | 按需阅读 |
|---|---|---|
| 需求抽象、整体方向不清楚 | 先定义主要任务；区分来源事实、综合判断与原创默认 | [原则与决策](references/01-foundations.md)：CTX-01–06 |
| 长文与中文阅读 | 用真实内容确定字阶、行长与主副关系；保留来源定位 | [视觉系统](references/02-visual-system.md)：TYP-01–02、LAY-01 |
| 品牌感与操作区互相干扰 | 让表达性视觉承担明确职责；操作区保持可辨认、一致 | [视觉系统](references/02-visual-system.md)：VIS-01–03、MOT-01 |
| 保存、建议或长任务 | 设计可恢复状态；保持用户编辑权；反馈对应真实执行 | [组件与交互](references/03-components-and-interaction.md)：CMP、AGT、COPY |

## 将判断落到当前页面

1. **定义结果**：主要任务、保留内容、设计约束和验收条件。整体改版可使用 [设计模板](templates/DESIGN.template.md)；小修无需新增文档。
2. **决定结构**：区分阅读、工作台、事务与展示场景。用实际长中文、文件名、数据与错误信息检查主副层级。主题服务结构；不为了套预设改需求。
3. **实现状态**：选择当前功能相关的组件规则。保存失败保留输入，迟到结果不覆盖新对象或手动编辑，组合输入确认不误发送，停止展示与取消执行分别表达。不强加后端不支持的控制。
4. **验证并交付**：运行与改动相称的项目检查，在可用浏览器中操作主要路径。说明实际改动与结果；未运行的视觉、输入法或读屏检查明确标注。可使用 [验收模板](templates/REVIEW.template.md)。

## 可选实现资产

已有系统默认继承。新项目可采用 `editorial-warm`（温暖阅读）或 `precise-light`（清晰工作区），也可按用户方向设计其他主题。它们是原创实施示例，不是两家公司的完整设计系统。

[token JSON](assets/tokens.json) 与 [CSS](assets/tokens.css) 需要显式主题属性 `data-hf-profile`、`data-theme`。品牌色与操作色分开；实际颜色修改后重新检查。可运行：

```bash
python <skill-directory>/scripts/check_contrast.py
```

此脚本仅检查包内列明的纯色色对。最终判断是实际页面能否读懂、操作、恢复，以及实现是否尊重用户任务；不能以色板通过替代页面验收。
