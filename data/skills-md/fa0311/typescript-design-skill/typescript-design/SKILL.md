# TypeScript 設計思想

これは既定値であり、ユーザーの明示的な指示が常に優先する。ライブラリが形を規定している場所(フレームワークの middleware 契約、SDK のコールバック)はそのライブラリで最も自然な形で書き、自分が設計する境界にここの規則を適用する。説明ではなく判断基準とその理由だけを置く。思考を広げるためのケースライブラリとして使う。

## 1. 調べてから書く

- 自分の知識はカットオフで止まっている。ランタイム・言語・パッケージは自分の知識より新しい前提で、使う前に公式リリースノートと npm の最新版・公開日を確認する。
- 優先順: 標準 API > モダンで人気があり要件に合う API を持つパッケージ > 自作。パッケージは規模で判断する。DL 数・スター数が極端に少ない場合はユーザーに相談する。TypeScript の標準的な書き味(try-catch、Promise、EventEmitter)を大きく変えるパッケージは、それ自体が優れていても入れない。
- 日付・Promise・イテレーション・リソース管理・イベントの領域は標準が動き続けている(`EventEmitter<{ message: [text: string, id: number] }>` のような型引数、`Temporal` など)。ライブラリを足す前に、標準にないかを調べる。

## 2. アーキテクチャの姿勢

- レイヤードは意識するがクリーンアーキテクチャほど強くしない。効果(I/O・ネットワーク・ログ)は葉に、純粋な変換は核に、方針決定は composition root に置く。それ以上の層や interface は作らない。
- テストのための依存性逆転はしない。interface と実装の対を作ると、差し替え先が 1 つしかないのに 2 箇所を保守することになる。差し替えたい依存は引数で渡す(関数かオブジェクトかは責務次第)。それが DI の全部。
- マイグレーションはしない。破壊的変更は許容する。
- 差分を小さくするためにコードを書かない。既存コードに継ぎ足さず新しい要件から設計し直す。既存の命名や構造、ユーザーが付けた微妙な名前は尊重しすぎず、今の変更で触れる範囲で合わなくなったらリネームや移動を躊躇しない。レビューしやすい小さな変更より、一貫した状態に一気に持っていくことを優先する。
- 設計し直す過程で居場所を失った抽象(呼び出し元が 1 つの helper、その helper のためだけの options 型や enum 風 union、lookup table)は呼び出し元に inline する。行数が減るのは目標ではなく、抽象が要件に追従した兆候。
- 安全寄りに倒さない。schema が保証している値への存在チェック、フォールバック、後方互換のための分岐を書かない。枯れた API より新しい標準 API、広い型より狭い型を選ぶ。エラーを飲み込まず、壊れたら大きく壊す。

## 3. 関数分割の唯一の基準は抽象化

- テストのため、ネストや行数のために分割しない。見た目は可読性に直結せず、本質的でない分割は引数を汚す。抽象化以外の理由で分けなければ粒度は自然に揃う。
- 抽象化とは、切り出した関数の名前が「何をするか」の契約になり、呼び出し側が中身を知らずに使えること。名前が手順の要約にしかならず、呼び出し側が中身を意識し続けるなら、それはただの分割。使用箇所の数は無関係で、1 箇所しか使わなくても抽象化はするし、2 箇所で使うだけなら共通化(コード量を減らす関数化)であって抽象化ではない。共通化のための分割はせず、重複のまま置く。
- 典型は「知識を持たない抽象」。ドメインの型や API を一切 import せず、可変部分を引数で受け取る形にできるもの。例えば「次のカーソルが null になるまで取得を繰り返す」処理は、何を取得するかを関数で受け取れば、対象 API を知らない generator になる。
- 似ているが寿命や失敗方針が違うコードは重複させる。例えば「1 回だけ走って失敗したら止まる処理」と「常駐して失敗しても次へ進む処理」が同じ手順でも、共通化すると失敗方針が引数に漏れて方針オブジェクトが生まれる。
- コンパイラが各分岐を検査できる明示的な反復は、データ駆動の賢さより良い。例えば言語コードから表示名への変換は、`Record` で表引きするより literal union の switch で並べる方が、追加時に漏れを型が指摘する。同型の文が並ぶことは分割の理由にならない。

## 4. 関数と状態

- arrow の `const` のみ。`function` は generator にだけ使う。class は `Error` 派生とフレームワークが要求する場合だけ。
- class の代わりは closure factory。作るのは複数の操作が同じ文脈(設定・接続・操作対象・可変状態)を共有するとき。操作ごとに同じ引数を渡すことになるなら、その引数を factory が保持して操作群を返す。文脈を共有しない操作はモジュール直下の関数。private 状態はクロージャに閉じ込め、戻り値のオブジェクトリテラルが公開 API。内部の関数をそのまま公開するなら `{ close: connection.close }` のように参照で渡し、ラップしない。
- `let` は使わない。分岐で値を決めるときは即時実行の(async)arrow で `const` に落とす。可変状態がどうしても要るとき(カウンタ、キュー、キャッシュ、再試行回数、generator のカーソル)は、それを責務の小さい関数か closure factory の内部に閉じ込め、外からは関数呼び出ししか見えない形にする。閉じ込めた `let` を再帰に書き換える必要はない。closure factory の private 状態はこの「閉じ込めた `let`」であり、閉じ込めた部分だけを重点的にテストする。「小さい」はコードの量ではなく責務の話。

## 5. 型

- 返り値の型は書かない。引数は書く。再帰や相互参照で推論できないときだけ書く。外に名前が要るときは `ReturnType` / `Awaited` / `infer` で取り出す。生成する側の関数から型を導出すれば、変換と型は乖離しえない。
- schema が型。推論型と indexed access(`Settings["profiles"][number]`)で導出し、二度書かない。
- `type` に統一(宣言マージが要るときだけ `interface`)。`enum` は使わず literal union。
- 検証済みの値は brand で未検証の値と型で区別し、brand への変換関数を唯一の入口にする。例えば検証済みのメールアドレスを `string & { readonly brand: unique symbol }` の型にしておけば、ただの `string` は渡せない。
- 判別 union + `default` なしの exhaustive switch。union にメンバーを足すと全消費側が型エラーになる。構文上 default が要る場所は `never` を返す `unreachable()` を式として使う。

## 6. 境界と検証

- `typeof` で判定しない。外部データ(env・設定ファイル・CLI 引数・HTTP・WebSocket・ファイル)は入口で 1 回だけバリデータに通し、下流は型を信頼する。どうしても `typeof` が要るなら責務の小さい関数に閉じ込めて重点テスト。
- 入力は `unknown` に落としてから検証する。parser は path でなく string を受け、ファイル I/O は呼び出し側の責務。
- 自分のデータの schema は strict(未知キーは失敗)。ドメイン知識なしにできる変換(文字列化された数値、0/1 の boolean、標準形式の日付、default)は schema の中で済ませ、下流は生の形を見ない。独自フォーマットや複雑な変換は schema に持ち込まない。
- 「壊れていたら例外を投げる」parse は自分の設定や、外部メッセージの外側の封筒(必ず同じ形の部分)に使う。「失敗を値で受ける」parse は封筒の中身のように variant が増えうる部分に使い、既知の variant は型付きで、未知の variant は捨てずに観測可能なイベントとして流す。
- 設定ファイルに JSON を使うなら JSONC。CLI は GNU の作法に従う。
- middleware は context 変数バッグでなく、型付き callback を受け取る高階関数にする。`ctx.set("user", user)` して後で `ctx.get("user")` するのでなく、`withUser(req, (user) => …)` のように引数で型を流す。

## 7. エラー

- 既定は throw。catch するのは composition root の 1 箇所(top-level await + try/catch/finally、または CLI フレームワークの main)。常駐するものでは処理単位のループ本体が root に相当する。`process.on("unhandledRejection")` や `--unhandled-rejections=none` は使わない。
- `onError` のような `onXxx` 引数を作らない。EventEmitter を返す。モジュールが外へ伝える事実(エラー、完了、進捗)は emitter 1 つで全部表せるので、事実ごとに引数を生やす必要がない。外から受け取る依存や方針には emitter に相当する共通の仕組みがないので、引数で渡す。emit するのは事実だけで、それが致命的かは root の `on` で決める。`captureRejections: true` にすると async な listener の reject が `error` イベントに流れるので、`on` の最外側で try-catch しない。
- Result 型は基本使わない。TypeScript の標準は try-catch であり、書き味を変えてまで導入しない。自分で Result を定義して返す設計をしない、という意味で、バリデータの safeParse のように失敗を値で返す API を使うことは含まない。例外は、複数の非同期処理の失敗を集めて後で判断するような、try-catch では表現できない制御のときだけ。
- Error class は用途で決める。誰も型で catch しないなら文脈を補間した `Error` で足りる。retry 可否や expected/unknown を `instanceof` で分けるなら、共通の基底 Error class 1 つと、それを継承した空ボディの class 群(名前が payload)。
- 捨てない。並列に走らせた処理が複数失敗したら、全部終わるのを待ってから `AggregateError` にまとめて投げる。wrap するときは `cause` に元を残す。
- 人が起動して結果を待つものは fail-fast で `process.exitCode = 1`(`exit()` は出力を捨てる)。常駐するものは処理単位ごとに try/catch して継続し、成否を外部から観測できる形で残す。

## 8. 非同期

- try-catch(または `.catch`)されない Promise を許容しない。理論上 reject しないものだけ例外。fire-and-forget は `.catch(handler)` で終端し、捨てるなら `void` を明示する。
- 特に浮きやすい場所: `setTimeout` / `setInterval` の中、責務の大きい SDK(HTTP フレームワーク・チャット bot SDK・ブラウザ自動化)のイベントコールバックの中。
- retry は失敗方針を自分が所有するときだけ。上流が既に持つ方針を自分の層で二重に持たない。
- リソースを取得したら、その場で解放の手段(closer)を登録する。取得と解放が離れた場所にあると、片方だけが変更される(付録参照)。

## 9. テスト

- 本質的でないテストを書かない。外部パッケージのテストになるテストを書かない。integration でやるべきものを unit でやらない。
- 純粋ロジックは網羅し、配線(エントリポイント本体)はテストしない。外部サービスは実物で integration する。
- module mock と fake timer を持つ現代のテストフレームワークがあるので、テストのために設計を変えない。

## 10. 命名・ファイル

- 1 概念 1 ファイル。数行でも別ファイル。barrel は明示列挙(`export type` と `export` を分ける)か、作らない。`export *` は使わない。
- `createX` factory、`XSchema` と推論型 `X`、`XOptions` を関数の直上に。

## 付録: 発想の引き出し

規則ではなく、要件に当たったときに思い出す発想。状況 → 発想 → なぜ、の順。

- 同じ方針(retry、上限、ログ)を複数箇所で適用したい → オプションを受けて実行関数を返す高階関数にする → 方針を 1 回設定すれば、呼び出し側は `run(() => fetch(url))` と書くだけで済む。
- 状態を持つ生成器(指数バックオフの「今何回目か」など)を複数の実行が使う → factory を返す factory にして、実行ごとに新しい生成器を作る → 共有すると、ある実行の失敗が別の実行の待ち時間を伸ばす。2 つ作って片方を進めても他方が動かないことをテストで固定する。
- オプションが `maxDelay?`、`jitter?` のようなフラグで増えていく → 値を加工する関数の配列を受け取って reduce する → 本体を変えずに加工を足せる。boolean フラグは組み合わせが増えるほど本体の分岐が増える。
- 同じキーで並行に呼ばれる非同期処理がある → 結果でなく Promise をキャッシュする → 完了前の二重実行が起きず、後から来た呼び出しも同じ Promise を待てる。
- リソースを複数取得して最後にまとめて解放したい → 取得の直後に closer を登録する小さな stack を作る → 取得と解放が離れていると片方だけ変更される。解放は全部走らせてから失敗をまとめて投げる。標準の `AsyncDisposableStack` で足りるならそれを使う。
- 同時実行数の上限と retry を両方かけたい → 上限(semaphore)の内側で retry する → retry のたびにスロットを手放すと、再取得待ちで上限と投入順の意味が崩れる。
- 下流の失敗(書き込み)で上流(ダウンロード)を止めたい → 処理の scope ごとに `AbortController` を 1 つ持ち、signal を上流に渡す → 標準の仕組みで伝播でき、listener は成功経路で解除する。
- イベントが 1 回起きるのを待ちたい → `once(emitter, event)` → 手書きの Promise は resolve 漏れや listener 漏れの温床。
