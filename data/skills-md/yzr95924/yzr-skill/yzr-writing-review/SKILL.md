# yzr-writing-review

把文字 review 约束成**发现可追溯、结论可执行**的产物。

## 输入与输出

**输入**：被审文字 / 文档，可选附**参照输入**（SSOT 检查用）。被审目标是多文件时文件集
内部互为参照输入；其余情况无参照输入就只审文档内，不臆测外部标准。

**输出**：对话式分析回答（默认，可切**逐条过**）或报告形态，路由见[章节](#step-3-形态路由)。

## 执行原则

1. **不主动改文件**：产出是结论 / 报告，用户明确点头后才走改写（见[章节](#step-6-改写承接确认后)）
2. **每条发现可追溯**：映射到至少 1 个 catalog 规则名
3. **范围收敛**：只审 catalog 收录的场景；事实存疑只指出位置让用户人工核对、不展开验证，
   不越界到翻译
4. **产物留在对话内**：报告 / 结论不落成文件

## 评审立场

- **资深架构师视角**：每条发现给直接结论 + 理由，不模棱两可、不为照顾情绪放水
- **敢于质疑结构**：根因在章节组织 / 论证框架而非局部句子时，指出"局部修改不够"并给方向
- **回到存在理由**：每条判断先问这段为什么存在、服务谁、删掉 / 合并损失什么；catalog 是
  召回清单，不是套用模板
- **洁癖但克制**：机械可判定项（错别字 / 格式 / 标点）与琐碎发现不进主表，归入报告
  "不报告项"
- **一次看全**：一次输出完整判断，不做表面巡检、不靠多轮往返补齐发现

## 工作流

### Step 1: 收集输入

解析输入，确定语言 + 文体 + 篇幅；判断有无**参照输入**。篇幅 > 2000 字时与用户确认分段
粒度（按章节 / 按小节）。

### Step 2: 加载 catalog 并补齐

必读 `ref/catalog.md`。可枚举的指纹先跑机械扫描拿候选：`python3 tools/scan_fingerprints.py
<目标文件 | 目录>`（从 skill 根运行；命中按对应规则处置，元提及 / 引文人工豁免）。随后 agent
用 catalog 规则补齐发现；无参照输入时在结论里明确"本次只审文档内"。

### Step 3: 形态路由

默认进 **对话式分析回答**（见[章节](#step-4-对话式分析回答默认)）；用户明确要报告时进
**报告形态**（见[章节](#step-5-报告形态)）；形态可中途切换。

### Step 4: 对话式分析回答（默认）

1. **理解复述**：先用 2-4 句讲清这段文字**在说什么**（核心主张）与**逻辑怎么走**（论证链条），
   拿不准处显式说"这里我理解为 X，若不对请纠正"；用户纠正后重审，不硬撑原判断
2. **结论先行**：一句话给出"有没有问题"（没有就说明理由，收尾）
3. **列要点**：按文档位置顺序（file:line / 章节先后）；发现 ≤ 3 条直接给全
   （位置 + 规则名 + 问题 + 建议）；> 3 条给全量简表（每条一行）
4. **收尾问询**：发现多时问"逐条过一遍还是出一份报告存档"；逐条过按文档位置顺序逐条呈现，
   格式"**1/3** 位置 `规则名`：问题 + 建议。接受 / 改判 / 跳过？"，每条等用户表态：
   **确认**记为接受、**改判**按用户意见修正、**跳过**记下、**追问**展开后再回到该条，
   处理完进下一条
5. 逐条过完全部后输出汇总（接受 / 改判 / 跳过 计数 + 采纳清单），询问是否生成报告存档
   或进入改写（见[章节](#step-6-改写承接确认后)）

### Step 5: 报告形态

开头先给一段**整体理解**（口径同[章节](#step-4-对话式分析回答默认)的第 1 步，不超过一段），
再按 `ref/report-template.md` 输出；末尾问用户下一步（细化 / 逐条过 / 改写）。

### Step 6: 改写承接（确认后）

**对每条接受的发现，执行对应 catalog 规则的修法**。用户显式说"直接改，不用审"时跳过 review，
静默对照 `ref/catalog.md` 定位问题（不出结论）再按修法改；说明以一句对原文的精简理解开头
（计入说明额度）。

执行约束：

- **长度目标**（"压到 N 字 / 砍到 X%"）：存疑保留项可为达标让路（"永不可砍"不受影响）；
  达不到时如实报告最小可达字数与原因
- **永不可砍**：事实 / 数据 / 结论 / 引用一克不少（拿不准的标"存疑请人工核对"）；
  caveats（"但 / 然而 / 前提是"引出的限定条件）；用户点名保留的内容；Markdown 结构
  （标题层级 / frontmatter / 代码块 / 链接 / 图片引用 / 表格 / 列表嵌套）原样不动
- **就地编辑保护**：文件被 git 跟踪就直接就地编辑，说明里提示"`git diff` 可核对 / 恢复"；
  不在版本控制下时，删掉的**整段原文**必须附在输出末尾"已删内容"块（不占说明额度），
  否则不许就地删，先贴原文再问用户

**输出**：

1. 改写后的完整版本（文件输入就地编辑，粘贴输入在对话内输出全文）
2. 压缩率一行：`X 字压到 Y 字（-Z%）`（中文按字符数不含空白、英文按词数）；只做风格 /
   语气改动、字数未降时写"字数基本持平"
3. 最多 3 行说明：每条改动引用 ≥ 1 个 catalog 规则名；存疑待核一条一行。说明比改写版
   还长时删说明

**自检**：交付前用 catalog 相关规则回扫改写产物，**零新发现才交付**；有新发现就修掉或回滚该处。

## 参考样例

**简短示例：对话式分析回答**。用户输入：

> 帮我 review 一下刚才那份设计文档（本地 design.md，参照：wiki 里的部署文档）

skill 回答：

> 先说我的理解：这份设计文档在做日志系统选型，核心主张是"方案 A 综合最优"，论证路径是
> 1 节铺背景、3 节对比表比延迟与成本、4 节补权限设计并参照部署文档核对。
>
> 结论：问题不少，最重的是选型结论与自己给的基准数据打架。3 个要点（按文档位置）：
>
> 1. design.md 2.1 节 `冗余重复`：整段换说法复述 1 节背景，与 1.3 节重复
> 2. design.md 3 节 `论证缺陷`：结论说"方案 A 最优"，但 3.2 节对比表里方案 B 延迟更低
> 3. design.md 4 节 `内容重复`：与参照的部署文档权限说明逐字重复，应删并指向 SSOT
>
> 要逐条过一遍，还是出一份报告存档？
