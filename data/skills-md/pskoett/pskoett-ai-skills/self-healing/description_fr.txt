Récupération active du runtime pour les agents de codage : quand quelque chose se casse en cours de tâche, diagnostiquer la cause racine, écrire un correctif, VERIFIER en relançant l’élément cassé, puis consigner une entrée `HEAL-` dans `.learnings/HEALS.md` avec la preuve. Utiliser chaque fois qu’une commande, un test, un build ou un lint échoue ou renvoie un code de sortie non nul ; en cas d’outils manquants, de désaccord de dépendance/fichier de verrouillage, de mauvaise version du runtime, d’erreurs d’environnement virtuel ou de permissions, de conflits de ports, d’un état git sale, ou d’un `.env` manquant ; lorsque l’agent a besoin d’un helper ou d’un script ponctuel qui n’existe pas encore ; lorsqu’une API externe, un outil ou le MCP génèrent des erreurs ou des limites de taux ; ou lorsqu’un test flake. Chercher d’abord dans `HEALS.md` par `Pattern‑Key` — la plupart des heals sont des récurrences, donc incrémenter `Recurrence‑Count` au lieu de dupliquer. La vérification est obligatoire : marquer `pending‑verify` honnêtement si sandboxed, `abandoned` si le correctif ne peut pas fonctionner. S’associe à `self‑improvement` (qui promeut les heals récurrents en mémoire durable) mais possède la discipline « vérifier avant de persister » que l’auto‑amélioration n’a pas.
