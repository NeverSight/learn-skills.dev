# Writing for Agents

参考 Matt writing-for-agents 的方法，让文档稳定地引导执行过程，而非强求每次产生相同输出。默认中文，保留项目术语。
这是写作参考，不额外启动需求、实施或发布流程。按用户请求起草、修改或仅审查目标文档；保持已确认能力、约束和授权范围。
目标是 skill 时，读取 [SKILL-MECHANICS.md](SKILL-MECHANICS.md)；其他文档无需读取。

## Context pointers：把读取条件写清楚

指针既说明材料是什么，也说明何时读取。必须执行的规则藏在含糊引用后，会造成不同轮次行为不一致；先改进指针，再考虑把全文搬进入口。

- 把决定触发条件的概念放在前面，每个不同分支对应一个条件；同义词堆叠不算多个分支。
- 用“发布 tracker 前读取 issue-tracker.md 的目标与写入规则”，而非只有“更多信息见 issue-tracker.md”。
- 引用真实存在且执行者可访问的材料。给新 session / 子代理的文档不能依赖“前面讨论过”；必要内容直接附上，或给出明确可读取来源。
- 指针常驻上下文，每个字都要有作用；目标文档已说明的身份和背景不重复放进指针。

## 两种负担

**Context load** 是常驻指令占用 agent 注意力和上下文的成本；**cognitive load** 是用户记住有哪些文档、何时调用它们的成本。
把内容移到参考文件会降低前者，但需要可靠指针；拆出手动入口会增加后者。用户判断必需的环节保留人工入口，不能仅为自动化隐藏决策。

## 信息层次与组织

区分按顺序执行的 steps 和按需查阅的 reference：

1. 所有分支都需要的步骤留在入口，顺序清楚。
2. 执行时常用且简短的规则留在同一文件。
3. 只有部分分支需要的细节放进参考文件，在使用位置写清读取条件。

这是 progressive disclosure，不是为少几个 token 把关键规则藏起来。定义、规则与例外放在一起，避免读到一半必须去其他段落找限制。
即便每句话都有用，过长的入口也会分散注意力；按真实分支拆分，不为了文件短而任意切块。

## 步骤与完成标准

完成标准同时需要**可判断**和**足够覆盖目标**。例如“列出变更”容易漏项，“每项验收条件都有对应实现或明确未完成说明”会驱动必要核查。
先用明确产物、可观察结果和验证证据改善模糊标准；不能通过发明新的需求或额外审批来使它看起来严格。

```text
含糊：确认修复正确。
明确：重跑用户原始复现步骤，记录症状是否消失及回归测试结果。
```

后续步骤可能诱使 agent 草率结束当前阶段。先改善当前阶段的完成条件；只有观察到持续抢跑且条件确实难以表达时，才考虑通过交接或独立上下文拆开流程。仅把后续内容放进同一上下文里的另一段，不会产生真正隔离。

## Leading words：用准确概念压缩

优先使用已有明确含义的短概念，如 regression test、tracer bullet、public seam，而不是在多处重复整段定义。
概念必须与任务匹配；自造术语要付出解释成本，不能靠“全面”“严谨”等形容词替代可观察标准。
优先描述目标动作。必要的禁止项保留为明确边界，并说明替代动作；不为了改成正面句式删掉权限或安全约束。

## 按行为精简

- **Single source of truth**：同一维护范围内一条规则有一个权威位置，其他位置用明确引用。独立安装需要的随包内容不能为了去重移到不可用的外部位置。
- **避免易过期副本**：现有命令、配置和目录能直接查明的事实，优先让 agent 查来源；文档保留配置无法表达的约定、原因和容易踩的坑。任务交接需要固定的基线 / 已验证事实时明确记录其范围。
- **Relevance**：逐段判断是否仍与目标有关，删除过时残留，把分支细节移到对应位置。
- **No-op test**：去掉一句后，执行决策是否改变？没有作用的说明整句删除；不要通过压缩字数牺牲有效的能力、约束、例外或验证要求。
- 模型是否默认会做某事不能靠想当然决定。存在争议时，用实际任务观察有无该句的行为差异，不宣称更短就更好。

## 交付前检查

从未读过本次对话的执行者视角检查：能否找到必要输入、适用分支、动作和完成标准？引用是否可用，例外是否与规则相邻，修改是否保留已确认行为？
检查适用的格式、链接和元数据。流程有实质变化时，用代表性场景核对正常路径、缺失输入和阻塞路径；结构检查与实际执行分开报告，未做行为验证就明确说明。
仅审查时给出具体问题与建议；修改时说明影响执行的变化，不把写作建议变成额外工作流。
