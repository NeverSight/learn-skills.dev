# Diagnosing Bugs

沿用 Matt 原版的六阶段诊断纪律。仅在明确说明理由时跳过阶段。
默认中文报告，保留项目技术标识符。读取项目 AGENTS.md / CLAUDE.md、已有 CONTEXT.md / CONTEXT-MAP.md 和相关 ADR。
接受症状、日志、失败测试或 issue，不要求先有 spec、tracker 配置或运行 setup。本入口可独立完成诊断与范围内修复，不自动调用其他 skill。
用户要求“只排查”时，做到根因和证据后停止，不修改产品实现。预期行为不明确或修复需要改变外部契约时，先确认行为和兼容影响。
不自动发布 / 关闭 issue、push、merge 或部署；若用户另行授权更新 tracker，先读取项目配置和目标对象，保留人工编辑。

## Redact

展示命令、输出和捕获产物前，先将所有秘密替换为 `<REDACTED>`。凭据通过环境变量使用，不写进展示的命令。
HAR、请求和 trace 可能携带认证头，只引用诊断所需且已脱敏的行。脱敏证据不足时说明缺失信息，不索取原始秘密。

## Phase 1: Build a feedback loop

先建立针对用户确切症状的快速 pass/fail 信号，再推测根因。此阶段值得投入最多精力。

按场景选择反馈闭环，通常依次尝试：

1. 能触达真实故障的 unit / integration / e2e 失败测试。
2. 对开发服务执行 curl / HTTP 脚本。
3. 带 fixture 的 CLI 调用，对照已知正确输出。
4. Playwright / Puppeteer 驱动 UI，断言 DOM、console 或 network。
5. 重放已脱敏的真实请求、payload、trace 或事件日志。
6. 临时 harness：启动最小系统子集，用一次调用触发故障。
7. Property / fuzz loop，重复输入以捕获间歇错误。
8. 在已知好坏 commit、数据或版本间建立可用于 `git bisect run` 的判定脚本。
9. Differential loop：相同输入比较旧 / 新版本或两种配置。
10. 必须人工操作时，复制 [HITL 模板](scripts/hitl-loop.template.sh) 并按症状改写步骤，请用户在自己的终端运行，把末尾的 `KEY=VALUE` 输出贴回。agent 的 shell 没有交互式 stdin，不要自己运行它；不让用户输入凭据。

持续收紧闭环：减少初始化时间、断言确切症状、固定时间 / 随机种子、隔离文件和网络。目标是秒级而非分钟级；无法达到时解释限制。
偶发故障以提高复现率为目标，可重复触发、并发压测或控制时序；记录样本数和失败率，不能用偶然一次通过认定修复。

进入下一阶段前，给出**已经实际运行过至少一次**的一个命令及脱敏输出，并确认：

- 能经过实际故障路径，针对用户症状报失败，而不只是“没有崩溃”。
- 结果稳定；偶发故障有足够高且可量化的复现率。
- 尽可能快，agent 能无人值守执行；人工介入仅作为最后手段。

可以阅读代码来构造复现，但不能在没有可失败的闭环时直接凭代码猜根因。
确实无法建立闭环时停止推测，列出已尝试的方法，说明需要可复现环境、脱敏产物或经授权的临时生产观测。

## Phase 2: Reproduce + minimise

运行闭环，观察失败。确认这是用户描述的故障，而不是附近另一个错误；多次运行确认稳定性或复现率，记录错误、错误输出或耗时。
逐个减少输入、调用方、配置、数据和步骤，每次都重跑。保留仍然导致失败的最小场景；剩余元素应各自对复现有必要。
复现并最小化后才进入假设阶段。

## Phase 3: Hypothesise

在测试假设前列出 3–5 个按可能性排序的可证伪假设，避免锚定第一个合理解释。
每个假设写明预测：“如果 X 是原因，改变 Y 应使故障消失 / 改变 Z 应使故障加重。”不能提出可检验预测的想法需要舍弃或细化。
先向用户展示排序，吸收其领域信息和已排除的原因；无需等待回复才开始验证。

## Phase 4: Instrument

每个探针对应一个假设的预测，每次只改变一个变量。
优先 debugger / REPL，其次是在能区分假设的位置添加定向日志，不采用“全部打日志再搜索”。
每条临时日志加唯一标记，如 `[DEBUG-a4f2]`，方便彻底清理。
性能回归先用 timing harness、profiler 或 query plan 建立基线，再二分定位；先测量再修复。

## Phase 5: Fix + regression test

回归测试必须经过正确的 seam，覆盖调用处发生的真实故障模式。例如需要多个调用方触发的问题，不能只用单调用方单元测试证明修复。
若没有这样的 seam，明确记录“当前架构无法锁定该故障”，不拿浅层测试制造信心，也不擅自扩大成架构重构。

最小修复以已验证根因为边界：检查相关调用方，选择能覆盖受影响路径的正确修复位置，避免只在报告中的一个调用处掩盖症状。优先复用已有机制，不无据增加重试、兜底或配置开关；也不以修 bug 为由顺手整理无关代码。原始场景与必要回归验证通过后停止扩展，不能为缩小 diff 省略其他受影响路径。

存在正确 seam 时：

1. 将最小复现转成回归测试。
2. 实际观察测试因该 bug 失败。
3. 应用针对已验证根因的修复。
4. 观察测试通过。
5. 重跑 Phase 1 的原始、未经缩减的场景，并执行相关检查。

“只排查”模式报告根因、证据、建议修复和适合的回归 seam，不执行产品修复。

## Phase 6: Cleanup

宣告修复完成前检查：

- 原始复现闭环已重跑，症状消失；偶发 / 性能问题用同等条件和足够样本对比。
- 回归测试通过，或明确说明缺少正确 seam 及验证限制。
- 搜索唯一标记，移除本次所有临时 debug 探针。
- 删除本次临时 prototype，或放入明确标记的 debug 位置；保留用户已有文件。
- 报告根因、验证证据和未验证事项；如任务包含 commit / PR，将最终成立的假设写入说明。

只排查也要清理本次探针；不得将“根因已定位”说成“修复已完成”，不得将未运行的检查记为通过。
