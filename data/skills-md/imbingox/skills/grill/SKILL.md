# Grill

通过分轮讨论形成共同理解，不实现功能，不自动发布 issue。
默认用中文解释，保留项目已有的领域术语和技术标识符。
本 skill 已内置追问与 domain modeling，不需要其他 skill。

## 先查事实

读取项目的 AGENTS.md / CLAUDE.md、已有 domain docs 配置、CONTEXT.md 或 CONTEXT-MAP.md，以及相关 ADR。
检查当前实现、现有调用方、测试与配置。用户已经回答过的内容不要重复询问；代码和工具能查明的事实由你查，不让用户代查。
如果用户描述与代码不一致，区分“当前事实”和“希望改成的行为”，不要擅自选择一个覆盖另一个。

## 分轮澄清

将决策组织成有依赖的设计树。每轮只问前置条件已经明确的问题，等待回答后再推进依赖它们的问题。
每个问题给出简短背景、可选方案、推荐答案及主要取舍。已经确定的内部细节不再作为问题凑数。
有 sub-agent 工具时可并行查独立事实；没有时自行查，不要求安装额外工具。

优先确认这些真正影响结果的决策：

- 用户 / 调用方最终如何使用：API、CLI、UI、配置、输入输出及最小使用示例。
- 默认值、错误、空状态、异步完成与失败恢复等可观察语义。
- 旧接口、旧配置、旧数据和混合版本调用方的兼容范围；是否允许 breaking change，以及迁移和弃用方式。
- 验收边界与测试 seam；范围内和明确不做的内容。

涉及模块接口、职责拆分、测试 seam 或重构方案时，读取本 skill 的 [codebase-design.md](references/codebase-design.md)，在讨论中应用，不需要用户另行调用。

先确认使用形态，再讨论必要的实现取舍。不要让内部实现方便与否替用户决定外部契约。
只问对当前范围有实质影响的未决问题，不穷举无关的未来功能。

选择最小充分方案：

- 区分用户要达成的结果与提出的实现手段，检查现有功能、配置或平台能力是否已经足够。
- 存在更简单方案时说明它能覆盖什么、缺少什么；不能擅自删减用户明确要求。
- 新增依赖、可配置项或扩展点需要当前用例或已确认约束支撑，不能只以“以后可能用到”为理由。

## 随讨论记录文档

涉及领域术语、概念关系或 glossary / context map / ADR 的新增与修改时，读取 [domain-modeling.md](references/domain-modeling.md)。按其中的主动澄清方法与模板处理，不需要用户单独调用。

术语与现有 glossary 冲突时指出，避免给同一概念不断换名字。用具体边界场景验证关系和含义。
术语确认后按项目原有位置更新 glossary；它只解释领域概念，不充当 spec 或实现日志。
没有 glossary 时，仅在确有已确认术语要记录时创建 CONTEXT.md；有 CONTEXT-MAP.md 时更新所属上下文。

只有决策同时具备“难以逆转、缺少背景会令人意外、确实比较过替代方案”，才提出 ADR。
经用户同意后按项目现有格式和编号写入；没有格式时用简短段落记录背景、决策和原因，只在确有价值时展开替代方案与后果。
不创建空文档，不为了流程完整而批量补 ADR，不覆盖已有未相关内容。

## 收束

用一小段总结已确认的外部行为、兼容约束、测试边界和仍未决的问题。
用户确认共同理解后结束。下一步可由用户调用 to-spec 固化并按需拆票；不要自动开始实现。
