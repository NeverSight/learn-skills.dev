Trouvez ce qu’un changement pourrait casser en dehors de son propre diff, puis prouvez le seul fait qui le rend sûr en exécutant du vrai code au lieu d’écrire un essai. Utilisez cela avant toute modification multi‑fichiers ou toute modification d’un chemin partagé (payload d’API, configuration, données stockées, un client que d’autres applications lisent, un prompt ou un fichier de politique), lorsqu’on vous demande « quoi cela pourrait casser » ou « rayon d’explosion de X », pour un petit diff en lequel vous n’avez pas confiance, ou lorsqu’une tâche affirme quelque chose sur le code existant (« X gère déjà Y », « il suffit de rendre X public ») avant de concevoir une solution qui contredit cette affirmation.
