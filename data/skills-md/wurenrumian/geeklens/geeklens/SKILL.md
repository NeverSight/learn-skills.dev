# geekLens（聚焦代码阅读版）

给一段**聚焦的真实源码**做一份**能直接顺读的注解版**：把打断顺读的噪声清掉、只留核心逻辑，把"这段在做什么、为什么这样写、和谁同步"讲清楚。

它**不是**源码，也**不是**项目文档：

- 真实源码保持原样——阅读版是**副本**，会随时间与源码漂移，所以记清来源与快照日期即可，不必追漂移。
- 阅读版面向"想读透这段实现"的人；项目 `docs/` 面向"想用这个结论"的人。
- 与 **project-memory** skill 配合使用：阅读版放 `./tmp/annotated/<focus-slug>/`，过程写进 `journal/`，入口写进 `STATE.md`。本 skill 只描述"怎么做出好的阅读版"，存放与生命周期交给 project-memory。
- **降级路径**：若目标项目没有 project-memory，则放 `./annotated/<focus-slug>/`，并在该目录内自建 `CHANGELOG.md` 记账。

## 何时用

- 用户说：给这段代码**加注解 / 出阅读版 / 逐行讲解 / 精读**某条路径 / **改前改后对照** / 整理这套**数据结构** / 讲清这个函数。
- 有一个明确的**焦点**：一个功能、一次改动、一条数据流或调用链。不是"把整个仓库注解一遍"。

## 核心原则

1. **源码只读。** 任何"让它变干净"的动作只发生在阅读副本上。删/改真实源码要单独、显式地征求同意。
2. **一个焦点一个目录。** 用焦点而不是文件来组织；同一焦点下的多个文件互相链接。
3. **阅读版是"顺读版"，不是 diff。** 读者应能从第一行读到注释结尾而不被 diff 噪声打断。
4. **只留核心逻辑，清掉打断顺读的东西。** 判据看两头：**是否参与核心逻辑**（参与的一律留）与**是否严重打断顺读**（打断的清掉）。只服务观测/调试的输出（调试打印、日志、埋点/计时/profile 分支、诊断 mock、只写不读的诊断字段）、注释掉的死代码、与本焦点无关的分支——阅读版里删掉。**删的位置留占位**（见下"砍什么"），源码原封不动。
5. **记来源与日期。** 每个阅读版顶部写清原文件路径 + commit 与快照日期，够用即可。摘来的代码是副本，不是真源。
6. **先骨架后逐段。** 先给出目录与文件表，再逐个文件注解；不要一次性铺开所有文件再补注释。
7. **语言跟随用户。** 用户用中文提问/评审时，注解就用中文，术语保留原文英文。
8. **解释与摘录分层。** 代码注释回答“这一行做什么、为什么需要、和谁同步”；路径文档再建立整体心智模型。不要把猜测写成源码事实；证据标签全篇统一用三档：**源码事实**（源码里直接可见）／**推断**（由调用/数据流推出）／**待验证**（需运行时或文档核实）。

## 与 calm-explain 的联动（必须启用，职责分明）

geekLens 被触发时，**必须**把 calm-explain 作为本次阅读版的讲解协议，不需要用户再次指定；calm-explain 可以单独使用。两类职责各归其主，不互相复述：

- **解释风格类 → calm-explain（唯一来源）**：讲解语气、术语处理（随用随定义；框架型讲解术语先行）、回答骨架与追问骨架、证据标签（**源码事实 / 推断 / 待验证**）、相近概念区分——一律以 calm-explain 为准，本文件只引用、不另立、不复述细节，避免双源漂移。
- **产物形态类 → 本 skill（唯一来源）**：阅读版文件的结构与注解约定、before/after 对照、数据结构手册、路径文档、占位符、源码只读、目录布局与生命周期——以本文件为准。
- 协作执行：每个重要结论尽量附源码证据（文件、函数、字段或调用点），标签用统一三档；追问时按 calm-explain 的追问骨架，只回答当前卡点并回链到对应阅读版段落，不要每次重讲整条路径。

## 工作流

1. **界定焦点，定位源码。** 明确这次要讲的是哪条路径/哪个函数/哪次改动，以及它的边界（入口在哪、出口在哪、依赖谁）。拿不准就先问，或先读一圈再与用户对齐范围。
2. **读源码，建两张清单。**
   - **改动清单**（若有改前/改后）：哪些文件、哪些函数真的变了；哪些是逐字节相同、不要误标。
   - **结构清单**：涉及哪些类型/字段/缓冲区/共享状态，谁拥有、谁写、谁读。
3. **建目录骨架 + 顶层 README**（见下"目录布局"）。先把"读什么、按什么顺序读"写出来，再填内容。
4. **逐个产出 `.annotated.<ext>` 阅读版。**
5. **抽数据手册** `data-structures.md`：把跨文件的类型/字段/同步语义集中讲一次，阅读版里只引用它。
6. **写路径文档**：把各文件按数据流/调用顺序串起来，形成端到端讲法。
7. **交叉链接 & 校验**（见下"校验"）。
8. **记 project-memory**：阅读版落 `./tmp/annotated/`，当天 `journal/` 追加一行；稳定结论挂进 `STATE.md` / `docs/`。无 project-memory 时走降级路径。
9. **迭代答疑**：用户会就阅读版追问概念，按下面"答疑模式"处理。

### 最小可交付与分层交付

先保证一个可读、可验证的最小结果，再按需要扩展，避免一次生成大量低价值注释：焦点声明与阅读顺序、核心阅读版文件、覆盖写者/读者/生命周期的数据表，以及一条标明证据和未验证假设的端到端路径。只有用户需要时才补齐改前/改后全量对照、布局实测或 project-memory 记录。

## 目录布局（建议）

放在 `./tmp/annotated/<focus-slug>/`（由 project-memory 管理该目录）：

```
./tmp/annotated/<focus-slug>/
├── README.md                  # 入口：焦点一句话、来源、文件表、阅读顺序
├── <topic-a>/
│   ├── README.md              # 本目录覆盖哪条路径、与其它目录的关系
│   ├── before/
│   │   └── <file-a>.annotated.h
│   └── after/
│       └── <file-a>.annotated.h
├── <topic-b>/
│   └── ...
├── data-structures.md         # 跨文件的结构 / 字段 / 所有权 / 同步手册
└── <path>.md                  # 端到端数据流或调用链讲解
```

同一焦点内**保持一致的命名与注解风格**；改前/改后用子目录（`before/`、`after/`）或文件名后缀区分，二者并排放在同一 `<topic>` 下，别散落。

## 注解版怎么做

### 每个阅读版顶部固定写

```text
来源：<原文件路径>  （commit <rev> / 快照 <日期>）
角色：<本文件在焦点里负责什么>
关系：<与相邻阅读版/数据手册的关系>
改动：<无 / 相对改前改了什么>
```

### 注解约定（保持全局一致）

- **行内解释**放行尾，一句话结论：`field = x;   // ← 只有本线程写，消费者只读`。
- **成段解释**放目标上方，用 `// ▶` 起头，讲"做什么 · 为什么这样写 · 与谁同步 / 谁拥有"。
- **砍掉的位置留占位**：`// …（省略：调试打印 3 行）`——让读者知道此处有删减，避免误以为文件完整。
- 长函数用分步编号（①②③…），让读者能对照着跳。

样例（格式与语言无关，这里用一段类 C 伪码示意）：

```c
// ▶ 环形容器提交：先写满描述符字段，再用 release 语义发布 tail，
//   保证消费者看到 tail 推进时描述符已完整（防读到半写状态）。
desc->addr = buf;                    // ← 描述符字段：仅本线程写
desc->len  = n;
atomic_store_explicit(&ring->tail,
                      next, memory_order_release); // ← 发布点
// …（省略：此处原有 2 行 debug 打印）
```

### 砍什么（仅阅读版）

总原则：**顺读优先，核心逻辑不丢**——严重打断阅读的清掉；参与核心逻辑的即便冗长也保留。

- 调试打印、日志、断言式诊断输出。
- 埋点/计时/profile 分支（预处理器开关、`if (profile)` 之类）——若其读写会污染结构，连诊断字段一起从阅读版移除。
- 只写不读的**诊断字段**（区分"语义字段"与"仅为观测存在、从不被业务读取"的字段再决定）。
- 注释掉的死代码、被条件编译关掉的旧实现（如 `#if 0`）。
- 与本焦点无关的分支（但要留一句"此处还有 X 路径，与本次焦点无关"）。

**保留**：若焦点涉及锁与内存序、原子操作、边界/环形回绕、并发握手、错误与回滚路径，它们通常就是焦点本身，别删。

### 怎么注

- 一段/一步讲三件事：**做什么 · 为什么这样写 · 与谁同步 / 谁拥有**。
- 同步/并发点显式标注：谁发布、谁消费、用什么同步原语，防的是什么（如 ABA、复用串台、丢唤醒；C/C++ 类系统代码写清 `acquire`/`release`）。
- 涉及数据放置时点明：字段归哪个结构、由谁持有、是否跨线程/进程/设备共享（C/C++ 系统代码再点明 host/device 与缓存行）。
- 对"看起来奇怪但正确"的写法专门解释一句，否则读者会以为是 bug。

## 改前/改后对照

- 只讲**真正变了**的东西，以及为什么变、代价是什么（额外内存、额外同步、额外分支）。
- **逐字节相同的部分要明确写出来**（例如"该核心函数在改前/改后完全一致，改动只在调用点"），避免读者误以为处处不同。
- 若做了重构/重命名，给一张"旧名 → 新名"小表。
- 有实测可得的结构体大小/布局差异时，写一个最小 mock 验证，**别凭感觉猜**。

## 数据结构手册 `data-structures.md`

按结构组织，每个结构包含：

- **定义**：贴关键字段（标来源），不贴整段无关代码。
- **字段语义**：每个字段"是什么、谁写、谁读、何时推进"。
- **所有权与生命周期**：谁创建、谁销毁、init/reset 在哪、失败如何回滚。
- **同步**：用什么原语、谁发布谁消费；防的是哪种竞争。
- **放置**：在哪个结构内、由谁持有、是否跨线程/进程/设备共享、是否随结构体整体拷贝（C/C++ 系统代码再点明 host/device 与缓存行）。
- **诊断字段**：显式标出"只写不读、仅供观测"的字段。

再加一张**角色对照表**，把改前/改后，或把并行的两条路径（如生产者侧 / 消费者侧、SQ 侧 / CQ 侧）逐行对应起来。

> 能实测就实测：结构体大小/布局用一个独立 mock 编译跑一下（如 C 的 `sizeof`/`offsetof`），比文字估算可靠。

## README 与路径文档

- **顶层 README**：焦点一句话、来源与快照、**阅读顺序**、文件表。
- **每个子目录 README**：本目录覆盖的路径、与其它目录/手册的关系。
- **端到端路径文档** `<path>.md`：从入口到出口，把各阅读版按顺序串起来，指出每一步的关键握手。
- 交叉链接一律用**相对路径**，保证在编辑器/渲染器里可点；改前/改后互链，阅读版链回数据手册。

文件表示例：

```markdown
| 文件 | 角色 | 对应源码 |
|---|---|---|
| `BaM.cq-reclaim.annotated.h` | CQ 改前完成/复用路径 | `src/.../page_cache.h`（commit abc123） |
```

## 校验

产出后逐项过一遍（能脚本化就脚本化，别只靠肉眼）：

- **结构平衡**：对源文件类阅读版，数一遍 `{}`（或括号/缩进）平衡，确认删改没破坏结构。
- **无 stale 引用**：没有指向已删小节/已改编号的"见 §x"；全目录 grep 一次旧措辞。
- **来源齐全**：每个阅读版顶部都有准确的原路径 + 快照日期。日期只作时点标记，不必回头校验源码是否已变。
- **源码未动**：`git status` 确认真实源码目录干净（阅读版在 `./tmp/`，不入库）。
- **改前/改后对齐**：两边同名函数、同注解风格；不同的只是该不同的。
- **源码事实/推断分开**：抽查每个关键结论都能回到源码证据，或明确标为推断/待验证。
- **链接可达**：README 中声明的文件、锚点和相对链接确实存在。

## 与 project-memory 的集成

- 阅读版固定放 `./tmp/annotated/<focus-slug>/`；本项目 `./tmp/` 已 gitignore、且顶层不可随意删。
- 没有 project-memory 时，退化为 `./annotated/<focus-slug>/` + 目录内 `CHANGELOG.md`，规则不变。
- 每完成一轮（一个文件、一次评审结论、一处修正）往当天 `./tmp/journal/YYYY-MM-DD.md` 追加一行。
- 焦点还在演进时，把"现在/下一步/待决"更新进 `./tmp/STATE.md`；稳定且会被反复引用的结论才升级到 `./tmp/docs/` 或项目 `docs/`（毕业要**先问用户**）。
- 详细目录/门槛/格式以 **project-memory** skill 为准，本 skill 不重复其规则。

## 答疑模式

用户常会就阅读版追问"这个字段干嘛的 / 这里为什么这样同步 / 和原来什么关系"：

- **用源码事实回答，不臆测**：先 `grep`/`read` 定位真实定义与使用点，再讲。
- 答完后判断是否值得**回填**进 `data-structures.md` / 路径文档；回填只改阅读版，**不动源码**。
- 主动给出可选的下一步深化（补某函数骨架、补某条路径、实测某结构大小、把某结论标准化），让用户挑。
- 结论如果涉及"源码里能验证的数值/事实"，尽量验一遍再写进文档。
- 回答结构以 calm-explain 的追问骨架为准（本文件不另立模板）；本 skill 只补“每个结论必须能回到源码证据”。简单追问不要机械套完整结构。

## 反模式（别这么干）

- 为了"变干净"去改真实源码。
- 把阅读版做成纯 diff/纯 patch，读者没法顺读。
- 留下无法追溯来源的代码摘录。
- 静默删除代码、不留占位——读者会以为阅读版是完整的。
- 一次铺开所有文件再逐个补注释；应先骨架后逐段。
- 把诊断字段顺手删进源码，或把诊断字段当核心语义字段讲解。
- 凭感觉报结构体大小/内存布局；能编译就编译验证。
- 在阅读版里塞进与焦点无关的全量函数；只留焦点及其必要上下文。

## 快速自检（交付前念一遍）

1. 焦点一句话说得清吗？边界在哪？
2. 每个阅读版都有来源（路径 + 日期）、角色、关系、改动说明吗？
3. 碍读的东西只清在阅读版、源码没动、且删减处有占位吗？
4. 改前/改后的差异讲清了吗？没差异的地方有没有明说"相同"？
5. 数据结构手册覆盖了所有权、同步、放置吗？诊断字段标了吗？
6. README/路径文档能让人按顺序读下去吗？链接可点吗？
7. 结构平衡、无 stale 引用、`git status` 干净吗？
8. journal / STATE 记了吗？
