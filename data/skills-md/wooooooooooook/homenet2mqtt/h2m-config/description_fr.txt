Méthodologie pour ajouter des entités d’appareils (climatiseur/lumière/capteur/ventilateur/interrupteur, etc.) ainsi que les automatisations/scripts nécessaires à une configuration Homenet2MQTT (h2m). La base principale est la configuration d’exemple déjà appliquée et le préréglage de la galerie du fournisseur (discovery.match, paramètre count, $repeat) ; seuls les appareils qui ne peuvent pas être expliqués par ces deux éléments sont traités en secours en utilisant l’ingénierie inverse de paquets RS485 bruts. Les automatisations/scripts issus des extraits de la galerie (interrogation périodique, réponses du proxy de bus, séquences de sonnerie de porte/ascenseur, génération composite de paquet TX) font partie du fonctionnement de l’entité, donc vous ne vous contentez pas de déplacer l’entité et d’arrêter là. Comme le bus HomeNet génère souvent du trafic uniquement lorsqu’il est actionné, le processus comprend une étape qui demande spécifiquement à l’utilisateur d’actionner un pad mural, un interrupteur ou une télécommande, et le nom du fournisseur/modèle fourni par l’utilisateur sert d’indice pour la priorité de recherche, mais l’exemple n’est pas finalisé uniquement sur la base du nom. Il est utilisé pour des requêtes telles que « nettoyer les paquets non appariés », « ajouter une entité qui correspond à ce paquet », « créer une entité uniquement à partir du paquet », « augmenter les chauffages/luminosité en utilisant le préréglage de la galerie », « brancher un appareil qui n’est pas dans la configuration », « le paquet n’est pas capturé, que dois‑je actionner ? », « ajouter une interrogation périodique pour que l’état se mette à jour », « attacher une séquence automatique d’ouverture de sonnette de porte/appel d’ascenseur », « envoyer le paquet directement pour vérifier que la lumière s’allume réellement », etc. Pour les utilisateurs qui ne connaissent pas l’adresse h2m ou la manière d’activer l’API Agent et d’obtenir un jeton, fournissez des instructions dès l’étape de connexion (references/connection-setup.md). h2m expose la même logique métier via REST (`/api/v1/agent`) et MCP (`/api/v1/agent/mcp`), donc si le client dispose d’un outil MCP, utilisez MCP ; si seul un shell est disponible, utilisez des scripts, et les différences spécifiques à chaque interface sont décrites dans references/interfaces.md. Lorsque vous avez l’autorisation d’envoyer des paquets, suivez cette séquence : aperçu uniquement pour vérifier que la commande générée déplace réellement l’appareil → approbation de l’utilisateur spécifiant la cible, l’hexadécimal, l’ordre et l’intervalle → envoi de la transmission unique ou séquentielle approuvée → confirmation du fonctionnement réel de l’appareil.
