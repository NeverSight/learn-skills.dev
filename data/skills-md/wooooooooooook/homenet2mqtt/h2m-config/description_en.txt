Methodology for adding device entities (climate/light/sensor/fan/switch, etc.) and the necessary automations/scripts to a Homenet2MQTT (h2m) configuration. The primary basis is the already‑applied example configuration and vendor‑gallery presets (discovery.match, count parameter, $repeat); only devices that cannot be explained by those two are handled by falling back to reverse‑engineering raw RS485 packets. The automation/scripts in the gallery snippets (periodic polling, bus surrogate responses, doorbell/elevator sequences, composite TX packet generation) are part of the entity’s behavior, so you don’t merely move the entity and stop. Because the HomeNet bus often generates traffic only when it is being operated, the process includes a step that explicitly asks the user to manipulate a wall pad, switch, or remote control, and the vendor/model name supplied by the user is used as a hint for search priority, but the example is not fixed solely by the name. It is used for requests such as “clean up unmatched packets,” “add an entity that matches this packet,” “create an entity just from the packet,” “increase heaters/lights using the gallery preset,” “attach a device that isn’t in the configuration,” “the packet isn’t being captured—what should I operate?,” “add periodic polling so the state updates,” “add an automatic door‑bell opening/elevator call sequence,” “send the packet directly to verify the light actually turns on,” etc. For users who do not know the h2m address or how to enable the Agent API and obtain a token, guide them from the connection step (references/connection-setup.md). h2m exposes the same domain logic via REST (`/api/v1/agent`) and MCP (`/api/v1/agent/mcp`), so if the client has an MCP tool you use MCP; if only a shell is available you work with scripts, and surface‑specific differences follow references/interfaces.md. When you have permission to send packets, you follow the sequence: preview only to verify that the generated command actually moves the device → user approval that clarifies target, hex, order, interval → approved single/sequence transmission → confirm real‑device operation.
