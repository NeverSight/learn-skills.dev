# Build a feature — the spec-kit cycle from a finished spec, with no human gate

**Two skills run this skill's script.** `plan-feature` runs preflight to analyze and ends by handing every question the spec leaves to the domain expert in `QUESTIONS.md`; this skill runs implement, converge and finish on a feature that `plan-feature` left with no open question, and closes out an already-implemented feature the same way, since implement skips every phase already done. The process is three loops over stock spec-kit commands: the domain expert's `/speckit-specify` and `/speckit-clarify` on the base branch; `plan-feature` and the domain expert's `/speckit-clarify` over its questions, repeated until no question is open; then this skill. This file is the reference for the whole script, both halves.

The code is written by LLM agents and no human reads it line by line, so the human gates spec-kit puts between its commands are replaced: one deterministic script, one fresh subagent per stage, a refutation review where each gate was, and a converge loop that ends at a severity floor, which by default tolerates no finding. **The specification is not automated.** A domain expert writes `spec.md` with stock `/speckit-specify` and `/speckit-clarify`; the script starts at `plan` and never writes that file.

## Run the workflow; orchestrate nothing yourself

**Call the Workflow tool with this skill's script from `implement`, from the base branch or the build branch, once `plan-feature` has ended with `status: "done"` or every question in `QUESTIONS.md` is left open, and run no spec-kit command from your own context.**

```
Workflow({
  scriptPath: "${CLAUDE_SKILL_DIR}/workflow.mjs",
  args: { from: "implement", featureDir: "specs/004-product-gl-config",
          wall: "node backend/scripts/wall.mjs" }
})
```

`wall` is the definition-of-done command the project's root `CLAUDE.md` names; a start after preflight must pass it. **A start at implement or later refuses while `<featureDir>/QUESTIONS.md` holds an open question, or cannot be read**: a `CRITICAL` or `HIGH` question the spec has not answered, or a `MEDIUM` or `LOW` one no person has left open. A file whose every question reads `yes — <who>` in its `Left open` column does not stop it. The refusal names `plan-feature` with `from: "review-plan"` as the next step once the domain expert has answered. The script with no `from` and no `until` runs every stage in one call and stops after analyze whenever a question is open; neither skill starts it that way.

Do not run `/speckit-plan` or any other spec-kit command yourself and judge the result: the context that wrote an artifact must not be the one that approves it. Do not use `specify workflow run speckit` either: its gates need a terminal, its effort cannot be set per step, and its command steps capture no output, so it cannot loop on what converge reports.

**Service projects work trunk-based on the base branch: everyone commits to `dev`, and the long-lived feature branch does not exist.** Preflight discovers what the run is for and puts the repository where the stage belongs; nothing is required on a first planning run.

- **Planning runs on the base branch.** A start at `preflight` through `analyze` refuses a dirty tree, checks the base out when it started elsewhere, and brings it up to date from origin by fast-forward only (`git fetch --prune origin && git merge --ff-only origin/<base>`); a failure, or a local base holding commits origin lacks, is a stop. It refuses while the feature's build branch, local or on origin, holds commits the base lacks: the spec is fixed once that branch exists, and the build's ticked tasks are there. A build branch with nothing the base lacks is no build yet. Planning commits only in the feature directory, plus what the plan step writes outside it: the managed section of the agent context file, which spec-kit's opt-in agent-context extension refreshes in its `after_plan` hook, an admitted constitution amendment, and a `docs/GATES.md` entry the plan records. Nothing is pulled between stages; before each push, `git pull --rebase origin <base>` moves only the run's own commits, a push origin refuses because it moved is tried again up to 3 times, and a conflict is `git rebase --abort` and a stop. A run that ends planning pushes its commits.
- **The plan review records the spec it read**: the blob id of `spec.md` at the base's HEAD, one line in `<featureDir>/spec-reviewed.sha`, committed with the plan. Every later start from `tasks` on, the build-branch step and the end-of-planning push compare the base's `spec.md` blob with it; a mismatch or a missing record before the build branch exists is a stop whose restart is `from: "review-plan"`.
- **The build gets a branch that lives only for the build: `build/<NNN>-<name>`**, or `args.branch`. It is looked up by that name only, never by the bare `<NNN>-<name>` spec-kit's `git` extension gives the branch it makes for `/speckit-specify`. A start at `implement` or later brings the base up to date the same way and reads everything it checks from the base's commit, checking nothing out. **Only once every preflight check has passed** does it resume the build branch — local, or on origin, fast-forwarded to origin's where that is ahead — or make it from the base and push it to origin at once, so a preflight stop leaves no branch behind. It merges the base in: `--ff-only` when behind or holding nothing the base lacks, an ordinary merge when diverged, never a rebase because the branch may be pushed; a conflict aborts the merge and stops with the paths. The return carries `createdBranch`.
- **A feature's spec is fixed once its build branch exists.** A later change to what the feature does is specified as a new feature whose spec states the change it makes to this one. Where the base's `spec.md` differs from the build branch's, nothing is merged or landed and the run stops; the stop tells the technical expert to revert the commit that changed it on the base with `git revert` and push — never a history rewrite — and the domain expert to specify the change as a new feature, after which the build restarts where it stopped.
- **Finish lands the build only with every task ticked, the wall green and the tree clean**: the base brought up to date and merged in when it moved, under the same spec rule; the wall again when that brought anything; then `git push origin HEAD:<base>`, which origin takes only as a fast-forward — refused, it goes back to the sync, up to 3 landings in all — the local base fast-forwarded, the local build branch deleted, and the one on origin deleted only when it is an ancestor of the landed head. A landing that does not happen is a stop at finish, with the branch checked out and pushed.
- **Feature directory:** `args.featureDir`, else the checked-out branch name (`build/<NNN>-<name>` → `specs/<NNN>-<name>`), else — a planning start — the one directory under `specs/` with a written `spec.md` and no `plan.md`, or — a build start — the one directory whose `tasks.md` on the base holds an open task; `.specify/feature.json` last, never overriding, because it is machine-local and names whichever feature this checkout last specified. Two candidates or none is a `needs-human` exit listing them, never a pick; the base holds several planned features, so every restart passes `featureDir`, and so does a close-out of a feature whose tasks are all ticked.
- **`.specify/feature.json`** is pointed at the resolved feature, the one file preflight writes: spec-kit's scripts resolve the feature from `SPECIFY_FEATURE_DIRECTORY`, then from that file, never from the branch name.
- With `push: false` the run contacts no remote: nothing is fetched, pulled or pushed, and finish fast-forwards the local base only.

The script path is this skill's own directory, substituted by Claude Code when the skill loads. A workflow starts only from a script the session may read, so a user-level install under `~/.claude/skills/` needs that directory added first — `/add-dir` with the same path, or a `Read` allow rule; a project-level install under `.claude/skills/` needs nothing. From a terminal: `claude -p "/build-feature" --permission-mode bypassPermissions`; the dispatching session can be the cheapest model, and it stays open until the workflow ends (idle ceiling `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`).

**The base branch is discovered, not assumed:** `args.baseBranch`; else one line in the repository root's `CLAUDE.md` of exactly the form `` Base branch: `dev` `` (branch name in backticks, the line unindented and alone, once); else `origin/HEAD` naming a local branch; else the one local branch among `main`, `master`, `develop` and `dev`, where exactly one exists; else the run stops at preflight before anything is checked out, merged or written, and names the fix — add that line, or pass `baseBranch`.

**A service works on `dev`: a base branch of `main` or `master`, from any of those sources, stops the run at preflight** before anything is checked out, merged or written, and names the fix — make `dev`, commit `` Base branch: `dev` `` on it, make it the forge's default branch. `main` takes pull requests from `dev` only, merged by a person when `dev` is stable, so no feature is planned, built or landed against it; `mergeInto: "main"` or `"master"` throws before the first agent starts.

- The file read is the root `CLAUDE.md` as committed at `HEAD` of the branch the run starts on; a backend's `CLAUDE.md` and the working tree are not read. A branch cut before the line was committed holds none; start from the base branch, or pass `baseBranch` once.
- **A line that is found and does not name a local branch is a stop, never a fall-through:** a line not in the exact form (bulleted, numbered, indented, emphasised, unquoted, trailing prose), two lines naming different branches, or a line naming a branch that does not exist locally each end the run at preflight, naming the line.
- **An `origin/HEAD` that names no local branch is unresolved too** (`git clone -b dev` records `origin/main` and makes no local `main`); the stop names `git branch <name> origin/<name>`.
- Nothing is fetched. Where `baseBranch` is absent, one read-only agent (`base branch`) runs a `grep` over `git show HEAD:CLAUDE.md`, `git symbolic-ref --short refs/remotes/origin/HEAD` and `git for-each-ref` over the local branches and returns their output verbatim; the script parses the line and applies the precedence (`resolveBase()`). The return carries `baseBranch` and `baseBranchSource` — `arg`, `claude-md`, `origin-HEAD` or `fallback`.

**A later start checks the artifacts it reads on the branch the run would work on, before any branch is made.** `plan.md` from `review-plan` or `tasks`; `plan.md` and `tasks.md` from `analyze`, `implement` or `converge`; `tasks.md` from `finish`. A planning start reads them on the up-to-date base, a build start on the base's commit (`git cat-file -s <base>:<path>`) before any branch is made, and the build-branch step again after the sync. A missing or empty one stops the run with nothing committed, naming the files and the `from` that writes them.

Optional `args`, all with a default: `featureDir`, `branch` (the build branch's name), `baseBranch`, `wall` (read from the project's `CLAUDE.md` on a full run), `planGuidance` and `tasksGuidance` (passed to `/speckit-plan` and `/speckit-tasks`), `push` (default true), `mergeInto` (accepted for compatibility; anything but the base branch throws), `maxReviewRounds` 3, `maxAnalyzeRounds` 3 (ordinary fix rounds before the cap fix and the final review, below), `maxConvergeRounds` 6, `maxWallAttempts` 3, `severityFloor` (default `NONE`), `tiers`. To restart, pass `from` (`preflight`, `plan`, `review-plan`, `tasks`, `analyze`, `implement`, `converge`, `finish`) and `wall`; `until` bounds a run the same way, and an unknown stage name throws before the first agent starts. `from: "review-plan"` reviews the plan already on the base branch against the spec as it stands, without regenerating it; `from: "plan"` regenerates the plan and discards every review fix. Discovery, bringing the base up to date, the build branch's sync and `.specify/feature.json` run on every entry, restarts included. A run with no `from` and no `until` plans on the base branch, pushes, and then makes the build branch before `implement`. An interrupted run resumes with `resumeFromRunId`, which replays every finished agent from its journal.

## The spec is fixed input, and no stage of this run edits it

**`<featureDir>/spec.md` is the fixed input: every stage reads it, no stage — no review fix, remediation, implement pass, repair or forced convergence task — writes it, and a finding a planning stage can close only by a change to the spec is a question for the domain expert, with a recommended answer. Nobody but the domain expert writes the spec: not the run, and not the session that launched it.** An artifact the run may rewrite cannot refute the run, so do not *align the spec* with what the run decided or built.

- The plan-review fixer, the tasks stage and the analyze remediator return such a finding in `specChanges` as a question — plain words, no technical terms — with the answer they recommend, then work on that answer and record in `research.md` that the reading waits on the domain expert. The script collects the questions across the three stages and hands the list to every later reader and fixer so none is asked twice.
- **Each question carries a severity: what a different answer would undo.** `CRITICAL` or `HIGH` where it would change what the feature does — a requirement's behaviour, the data model, a contract, a state or transition, an error case, a security, money or compliance rule; `MEDIUM` or `LOW` where it changes a local detail — a message, a label, a default, a documented value — that one later task can change. Each also carries what a different answer would change, in one sentence. After analyze, a run holding an open question returns `needs-human` with every question at once, committing `<featureDir>/QUESTIONS.md` beside `HANDOFF.md`.
- **Only a person leaves a question open, and only a `MEDIUM` or `LOW` one.** The technical expert, or the domain expert through them, says the build may start on the recommended answers; the session records it as `yes — <who>` in the question's `Left open` cell, commits that file alone and pushes. The domain expert can still answer it later or never. The session never leaves one open on its own judgment. A `CRITICAL` or `HIGH` question reads `cannot be left open`.
- **`QUESTIONS.md` and the top of `HANDOFF.md` show the questions as one table** — question, recommended answer, what a different answer would change, severity, left open — then the numbers the build waits for. A later planning run carries the questions left open into the file it rewrites, and its restart review drops one the spec now answers.
- `QUESTIONS.md` is on the base branch beside the spec, and carries one line for the domain expert to paste into Claude Code opened in the project: stock `/speckit-clarify`, told the feature directory, to update the base branch from origin first, to write the answers as a new feature with `/speckit-specify` instead when origin has the build branch or every task is ticked, otherwise to ask the file's questions first, and at the end of every session, whatever is left, to commit `spec.md` on the base branch and push — on a refused push `git pull --rebase` and push again, on a conflict stop and say so in plain words — so the domain expert runs no git. Clarify takes the file as its prioritisation context, asks up to five questions per run, each with a recommended answer, and writes the answers into the spec.
- **A finding whose remedy changes behaviour an earlier feature's spec specifies is still a question for this feature's spec**, phrased as a change this feature makes to that feature and naming it. The earlier feature's spec is left as the record of what was built.
- **The build asks the domain expert nothing.** Every question that could change the spec is asked during planning. Converge and the forced append follow the reading the plan recorded, one waiting on the domain expert's answer included; where neither the spec nor the plan decides a reading, they decide it from the spec, the constitution and the code and have the task record it in `research.md`.
- The domain expert works on the base branch and keeps working there while the run goes on. A planning run reads the spec as preflight pulled it; a later planning start that pulls a changed spec, or a planning run whose final pull brings one, is a `needs-human` exit whose restart is `from: "review-plan"`. A build whose base spec changed stops, as above, and merges nothing.
- Every agent is told to ignore a `CLAUDE.md` or other project file that tells it to fetch, pull, check out, rebase or push, and to run only the git steps its prompt names.
- Preflight refuses on a `[NEEDS CLARIFICATION]` marker still in the spec and lists them: those are the domain expert's to answer with `/speckit-clarify`.
- An implement agent that can see no fix but a spec edit leaves the task unticked and quotes the requirement. The wall-repair prompts name editing the spec among the moves that may never buy a green wall.
- Traceability: an FR or SC is cited `<NNN>/FR-nnn` outside the feature directory; a row in `specs/trace-waivers.tsv` is authored at the tasks stage and nowhere else.

**After the domain expert has answered into the spec, `plan-feature` restarts at `from: "review-plan"`, whatever stage stopped, and never at `plan` unless a person asks for a new plan.** That start's first review is told the spec may have changed since the plan was written; a plan artifact that disagrees with the current text is a blocking finding, and the fixer brings it into agreement in place; a reading `research.md` records as waiting on the domain expert that the spec still does not answer goes back to them as a question, unless a person left it open; tasks, analyze and every later stage run again. Every exit whose whole remedy is a spec change — the questions stop after analyze, preflight's exits for a spec that moved under a later start, and preflight's refusal while `QUESTIONS.md` holds an open question — returns `restartFrom: "review-plan"`, and its handoff names the same stage. Preflight's missing-input exit restarts at `plan` only where `plan.md` itself is missing.

**When that restart reaches the tasks stage over work already done, `tasks.md` is updated in place and never regenerated.** Preflight lists the file's tasks, ticked and open, whenever the tasks stage will run; where any is ticked, `/speckit-tasks`' generation does not run.

- A ticked task whose requirement, criterion or plan decision is unchanged stays ticked, convergence and forced convergence phases included.
- A ticked task whose requirement changed is unticked with its reason: `- [ ] T014 … (reopened: <what changed>)`.
- A task no longer needed, ticked or not, is marked removed and never deleted: `- ~~T015~~ (removed: <reason>)`. Its id counts toward the maximum and is never reused; every stage that reads `tasks.md` is told such a line is not a task. **The removed line is one line and names no `FR` or `SC` id**, because the traceability gate reads every id anywhere in `tasks.md`. An id the edited spec no longer defines leaves every line of `tasks.md`, and a new task takes it out of the code, tests and waiver rows that still cite it.
- New work gets new unticked tasks with ids after the maximum, in the phase it belongs to; the update ticks nothing.
- **A parse-only reader certifies the update:** every task preflight saw ticked must come back ticked, reopened with a reason, or removed with a reason; every one it saw open must come back open or removed with a reason. A ticked one unticked without a reason, any one gone, or an open one ticked stops the run at tasks. A first run, with no ticked task, generates `tasks.md` as usual.

## Each stage runs on the tier it earns

**Take the model and effort of every stage from the `TIERS` table in `workflow.mjs`; every row is Opus at low, medium or high effort. Change a row for one run with `args.tiers`, never by editing the table.** The model is the alias `opus`, not a pinned id, because `agent()`'s `model` takes aliases. A row on any other model, or on `xhigh` or `max`, fails the run before its first agent starts.

| Stage | Tier | Why this tier |
|---|---|---|
| preflight, phases, finish | Opus low | shell commands and parsing; the return value is a list of facts, and the one judgment preflight meets (several candidate directories) is one it refuses |
| handoff | Opus low | writes files whose whole text the script hands it, commits, pushes |
| plan | Opus high | the one decision-heavy pass; every later stage inherits its errors |
| review-plan | Opus high | the refutation that stands in for the human, at the same effort as the pass it refutes |
| fix-plan, remediate (critical) | Opus medium | edits that may reach the constitution, and the two rows that decide a finding needs a spec change |
| tasks, analyze, remediate | Opus medium | decomposition and cross-checking of artifacts a high-effort review already passed |
| implement, one agent per phase | Opus medium | a bounded context per phase; the wall is the check |
| converge | Opus medium | reads the whole implementation and grades every gap on `/speckit-converge`'s Step 5 scale; raise it with `args.tiers` when converge misses a gap a person can see |
| reconcile-tasks | Opus medium | brings `tasks.md` to a known state after a failed forced append; must return `unsure` rather than guess, and its verdict is certified by the `phases` row |
| check-deferrals | Opus low | a text search of `spec.md` for each deferral quotation |
| force-append | Opus medium | writes one task per finding from findings, not from a finished document, so a paraphrase becomes a task that closes on something else |

Low goes to stages whose output is facts or a document the script rendered; medium to stages that write an artifact or code, each reviewed by a higher-effort pass or checked by the wall; high to plan and its refutation only, the two stages the rest of the run derives from.

## A gate is a fresh-context refutation, not a human

**Where spec-kit pauses for approval, a review agent with no memory of the writing refutes the artifact and returns findings as data; a fix agent applies them; the review runs again. The loop stops the run only on a survivor — a blocking or major finding that restates one an earlier fix round was handed. At its round cap it applies the last review's findings, runs one final review over that fix, and goes on with the final review's findings reported open.**

- Review-plan reads `spec.md`, every plan artifact, the constitution, the project rules and the code the plan touches, and reports every requirement no design element realises, every gate or article the design violates, and every contract that contradicts the schema. A requirement no plan can realise is reported as a change to the spec, which the fixer returns under `specChanges`.
- A constitution amendment is proposed or applied only when it passes the constitution's admission test — the rule binds two or more features, or a table the feature does not own; otherwise the finding is against the plan.
- **The script decides a survivor from a label.** From round two the reviewer gets the numbered list of every finding an earlier fix round was handed and returns `repeatOf` per finding. A finding restates an entry when the same requirement, invariant, property or contradiction at the same place is still unmet, however worded — including where the fix swapped the mechanism for one that fails the same way, or declared, narrowed or accepted the gap instead of closing it; a defect the fix introduced elsewhere is new. Exact identity (artifact, location, problem, normalised) counts too; a `repeatOf` naming no entry is ignored. The exit names each survivor with the round that handed it, and carries as `skippedByThatFix` what that round's fix agent declined and why.
- **After the cap fix nothing is applied without a review.** The final review, `review-plan <max + 2> (final)`, stops only on a survivor; its other findings are returned as `reviewPlan.ended: "round-cap"`. Its open blocking and major findings are handed to the first analysis, which returns each that still holds as its own finding, a blocking one graded no lower than `HIGH`, so a remediation applies it and the next analysis reads the fix.
- A loop runs at most `max + 1` fix rounds and `max + 2` reviews, plus a minors pass where a review approves with only minor findings (applied once, not re-reviewed).
- The analyze loop has the same rule on `CRITICAL` and `HIGH`, with `maxAnalyzeRounds` and `analysis.ended`. A `MEDIUM` or `LOW` that restates an entry is not a survivor in either loop.

## Analyze goes back to the artifact it names; converge goes back to implement

**A finding is resolved by editing, in place, the artifact it names — never by re-running the command that generated it (which regenerates the file and discards every review fix), and never by editing the spec.** The analyze remediator adds tasks with new ids for a coverage gap, changes the plan for a violation, touches the constitution only when the finding says the constitution is wrong, and returns under `specChanges` what only `spec.md` can close; then analyze runs again. `/speckit-converge` appends one phase of tasks and returns every gap it found, graded `CRITICAL`, `HIGH`, `MEDIUM` or `LOW` by its Step 5 rule; the next implement agent runs that phase alone; converge runs again.

**The severity floor is the converge loop's only stop test.** The loop ends on the first round whose findings hold nothing above `args.severityFloor`, and the return says whether that round appended tasks (`severity-floor`) or nothing (`converged`). Legal values: `NONE` (default; ranks below every severity, so the loop tolerates nothing), `LOW`, `MEDIUM`, `HIGH`. `CRITICAL` is refused, because `/speckit-converge` grades a constitution MUST violation there and the floor would tolerate everything. A round that appends tasks and grades nothing counts as above the floor.

- **A round that reports converged while grading a finding above the floor is not a human question: the loop appends those findings itself and implements them.** One `force-append` agent receives the findings rendered by the script, appends one task per finding as `## Phase N: Convergence (forced round n)` in `/speckit-converge`'s append format, and commits `tasks: forced convergence round n`; the phase goes through the same implement agent and wall gate as any other.
- **A forced task is closed by the fix and by nothing else.** Its text offers no route that closes it by recording why it was not done, and a finding about an absence is closed by a check that fails when the absence stops being true. A fix is blocked in exactly two cases: a numbered requirement or a constitution article forbids it, a fix that would need an edit to `spec.md` included, quoted with its id; or it needs a system outside the repository that does not exist. "The toolchain cannot express it", "a deployment decision", "the plan already names it as a gap" and "the file is append-only" are not blockers. A blocked task stays unticked and comes back in `blocked`; after the second pass every phase gets, the run exits `needs-human` with every other task fixed and the blockers in the handoff.
- **A finding is forced at most once.** Identity is severity, location and summary, normalised, or the assessment's own `repeatOf` label against the numbered list of what the run already forced. The forced set is returned as `converge.forced`. A forced round runs inside the slot of the round that found it, so `maxConvergeRounds` stays the single bound.
- **A finding that comes back above the floor after its forced round is the `needs-human` exit**, and the handoff says the loop already appended, implemented and wall-checked it.
- **`maxConvergeRounds`, not the floor, ends a long run**; raise the cap for more passes. The cap is followed by one assess-only round that appends and commits nothing; its findings are the ones the run carries — under `"round-cap"`, open, when it grades anything above the floor, otherwise `"severity-floor"`, or `"converged"` at floor `NONE`. A `round-cap` goes to finish, where the wall decides. Under `NONE` a run usually ends at the round cap or at `needs-human`; the wall plus the reported findings say the feature is done.

**A deferral written into `spec.md` wins over forcing.** A converge finding against something `spec.md` itself defers, puts out of scope or leaves to a later feature is not forced, does not count against the floor and is never a survivor: the assessment returns it with `deferredBy` quoting that text, and the run reports it under `converge.deferred`. **The quotation is checked first**: one `check-deferrals` agent searches `spec.md` for each new quotation, whitespace and Markdown emphasis aside; one it does not find is dropped, the finding is handled like any other, and it is listed under `converge.deferralsRefused`. Only `spec.md` counts: a scope boundary or deferral in `plan.md`, `tasks.md`, `research.md`, `docs/GATES.md` or `specs/trace-waivers.tsv` exempts nothing, because those were written from the spec by the run.

## Unattended means the agent decides by a written rule

**Every question a speckit skill would put to a person is answered by the rule in that stage's prompt, and the answer is written into the artifact.**

- Preflight establishes the feature and the branch rather than asking, on every entry, restarts included.
- Plan decides each open question from the spec, the constitution and the code and records it in `research.md`. **A reading the plan decided stands: the tasks, remediate, converge and force-append stages write no task whose completion waits on a person** — an owner's answer, a `/speckit-clarify` session, a sign-off. During planning a question only the domain expert can answer goes to `specChanges`; converge and force-append ask nothing.
- Implement proceeds past an unchecked checklist and lists the items. Analyze returns findings instead of offering remediation.
- **A run never hands back work it could have done itself: every escalation is something the loop attempted and failed at, or something it is not authorised to do.** A red wall gets one fresh-context repair pass before it escalates; a phase with tasks left unchecked gets one second pass over exactly those ids. Three implement agents per phase is the ceiling. A red wall at `finish` is repaired the same way, and **the re-check is a second `finish` agent: an agent that repairs a gate may not declare it green.**
- **No gate is ever weakened to make a wall pass.** The repair prompts forbid skipping, disabling, quarantining or deleting a test; a suppression, exclusion, baseline entry, waiver row or ignore comment; an edit to the feature's `spec.md`; a lowered threshold or coverage figure; a relaxed or removed gate; an edit to the wall script, the build file or any gate configuration; a force flag. Where those are the only route, the agent changes nothing and returns the wall red.
- **A failed forced append is reconciled, not escalated.** One reconcile agent reads `tasks.md` against git — an uncommitted change to it at that point is the append's own partial write — and brings it to wholly absent or wholly present; the parse-only `phases` reader certifies that state. Present: the loop implements it. Absent: one retry of the append. The reconcile writes only `tasks.md`, never ticks or unticks a task, touches only this round's forced phase, and returns `unsure` rather than guess.

**What stops the script.** Each stop goes to the launching session first; only the three classes in the resolution rule below reach a person.

- Preflight: no resolvable base branch; a base-branch line not in its one form, or naming no local branch; a base that cannot be brought up to date from origin, or a local base holding commits origin lacks; a feature that cannot be resolved; zero or several candidate directories; a planning start while the feature's build branch holds commits the base lacks; a merge conflict between the base and the build branch; a base `spec.md` that differs from the build branch's, or, before a build branch exists, from the one the plan review recorded; a repository not ready (dirty tree, detached HEAD, missing speckit skill); on every start, whatever its `from`, a base branch without `scripts/check-traceability.mjs` or `scripts/check-traceability.selftest.mjs` at the project root or without a `scripts/wall-checks.txt` line listing each, whose fix is `/init-pipeline`; no definition-of-done command; a `[NEEDS CLARIFICATION]` marker in the spec; a spec the update changed under a planning start later than `review-plan`, or one the plan review did not record; a later start whose input artifacts are missing on the branch it would work on; a start at implement or later while `QUESTIONS.md` holds an open question; a preflight that reports no problem while on the wrong branch — off the base for planning, on it for a build — or a detached HEAD.
- Then: a tasks update the certification rejects; an open question for the domain expert, after analyze; a survivor at review-plan or analyze; a conflict pushing the planning commits, a push still refused after 3 attempts, or a base spec after their final pull that is not the one the review recorded; a build branch that cannot be made or checked out, a merge conflict with the base or a differing base spec in the build-branch step; a wall still red after its repair pass, at a phase or at finish; a task two implement passes decline to tick; a converge finding that survives its forced round; a reconcile that cannot establish what is in `tasks.md`, or a reconcile and a reader that disagree; a forced append whose retry failed too; an appended phase two parse-only reads do not return; at finish, unticked tasks, a merge conflict with the base, a base spec that changed during the build, a base that cannot be updated, or a landing still refused after 3 attempts.
- Every stop carries what was attempted and how often. A converge loop at its round cap is not a stop. Preflight's exits commit nothing, and the return value is the report; preflight makes no branch.

## A needs-human exit leaves a file behind

**Every `needs-human` exit after preflight writes `HANDOFF.md` into the feature directory, commits it where the run stands — the base branch during planning, the build branch during the build — and pushes it when `push` is true, before it returns** — with `QUESTIONS.md` beside it when the run holds questions for the domain expert. A `done` return whose questions left open changed rewrites `QUESTIONS.md` alone. The file starts with the questions table when the run holds questions, then says that the run stopped and who reads it first, then carries the stage, the reason, the full findings item by item, the branch, the round counts, the stages run, the definition-of-done command, the severity floor, the date, the arguments that restart the run, and where the run journal is kept. **It names no journal path:** the script cannot see its own run id; the run id is on the Workflow tool result, and the session records it in `RESOLUTIONS.md`. The document is rendered in `workflow.mjs` and handed finished to one Opus-low agent, with one placeholder, the date, so the agent cannot paraphrase or drop a finding. The commit is by pathspec, those files only, because the tree may hold the run's failing work.

**A failed handoff never costs the run its verdict:** the full payload stays on the return value, with `handoff.written: false` and the reason in `handoff.note`. **An exit before a base branch or a feature directory is resolved, every preflight exit, an exit on a detached HEAD, a build stop before the run is on its build branch, and an exit whose planning commits could not be pushed write nothing** and say so on the return. A stop at `finish` gets the same file, on the build branch that did not land, on a return that keeps its own shape.

## A needs-human return is the session's to resolve, not to relay

**When the workflow returns `status: "needs-human"`, do not hand it to the person. Read the return value and `HANDOFF.md`, and form a recommendation for each item. Where you hold it with high confidence, act on it: apply it — never as an edit to `spec.md`, which is the domain expert's alone — commit it, append what you did and what the confidence rested on to `<featureDir>/RESOLUTIONS.md`, and restart the run with the arguments the handoff names. Then tell the person what you decided, as work done. Take an item to a person only where you do not hold a high-confidence recommendation, where the item came back after its resolution was applied once, or where the only resolution is a move this skill forbids. An item that goes to a person goes with your recommendation and what is missing from it.**

**High confidence: the recommendation you would hand the person expecting them to take it unchanged.** One answer, no hedge; an alternative or a caveat that could change the choice means it goes to the person. It rests on the repository's own text — the spec, the constitution, code, schema or configuration that existed before the feature, and the evidence the handoff quotes. **The run's own output can corroborate and never be the whole of it**: `plan.md`, `tasks.md`, the data model, contracts and migrations were written from the spec by the run that stopped. A business value — a bound, rate, limit, period, threshold or name — that nothing in the repository states or implies is not high confidence; one the spec already carries as its working value is.

**One attempt per item, no retry of a retry.** If the restarted run stops on the same item, it goes to the person with what was applied and why it did not take.

**What it does not license.** Every prohibition on the run's agents binds the session: no gate weakened, reordered or removed; no test skipped, quarantined or deleted; no suppression, exclusion, baseline entry, waiver row or ignore comment; no lowered threshold or coverage figure; no edit to the wall script, the build file or any gate configuration; no force flag; **no commit on the base branch outside the feature directory, and none to the feature's `spec.md` or plan while its build branch exists** — a planning stop is resolved on the base branch, a build stop on the build branch; and nothing that resolves somebody else's state — an uncommitted tree preflight refused on, or a conflict between the base and the feature's work.

**A change to the spec is the domain expert's, never the session's.** The session answers every technical question that leaves the spec as it is. When the return carries `questions`, show the person the questions table first, ask whether the `MEDIUM` and `LOW` ones may be left open as `plan-feature` words it, send the domain expert the one line in `clarifyCommand` — the same line is in `QUESTIONS.md` — and add nothing to the spec; `/speckit-clarify` shows each question with its recommendation, and skips one the spec already answers. The restart after their answer is `plan-feature` with `from: "review-plan"`.

**The trace is `<featureDir>/RESOLUTIONS.md`, appended to and never rewritten** — one dated section per stop, naming the stage, the reason and the run id, and per item: the item as the handoff stated it, the recommendation, what the confidence rested on, and the commit; or, where it went to a person, that fact and what was missing. It is a file because the script overwrites `HANDOFF.md` at the next exit, and the one-attempt test must be answerable by a later session. A run that wrote no handoff gets no `RESOLUTIONS.md` either.

## What this skill does not do

**It does not specify, clarify or write a spec**: that is the domain expert's, before the run and again over `QUESTIONS.md`; a feature with no `spec.md`, or with a clarification marker left, is refused at preflight. Its only git operations are bringing the base up to date by fast-forward, planning commits on the base inside the feature directory and what the plan step writes outside it, `git pull --rebase` of the run's own unpushed commits before a push, making or resuming the build branch and merging the base into it, and landing the build on the base by fast-forward; it never rebases shared history, never force-pushes and never writes another feature's spec. It reads `QUESTIONS.md` only for its questions, their severity and whether each is left open; it never reads `HANDOFF.md` back; it does not write, read or enforce `RESOLUTIONS.md`. It does not install spec-kit; preflight fails when `speckit-plan` through `speckit-converge` are missing under `.claude/skills/`, and, on every start, when the traceability gate `/init-pipeline` installs or its self-test is missing or not listed in `scripts/wall-checks.txt`. It does not choose the definition of done. It lands every finished build on the base branch and never opens a pull request; merging `dev` into `main` is a person's. It runs stages in sequence. It is Claude Code only; the stage prompts and the loop in `workflow.mjs` are the portable part. It does not record its cost: the Workflow journal does, machine-local under `~/.claude/projects/`. It replaces the human plan review with the review-plan refutation; a person who wants to read the plan runs with `until: "review-plan"`, reads it, and continues with `from: "tasks"`.
