Cache-Disziplin für jedes Repo, das einen Wert aus dem Speicher oder einem Cache‑Server bereitstellt, anstatt ihn aus dem dauerhaften Speicher neu zu berechnen, in jeder Sprache — eine Adapter‑Nahtstelle, keine Caching‑Annotation oder Dekorator, ausschließlich Read‑Through, nichts, das Korrektheit im Cache trägt, Schlüssel, die den Scope des Aufrufers transportieren, eine festgelegte Veralterungsobergrenze, nur Delete‑Invalidierung nach dem Commit, exakte Serialisierungs‑Round‑Trips, kein ersetzter Wert bei einem Cache‑Fehler und das dreikonfigurations‑Differenzial‑Tor. Trägt das Urteil über jede Form, die ein Repo aus diesen Primitiven zusammenbaut — zwei Cache‑Ebenen, eine Sammlung, die neben ihren Mitgliedern gecached wird, ein Cache, der von zwei Deployables geteilt wird, ein Hintergrund‑Warm‑Up, ein Loader, der einen anderen Service liest. IMMER zuerst laden, bevor man einen Cache, ein Memo, einen Loading‑Cache, eine Caching‑Annotation oder ein Expiry hinzufügt, bevor man entscheidet, ob ein Repo überhaupt einen Cache benötigt, bevor man einen Cache hinter einem Proxy oder einem Content‑Delivery‑Network platziert und bevor man einen Wert cached, der von einer anderen Regelmenge gesteuert wird. Gibt an, welche Art von Prüfung jede Regel benötigt; das Werkzeug ist im passenden Stack‑Skill (caching-java) benannt.
