L’architecture et les règles de processus auxquelles un dépôt se soumet parce que son mainteneur est un agent LLM plutôt qu’une personne — magie « startup‑loud » autorisée et magie « runtime‑silent » interdite, raisonnement sur le programme complet éliminé, état opérationnel dans le dépôt, un module de taille d’une session, topologie déterminée par le nombre de volontés indépendantes plutôt que par les services, un idiome imposé mécaniquement, un humain de pilotage qui n’est pas évaluateur, un passage antagoniste en contexte frais comme substitut à la revue, un système prédécesseur comme inventaire et jamais oracle, zéro tentative de réessai et une quarantaine qui ne peut pas se détériorer, dépendances tarifées selon la forme d’échec, et un argument de sécurité à côté de chaque morceau de code subtil construit à la main. Il porte le cas fonctionnel d’un dépôt — les favoris du corpus qu’il a rejetés, chacun nommé d’après le terrain sur lequel il a échoué — et le verdict sur chaque forme qu’un dépôt assemble à partir de deux de ces primitives — un module poussé par deux volontés, une dépendance qui apporte son propre idiome, une quarantaine qui vit dans une console, un prédécesseur qui continue de servir le trafic. CHARGEZ TOUJOURS avant de dessiner ou de déplacer une frontière de module, de choisir une topologie d’exécution, de décider pour quoi une barrière de construction peut être assouplie, d’adopter un cadre, une base de données, un service géré ou une API fournisseur, d’écrire un mécanisme de réessai ou de gestion d’erreur, d’écrire un morceau de code suffisamment subtil pour nécessiter un argument de sécurité, d’introduire une seconde façon de faire quelque chose que le dépôt fait déjà, de migrer depuis un système existant, ou de rédiger une constitution de dépôt.
