Cómo elegir un stack de backend para un repositorio cuyo código es escrito por agentes LLM y que nadie lee línea por línea — clasifica a los candidatos por lo que su proceso de construcción puede rechazar enviar en lugar de por lo que te permite expresar, cuenta los hosts de enforcement independientes que ofrece un stack en lugar de sus características de sistema de tipos, prefiere un stack donde la llamada incorrecta no pueda ser escrita sobre uno donde se escribe y luego se marca, valora la gravedad del corpus como un costo que el ganador lleva, no como una razón de su victoria, y trata la operatividad como un veto más que como el criterio decisivo. Presenta el caso trabajado de este conjunto de habilidades: Java con Spring Boot Web MVC, jOOQ y PostgreSQL, con los perdedores a nivel de lenguaje — C#/.NET, Kotlin, Go y TypeScript, cada uno con el terreno en el que perdió — más el veredicto sobre cada forma que una organización ensambla a partir de elecciones de stack: un segundo stack junto al primero, un segundo lenguaje dentro de un repositorio y un candidato rechazado que llega de todos modos como dependencia. SIEMPRE carga antes de elegir un lenguaje, runtime, framework web, biblioteca de persistencia o base de datos para un nuevo backend, antes de argumentar que un stack existente debería cambiar, antes de añadir un segundo lenguaje a un repositorio o a una organización, y antes de escribir un conjunto de reglas para un stack que nadie ha justificado al escribir.
