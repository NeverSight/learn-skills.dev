Comment choisir une pile backend pour un dépôt dont le code est écrit par des agents LLM et lu ligne par ligne par personne — classez les candidats selon ce que leur processus de construction peut refuser d’expédier plutôt que selon ce qu’ils vous permettent d’exprimer, comptez les hôtes d’application indépendants qu’une pile offre plutôt que ses fonctionnalités du système de types, privilégiez une pile où l’appel incorrect ne peut pas être écrit plutôt que celle où il est écrit puis signalé, évaluez la gravité du corpus comme un coût que le gagnant porte plutôt que comme une raison de sa victoire, et considérez l’opérabilité comme un veto plutôt que comme le critère décisif. Ce guide s’appuie sur un cas concret : Java avec Spring Boot Web MVC, jOOQ et PostgreSQL, avec les perdants du niveau langage — C#/.NET, Kotlin, Go et TypeScript, chacun avec le terrain sur lequel il a perdu — ainsi que le verdict sur chaque forme que peut prendre une organisation à partir des choix de pile : une deuxième pile à côté de la première, un deuxième langage dans un même dépôt, et un candidat rejeté qui arrive quand même comme dépendance. Chargez toujours avant de choisir un langage, un runtime, un framework web, une bibliothèque de persistance ou une base de données pour un nouveau backend, avant d’affirmer qu’une pile existante devrait changer, avant d’ajouter un deuxième langage à un dépôt ou à une organisation, et avant d’écrire un ensemble de règles pour une pile que personne n’a justifiée par écrit.
