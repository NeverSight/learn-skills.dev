如何为代码由 LLM 代理编写、没有人逐行阅读的仓库选择后端技术栈——通过构建系统能够拒绝发布的能力来排名候选方案，而不是它们允许你表达的能力；通过技术栈提供的独立执行主机数量来计量，而不是其类型系统特性；倾向选择“错误调用根本写不出来”的技术栈，而不是“写出来后再被标记”的技术栈；把语料库的重量视为获胜者必须承担的成本，而不是它获胜的原因；并把可运维性当作否决权，而不是决定性标准。该技能集合的实际案例是 Java 与 Spring Boot Web MVC、jOOQ 和 PostgreSQL，同时列出语言层面的败者——C#/.NET、Kotlin、Go 和 TypeScript，以及它们各自失利的依据——再加上对组织在技术栈选择上可能出现的各种形态的判决——例如在第一套栈旁边再加第二套栈，在同一个仓库里使用第二种语言，或是即使被拒绝仍作为依赖引入的候选。始终在为新后端挑选语言、运行时、Web 框架、持久化库或数据库之前，在争论要改动现有栈之前，在向仓库或组织中添加第二种语言之前，以及在为一个没有得到充分论证的栈编写规则集之前，都先进行评估。
