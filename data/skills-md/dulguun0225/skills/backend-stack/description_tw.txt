如何為代碼由 LLM 代理撰寫、卻沒有人逐行閱讀的倉庫選擇後端堆疊——依照它們的構建能拒絕出貨的情況來排序候選者，而不是依照它們允許你表達的內容；計算堆疊提供的獨立執行強制機制數量，而不是它的類型系統特性；偏好那種錯誤呼叫根本寫不出的堆疊，而不是寫了之後才被標記的堆疊；把語料庫的重量視為勝出者必須承擔的成本，而不是它獲勝的理由；並把可運作性當作否決權，而非決定性標準。此技能組的實例是 Java 搭配 Spring Boot Web MVC、jOOQ 與 PostgreSQL，語言層面的失敗者則是 C#/.NET、Kotlin、Go 與 TypeScript，各自因何而敗；以及對組織從堆疊選擇中組成的各種形式——第一個堆疊旁的第二堆疊、單一倉庫中的第二語言、以及最終仍以相依性形式出現的被拒絕候選者——的判決。永遠在選擇語言、執行階段、Web 框架、持久化函式庫或資料庫之前先進行載入，無論是為了新的後端、為了主張既有堆疊需變更、為了在倉庫或組織中加入第二種語言，或是要為一個沒有人真正正當化的堆疊撰寫規則集，都應先這樣做。
