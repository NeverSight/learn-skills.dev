Construisez un serveur de secours sur site qui maintient une réplique RxDB bidirectionnelle en temps réel d’une partie de Firestore d’un site, prend le relais pour servir les terminaux LAN lorsque le cloud est injoignable, et rejoue le travail hors ligne lors de la reconnexion. Utilisez-le quand : (1) un site physique (magasin, salle de sport, clinique, entrepôt) doit continuer à prendre des réservations, déplacer du stock et activer du matériel pendant une panne d’internet, (2) les kiosques ou les PWAs du personnel doivent basculer eux‑mêmes entre une API cloud et une API locale, (3) un serveur hors ligne existant doit être audité : une purge à la reconnexion qui double‑compte le stock, une réplique qui cesse de tirer les données, un basculement qui ne trouve jamais la boîte, (4) l’utilisateur mentionne : mode île, serveur de secours hors ligne, basculement LAN, réplique sur site, serveur local avec synchronisation bidirectionnelle vers Firestore, « le site continue de fonctionner quand internet est coupé », replicateFirestore, rxdb/plugins/replication-firestore, point de contrôle serverTimestamp, _offlineCreated, _locallyModified, syncedIds, FieldValue.increment, cron de heartbeat, apiBaseUrl, authentification HMAC des appareils, island.local, avahi. Intègre les trois niveaux de réplication, le tampon de point de contrôle requis à chaque écriture cloud, le déploiement delta de stock par ID, une ingestion idempotente indexée sur des IDs générés par le client, le secours de jeton personnel limité hors ligne, la chaîne de heartbeat et d’état, et une suite de 17 tests vitest pour la logique critique de confiance. Serveur local Node/NestJS et cloud Firestore avec gestionnaires de route Next.js comme API de référence ; le framework HTTP, l’IdP et le vocabulaire sont des points d’articulation dans architecture.md. Ce n’est pas un cache de lecture, pas une synchronisation multi‑maître entre sites, et pas destiné à une base de données cloud autre que Firestore.
