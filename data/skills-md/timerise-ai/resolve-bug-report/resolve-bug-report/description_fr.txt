Résoudre un rapport de bug qu’un client ou un membre du locataire a soumis via un pont de signalement intégré dans l’application en le transférant dans un suivi de tickets : lire le ticket et les métadonnées du pont, décider s’il y a suffisamment d’informations pour agir, reconstituer ce que le rapporteur a fait à partir des données de production en lecture seule, corriger la cause racine et toutes ses variantes connexes, prouver que la correction échoue sur l’ancien code et réussit sur le nouveau dans l’application en cours d’exécution, valider le commit avec le mot‑clé de clôture, et répondre au rapporteur via le pont en langage clair en demandant une confirmation. Utiliser quand : (1) l’utilisateur fournit un numéro de ticket ou l’URL d’un rapport soumis par un client, (2) le rapport a un titre et une description vide ou très succincte, (3) l’utilisateur demande de vérifier s’il dispose de toutes les informations avant de corriger, (4) l’utilisateur veut répondre au rapporteur une fois la correction apportée, (5) les preuves montrent que l’application fonctionne comme prévu et la correction relève d’une décision produit, (6) le rapport demande quelque chose que l’application possède déjà et la réponse doit être un « how‑to », (7) le rapport demande une fonctionnalité que l’application n’a pas et le rapporteur a besoin d’une réponse immédiate, construite ou non, (8) une réponse déjà envoyée était incorrecte et nécessite une correction, (9) l’utilisateur mentionne : résoudre le ticket, corriger le ticket #, étiquette tenant‑report, rapport de bug client, « check if you have everything you need », /reply, laisser une réponse pour le rapporteur, demander la confirmation du rapporteur, journal d’audit, production en lecture seule, requête supabase db --remote --read‑only, PostgREST max_rows, plafond de 1000 lignes, « Fixes # », « settled separately instead of together », « it already exists », « for the whole salon », « can it be done », demande de fonctionnalité, gel de fonctionnalités, hors de portée, « only clients starting with A », « explain where the list is », « I am at reception and cannot settle », rôle incorrect, dépassement d’autorisation, « could not move the visit ». Comprend une matrice de suffisance, un protocole de production en lecture seule avec l’approbation de l’utilisateur, une requête de chronologie du rapporteur, une table de causes racines avec un contrôle permettant de différencier chaque cause, les variantes à proposer à l’utilisateur lorsque la cause est un comportement, un test de garde qui échoue sur l’ancien code, une vérification de réclamation avant toute réponse, ainsi que des modèles de réponse pour une correction, un « how‑to », une fonctionnalité non développée pour l’instant, la configuration du compte et une correction. Tout dépôt git avec l’interface gh CLI et une application multi‑locataire soutenue par Postgres ; le suivi, le canal de réponse, l’accès à la production et la procédure de vérification de l’application constituent les points de raccordement. Pas le pont lui‑même, pas de triage massif, pas de réponse à une panne.

Veuillez toujours répondre dans la langue de l’utilisateur.
