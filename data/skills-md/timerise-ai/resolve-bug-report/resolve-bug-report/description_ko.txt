고객 또는 테넌트 구성원이 인앱 보고 브리지를 통해 제출한 버그 리포트를 이슈 트래커에 등록하고 해결하십시오: 이슈와 브리지 메타데이터를 읽고, 조치하기에 충분한지 판단한 뒤, 프로덕션 데이터 읽기 전용으로 보고자가 수행한 작업을 재현하고, 근본 원인과 그와 관련된 모든 문제를 수정하며, 수정이 이전 코드에서는 실패하고 실행 중인 새로운 앱에서는 통과함을 증명하고, 마감 키워드와 함께 커밋한 뒤, 브리지를 통해 평이한 언어로 보고자에게 확인 요청을 포함한 답변을 보냅니다. 사용 상황: (1) 사용자가 고객이 제출한 이슈 번호나 보고서 URL을 제공할 때, (2) 보고서에 제목은 있지만 설명이 비어 있거나 간략할 때, (3) 사용자가 수정하기 전에 충분한 정보가 있는지 확인해 달라고 요청할 때, (4) 사용자가 수정이 완료되면 보고자에게 답변해 달라고 요청할 때, (5) 증거가 앱이 설계대로 작동하고 수정이 제품 결정임을 보여줄 때, (6) 보고서가 앱에 이미 존재하는 기능을 요구하고 답변이 사용 방법일 때, (7) 보고서가 앱에 없는 기능을 요구하고 보고자가 지금 바로 답변을 필요로 할 때(구현 여부와 관계없이), (8) 이미 보낸 답변이 잘못되어 수정이 필요할 때, (9) 사용자가 다음과 같은 문구를 언급할 때: resolve issue, fix issue #, tenant-report label, customer bug report, "check if you have everything you need", /reply, leave a reply for the reporter, ask the reporter to confirm, audit log, production read only, supabase db query --remote --read-only, PostgREST max_rows, 1000-row cap, "Fixes #", "settled separately instead of together", "it already exists", "for the whole salon", "can it be done", feature request, feature freeze, out of scope, "only clients starting with A", "explain where the list is", "I am at reception and cannot settle", wrong role, permission override, "could not move the visit". 충분성 매트릭스, 사용자의 승인 하에 읽기 전용 프로덕션 프로토콜, 보고자 타임라인 쿼리, 각 원인을 구분하는 체크가 포함된 근본 원인 표, 원인이 행동일 때 사용자에게 제시할 변형들, 기존 코드에서 실패하는 가드 테스트, 어떤 답변을 하기 전에 진행하는 클레임 체크, 그리고 수정, 사용 방법, 현재 구현되지 않은 기능, 계정 설정 및 정정에 대한 답변 템플릿을 포함합니다. gh CLI와 PostgreSQL 기반 멀티 테넌트 앱이 있는 모든 git 리포지토리; 트래커, 답변 채널, 프로덕션 접근 및 앱 검증 절차가 접점(seam)이며, 브리지 자체, 대량 트라이에이지, 서비스 중단 대응은 포함되지 않습니다. 항상 사용자의 언어로 응답하십시오.
