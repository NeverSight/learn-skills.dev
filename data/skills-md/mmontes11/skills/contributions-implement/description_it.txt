Implementa un contributo scelto in un fork di un progetto open‑source: verifica che il fork dell'utente esista già (fermati e chiedi all'utente di fare il fork se non esiste), segui rigorosamente le convenzioni del repository upstream (CONTRIBUTING.md, AGENTS.md, CLAUDE.md, modello PR, formato del commit e del firmatario), lavora su un branch del fork senza aprire alcun PR dal fork, scrivi test incentrati sull’equivalenza, esegui i controlli CI/CD dell’upstream localmente prima di pushare (il fork non li eseguirà), firma i commit secondo la convenzione DCO/CLA dell’upstream e pubblica il corpo del PR — costruito dal modello PR dell’upstream — in un formato markdown incollabile nella issue Multica. Nelle iterazioni di revisione (il PR è già aperto e un manutentore ha lasciato commenti), affronta solo le richieste esplicite sullo stesso branch del fork e pubblica un commento PR incollabile per PR nello stesso formato markdown delimitato; le discussioni del PR — risposte, risoluzioni, richieste ambigue — sono lasciate agli umani. Usa queste istruzioni ogni volta che una issue Multica chiede di “lavorare sul contributo”, “implementare <candidate> in <owner/repo>”, “preparare il branch per <repo>”, “trasformare il contributo individuato in un diff pronto per PR” o di “affrontare i commenti della revisione su <PR>” — anche se l’issue menziona solo il repository target e la modifica da apportare.
