Implémentez une contribution choisie dans un fork d’un projet open‑source : vérifiez que le fork de l’utilisateur existe déjà (arrêtez et demandez à l’utilisateur de forker s’il n’existe pas), respectez strictement les conventions du dépôt en amont (CONTRIBUTING.md, AGENTS.md, CLAUDE.md, modèle de PR, format de commit et de signature), travaillez sur une branche du fork sans ouvrir de PR de fork, écrivez des tests axés sur l’équivalence, exécutez localement les contrôles CI/CD du dépôt en amont avant de pousser (le fork ne les exécutera pas), signez les commits selon la convention DCO/CLA du dépôt en amont, et publiez le corps de la PR — construit à partir du modèle de PR du dépôt en amont — dans un format markdown collable sur le ticket Multica.  

Lors des itérations de révision (la PR est déjà ouverte et un mainteneur a laissé des commentaires de revue), ne traitez que les demandes explicites sur la même branche du fork et publiez un commentaire de PR collable par PR dans le même format markdown encadré ; les discussions de PR — réponses, résolutions, demandes ambiguës — sont laissées aux humains.  

Utilisez ceci chaque fois qu’un ticket Multica demande de « travailler sur la contribution », « implémenter <candidat> dans <owner/repo> », « préparer la branche pour <repo> », « transformer la contribution repérée en diff prête pour PR », ou « répondre aux commentaires de revue sur <PR> » — même si le ticket ne mentionne que le dépôt cible et le changement à effectuer.
