Реализовать выбранный вклад в форке проекта с открытым исходным кодом: проверить, существует ли уже форк пользователя (при отсутствии — остановиться и попросить пользователя создать форк), строго следовать конвенциям upstream‑репозитория (CONTRIBUTING.md, AGENTS.md, CLAUDE.md, шаблон PR, формат коммита и подписи), работать в ветке форка без открытия любого PR из форка, писать тесты, ориентированные на эквивалентность, запускать проверки CI/CD upstream локально перед отправкой (форк их не выполняет), подписывать коммиты согласно DCO/CLA upstream и разместить тело PR — построенное по шаблону PR upstream — в виде вставляемого markdown‑текста в issue Multica. В циклах ревью (PR уже открыт, и мейнтейнер оставил комментарии) отвечать только на явные запросы в той же ветке форка и разместить вставляемый комментарий к PR в том же формате fenced‑markdown; обсуждения PR — ответы, разрешения, неоднозначные запросы — оставляются людям. Использовать данную схему каждый раз, когда issue Multica просит «работать над вкладом», «реализовать <candidate> в <owner/repo>», «подготовить ветку для <repo>», «превратить найденый вклад в готовый к PR дифф» или «ответить на комментарии ревью в <PR>» — даже если в issue указано лишь целевое репо и требуемое изменение.
