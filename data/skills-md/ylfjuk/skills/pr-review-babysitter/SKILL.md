# Code review babysitter

Perform a general code review of the requested changes. Identify actionable defects with evidence from the change and relevant repository context. Read applicable repository standards and the references needed to interpret them before concluding the review. Check whether added or moved code and data belong in their files and layers, even when the issue suggests a location; call out conflicts between the issue and repository conventions.

When a change centralizes behavior or data, trace the consumers it is meant to serve. Search code and content files for remaining direct implementations or hard-coded values, and check whether those consumers use the shared source.

For added or changed constants, configuration values, and variables holding fixed domain values, search beyond the diff for existing definitions of the same concept. Search by meaning, related names, and literal values; different names or equivalent expressions can hide duplication. Inspect the matching definitions and their consumers to determine whether they encode the same rule and should change together. Multiple variables or configuration entries referencing the same canonical constant are valid reuse. Independently redeclaring its value or expression for the exact same rule creates a second source of truth, even if the values currently match. Flag that duplication when it can drift, citing both locations and the concrete consequence. Equal values alone are not evidence: keep independently owned rules separate, and check dependency boundaries before recommending a shared import. Apply this check even when the change does not claim to centralize anything.

Find the issue or spec behind the change through the request description, linked tracker items, or branch name. Compare the implementation with its requirements, but also check whether those requirements make sense in the repository. Raise missing or partial behavior as a finding and quote the relevant requirement. For materially unrequested behavior, explain why it exceeds the stated scope and why that matters. If a requirement itself appears mistaken or conflicts with repository behavior or standards, ask the author about it and show the evidence, even when the code follows it. If no originating issue or spec is available, say so in the review summary rather than inferring requirements from the implementation.

When posting an issue, use the host's review or discussion mechanism that lets the team track it as unresolved until addressed. Attach it to a relevant code location when that helps; use a request-level resolvable thread for an issue that has no useful single location. Do not leave an actionable finding only as a general comment that the team cannot track to resolution. General comments are fine for a review summary or an open discussion. If the host has no resolvable mechanism, state the finding clearly and track its status in the review checkpoint. Avoid repeating existing feedback or inventing issues to fill a review.

If local verification would write files, switch branches, or otherwise disturb the implementor's workspace, use a temporary worktree at the commit being reviewed. Do not edit files or run mutating tests in a checkout the implementor may be using. Reuse an existing isolated checkout when one is available, and remove temporary worktrees after verification. Read-only inspection does not require a new worktree.

After the initial review, set up a monitor for the same review request until it closes, merges, or the user ends the assignment. If the user defers or declines monitoring, complete the review and post its findings now, then skip the monitor. The skill defines what to do when invoked; it does not keep an agent running. Use the available host and scheduler capabilities: prefer an event trigger for comments and commit updates, then a scheduled check if event triggers are unavailable. If neither is available, tell the user that follow-up requires a new invocation. On each wake-up, fetch the current request state before deciding whether work is needed.

Keep a durable per-request checkpoint with the last reviewed head commit and processed comment or review IDs. If a reliable checkpoint is unavailable, reconstruct what has already been reviewed from the request history before posting. Ignore the agent's own comments as triggers for a reply.

For new commits, wait for a short quiet period after the latest push, around ten minutes by default, so a burst of pushes gets one review. If woken during that period, arrange another check after it ends and leave the head unreviewed in the checkpoint. Compare the last reviewed head with the latest head. Check whether prior findings were addressed and whether the new changes introduced defects. A response without a code change calls for a focused reply, not a full code review. If the head changes during review, refresh it before posting conclusions tied to that head.

Own the decision to resolve findings you raised. Review the implementor's change or explanation, then resolve the thread when the concern is addressed. The implementor may resolve a thread without waiting for you only when they applied your suggested diff in full, line for line, and that diff covers the entire concern. If they changed the approach, applied only part of the suggestion, or answered without changing code, leave the resolution decision to you. Treat routine questions and minor disagreements as part of the thread discussion.

Once you have no remaining findings on the current head commit, post one clear review summary so the implementor knows your review is complete. Name the reviewed commit and say that you have no further comments; this is also appropriate when the initial review finds nothing. Report conformance with the originating issue or spec separately from repository standards, and note any requirements you questioned. Scope the statement to your own review. Check other reviewers' visible status and do not imply the whole request is ready while their feedback is open or pending. Do not repeat the summary on idle checks. A later commit makes your earlier completion statement stale: review the new head before giving a new one.

After each substantive review pass, leave a brief update in the local work thread, separate from the host review discussion. State the head reviewed, what findings were opened or resolved, what remains open, and what you are waiting for. Link to review threads when useful. Summarize outcomes rather than copying the diff or discussion history; skip updates for checks that found nothing new.

Include a decision summary in that update and in the final reply. Link the request and name the reviewed head. Refresh the host state before reporting: open/draft/closed/merged, current head, conflicts, required checks, required approvals, and unresolved review threads. Report whether it is mergeable now as yes, no, or unknown, with the concrete blockers or missing information. Distinguish conflict-free merging from satisfying the host's merge requirements and from your recommendation. If the head has changed, mark the assessment stale until the new head is reviewed.

Give a compact scorecard. Choose criteria relevant to this code review based on its purpose, scope, and risks, honoring user-specified criteria. There is no fixed roster or required number of criteria. Score each assessed criterion from 1 to 10, with higher scores meaning greater readiness and fewer concerns. Anchor the scale at 1 for serious concerns, 5 for mixed evidence or meaningful gaps, and 10 for strong evidence with no material concerns found. Give a brief evidence-based reason and any remaining concern for each score. Mark relevant criteria with insufficient evidence as `unknown` rather than inventing a score or omitting the uncertainty. Passing CI alone does not justify high scores across criteria.

End with a recommendation to merge, wait, or request changes, and the reasons that matter to the user's decision. Keep blocking findings and unmet host requirements explicit regardless of scores; do not average them away. A recommendation does not authorize approval or merging. The decision summary is informational; continue posting findings and follow-up replies within the authorized scope without waiting for the user's approval of it.

Label every comment the agent posts on the request. Use `Agent-authored` when the agent decided on or substantially wrote the point. Use `Agent-assisted at the user's direction` when the user directed the point and asked the agent to phrase or post it. This distinction depends on who directed the substance, even when the same account posts both. Include the agent name or identity when available; never imply a human wrote an agent comment.

Do not approve, merge, or close the request unless separately asked. When the request closes or merges, stop its monitor and report the final review status.
