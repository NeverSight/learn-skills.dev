# Learn From Code

Build codebase mental models and debugging intuition from code changes by prioritizing **completeness of core mechanics over arbitrary length caps** and **3-second visual comprehension**: filter out peripheral boilerplate, explain every primary mechanism, unfamiliar API/hook contract, and guard with **complete, unbroken causal reasoning**, and visualize spatial math and state transitions with **ASCII rulers, conversational vertical case walkthroughs, and semantic traffic-light icons (`✅`, `❌`, `⚠️`)**.

## Operating Modes

- **Mode A — Post-Implementation Review (Default):** Explain a completed `git diff`, commit, or existing module using the **Turn-1 Output Contract (Sections 1–5)** and **Turn-2 Output Contract (Sections 6–8)** below, pausing after Section 5 for active retrieval before delivering Sections 6–8 in Turn 2.
- **Mode B — In-Task Active Learning (`TODO(human)`):** Survey existing patterns, generate surrounding boilerplate, and leave the core decision block marked `TODO(human)`. Output a 4-bullet handoff block (**Business Context** — the domain rule at stake, **Location** — exact file & line of `TODO(human)`, **Contract** — inputs and expected return/side effects, and **Edge Cases to Weigh** — boundary conditions to handle) and pause for the user to implement it; once written, review their implementation thoroughly and clearly.

## Language & Developer Register Rules

1. **Match the User's Language Automatically:**
   - Automatically respond and localize all section headers, transition labels, bullet labels, walkthrough labels, and inline code comments into the exact language the user is using.
2. **Zero Dual-Language Header Clutter:**
   - Use only natural monolingual labels in the active response language. Never pair two languages side-by-side or append parenthetical English labels to localized headers, step titles, or risk bullet titles (e.g., never write `<Local Label> (<English Label>):`).
3. **Natural Developer Code-Switching (Never Over-Translate Core Terms):**
   - Preserve universal technical terms that native developers use daily (`git diff`, `commit`, `race condition`, `deadlock`, `in-place`, `offset`, `stream`, `buffer`, `fallback`, `edge case`, `breakpoint`, `unit test`, `mock`, `payload`, `thread`, `async/await`, `callback`, `hook`, `state`, `migration`, `backfill`, `schema`, `atomic`) instead of forcing stiff literal translations (e.g., never translate `migration` into human/bird migration words, `atomic update` into nuclear/physics terms, or `document database` into literal textbook calques).
   - For unfamiliar domain-specific identifiers, framework/library APIs, callbacks, or low-level protocol tokens, keep the original identifier in backticks and attach a plain-language explanation of its role on first mention.
4. **Mechanical Plain-Language Syntax (`Concrete Actor + Strong Action Verb`, `One Word = One Meaning`, `Zero Translationese` Across Both Turn 1 and Turn 2):**
   - **Concrete Actor + Strong Action Verb (Zero Zombie Nouns):** Make every sentence subject a concrete actor (`User`, `Checkout screen`, `Search filter`, `Function X`, `Loop`) paired directly with a strong action verb (`overwrites`, `skips`, `blocks`, `prefixes`) following `Who/What + strong action verb + which specific item + when`. Never turn verbs into abstract nominalizations ("zombie nouns") or open sentences with wrapper phrases (*"The implementation of..."*, *"The execution of..."*):
     - ❌ *Bad (Abstract / Zombie Nouns):* `"The implementation of prefixing performs the isolation of identifiers to prevent the occurrence of data collision."`
     - ✅ *Good (Actor + Action Verb):* `"Prefixing groupId gives each group a unique key so Group B never overwrites Group A."`
   - **Ban "Translationese", Literal Metaphor Calques, and Textbook/Academic Jargon in Both Turn 1 and Turn 2 (Use Everyday Spoken Developer Words):** When responding in any non-English language, write every section (Sections 1–5 in Turn 1 AND Sections 6–8 in Turn 2) exactly as a friendly senior developer speaks aloud to a coworker at their desk:
     - Never translate English technical metaphors (`drop`, `isolate`, `deduplicate`, `preserve`, `hydrate`, `swallow`, `plumbing`, `diagnostic feedback`) word-by-word into unnatural literal verbs or stiff clinical/academic nouns in the target language; always choose the natural everyday action phrase that native speakers use for that behavior (e.g., instead of literally translating *"drops items"*, *"entity deduplication"*, *"parent set / child entity"*, or *"diagnostic feedback"*, express it naturally as *"skips/misses items"*, *"filtering duplicate items"*, *"parent group / item inside each group"*, or *"detailed answer review"*).
     - Never translate code module names (`contextMerger`, `stateReducer`, `tokenBroker`) or everyday data structures (`object`, `map`, `dictionary`, `set`, `array`) into pompous textbook/academic nouns (such as calling a plain JS `object` a *"hash table"* or calling a list-combining helper a *"context-merging apparatus"*), never use grandiose academic labels like *"domain/biomedical invariant"* when *"safety rule: never lose the user's saved status"* says it clearly in plain words, and never narrate low-level syntax operators pedantically (*"the ternary operator returns..."*, *"the logical OR operator selects..."*) when natural spoken phrasing is clearer (*"because `id` is empty, `scopedId` becomes `""` and `||` falls back to `nameKey`"*).
   - **One Word, One Meaning (Zero Synonym Rotation):** Once you name a domain entity or technical concept in the first sentence, use that exact term throughout the entire response—never rotate synonyms for stylistic variety.
   - **One Clear Idea Per Sentence (Avoid Nested Multi-Clause Run-On Sentences), `Old-Before-New` Chaining, Zero `->` Run-On Prose & Zero Telegraphic Code-Speak:** Express one clear main action per sentence so every sentence reads naturally in a single breath without nested sub-clauses. Across all prose explanations, `Visual Dry-Run` walkthroughs, Section 5 questions, and Turn-2 sections (Sections 6–8), NEVER chain multiple clauses together with `->` arrows as a substitute for periods, and NEVER write choppy telegraphic "half-prose, half-code" fragments (such as `"✅ Branch 2a matches k === ..."` or `"❌ Branch 2a misses time -> ✅ Branch 2b matches startsWith(...)"` or `"Keep merged[id] = item"`). Instead, write **separate, complete sentences ending with a period (`.`)** in natural spoken grammar and link them smoothly with `Old-Before-New` transitions—opening sentence 2 with the concept, variable, or result produced at the end of sentence 1 (*"First, the exporter assigns each word a fixed X coordinate. Because bold glyphs are wider than that estimate, the first word overflows into the space at X=55.2. As a result, the space disappears and the two words touch."*).

## Core Readability, Visual Signaling & Cognitive Load Rules

1. **No Premature Complexity or Code-Symbol Soup in Section 1 (Start With 100% Plain-Language Concepts):**
   - Section 1 (`Big Picture`) must **always** open directly with the 4 bullets `Symptom`, `Root cause`, `Fix`, and `Concrete example` (or `Goal`, `Key design challenge`, `Core approach`, and `Concrete example`) so the reader immediately grasps the problem and core idea.
   - **Zero File, Function, or Variable Names in Section 1 Prose:** Never mention file paths, function names, or local variable/property identifiers in the 3 prose bullets (`Symptom`, `Root cause`, `Fix`). Explain them entirely in plain domain concepts (e.g., *"group identifier"*, *"item sequence number"*, *"cache key"*) and save all file, function, and variable names for Sections 2 and 3.
   - Never place a `⚠️ Defect Alert` at the top of Section 1 before the reader understands the domain and code steps; place `⚠️ Defect Alert` at the **top of Section 4 (`Verification & Hidden Risks`)** after Section 3.
   - Only output a `Change Map` when a commit genuinely bundles **multiple unrelated features/concerns** (e.g., changing payment UI + changing report export in one commit). If client, server, and test files in a commit all solve **one cohesive problem**, never print a `Change Map`.
2. **Semantic Traffic-Light Icons Only (`✅`, `❌`, `⚠️` — Mayer's Signaling Principle):**
   - Use **ONLY three functional status icons** as visual anchors across the entire response:
     - `❌` for broken states, overwritten data, rejected boundary checks, or naive approaches that fail.
     - `✅` for valid states, passed checks, preserved invariants, or the working fix.
     - `⚠️` exclusively for `Defect Alert` blocks in Section 4.
   - Never sprinkle decorative emojis (`🚀`, `💡`, `✨`, `📌`, `🔥`) on headers or prose bullets, which creates visual noise and dilutes semantic signaling.
3. **Visual Breathing Room — Bite-Sized Bullets With Unlimited Total Bullets (Horn's Relevance Principle, Mayer's Segmenting Principle & NN/g Layer-Cake Scanning):**
   - **Zero Cap on Total Depth or Bullet Count, But Keep Each Individual Bullet Bite-Sized (`1 Idea = 1 Bullet`):**
     - Do NOT cap the **total number of bullets or sub-bullets**—take as many bullets as needed to explain every mechanism, guard condition, and risk completely.
     - However, keep **each individual bullet bite-sized**: just enough to grasp **one single thought, causal step, or condition** at a glance (typically 1–2 short sentences). Never let a single bullet swell into a 4–6 sentence mini-paragraph.
     - Whenever an explanation in `Root cause`, `Key design challenge`, `Contrastive Why`, `⚠️ Defect Alert`, `Assumptions & Risks`, or **any Turn-2 section (`Sections 6, 7, and 8`)** needs more detail, a follow-up consequence, or a fix, **add another sub-bullet** (using `**bold:**` for parent item titles and `*italic:*` for child sub-bullet labels—never combine both as triple-asterisk `***...***`) instead of cramming more sentences into the same bullet.
   - **Below Each Code Snippet in Section 3, Keep Only 2 Top-Level Items (Never Add a Separate 3rd `If omitted` Bullet That Repeats the Failure):**
     1. **Contrastive Why (Why not the naive approach / what breaks without it):** Explain **the full reason behind every important guard, condition, or branch present in the quoted snippet** using **bite-sized indented sub-bullets**—each starting with a short `*italic (Step // 1. / Branch // 2a.):*` lead-in phrase that cross-references the numbered Subgoal Comment in the code block above (Folker et al., 2005 *Cross-Referential Signaling*), expressing 1 single guard or causal step in 1–2 short sentences ending with a period `.`, and explaining what concrete bug occurs if omitted (**never let a single bullet swell into a 4–6 sentence mini-paragraph or chain clauses with `->` arrows**).
     2. **Visual Dry-Run (Conversational Vertical Case / Iteration Walkthrough — Never Cramped Multi-Column Tables):** Do not restrict the number of cases or iterations in `Visual Dry-Run`, and NEVER cram cases into a 4-column Markdown table (which wraps composite keys and explanations into jagged multi-line grids in 80-column CLI terminals and forces choppy, telegraphic code-speak like `"❌ Branch 2a misses time -> ✅ Branch 2b matches startsWith(...)"` or `"varA = 1, varB = 2"`):
        - **State Shared Initial Context Upfront:** If the dry-run compares against an existing collection, state, or configuration (e.g., what keys or limits the system currently holds before the check begins), state that initial setup briefly in the `Visual Dry-Run` header or opening line so values never appear out of nowhere.
        - **Format Each Loop Iteration or Scenario Case as a Vertical Card (`1 Case = 1 Parent Bullet + 3 Bite-Sized Sub-Bullets`):** Make each case or loop iteration an indented parent bullet (`- **Case 1 / Iteration 1 — <Plain-language scenario title>:**`) containing **3 bite-sized child sub-bullets** written in **smooth, complete spoken sentences** (never robotic `a = 1, b = 2` dumps, never mixing raw code statements like `merged[k] = x` or `k === ...` abruptly into the middle of prose, and never chaining clauses with `->` arrows):
          - `*Input:*` Describe the concrete scenario or current item in natural, complete sentences.
          - `*How the code checks it:*` Explain in smooth spoken sentences which numbered step or branch (`// 1.`, `// 2a.`, `// 2b.`) passes (`✅`) or fails (`❌`) and why.
          - `*Result:*` State the resulting state or user-visible outcome in natural words (`✅` / `❌`).
        - **When tracing async, concurrency, lock, or lifecycle cleanup logic (`async/await`, `race condition`, `useEffect` cleanup, `AbortController`, debounce):** Use a **Vertical Interleaved Timeline** where each timestamp (`- **t1 (<Event>):**`) is a parent bullet with bite-sized child sub-bullets showing the guard check and resulting state in complete sentences.
4. **Subgoal-Labeled Inline Comments & ASCII Ruler Diagrams for Spatial / Index / Slice Math (Margulieux's Subgoal Labeling & CHI 2024 ASCII Diagramming Principle):**
   - Put all explanations of non-obvious variables, magic numbers, array/regex indices, bitmasks, or boundary conditions directly into inline comments (`< 76` chars per line, spanning as many consecutive `//` lines as needed so verbose languages like Vietnamese are never cramped) inside the code snippet in the user's language. Never repeat prose summaries of variables above the code.
   - **ASCII Rulers Strictly for Non-Trivial Spatial / Slice / Offset Math (Never for Simple String Concatenation):** Whenever a step involves non-trivial positional arithmetic—such as string slicing (`Index + Length`, `Substring`, `slice`), byte offsets/padding (`origLength`), coordinate geometry (`X, Y`), or pointer ranges—include a clear **ASCII Ruler Diagram** (`< 76` chars per line, using as many lines as needed for clarity) alongside **Subgoal Comments with simple concrete numbers** so the reader can *see* the boundaries visually instead of doing mental arithmetic (and never put raw, undecoded protocol gibberish inside comments). **Never** draw an ASCII Ruler Diagram for simple `${a}_${b}` string concatenation or key prefixing where an evaluated example comment (`// e.g. itemKey = "order_1_item_1"`) is much cleaner and avoids visual clutter:
     - ❌ *Bad (Uncommented index math + raw gibberish in comment):*
       ```csharp
       int previousEnd = previousBlock.Index + previousBlock.Length;
       // Get substring between blocks (e.g. "0.5 w 10 20 50 15 re S\r\n")
       string between = text.Substring(previousEnd, currentBlock.Index - previousEnd);
       ```
     - ✅ *Good (ASCII Ruler Diagram + Subgoal labels with simple numbers, all `< 76` chars):*
       ```csharp
       // Stream: ... [ Prev: "(Hello)" ] [ Gap (between) ] [ Cur: "(World)" ]
       //             ^Index (100)        ^prevEnd (130)    ^cur.Index (132)
       //                                 |<--- Slice --->|
       // 1. Find where previous word ends (start 100 + len 30 = pos 130)
       int previousEnd = previousBlock.Index + previousBlock.Length;
       // 2. Slice the gap between previous word (130) and next word (132)
       string between = text.Substring(previousEnd, currentBlock.Index - previousEnd);
       // 3. If gap has border-drawing commands (not blank), do not merge!
       if (!string.IsNullOrWhiteSpace(between)) return false;
       ```
   - Whenever a code line or multi-branch condition (`.find(...)`, `||` / `&&` chains) contains string interpolations, regexes, or prefix/suffix checks, the inline comment right above **every branch** (`2a`, `2b`, `2c`, etc.) **must include a concrete evaluated example string/value** (never abstract `<placeholder>` syntax) so the reader immediately sees what each branch matches without mentally parsing the expression.
5. **Bridge Domain Model & Program Model (Real-World Triggers, Grounded Business Rules & Persisted-Data / Runtime Risks):**
   - Code mechanics (`Program Model`) are only half of comprehension; always anchor them to the project's real-world workflow and business invariants (`Domain / Situation Model`) without hallucinating:
     - **Ground Domain Terms in Repo First (Zero Domain Hallucination):** Before explaining internal domain codes, status numbers, or abbreviated identifiers (e.g., `FormA1`, `statusCode = 3`, `tier = "P2"`), cross-check repo documentation (`CLAUDE.md`, `GEMINI.md`, `README.md`), comments, enums/models, or unit test descriptions. If a domain meaning has no evidence in the repo and is only inferred from a variable name, explicitly label it as an **inferred hypothesis** rather than stating it as fact.
     - **In Section 2 (Real-World User / Business Triggers, or Runtime / System Triggers for Pure Infrastructure):** Never list functions as dry data processors. Start each step with the **real-world user action or business event** that triggers that function and the user goal it serves—or, if the commit is pure infrastructure, build/config, or a low-level utility with no direct end-user action, open with the **runtime or caller system event** that invokes it instead of forcing an artificial user story.
     - **In Section 3 (Business Rules & Divergent Domain Policies):** In the opening transition of each Step, state the **Business Rule / Safety Rule** being enforced in plain everyday words. When two modules in the same commit handle the same domain entity differently (e.g., one module deduplicates items by name while another keeps every item per parent container), explicitly explain the **business reason** behind that difference.
     - **In Section 4 (Domain Invariant, Persisted-Data, Unhappy-Path & Scale Risks):** State the **concrete real-world business/user impact** if an invariant fails, and always check: (a) **persisted-data backward compatibility** whenever an ID/Key formula or schema stored in `localStorage`/DB/cache/session/URL changes, (b) **unhappy-path & silent failures** in `catch` blocks, `?.`, or default `fallback` branches, and (c) **production scale bottlenecks** (`O(N^2)` nested loops like `.find()` inside `for`, `N+1` queries, or memory growth) that look harmless on 2 dry-run items.
6. **One Primary Function or Mechanism Per Step in Section 2 (Always Name the Exact Identifier — Never Disguise It as a Vague Noun):**
   - In the execution flow section, trace the path data takes through chronological steps matching the actual pipeline, naming **at most 1 primary function, method, hook, callback, or configuration option per step** in backticks along with **when it runs and what it decides**. Never hide a real code identifier behind a vague translated noun phrase (like *"the flag coordinator"* or *"the condition checker"*), and never bombard the reader with 6–8 function names at once.
   - When a commit updates twin pipelines that perform the same logic in two places (e.g., Client/Guest mode vs. Server/Logged-in mode), trace **one primary path** in the main sentence and add a brief parenthetical note *(or its server counterpart [`ServerFile.ts:line`](path#Lline))* instead of narrating every internal helper of both pipelines side-by-side.
7. **Pre-Training for Both Unfamiliar API / Library Mechanisms AND Low-Level Formats (Mayer's Pre-Training Principle & Hermans' LTM Syntax Support):**
   - Replace repetitive property mappings or unchanged fields with `...` so the reader immediately spots the exact transformation, **but always keep the enclosing function, method, class, or component signature** so inner logic or options never float in mid-air without their parent container.
   - **Pre-Decode Unfamiliar APIs, Library Mechanisms, Callbacks, Hooks, or Configuration Options Before the Code Block:** Never assume the reader already knows how a third-party library method, framework hook, event callback, middleware, or configuration option works. Whenever a Section 3 step uses or implements such a mechanism:
     1. **In the step's opening transition (right above the code block):** Introduce each key mechanism with a bite-sized bullet stating **(a) what it controls or does**, **(b) the exact moment it runs** (e.g., on startup, before each request, or on every input event before state updates), **(c) what its incoming parameters or fields represent** (e.g., candidate state if the action succeeds vs. current committed state), and **(d) what its return value or setting causes** (e.g., returning `true`/`false` to allow or reject the operation).
     2. **Inside the code snippet's inline comments:** Explain any **default/fallback resolution chains (`??`, `||`, `coalesce`) or multi-source lookups** so the reader knows why the code checks source A before falling back to source B (e.g., respecting a caller's explicit override before applying the default rule, or supporting an option passed in two different shapes).
   - **Syntax Anatomy Legend Before Unfamiliar Low-Level Formats:** Whenever a `Before -> After` snippet, code block, or code comment includes unfamiliar format tokens, protocol commands, graphics/bytecode operators, regex patterns, or DSL syntax, **ALWAYS place a clear Anatomy Legend comment (`< 76` chars per line, spanning as many comment lines as needed) at the very top of that snippet** decoding every token in plain words so the reader never has to guess unfamiliar syntax. Never put raw, undecoded protocol commands inside a comment:
     - ❌ *Bad (Unexplained tokens):*
       `CMD ... 28.8 14.5 POS (ItemA) DRAW END`
     - ✅ *Good (With Anatomy Legend at the top, `< 76` chars per line):*
       `// Anatomy: CMD..END (block) | 28.8 (X) | 14.5 (Y) | (ItemA) DRAW (text)`
       `CMD ... 28.8 14.5 POS (ItemA) DRAW END`
8. **Chronological Story Pipeline (`Step 1 -> Step 2 -> ...`):**
   - Order the steps chronologically along the actual data or execution flow and title each step with the practical technical question that step resolves.

## Cross-Surface CLI & GUI Rendering Discipline

Because this skill runs across both 80-column Terminal CLI/TUI tools (e.g., OpenCode TUI, Claude Code CLI) and narrow GUI IDE chat sidebars (~400px wide in Cursor, VS Code), strictly enforce these 4 layout rules:

1. **76-Character Width Cap Inside Code Blocks & ASCII Diagrams (Wrap Long Comments & Multi-Part Code Lines Cleanly):**
   - Both CLI terminals (80 columns) and IDE chat sidebars wrap or clip long monospace lines, which destroys the alignment of ASCII pointer arrows (`^` and `|<--->|`) and forces horizontal scrolling on code blocks.
   - Keep every individual line inside ASCII diagrams, inline explanatory code comments, and multi-condition code expressions **under 76 characters** (wrapping long `||` / `&&` chains or string concatenations across lines where syntax allows). When an inline comment or Syntax Anatomy Legend needs more words (especially in wordier languages like Vietnamese), wrap it cleanly across **as many consecutive `//` comment lines as needed** above the code statement—never cram or truncate the explanation to fit on 1 or 2 lines.
2. **Vertical Case Walkthroughs Over Narrow Multi-Column Tables & Safe Backtick Escaping:**
   - Avoid multi-column Markdown tables when tracing code with composite keys, method calls, or multi-word explanations: in 80-column CLI terminals and narrow IDE sidebars, 4-column tables wrap into jagged grids, split long identifiers mid-word, and force choppy telegraphic phrases. Use **Vertical Case / Iteration Walkthroughs** (`*Input:*`, `*How the code checks it:*`, `*Result:*`) instead.
   - **Never wrap an expression that already contains backticks (such as a JS template literal `` `${a}_${b}` ``) inside single inline backticks `` `...` ``** (including in `Verified` breakpoint invariants): in CommonMark/GFM, the inner backtick closes the code span early and causes underscores (`_..._`) to render as broken italics. Refer to the expression by its numbered Subgoal Comment label (`Branch 2a`, `Step // 4.`), rewrite string prefix checks with `+` concatenation (`k.startsWith(groupId + '_')`), wrap it in **double backticks with spaces** (```` `` `${a}_${b}` `` ````), or place it in a fenced code block.
3. **Always Include `filename:line` in Visible Link Text (Never Wrap Markdown Links in Outer Backticks):**
   - Many CLI terminals do not reveal hidden link URLs, while GUI IDEs support clickable links. Always put `filename:line` directly inside the visible label with backticks **inside** the brackets (e.g., `` [`OrderService.ts:142`](path/to/OrderService.ts#L142) ``)—**never wrap the entire `[label](url)` link inside outer backticks** (`` `[OrderService.ts:142](...)` ``), which disables the clickable link and prints raw URL syntax on screen. Link a file or symbol only on its **first appearance** in a section.
4. **Pure Portable Markdown Only (Zero HTML Tags or Mermaid Blocks):**
   - Never use raw HTML tags (`<br>`, `<details>`, `<summary>`, `<sub>`) or `mermaid` diagram blocks, which render as broken raw text in CLI/TUI tools. Rely strictly on standard Markdown and `< 76-char` monospace ASCII diagrams.

## Turn-1 Output Contract (Mode A — Sections 1–5)

Localize the section titles and bullet labels below into the user's language (single-language labels only, zero decorative emojis):

### 1. Big Picture (Context-Adaptive — 100% Plain-Language Macro Story)
Explain the causal chain at the **Macro / System behavior level** using **100% plain-language domain concepts**—never mention file names, function names, or local variable/property names in the 3 prose bullets below (leave all code symbols for Sections 2 and 3). Always start directly with the 4 bullets below (only prepend a `Change Map` if the commit mixes unrelated features):
- **For Bug Fixes / Performance Fixes:**
  - **Symptom:** Describe the **concrete scene the user actually sees on screen** using specific sample names/times—never use compressed abstract noun phrases (like *"loses overlapping slots"* or *"drops subsequent items"*). If a bug causes 2 symptoms on 2 different screens/features, split them into **2 separate sub-bullets** (never cram both into one sentence with *"simultaneously / and"*):
    - *Example:* Instead of *"The search drops subsequent items and the cart loses overlapping entries"*, split into two concrete screen behaviors: (1) *In Search results:* the filter reads only Category A and skips all items in Category B; (2) *On the Checkout screen:* if two orders share item number `#1`, the screen displays only 1 item and the other disappears.
  - **Root cause:** Open with a brief everyday analogy, then explain the complete macro causal chain in **bite-sized indented sub-bullets** (each starting with a short `*italic:*` lead-in phrase and expressing 1 single causal step in 1–2 short sentences ending with a period `.`—**never chain clauses with `->` arrows or pack multiple steps into one big paragraph**, and add as many sub-bullets as needed).
  - **Fix:** State the high-level conceptual solution in everyday spoken words without listing file, function, or variable names.
  - **Concrete example (`Before -> After`):** A visual snippet (`< 76` chars per line, using `❌` and `✅`) that **clearly shows the collision, overwrite, or transformation happening** in `Before` and how data is kept intact in `After` across concrete items with vivid sample names (never write a single abstract variable assignment). **If the example contains any domain-specific format tokens, protocol commands, regex syntax, or DSL operators, place a Syntax Anatomy Legend comment (`< 76` chars per line, spanning as many comment lines as needed) at the very top of the snippet decoding each token in plain words:**
    ```ts
    // Before: Both orders use item "1", so Order B overwrites Order A
    items["1"] = "Laptop (Order A)";
    items["1"] = "Mouse (Order B)"; // ❌ Wipes out Laptop!

    // After: Prefixing order ID keeps both items in separate slots
    items["OrderA_1"] = "Laptop (Order A)";
    items["OrderB_1"] = "Mouse (Order B)"; // ✅ Both kept!
    ```
- **For New Features / Refactors / Existing Module Walkthroughs:**
  - **Goal:** State the capability or architectural outcome being built in plain words.
  - **Key design challenge:** Open with a brief everyday analogy if helpful, then use a **Contrastive Explanation** broken into **bite-sized indented sub-bullets** (each starting with a short `*italic:*` lead-in phrase and expressing 1 single causal step or constraint in 1–2 short sentences ending with a period `.`—**never chain clauses with `->` arrows or pack multiple steps into a dense prose paragraph**) to explain why the obvious/naive approach falls short.
  - **Core approach:** Summarize how the chosen design solves that challenge in plain words (zero file, function, or variable names).
  - **Concrete example (`Input -> Output`):** A noise-free visual snippet (`< 76` chars per line) with vivid sample values illustrating what enters and exits the system (starting with a **Syntax Anatomy Legend comment** at the top if any unfamiliar format/protocol/DSL tokens appear).

### 2. Main Execution Flow (Anchored to Real-World User / Business or Runtime System Triggers — Max 1 Primary Mechanism Per Step)
- A numbered list of plain-language steps tracing the path data takes from entry to output, naming **at most 1 primary function, method, hook, callback, or configuration option per step** in backticks (with `` [`filename:line`](path#Lline) `` on first mention, never wrapped in outer backticks, and never disguised as a vague translated noun like *"the condition checker"*) so the reader sees the exact identifier and what it decides without being overwhelmed by 5–6 names at once (or tracing the **Data Transformation Phases / Constraint Layers** for declarative SQL, Schema, Config, and CSS/UI). If twin pipelines run the same logic in two places (e.g., Client vs. Server), narrate **one primary path** and mention the twin briefly in parentheses *(or its server counterpart [`ServerFile.ts:line`](path#Lline))*. Each step opens with the **real-world user action or business scenario** that triggers it (or, for pure infrastructure/plumbing/low-level utilities without direct user interaction, the **runtime or caller system event** that invokes it).

### 3. Core Code Steps (Scaled to the Actual Number of Engineering Decisions — Micro / Code Level)
Divide into steps corresponding to the **actual number of distinct engineering decisions or guards in the execution flow** (`#### Step 1: <Practical technical question?>`, `#### Step 2: ...`—filter out peripheral boilerplate, but never omit an important logic step just to fit an arbitrary step limit):
- **Plain-language transition opening & Unfamiliar API / Mechanism Contract (Pre-Training before the code block):**
  - Connect this step to the previous one (including `` [`filename:line`](path#Lline) `` in the visible link label) and state the **Business Rule / Safety Rule** this step protects in plain everyday words (and, if another module in the commit treats the same entity differently, why the business domain requires that difference).
