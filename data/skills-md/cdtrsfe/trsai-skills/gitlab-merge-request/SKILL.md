# GitLab Merge Request

## 核心目标

把当前项目分支推送到远程，并创建 GitLab Merge Request。默认行为是：源分支为当前 Git 分支，目标分支为 `master`，分配人为 `pu.yuchun`。创建成功后，把 MR 地址明确告诉用户，并说明推送成功。

提 MR 永远只处理已有 commit。未提交改动只提示，不因此中断流程；源分支与目标分支的提交差异及能否创建 MR 交给 GitLab 判断。

这是 TRS 团队的 GitLab MR 流程。除非用户明确说项目使用其他代码托管平台，否则不要提非 GitLab 平台、非 GitLab 合并流程或非 GitLab CLI。

## 触发场景

用户出现以下意图时使用本技能：

- “提交 MR 到 master”
- “提个 MR”
- “创建 merge request”
- “发起合并请求”
- “把当前分支提交到 master”
- “推送并提交 MR”

如果用户只是要求 `commit`、普通 `push`、按 Jira 信息提交或收尾，优先使用 `jira-git-workflow`；只有用户明确要创建 MR 时，才使用本技能。

单纯“提交 MR”属于已有 commit 的发布操作，不触发 `trs-code-review` 或开发完成验收流程。除非用户另外明确要求审查或验证，否则不运行 `pnpm check`、build、测试或浏览器验证；确认推送和 MR 操作结果即可。

## 默认参数

按以下优先级确定参数：

- 源分支：用户明确指定的源分支；否则使用当前 Git 分支。
- 目标分支：用户明确指定的目标分支；否则使用 `master`，直接填入确认信息，不单独询问“合入哪个分支”。
- 分配人：用户指定时按“分配人解析”处理；否则使用已知用户名 `pu.yuchun`，不额外查询。确认信息展示显示名和真实 `username`（无显示名时仅展示用户名），传给 `--assignee` 的值必须是真实 `username`。
- remote：优先使用当前分支 upstream 对应 remote；没有 upstream 时默认 `origin`。
- MR 标题：优先使用用户明确给出的标题；否则根据最近一次 commit 信息、分支名或 Jira 上下文生成简洁标题。无法判断时先问用户。
- MR 描述（description）：由 AI 根据本次已有 commit 的实际改动分析生成，展示给用户确认后作为 MR 正文提交；用户提出的修改应同步到描述中。

注意：用户说“提交 MR 到 master”时，`master` 是目标分支，不是源分支。

## 第一响应与耗时控制

用户要求“提交 MR”后，第一条可见回复必须简短说明将要做的事情和边界，不要先沉默执行大量检查。建议话术：

```text
我先确认当前分支、工作区状态和 upstream/remote。此次 MR 只处理已有 commit；如有未提交改动，会提示并继续，提交差异交给 GitLab 判断。
```

前置检查保持轻量，只做能直接判断 MR 是否可创建的 Git/GitLab 信息。不要在创建 MR 前自动触发完整代码审查、build、测试、全仓搜索、依赖安装、浏览器验证或非必要的远程同步。

如果因为推送、网络或认证导致等待超过约 30 秒，应先告诉用户当前卡在哪一步、已经看到什么、下一步要等什么；不要等全部命令结束后才汇报。

## 执行前检查

创建 MR 前只检查并向用户说明关键上下文：

1. 当前仓库路径和当前分支。
2. `git status --short` 工作区状态，仅用于提示未提交内容，不作为继续流程的门槛。
3. 当前分支 upstream、remote 和 GitLab 项目地址。
4. 将使用的源分支、目标分支、分配人、MR 标题和 MR 描述。
5. 将执行的推送和创建 MR 命令。

推荐最小命令集合：

```bash
git branch --show-current
git status --short
git remote -v
git rev-parse --abbrev-ref --symbolic-full-name @{u}
```

不在本地检查源分支相对目标分支的 commit，不为比较差异或更新目标分支引用执行 `git fetch`。提交差异及能否创建 MR 由 GitLab 判断，按其返回结果说明情况。需要生成标题时可读取源分支最近一次 commit 信息，无需比较目标分支。不要因为要创建 MR 就扫描整个仓库或检查无关 CLI。

如果工作区有未提交改动，简短提示“当前有未提交改动，本次 MR 只处理已有 commit”，然后继续流程，不再询问是否只推已有 commit 或先提交。不要自动提交、暂存、还原、删除或 stash 这些改动。

如果当前分支是 `master`，或源分支与目标分支相同，必须停止并提醒用户切换或指定正确源分支。

## 分配人解析

在展示完整 MR 信息供用户确认之前完成解析，只在用户提供的身份信息需要解析时查询：

1. 用户明确提供准确用户名、个人主页链接，或当前会话已在同一 GitLab 实例核实过该账号时，直接使用真实用户名。不能仅凭输入是英文就认定它是准确用户名。
2. 用户提供中文姓名、显示名或模糊英文名（如“赵清”“zhaoqing”）时，通过 `glab api` 查询当前仓库对应 GitLab 实例，优先搜索当前项目成员（含继承成员）。按真实用户名精确匹配、显示名精确匹配、英文规范化匹配的顺序解析；英文规范化只用于辅助匹配，可忽略大小写、点号、下划线和连字符，最终始终使用接口返回的原始用户名。
3. 搜索接口未必会忽略标点，不能因为搜索 `zhaoqing` 为空就断言没有 `zhao.qing`。必要时缩短检索词获取候选，再在结果中规范化匹配；处理分页，未读完整个相关结果集时不得宣称唯一匹配。
4. 在当前匹配层级只有一个可靠候选时，将其作为分配人放进完整确认信息，如“赵清（`zhao.qing`）”，不再单独问一次。多个同等候选时，列出显示名和用户名让用户选择；只有弱相似结果时也先让用户选择，不按相似度最高直接分配。中文姓名按实际显示名匹配，不自行把拼音猜测当作已核实账号。
5. 项目成员中没有可靠匹配时，再按需搜索当前 GitLab 实例的用户。仍未找到时，请用户补充真实用户名或个人主页链接。实例搜索找到账号不代表它一定可被分配到该项目；若 GitLab 明确拒绝分配，按返回原因说明。
6. 区分“未找到匹配账号”“查询认证失败”“查询权限不足”，不得把查询失败当作空结果，也不得把空结果直接说成账号不存在或不在项目中。查询失败后按认证和权限规则处理，不重复尝试创建 MR 来猜账号。

查询使用 `glab api` 的只读请求，明确绑定当前仓库的 GitLab host 和项目；检索参数安全编码，不把用户输入直接拼入 shell。解析结果只在同一实例内复用，避免跨服务器混用用户名或用户 ID。

## 生成描述与用户确认

前置检查通过且分配人已解析后，先准备完整 MR 信息，再交给用户确认：

1. 根据本次任务上下文及对应的已有 commit 分析实际改动，生成中文 description。必要时使用 `git show <commit>` 读取相关已提交内容；不读取未提交改动来充当 MR 内容，也不恢复源分支与目标分支的本地比较或 fetch。
2. 描述应说明本次解决的问题、主要修改和影响范围；只写有依据的验证结果。按改动规模组织简洁段落或列表，不只是复制最近一次 commit 标题，不编造功能、验证结果或风险。
3. 如果上下文不足以确定本次涉及哪些 commit，先询问本次提交范围，避免把其他历史改动混入描述。
4. 一次展示 source、target、person（分配人）、title、description，以及将执行的推送和创建命令。用户确认这份信息后，再推送分支并创建 MR。
5. 用户提出修改时，更新相应字段并重新展示确认；如果用户已经明确确认了同一份完整信息，无需重复询问。

前置检查未通过时，说明具体问题，待问题解决后只复查相关失败项。推送时才出现的非快进冲突或认证错误，在实际失败后按对应规则处理，不为预判这些错误增加远程同步。

## 推送分支

创建 MR 前必须确保源分支已经推送到远程：

- 当前分支已有 upstream：执行 `git push`。
- 当前分支没有 upstream：执行 `git push -u <remote> <源分支>`。
- 用户指定了非当前源分支时，先确认该分支在本地或远程存在；不存在则停止说明。

如果 `git push` 因远程分支有本地没有的新提交而失败，例如 `fetch first`、`non-fast-forward`，不要自动改写历史。说明失败原因，并询问用户是否执行 `git pull --rebase` 或其他同步方式。

## 创建 MR

固定使用 `glab` 创建和查询 MR；分配人解析允许使用 `glab api` 进行只读查询。不切换项目脚本、浏览器或绕过 `glab` 直接调用 GitLab API。

直接执行流程所需的 `glab` 命令，不每次预先运行版本检查、`glab auth status` 或登录流程。已有认证配置复用，权限由 GitLab 随请求校验。

- 命令不存在：提示安装 `glab`（macOS 可用 `brew install glab`），配置完成后继续。
- 未登录、认证失效：提示运行 `glab auth login --hostname <GitLab域名>`，不要要求用户在对话里明文粘贴 token。
- 权限不足：说明失败操作及所需项目权限，由用户处理账号或 token 权限，不反复登录或重试。

不要检查或建议安装任何非 GitLab CLI；它们不能作为本技能的 MR 创建路径。

`glab` 命令示例：

```bash
glab mr create --source-branch <源分支> --target-branch <目标分支> --assignee <分配人> --title "<MR标题>" --description "<已确认的MR描述>"
```

description 必须使用用户已确认的正文，并保留实际换行。执行时使用安全的参数传递方式，避免描述中的反引号、美元符号等被 shell 解释执行。

## 已有 MR 处理

创建前尽量检查是否已存在相同源分支到目标分支的 open MR：

- 如果已存在，直接给出已有 MR 地址，并说明没有重复创建。
- 如果工具无法可靠检查，创建失败且提示重复 MR 时，转为查询或让用户打开失败信息里的地址。

## 成功反馈

成功后必须告诉用户：

- 分支已推送成功。
- MR 已创建成功。
- MR 地址。
- 源分支、目标分支和分配人。

示例：

```text
推送成功，MR 已创建：

- 源分支：feature/demo
- 目标分支：master
- 分配人：pu.yuchun
- 地址：https://gitlab.example.com/group/project/-/merge_requests/123
```

## 安全边界

- 展示完整 MR 信息并得到用户明确确认后，才能推送分支和创建 MR；用户已确认同一份信息时不重复确认。
- 不得在本技能中自动 `git add`、`git commit`、`git reset`、`git checkout --` 或删除文件。
- 不得把未提交改动偷偷带入 MR 流程；只能推送已经存在的 commit。
- 不得默认 force push。除非用户明确要求并理解影响，否则不要执行 `--force` 或 `--force-with-lease`。
- 如果权限、认证、分支保护或 token 缺失导致失败，停止并说明需要用户处理的具体信息。
- 如果无法判断 GitLab 项目地址或 MR 创建工具不可用，先说明缺少的依赖或配置，不要假装已创建。
- 不得把 GitLab MR 说成其他平台的合并流程；最终反馈和中间进度统一使用“GitLab / MR / 合并请求”。

- “源分支 feature/a，目标分支 release/1.2，提交一个 MR。”
