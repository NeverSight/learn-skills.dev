# QBS · 先找书、读书，再做 Skill

**用户不必先读过这个领域的书。负责找书、取得正文、阅读和提炼的是执行 QBS 的 AI。**

让书里的一个方法先帮上眼前的忙，再给用户一个愿意回到原书的入口。阅读热情是否增加需要真实反馈，不预先宣称有效。

QBS 在本项目中表示 Question → Book → Skill。默认执行下面这条完整流程，而不是直接把聊天内容整理成一个文件：

**实际问题 → 找合适的书 → 定位相关章节 → 取得并读完正文 → 提取可操作的方法 → 制作 Skill → 用任务检验。**

用户说“帮我用 QBS 做一个 Skill”，就主动推进这条流程。选书建议、目录、下载成功和读完正文是不同进展；不能在找到书名后就跳到生成 Skill。

## 1. 从问题确定要学什么

把用户的处境写成一个具体任务：想完成什么、现在卡在哪里、什么结果才算有用。已有信息足够就继续，只追问会影响选书或交付的缺项。

例如：“想把内容排期交给运营，但不知道如何分工和验收。”据此寻找关于委派、生产流程、规划与反馈的方法，不先凭模型经验写一整套制度，再去找书名背书。

用户已指定书时保留其选择；已有电子书或章节文件时，直接核对版本、目录和正文，不重复让用户找书。

## 2. 主动找书，并选出本次要读的一本

未指定书时，使用当前可用的搜索或书籍工具寻找少量候选，通常比较两三本即可。核对作者、出版社或权威书目及目录，不只引用模型记忆或搜索摘要。

选书时回答三个问题：

- 哪个章节可能解决用户的具体问题，为什么？
- 这本书是否提供可以转成判断和行动的方法，而不只是概念介绍？
- 当前能否取得足够的相关正文，实际入口在哪里？

向用户简要说明首选书和选读章节后继续找正文，不默认等用户再发一次“继续”。不能只因为一本书容易下载就忽略相关性。书龄可作为筛选条件，但不自动等于适用或可靠；用户明确要求经典或特定年代时保留该偏好。

## 3. 取得正文，并确认确实可读

按当前环境使用合适的渠道：用户已提供的文件或有权限的书库、出版社或作者公开章节、开放教材、正规平台试读及已授权的阅读入口。搜索与阅读应实际调用可用工具；没有工具或访问失败就如实说明，不假装已经查过。

对找到的材料检查书名、作者、版本、目录与正文。根据格式读取：PDF检查文本和必要图表，EPUB按章节解析，网页或阅读器读取实际正文。扫描件需要OCR或逐页阅读；只提取出目录、图片读不清或试读中途截断时，不能算读完。

一个入口只有序言或残缺试读时，继续检查其他可信入口。合理可用的渠道仍拿不到正文，再明确告诉用户缺哪本书、哪几章，以及需要的文件、访问或购买决定。不得绕过访问限制；没有购买授权就不下单。

此时可以交选书结果与阅读计划，保留已有的场景草案；**不能把资料缺口改写成“读序言也足够”，或把草案当作完成的书籍方法 Skill。** 用户指定的书读不到时，列出可选替代及理由，不悄悄换书。

## 4. 完整读相关章节，留下阅读记录

至少完整读取一个与任务直接相关的正文章节；章节较长就分段读，确认从章首到章末均已覆盖。涉及其他章节的方法继续补读。一个章节不是全书，阅读范围必须与能力范围相符。

阅读时核对作者的推理、案例、适用条件、例外和相关图表。不要只搜到几句符合预想的句子，就宣称掌握了章节方法。

在子 Skill 的 `references/source-notes.md` 中留下简洁记录：

| 记录 | 内容 |
|---|---|
| 书与版本 | 书名、作者、出版社、版本或ISBN |
| 实际入口 | 公开链接，或私有材料的名称；公开包不泄露私人路径 |
| 已读范围 | 章节名、实际页码或小节位置、阅读日期 |
| 完整性 | 是否读到章末；缺页、截断、未读图表和其他未读部分 |
| 与任务的关系 | 这次用到哪些方法，哪些能力尚无正文支持 |

网页没有页码时用章节、小节及定位链接，不编页码。序言、目录和书评只作背景或定位线索。阅读记录由实际访问结果填写，不能在读之前预填“已完成”。

## 5. 把书中方法变成任务规则

读完后再提炼会改变行动的规则，按 [子 Skill 合约](references/child-contract.md) 记录：

**原文位置 → 作者的方法 → 适用条件与例外 → 本任务如何执行 → 怎样验收。**

例如，只有读到相关正文并核对后，才能把某种生产流程方法用于内容排期。不能把模型自己补出的截止时间字段、提醒频次或验收表，全部归给作者。

明确区分三种内容：来源概括、根据来源的推断、为本场景添加的设计。找不到正文依据的规则保留其场景设计身份；不同材料有分歧时保留条件，不强行合成万能规则。

## 6. 制作 Skill，并实际跑一个任务

将核对后的方法写成独立子 Skill：触发场景、必要输入、判断步骤、产物、验收与不适用情形。长来源记录和模板放进自身的 `references/`，不能依赖本次聊天才能使用。

同时制作带真实封面的书籍说明，注明作者、版本、已读章节及未覆盖部分。封面未找到就标注缺口，不仿造官方封面。书籍正文不随公开仓库分发，私人团队信息留在用户本地。

按 [验证方法](references/evaluation.md) 用新任务实际执行，保留输入和产物；至少检查一条从正文提取的方法是否正确用到任务里，以及不适用时是否停止套用。运行失败就改规则再测，不能只交一个文件或只跑安装检查。

需要证明收益时，再比较直接提问、附上同范围已读正文、使用 Skill。给各组相同的任务与追问机会；没有优势就照实记录。一次模拟不代表长期稳定或真实团队省时。

## 7. 从用过的方法，留一个回到书里的入口

先交付任务结果，再用两三句话连回本次实际用到的方法：它改变了哪个判断、出自哪一章哪一节，并附可访问的原文链接或用户文件中的位置。挑一个与刚才结果有关、值得继续追问的问题，让用户按兴趣接着读。不要追加必读书单或阅读打卡，也不要在结果还未验证时写“这本书已经帮你解决了”。

## 交付时让用户看得见“找过、读过、用过”

先给用户本次任务的实际产物和 Skill 入口，再简要交代：选了什么书及原因、完整读了哪些章节、哪些规则来自哪些位置、测试得到了什么结果、还缺什么。不要只给书单、抽象总结或一串“检查通过”。

仓库维护者按合约更新 [书籍索引](references/library.json)，运行本仓库已有校验与相关测试；在其他环境按实际能力检查，不虚构工具执行成功。公开发布和真实任务系统写入仍以用户授权范围为准。

## 已有 Skill 的使用支路

只有用户要直接处理一次任务、明确调用已有子 Skill，或已有阅读材料确实覆盖本次目标时，才复用已完成的部分。使用 [书籍索引](references/library.json) 核对来源范围，再读取实际可用的子 Skill；索引不是正文，也不能证明子 Skill 已加载。

用户要求新做或补强书籍 Skill 时，回到上面的找书与阅读流程，不能拿已有模板替代它。当前 `high-output-management` 仅是序言启发的草案，尚未满足完整章节阅读要求。
