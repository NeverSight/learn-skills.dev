# 项目简历与面试

## 概述

将现有项目转化为两份配套的职业文档输出：

- **`01-简历精简版.md`** — 可直接复制到简历。含项目简介 + 严格 1 行的条目。
- **`02-面试专项详情版.md`** — 面试问答素材。每条对应简历版的一条条目，按「背景→方案→成果」展开。

两个文件的关系：简历版条目是面试版各章节的摘要目录，面试版是简历版的深度展开。

核心原则：先看证据再动笔。检查源代码、文档、脚本、包元数据、路由、状态管理、服务、组件和模拟数据后再写。不虚构技术栈、优化指标、性能数据或项目所有权。

## 工作流程

1. 检查项目上下文后开始撰写。
2. 明确项目的真实定位、技术栈、模块划分和用户价值。
3. 从实际代码中提取高频面试话题。
4. 分别撰写两个独立文件，不合并为一个文件。
5. 任何量化指标标注为估算值，不编造不存在的精度。
6. 确认输出路径，简要总结改动内容。

## 证据收集

检查以下领域（如有）：

- `package.json`、README、`AGENTS.md`、项目文档
- 路由和权限文件
- 状态管理 / 会话生命周期
- API 请求封装和自动生成的 API 模块
- Agent/AI 对话模块、WebSocket/SSE 传输、模拟数据、回放脚本
- 核心业务页面和可复用组件
- 构建、lint、模拟数据、提交、自动化脚本

优先使用 codegraph/explore/search 工具发现源码。对独立调研领域（如 AI/Agent、前端架构、后端/API 集成、可视化、工程配置）可派发子 Agent 并行处理。

## 输出文件

用户指定输出目录后，创建以项目名称命名的子文件夹，写入：

- `01-简历精简版.md` — 可直接复制到简历，每条条目严格 1 行，含项目简介行
- `02-面试专项详情版.md` — 面试问答素材，按「背景→方案→成果」结构展开

两个文件严格对应：简历版的每一条条目对应详情版的一个章节。

如果用户未提供输出目录，问一句目标路径即可。

## 简历版规则（可直接写入简历）

### 整体结构

```
# {项目名称}

**项目简介：** {从业务价值和技术规模角度描述项目，2-3 句。突出核心能力、服务规模或关键价值点。}
**技术栈：** {关键技术栈，用 + 连接}

### 核心贡献

1. {条目}
2. {条目}
...
```

### 条目规则

- **严格 1 行**（40-65 字），禁止跨行。
- **强力动词开头**：优先「打造/构建/设计/搭建/落地/建立/主导/优化/抽象」，杜绝「封装/设计并实现了/负责了/参与了/实现了」。
- **一个条目只陈述一个核心成果**，一个主谓结构到底。不要用「同时/此外/支持」挂载多个功能。
- **每句要有「做了什么 + 方案含金量 + 业务价值」**，让对方读完后觉得「这人做了件有挑战的事」。
- **不说实现细节**：比如不说"基于工厂模式抽象 ImageProvider 接口"，只说"工厂模式统一多家上游 API"。
- **不出现具体类名/组件名/颜色值/配置名**：比如不说 `TsResourceCrudPage`、不说"深蓝顶部导航与暗色侧边栏"，只说"通用 CRUD 组件"、"两套预设主题"。

对比示例：

> ✅ 构建多供应商 AI 图片生成平台，工厂模式统一多家上游 API，支撑全站 AI 生图能力。
>
> ✅ 搭建基于 BullMQ 的异步任务调度体系，信号量并发控制保障 API 限频零故障。
>
> ❌ 封装多供应商 AI 图片服务，工厂模式统一 4 家上游 API，新供应商接入成本降低约 60%。（"封装"太弱、"4家"太具体）
>
> ❌ 设计并实现了多供应商 AI 图片生成服务：基于工厂模式抽象 ImageProvider 接口，统一封装 mytokens 和 qiuqiutoken 两家上游 API，支持同步/异步双模式切换；生成结果通过 GitHubStorageService 自动上传至 GitHub 仓库并经由 jsDelivr CDN 分发，同时用 sharp 生成 160×160 缩略图，估算同类供应商接入成本降低约 60%。（"设计并实现了" + 实现细节 + 类名）

### 措辞风格——简历包装版

目标：**技术正确 + 听起来厉害**。同一个人、同一个项目，换种说法就能从「做了个功能」变成「搭建了一套体系」。

| 不够牛逼 → | 听起来厉害 → |
|-----------|------------|
| 封装/实现某服务 | 构建/搭建某平台/体系 |
| 支持某功能 | 支撑某业务能力 |
| 实现了某机制 | 落地某方案/机制 |
| 用某技术解决 | 基于某技术打造 |
| 降低成本 xx% | 提升接入效率 / 保障生产稳定性 |

核心心法：

- **用「平台/体系/方案/机制/能力」替代「服务/功能/模块」**，同一件事听起来高一个量级。
- **体现体量感**：适当使用「多家/全站/日均/大规模/零故障」等词，让读者感受到项目规模。
- **ownership 感**：每条暗示「我主导/设计/搭建了」，而非「我参与了/配合了」。
- **技术名词是加分项**：NestJS、BullMQ、JWT 保留，它们是技术深度的佐证，不解释。
- **不虚构**：只是换说法，不编造不存在的数据或能力。（"了解深后其实就是换一种说法"）

### 与详情版的对应关系

- 每条简历条目对应详情版的一个章节。
- 详情版的「简历对应行：」字段会原文引用条目内容。

## 面试详情版规则

每个话题使用以下固定结构：

```markdown
## N. 话题标题

- **简历对应行：** {引用简历版对应条目的原文}

**① 原有问题：**  
描述实际业务痛点、复杂度、风险或工程问题。

**② 实现方案：**  
说明具体实现，包含文件名/模块名和技术选型理由。

**③ 落地成果：**  
说明实际收益。无量化数据时明确标注为估算。
```

推荐的话题类别：

- Agent 流式协议与 UI 集成
- Agent 上下文/会话管理
- Agent 结果到业务 UI/数据可视化
- 复杂前端状态管理与异步取消
- 可视化/地图/图表/Canvas 渲染（如有）
- 动态路由与权限
- CRUD/资源抽象与数据规范化
- 请求封装与认证处理
- 状态管理/会话生命周期与清理
- 主题/布局/组件系统
- 工程化、模拟数据、回放、lint、构建、调试工作流

## 量化指标策略

如果仓库中没有可测量的性能数据，在文档中明确说明。

允许的估算措辞：

- “估算：同类页面重复代码减少约 50%-70%。”
- “估算：流式协议处理重复代码减少约 60%。”
- “主要提升调试可复现性和交互可观察性。”

禁止的无依据措辞：

- “首屏提升 xx%”（无实测数据）
- “FPS 提升 xx%”（无采样数据）
- “包体减少 xx%”（无构建对比）
- “QPS/并发/服务稳定性提升”（无后端数据支撑）

## 最终检查

每次回复前，确认：

- 两个独立文件已生成
- 简历版符合规则：项目简介行 + 严格 1 行条目 + 精简措辞
- 简历版条目不是讲解/介绍/说明文风格
- 面试版采用了三段式结构（问题→方案→成果）
- 所有估算指标已标注
- 如仅修改了文档文件，说明未运行构建/测试
