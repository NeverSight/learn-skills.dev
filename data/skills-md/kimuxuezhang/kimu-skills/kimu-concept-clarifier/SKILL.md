# Kimu 概念澄清

把模糊词语还原成当前问题中可观察、可比较、可使用的定义。目标不是寻找唯一字典答案，而是让用户知道自己究竟在判断什么。

用户可以输入：

```text
Kimu 概念澄清：{概念或原句}
Kimu 概念澄清：“产品有价值”到底应该怎么判断？
Kimu 概念澄清：做“个人品牌”和做“流量账号”有什么区别？
```

## 先锁定语境

优先使用用户提供的原句、争议双方和现实决策。若一个词离开语境会产生多种合理解释，只问一个最能区分用法的问题，例如「你是在描述事实，还是在评价好坏？」

已有足够上下文时直接分析，不先做问卷。

商业、内容或教育语境中，还要识别说话者、对象和业务阶段。例如同一个“效果”，可能分别指用户完成任务、客户感受满意、服务按时交付或宣传带来成交；不能默认它们是一回事。

## 澄清框架

### 1. 找出这个词正在完成什么任务

判断它在句子里主要用于：

- 指认对象；
- 描述机制；
- 划分类别；
- 评价好坏；
- 争取立场或推动行动。

同一个词同时承担多项任务时，先拆开再讨论。

### 2. 列出候选含义

最多保留三个与当前语境真正相关的含义。每个含义都写出：

- 它包含什么；
- 它排除什么；
- 用什么证据判断；
- 采用它会改变哪项结论。

不要用更多抽象词替换原来的抽象词。

### 3. 做边界测试

为主要定义构造三类例子：

- 明确属于；
- 明确不属于；
- 容易争议的边界情况。

如果定义无法稳定区分这三类，说明它仍不可用，需要缩小范围或补充判断条件。

### 4. 定位争议类型

区分问题究竟来自哪里：

- 双方使用了不同定义；
- 定义一致，但事实证据不同；
- 事实一致，但价值排序不同；
- 把相关性说成因果；
- 用群体标签代替对具体行为的判断。

不要把所有分歧都归因于“概念不清”。

### 5. 给出工作定义

工作定义必须服务于当前任务，格式为：

```text
在这次讨论中，“{概念}”暂时指：{对象或行为}在{条件}下表现出{可观察标准}。
它不包括：{最容易混入的相邻概念}。
```

若没有足够证据选定一个定义，保留两个版本，并明确各自会导向什么不同判断。

### 6. 翻译成行动条件

如果用户澄清概念是为了做决策，再补充三项：

- 采用这个定义后，正在决定什么；
- 最先能观察到什么证据；
- 即使满足定义，也不能顺带推出什么结论。

不要为了显得实用而强行给方案。若问题真正缺的是事实、数据或业务诊断，应说明澄清概念只能解决哪一部分。

## 商业、内容与知识服务场景

遇到商业、内容创作、课程或专业服务中的概念，先判断它主要属于哪一层：

- **用户结果层**：用户是否真正使用、完成任务或产生可观察变化；
- **产品与交付层**：产品内容、服务动作、完成条件和责任边界；
- **内容与获客层**：曝光、有效注意、信任和合格线索；
- **成交与复购层**：购买行为、统计口径、时间窗口和下一产品关系；
- **品牌与信任层**：稳定定位、专业证据、识别度与选择理由。

只展开与用户原问题有关的层级。尤其注意以下常见混用：

- “产品价值”可能指使用价值、结果价值、服务体验或交易价值；
- “交付完成”不能只用内容已经发出、服务者已经讲完来代替；
- “个人品牌”不等同于流量、名气或频繁发布内容；
- “交付完成”不自动等于学生学会，更不自动等于产生结果；
- “私域”“转化率”“复购率”等运营词必须说明对象、分母和统计周期。

这些例子用于提醒检查维度，不是预设的标准答案。最终工作定义仍以用户的真实业务、受众、产品和决策为准。

## 输出格式

```markdown
## 当前语境
{原句和实际要解决的问题}

## 含义分叉
1. {含义 A}：判断标准...
2. {含义 B}：判断标准...

## 真正的争议
{定义、事实、因果或价值中的哪一层}

## 边界测试
- 属于：...
- 不属于：...
- 边界情况：...

## 本轮工作定义
{可直接用于后续讨论的定义}

## 对原问题的影响
{定义澄清后，哪些问题消失了，哪些仍需证据}

## 可执行判断（需要决策时）
{下一步观察什么，以及不能据此推出什么}
```

简单概念可以压缩，不为凑格式制造内容。

## 可靠性边界

- 专业术语、法律定义、技术标准和时效性概念应核对权威来源。
- 商业和运营术语经常没有唯一权威定义，应明确这是当前任务中的统计口径或工作定义，而不是普遍真理。
- 词源可以提供背景，但不能替代当代语境中的实际用法。
- 不把某位思想家的可能看法写成未经核实的直接引语。
- 不替用户偷偷加入价值判断；需要规范性定义时明确说明。

## 与其他模块的边界

- 核心任务是判断业务处于什么阶段、卡在哪里或下一步验证什么时，转入 `kimu-business-diagnosis`；
- 概念已经清楚，但缺真实案例或证据时，转入 `kimu-case-bank`；
- 只有用户需要澄清后的定义继续支持其他任务时，才把工作定义作为输入交给相应模块。

完成澄清后停止。只有用户带来新语境或新证据时，才重新调整工作定义。
