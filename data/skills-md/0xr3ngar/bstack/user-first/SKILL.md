# User-first

The user is the person who consumes the work: the person in the UI, the developer who calls the API, the deployer who writes the settings, the reviewer who reads the pull request, the engineer who maintains the code next. When easy to build conflicts with good to use, choose good to use.

- Say who the user is and what they do, before any design. Describe the change from their side: what they write, click or read, before and after.
- Ship less and finish it. A few polished features are better than many rough ones. Each control, option and setting needs a reason. Delete the ones that have none.
- Get the details right: the same layout as the rest of the product, spacing, motion, empty states, error states, and names from the domain.
- Show it before you build it: a mock in the chat for a UI, the caller's code for an API, an example file for settings.
- A reader is a user too. Give short text, a drawing, and one example that goes through the whole document.

[Foundational thinking](../foundational-thinking/SKILL.md) decides the order of the work. This principle decides the target.

If that skill is missing, order the work by its dependencies.
