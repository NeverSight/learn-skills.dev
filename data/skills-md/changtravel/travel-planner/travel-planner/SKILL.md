# 分阶段旅行规划

## 任务与完成态

帮助旅行者先发现自己真正想要的体验，再理解路线与价格取舍，最终确认可执行方案并按需制作路书。完整行为标准见 [可观察行为契约](references/behavior-contract.md)。

完整交付包括已确认的路线、按时段展开的每天安排、适用条件明确的费用预算与来源、关键预约和未定事项，以及用户需要时制作的旅行预算表或可阅读路书。旅行预算表用于呈现旅行者预计支出，不是旅行社销售报价。每个阶段都是有效停止点，不擅自跨越确认门槛。

## 先隐性分流

收到请求后自行判断，不让用户选择流程：

| 模式 | 可观察条件 | 动作 |
| --- | --- | --- |
| `direct_task` | 只修改已有行程、查一个票价／开放时间、解释单项信息 | 直接完成局部任务；不建新项目、不发问卷、不重启规划 |
| `light_exploration` | 本地或单一城市、1～2 日、没有航班住宿联动、没有复杂同行或高风险约束，且偏好尚不清 | 直接进入体验发现；首轮不发完整问卷 |
| `full_planning` | 跨城、多日、涉及航班或住宿、多人条件、预算联动、签证／健康／无障碍等高风险约束 | 建立状态，按当前决策渐进补齐条件；必要时提供预填问卷，不一次追问全部字段 |

无法确定复杂度时，先做不会浪费的体验发现和最少约束确认；一旦出现航班、住宿、同行或高风险联动，升级到 `full_planning`，保留已得到的偏好证据。

`full_planning` 的首次回复必须在体验候选之外启动可行性 intake：至少询问日期窗和当前最高风险约束，并说明会在进入路线报价前渐进补齐航班、住宿与预算。每轮只问 1～3 组会改变下一步的问题，不能只做体验候选，也不能一次发完整问卷。

## 三阶段流程

### 第一阶段：体验发现 `discovery`

读取 [需求与菜单](references/intake-and-menu.md)。

- 一次给 3～5 个差异明显、具体可想象的体验候选，说明各自“会怎么度过这段时间”，让用户直接说喜欢、拒绝或补充。
- 每轮更新候选的 `liked`、`disliked`、`unknown`；利用反馈生成下一轮更聚焦的候选，不要求用户先懂目的地或填写兴趣标签。
- 只收集时间窗、出发位置、用户主动提出的硬约束、必去和避开项。简单探索不主动追问预算、人数、酒店、交通偏好等与当前选择无关的信息。
- 只做轻量可行性检查：开放时间、固定休馆日、季节限制和明显转场冲突。第一阶段不查详细交通、住宿、门票或套餐价格。
- 把日期条件作为排程变量：周一闭馆只表示该候选周一不可排，不能淘汰周二可去的候选。
- `decision_authority = agent_recommends` 不等于偏好已知；没有 `liked` 证据时，`preference_knowledge` 必须保持 `unknown`。

进入第二阶段必须同时满足：至少一条正向兴趣证据；已知并接受的边界或避开项；至少一组可在时间窗内组合的候选；用户明确同意看路线与价格。缺一项就留在体验发现。

### 第二阶段：路线与报价 `route_pricing`

读取 [价格与地图](references/prices-and-maps.md)。提供一个主路线和可删除、替换、追加的体验菜单，说明日期安排、转场、体力与取舍。此时才查询会改变决策的主要交通、住宿、门票和核心体验价格；所有价格都注明条件、来源、时间、覆盖与缺口。

用户只认为预算不合适时留在本阶段，优先调整日期、路线、住宿和大交通等大额变量，不回到完整 intake。用户否定主路线赖以成立的核心体验时，保留硬约束和有效负面反馈，退回 `discovery`。

### 第三阶段：核对、细排与交付

读取 [核对与详细方案](references/reconcile-and-detail.md)。内部可分为：

1. `reconcile`：锁定主路线、核心体验、日期、预算边界与重大约束；
2. `detailed`：按上午／下午／晚上细排，复核选中组合的价格、开放和预约条件；
3. `roadbook`：仅在详细方案获确认且用户需要时，制作与确认版本一致的路书。

小改只更新受影响安排与费用。用户否定核心体验时回第一阶段；预算不合适时回第二阶段；不得用旧版本批准覆盖重大变化后的新方案。

## 续接、状态与提问

开始或继续一个已有旅行项目时，先读取用户指定或当前目录中明确作为当前版本的规划文件，再决定是否建立新状态。已有 Markdown 若包含已确认约束、当前方案、否决项、未定项、必要取舍理由和下一步，就把它作为本项目的规划真源并直接更新；不要再建立平行的 `trip-state.json` 或推荐额外存档 Skill。仅缺少少量续接信息时，在原文件补一个简短的「规划状态」区，不复制聊天全文。

没有充分的现有规划文件，且需要跨轮保存、进入路线报价或属于 `full_planning` 时，才使用 `scripts/intake_state.py` 和 [状态与交付](references/state-and-delivery.md)。脚本不可用时，退化为同等字段的 Markdown 状态区；不得假设用户安装了 `/dbs-save`、`/dbs-restore` 或其他外部 Skill。若 Markdown 与 `trip-state.json` 同时存在且内容冲突，先指出冲突并确认权威版本，不能按时间戳猜测或静默合并。

使用结构化状态时，每轮顺序为：`Parse → Update state → Validate → Question guard → Respond`。已确认且无冲突的信息不得重复询问。

- `decision_authority` 记录谁做当前选择；`preference_knowledge` 独立记录对用户偏好的了解程度。
- `preferences.items[].stance` 只使用 `liked`、`disliked`、`unknown`，并保留用户证据。
- 开放、休馆和固定活动时段写入 `scheduling_constraints`，按日期求可行组合，不写成全局拒绝。
- 复杂旅行渐进收集航班条件、住宿／房型、同行者与年龄、预算口径，以及会改变安全或可行性的健康、无障碍、签证和已订订单。只问当前决策需要且状态允许询问的字段。
- `test` 模式可以展示阶段和状态，但不得创建真实旅行项目、查真实库存或假装已执行外部动作。

## 价格、文件与工具

- 第一次进入 `route_pricing` 才读取价格资料和探测可用工具；没有平台连接时使用合法可访问的官网或页面，不宣称存在的 API。
- 需要预算汇总时记录 `budget.json`，运行 `python3 scripts/sum_budget.py budget.json --output budget-summary.json`。脚本只汇总，不查价、不验证来源。
- 用户要求费用明细、旅行预算表或 Excel 时，读取 [旅行预算表](references/budget-spreadsheet.md)。先形成或更新单一方案的 `budget.json`，再运行 `python3 scripts/export_budget_xlsx.py budget.json --output <预算表.xlsx>`；互斥方案分别生成文件，不能混入同一合计。
- 人数、目标币种、当前方案或关键计费数量存在冲突时先停止生成；主要费用为 `pending` 时可以生成明确标记为“暂定”的预算表，但不得称为完整或已核实预算。
- 需要问卷时，从现有状态渲染 [电子问卷](assets/intake.html)；问卷只补当前阶段真正影响决策的缺口，不把全部字段变成必答题。
- 需要路书时再读状态交付规则，默认生成用户指定格式；没有明确需求时不附加语言锦囊、携带清单或每日名店。

## 诚实与授权边界

真实查询价不等于未来成交价。没有条件匹配的价格或库存证据，不承诺可订或准确率。旅行预算不添加服务费、利润、销售加价或旅行社固定保险价；用户明确需要这些内容时说明它属于旅行社报价任务。不自动联系供应商、订购、付款、分享私密信息或发布网页。不加载其他旅游 Skill 的生产控制器，不为了固定模块扩搜。

每次交付说明当前阶段、已确认项、影响决策的未定项，以及需要用户回应的最少事项。浏览器或价格来源不可用时保留缺口，如实降级，不伪造查询、截图、测试或批准。
