# Humanize Tech Writing

让技术文字准确、直接、自然，并尽量减少无意义的改动。

## Scope

主要处理：
- README、开发指南、故障说明、API 和配置说明
- 架构说明、设计文档、ADR、RFC
- API / 文档注释，例如 JavaDoc、docstring、JSDoc/TSDoc、KDoc、Rust doc comments、Go declaration comments、C# XML docs 等
- 行内注释、块注释、TODO、兼容性和 workaround 说明
- PR description、changelog、migration guide 等变更说明

市场文案、小说、公众号等通用写作不在主要范围内。

## Priority

发生冲突时按以下顺序处理：
1. 技术含义和事实正确
2. 项目术语和契约一致
3. 保留强弱语义、不确定性和边界条件
4. 清楚、具体、容易理解
5. 自然、简洁

风格优化不能改变前 3 项。

## Hard constraints

### 具体化必须有来源

具体行为只使用待改文字、代码、测试、API/schema/配置、项目文档、ADR/RFC、issue/PR 上下文或用户明确提供的信息。原因、重试次数、错误码、性能数字、触发条件、设计动机、兼容性结论等同样需要来源。

如果原文只有“优化失败场景处理”，上下文没有说明具体改动：
- 编辑模式：只改到证据支持的粒度，例如“调整失败场景的处理”。
- 审阅模式：指出“这里需要补充实际行为”，不要替作者编实现。

设计理由也必须有来源。

### 保留事实颗粒度

精简和改写后，原文已有的独立事实、数据、条件、约束和例外仍应保留。

优先删除不承载信息的修饰、评价和包装，而不是把多个具体事实压成一个笼统总结。如果一句话包含多个彼此独立的信息点，改写后仍应能还原这些信息点。

### 保留程序语义载体

默认原样保留类名、方法名、变量名、常量名、API/协议/数据库字段、CLI 命令、配置键、环境变量、日志原文、错误码、异常类型、路径、URL、版本号、固定 UI 文案、本地化 key 和测试固定字符串。只有用户明确要求时才修改这些内容；可以修改它们周围的说明文字。

### 保留正式术语和项目术语

词形、后缀或隐喻词源本身不是 AI 生造词的证据。`XX性`、`XX化`、`XX度`、`XX链路` 都可能是正常工程表达。

例如：幂等性、原子性、一致性、可观测性、序列化、初始化、结构化、复杂度、相似度、置信度、调用链路、数据链路、全链路压测、回源、透传、背压、熔断、扇出、心跳、流水线、冷启动。

术语判断优先级：
1. 用户明确指定的术语
2. 项目 glossary、`AGENTS.md`、`CONTRIBUTING.md`、ADR/RFC 中的既有术语
3. 代码和接口中稳定使用的领域术语
4. 当前中文技术语境中稳定、精确的行业术语
5. 普通中文

拆掉一个“概念词”需要同时满足：项目和行业中没有稳定含义、没有增加技术精度、只是包装本可直接描述的动作或状态。实际行为未知时保持原有事实粒度或指出缺少依据。

### 保留 modality 和 uncertainty

保持原有要求强度、发生概率和确定性，包括：
- 必须 / 应该 / 可以 / 可能 / 不得
- MUST / SHOULD / MAY
- always / sometimes / never
- 通常 / 偶尔 / 仅在 / 至少 / 至多

例如，“可能失败”仍然表示可能，而不是确定发生；SHOULD 仍然是 SHOULD，而不是 MUST。

### 最小编辑

只修改真正影响理解、准确性或明显带有 AI 腔的文字：
- 已经准确、自然的段落保持不变。
- 保留无关章节顺序和项目模板。
- 同一技术对象沿用同一名称。
- 保留原有 Markdown、代码块、链接和结构，除非结构本身影响阅读。
- 修改范围尽量与当前任务和 diff 对齐。

## Document-type rules

先判断文字属于哪一类，再使用对应标准。

### README、设计文档、ADR、RFC

优先写清行为、约束、接口关系、取舍、决策和有来源的理由。已有模板、规范章节顺序或团队约定优先于通用写作偏好。

### API / 文档注释

以 public contract 为核心。根据接口需要记录参数、返回值、异常、nullability、units/format、side effects、thread-safety/concurrency、blocking behavior、ordering、lifecycle、前置条件和边界条件。“注释解释 why”不能替代这些契约信息。

这适用于 JavaDoc、docstring、JSDoc/TSDoc、KDoc、Rust doc comments、Go declaration comments、C# XML documentation comments 等各种语言。代码或类型系统已经完整表达的信息可以省略；公开契约需要明确时应保留。

### 行内注释和块注释

注释优先记录代码本身看不出的信息：有依据的设计原因、不变量、边界条件、外部系统限制、兼容性、concurrency/ordering、workaround 条件和反直觉约束。

代码已经清楚表达的动作通常不再重复注释：
```java
// 获取用户
User user = userService.getUser(id);
```

长期代码注释保留今天仍然有效的信息。纯变更历史、bug 排查过程、尝试过的方案和完整修复故事放在 issue、PR、commit、ADR 或设计文档中。

如果历史问题留下了当前仍然成立的约束，只保留约束、必要原因，以及修改它可能破坏什么。例如：
```java
// 必须精确匹配；模糊匹配会把其他类型错误地归为 foo。
if (type.equals("foo")) {
```

详细背景已有文档时可以直接引用。TODO 写清剩余工作或解除临时方案的条件；日期、负责人和原因只在有依据时写。

### PR、commit、changelog、migration guide

这些内容用于记录变更，可以直接写新增、删除、替换、兼容性变化、迁移步骤和影响范围。变更历史在这里是有效信息。

## Editing preferences

以下是软偏好。项目规范、准确性和特定文档结构优先。

### 用普通词和具体动作

优先使用熟悉、准确的词和具体动作。赋能、抓手、闭环、承接、拉齐、收口、心智、打法、组合拳、底层逻辑，以及没有实际内容的“能力 / 机制 / 体系 / 方案”等表达，只有在确实增加技术精度时才保留。

例如：
- `对请求参数进行合法性校验` → `校验请求参数`
- `对配置进行统一管理` → `统一管理配置`

`优化`、`增强`、`提升`、`完善`、`显著`、`高效`、`稳定`、`可靠` 等判断需要代码、测试、规范、benchmark、项目约定或原文依据。依据不足时，使用证据能支持的说法。

### 避免英文概念和隐喻的逐词直译

很多难读的中文技术文字来自把英文术语、搭配、noun phrase 或隐喻逐词映射成中文。每个字都认识，组合起来却不像自然中文，读者还要先猜原英文才能还原技术含义。

按以下顺序处理：
1. 有成熟、自然的中文术语时，用成熟译法。
2. 项目明确采用某个中文术语时，按项目约定保留。
3. 没有成熟译法时，用普通中文说明实际含义；保留英文原词并配自然中文解释也可以。

重点检查：只有翻回英文才自然的中文、原样搬入中文的英文隐喻或固定搭配、类似英文 noun phrase 的名词堆叠，以及缺少稳定中文用法的“术语”。

代表性例子：
- `single source of truth`：根据上下文写 `唯一配置来源`、`以 X 为准` 等，比生造 `真相源` 更直接。
- `configuration drift`：项目未采用该译法且上下文只表达差异时，写 `配置差异` 或 `配置不一致`。

改写只使用上下文已有事实。

### 优先字面事实，降低隐喻解码负担

技术文字优先直接说明真实的对象、动作、状态和关系。“隐喻率”可以作为观察信号，但不设机械阈值；真正判断的是读者是否需要先把修辞、黑话或形象标签还原成字面含义，才能理解技术事实。

先确认表达是不是项目术语或稳定、精确的中文行业术语。不是时，再判断隐喻是否帮助理解；只增加气势、包装感或“专业感”时，优先改成字面表达。

只有能给出同样准确、信息不减少但更字面的表达时才改写；否则保留原表达。

短标签隐藏“谁做什么、对什么做、在什么条件下做”时，在上下文有依据的范围内展开；信息不足时保持原有事实粒度或指出需要补充依据。

例如：`写路径收口为管理后台` → `配置只能通过管理后台写入`。

### 减少模板化包装

直接写承载信息的结论、条件和原因。`值得注意的是`、`需要指出的是`、`综上所述`、`总而言之`、`Bottom Line:`、`In short:`、`it's worth noting`、`The simplest mental model is:` 等不承载信息时可以删除。

真实存在两个方案、排除关系或用户正在比较 X/Y 时，可以正常使用 `不是 X，而是 Y` / `This isn't about X. It's about Y.`；其他情况直接写实际结论。

局部检查、布局或分支使用项目已有名称。`exact-head checks`、`editorial-row layouts` 这类临时复合标签只有项目已经定义时才使用。`delve`、`foster`、`leverage` 等英文词按语境判断，有更直接的普通表达时优先普通表达。

### 句子、段落和列表

- 使用清楚、具体的动词。
- 主体影响理解时写清主体；上下文明确时省略机械重复。
- 条件、结果和边界影响理解时写出来。
- 能明确主体时通常优先主动句。
- 一个段落尽量围绕一个主要意思。
- requirements、constraints、options、steps、error cases、字段说明和检查项等适合列表；连续解释保持连续段落。

## Project workflow

能访问仓库时，先快速确认局部语言约定：`AGENTS.md`、`CONTRIBUTING.md`、README、glossary、相关 ADR/RFC/API 文档，以及同目录下类似文字。找到足够依据后开始工作，无需为了找术语遍历整个仓库。

- **编辑已有文字**：理解对应代码、接口或设计上下文，只改真正有问题的表达，用已有术语和有来源的事实改写，并保持 diff 尽量小。
- **Review**：指出原文位置、问题和有依据的改法；缺少事实时明确标记需要补充实际行为或设计依据。
- **新写文字**：从一开始使用项目已有术语和直接表达。

## Completion criteria

完成时以下条件全部成立：
- **事实**：没有加入无依据的新事实、设计理由或实现细节，也没有因精简丢掉已有事实、数据、条件、约束或例外。
- **语义**：标识符、程序语义、MUST/SHOULD/MAY、可能性、频率和边界保持不变。
- **术语**：项目术语和成熟中文技术术语得到保留；词形、隐喻词源或英文原词本身没有被当作判断依据。
- **注释**：API / 文档注释保留必要 contract；行内注释记录代码看不出的长期有效信息。
- **表达**：没有需要读者二次还原的空泛黑话、英文直译腔、宣传话术、无帮助的隐喻或压缩标签，也没有模板化过渡、假对立或临时概念名。
- **范围**：项目结构和格式得到保留，只修改真正需要修改的文字。

一句话已经准确、自然、符合项目习惯时，保留它。
