# Roblox 游戏拷问

当关键产品或技术取舍无法由项目证据消除，且继续会改变目标、范围、权威边界、成本、风险或验收时，先调查，再逐项请用户决定，并把结论写入工作流控制面。拷问是解决必要决策的流程，不是每个工作项的固定前置步骤。

## 触发与边界

用户明确要求拷问时进入本流程。没有明确要求时，只有仍存在会实质影响受影响工作项的人工取舍才触发，例如：

- 玩家目标、核心循环、多人合作或竞争方式、版本范围及优先级。
- 服务器与客户端的权威归属、Remote 契约、模块边界、Place 间职责或持久化责任。
- 视觉方向、参考图可用范围、资源来源与许可、生产成本或性能预算。
- 经济节奏、奖励规则、随机性、付费权益、数据留存和运营策略。
- 发布目标、公开范围、商业化、隐私影响、数据迁移、回滚和风险接受。
- 人工验收标准、风险门槛或授权边界仍有多个合理选项。

以下情况不触发拷问：首次实现本身、小修、可从官方资料/项目/Studio 中查明的 API 或对象事实、普通且已授权的本地测试，以及不改变已批准目标和范围的实现细节。先通过现有文档、只读项目检查、Studio 插件实际提供的只读查询或可信来源消除事实问题；不可核实的内容标为假设或未知，不能伪装成事实。不得把可由证据回答的问题交给用户。

领域技能发现必要取舍时，交给本技能取得决定并记录，然后回交原工作项。决策闭合后，原任务已授权且仍在其目标与 scope 内的可逆文件或 Studio 实施可继续，无需重复批准；拷问结论不扩大原任务授权。上传、线上服务操作、付费、公开发布、破坏性数据操作或真机验收仍须单独核对对该动作、对象和影响的明确授权。

## 执行顺序

1. 读取当前工作项、其 scope、设计文档、相关实例/文件、已有 `decisionRefs` 及有效决策记录。只用 Studio 插件完成该决策所需的最小只读检查；按 [Studio 插件路由](../roblox-development-workflow/references/studio-plugin-routing.md)辨别工具实际能力。插件没有提供的状态保持未知。
2. 列出已核实事实及其可追溯来源、假设、未知和必须由用户选择的事项。来源记录用于追溯，不计算或比较 SHA。
3. 按依赖与影响排序。互不依赖、低影响且推荐相同的决定可组成一组；高影响、相互依赖、存在冲突或会影响下游批准的事项一次只问一个。
4. 每个问题说明已知事实、唯一待决定事项、对目标/范围/成本/风险/返工/验收的影响、二至三个互斥选项，以及带理由的推荐。推荐不是事实，不得把沉默、继续执行、审查通过或技术 PASS 当成回答。
5. 只把真实用户消息或宿主提供的可信消息收据记为用户回答来源。含糊、缺少对象/版本、彼此冲突或未覆盖问题的答复，应继续澄清当前问题；不得猜测用户意图。
6. 问题回答完毕且未知项清零后，提交一份版本化结论，列明批准对象、范围、非目标、拒绝选项、接受风险、验收依据和下一步，并请用户明确批准该结论。已有真实回答若明确批准同一完整对象与范围，可复用，不重复索要批准；不确定时先核对原消息。
7. 按[决策记录约定](references/decision-record.md)保存 JSON 记录，将其项目相对路径加入当前工作项的 `decisionRefs`。批准后核实记录修订、对象和范围与真实用户批准一致，再将受影响内容交回原工作项。

## Roblox 决策范围

- **体验与范围**：目标玩家、核心循环、失败和重试、会话情境、目标设备、MVP 和非目标。
- **架构与多人**：服务器权威状态、客户端表现、Remote 的调用方向和校验、多人关系与人数边界、重生/退出清理、模块和共享状态所有权。
- **Experience 与 Place**：目标 Experience/Universe、Place、DataModel 对象和工作项范围。`get_studio_state` 不提供 Place 身份；不得把 Studio 当前打开状态推断为获批目标或其他 Place 的状态。
- **视觉与资源**：全局风格、素材用途、参考图允许用途、模型/贴图/动画边界、许可证据、Asset ID、预算与性能取舍。搜索或生成结果不等于获得使用许可。
- **经济与在线服务**：奖励和成长规则、付费权益、随机商品、数据字段与留存、DataStore 策略、开发者产品和收据行为、运营配置及测试命名空间。
- **质量与发布**：可观察验收、适用设备/多人测试范围、风险接受、公开范围、上传/付费/线上写入、版本发布和回滚影响。

现有有效记录仅在绑定同一工作项、主体和修订范围时复用。候选实现变化或普通实现调整不自动使决策失效；只有目标或批准范围实质变化才创建更高修订，并重新处理受影响的决策。未解决的决策只暂停依赖该决定的内容，独立且已授权的工作可以继续。

## 写入与授权边界

- 记录前先检查工作项 `scope`。`subject.files` 与 `subject.instances` 必须逐项落在其精确白名单内；概念决定可将两者都留空。决策记录不能扩展工作项授权。
- 未获明确批准前，只做只读调查、候选比较、问题记录，以及不依赖该决定的已授权工作。仅在当前授权明确覆盖目标对象时，才写入受影响文件或 Studio 实例。
- 需要上传、外部服务写入、线上配置、付费、公开发布、破坏性数据操作或真机验收时，必须对该动作、对象和影响另行取得明确授权；拷问结论不能推定这些授权。
- 决策记录是项目内数据，不是身份证明。不得伪造、代签或补造用户回答、用户消息引用、审批人或批准时间。工具可以检查 JSON 结构，不能证明消息来源真实；运行者必须核对真实对话或宿主可信收据。
- 不在记录中保存凭据、个人数据或受限合同全文。示例只展示待决策结构，不能作为项目事实、有效批准或可继续工作的证据。

## 完成条件

- 需要人工决定的事实问题已先调查；事实、假设、未知与选项彼此分开。
- 所有阻断问题均由真实用户明确回答，未知项已清零，结论已获适用范围内的明确批准；已有有效批准按原消息核对后复用。
- JSON 决策记录符合[决策记录约定](references/decision-record.md)，且 `decisionRefs` 与记录中的工作项、主体及修订对应。
- 未决问题继续阻断受影响的工作项完成；独立工作不被无关问题暂停，也不把决策批准扩展为其他受保护操作的许可。
