# obsidian-log スキル

## 目的

Obsidian vault に**追記型の日次ログ**を書く／読む。**1日1ファイル**（`{date}.md`）へ、発生の都度エントリを末尾に足していく。

設計思想は「**ログは貯める、集約は生成する**」。ログ自体は事実の蓄積に徹し、要約・集約・レポートは後から別途生成する。ログを書く時点で「どのノートにまとめるか」を判断しないため、判断ミスによる取りこぼしやノートの乱造が起きない。

**本スキルは書き方（配置と形式）だけを定める**。何を書くか（本文の内容設計）は呼び出し側が決める。

---

## 前提：[[obsidian-config]] を先に適用する

vault パス・保存先フォルダ・タイムゾーン・日時取得手段の解決は、すべて [[obsidian-config]] に従う。本スキルはその**解決結果を受け取って使う**（規約を再定義しない）。

- **purpose は `logs`**（既定 `ai/logs`）。呼び出し側が別の purpose・明示パスを指定した場合はそれに従う
- **日時は暗算しない**。取得手段は下記「日時の取得」に従う（[[obsidian-config]] の優先順に従う）
- フォルダ作成・パス制約・vault 状態の判定も [[obsidian-config]] のルールをそのまま使う

---

## 日時の取得

**AI は日時を暗算しない。** 現在時刻はコンテキストに無く、推測すると必ずずれる。

取得手段と優先順は [[obsidian-config]] の「日時の取得」に従う（python → `date` → node → PowerShell の順に試し、**最初に成功した手段で確定する**）。`timeZone` / `TZ` には [[obsidian-config]] が解決した `timezone`（既定 `Asia/Tokyo`）を必ず指定する。

- **生の出力書式に依存しない**。年月日時分の各成分を取り出し、ファイル名には日付、エントリ見出しには `HH:mm` を組み立てる
- **追記のたびに取得し直す**。セッション開始時の値を使い回すと日跨ぎで前日のファイルに書き続ける
- 全手段が失敗した場合は暗算せず中断する（下記）

node を使う場合の例（`24` 対策込み）:

```bash
node -e "const p=new Intl.DateTimeFormat('en-CA',{timeZone:'Asia/Tokyo',year:'numeric',month:'2-digit',day:'2-digit',hour:'2-digit',minute:'2-digit',hour12:false}).formatToParts(new Date());const g=t=>p.find(x=>x.type===t).value;const h=g('hour')==='24'?'00':g('hour');console.log(`${g('year')}-${g('month')}-${g('day')} ${h}:${g('minute')}`)"
```

出力例: `2026-08-07 16:48` → ファイル名に `2026-08-07`、エントリ見出しに `16:48` を使う。

- `hour12:false` は環境によって深夜 0 時台を `24` で返すため、**`24` は `00` に読み替える**（node 経路の注意点）

### シェルの実行が制限されている環境

統制のためシェルを塞いでいる環境では、上記コマンドを実行できない。その場合は次の順で対処する。

1. **その環境が用意した時刻取得手段を使う**。固定スクリプトを許可リストに載せている場合があるので、
   プロジェクトの規約（`AGENTS.md` 等）を確認する
2. 手段が無く、かつ**機械が記録したタイムスタンプが手元にある**場合（操作ログの UTC 値、
   API レスポンスの完了時刻など）は、それを根拠に使ってよい。
   ただし**どの記録に基づくかをエントリに明記する**（AI の推測でないことを読み手に示す）
3. どちらも無ければ、**暗算せず中断してユーザーに確認する**

## [[obsidian-config]] の既定から意図的に外れる点

ログは「新規ノートを作る」のではなく「同じファイルに足していく」ため、以下だけ挙動が変わる。**それ以外はすべて [[obsidian-config]] に従う**。

| 項目 | [[obsidian-config]] の既定 | 本スキル |
|---|---|---|
| ファイル名 | titled → `{date}-{title}.md` ／ untitled → `{date}-{time}.md` | **`{date_format}.md` 固定**（タイトルも時刻も付けない） |
| 同名ファイルが既存 | 上書きせず連番 `-2`…`-99` | **連番を付けず、そのファイルに追記** |
| 時刻の取得 | untitled 確定時のみ | **エントリごとに毎回必要**（見出しに使う） |
| タイトル | ファイル名に使う | ファイル名には使わない。**エントリ見出しに使う**（原則必須） |

`title_max_chars` / `time_format` / ファイル名サニタイズ・衝突連番のルールは、本スキルのファイル名決定には**使わない**（`{date_format}.md` 固定のため）。

---

## ファイルの決定

```text
<vault_path>/<purpose=logs で解決したフォルダ>/{date_format 整形の日付}.md
例: obsidian/ai/logs/2026-08-07.md
```

- 日付は**追記のたびに取得し直す**。セッション開始時の日付をキャッシュして使い回さない（日をまたぐと別ファイルに書くべきだが、キャッシュしていると前日のファイルに書き続けてしまう）
- ファイルが存在しなければ新規作成、存在すれば追記

---

## 新規作成時の骨格

その日の最初のエントリで、ファイルを次の形で作る。

```markdown
---
date: 2026-08-07
type: log
---

## 14:30 — 添付ファイルを必須にしたい

本文。
```

- frontmatter は `date` と `type: log` のみを既定とする。呼び出し側が追加のプロパティを指定した場合はそれも書く
- **frontmatter は新規作成時にだけ書く**。追記時には触らない
- ファイル名が日付なので、本文冒頭に `# 2026-08-07` のような見出しは置かない

---

## エントリの形式

```markdown
## HH:mm — <見出し>

本文（自由。箇条書き・コードブロック・リンク可）
```

- 見出しレベルは **`##` 固定**。本文中で階層が要るときは `###` 以下を使う
- **`— <見出し>` は原則必須**。そのエントリが何の記録かを1行で示す。本文が短くタイトル化の意味が無い場合のみ `## HH:mm` だけにしてよい
- タイトルは**1行**。改行と見出し記号（`#`）を含めない
- 時刻は **`HH:mm`**（24時間・ゼロ埋め）。[[obsidian-config]] の `time_format`（ファイル名用の設定）には従わない
- 同一時刻のエントリが並んでも連番等は付けない。**発生順に並んでいることが時系列の保証**

---

## 追記の原則

1. **末尾に足すだけ**。既存のエントリを書き換えない・削除しない・並べ替えない
2. 追記前にファイル末尾を確認し、**直前のエントリとの間に空行が1つ**入るようにする（末尾に改行が無ければ補う。空行が2つ以上あれば1つに詰める）
3. 追記に失敗した場合はリトライせず中断して報告する（部分的に壊れた内容を残さない）
4. **事実と推測を混ぜない**。実行結果・エラー文は原文を引用し、解釈は解釈として分けて書く

---

## 読み取り

集約・要約の材料としてログを読むときは、フォルダ解決だけを [[obsidian-config]] から受け取り、対象ファイルは呼び出し側が指定する（新規ファイル名生成・フォルダ作成はしない）。

- **単日**: `{date}.md` を読む
- **期間**: フォルダ内のファイル名が `{date_format}` そのものなので、**ファイル名の辞書順＝時系列順**。範囲指定はファイル名の文字列比較で足りる（`date_format` が既定 `YYYY-MM-DD` の場合）
- 対象ファイルが存在しなければ「その日のログは無い」と報告する（空ファイルを作らない）

`date_format` が `YYYY-MM-DD` 以外に変更されていて辞書順と時系列順が一致しない場合は、範囲指定に文字列比較を使わず、日付として解釈してから比較する。

---

## 報告ルール

書き込み後は簡潔に報告する。

```text
記録しました: <ファイルパス> (HH:mm)
```

中断時は記録完了と報告せず、失敗理由と確認したい内容を報告する。

### 警告として報告する（該当時のみ）

- 追記に失敗して中断した
- 日時取得手段が全滅して中断した（[[obsidian-config]] の規定に従い暗算しない）
- 既存ファイルの frontmatter が壊れていた（**触らずに末尾追記だけ行い**、その旨を伝える）
- [[obsidian-config]] 側の警告事項（vault 未確認モード・`obsidian.json` パース不能・フォルダ作成失敗）

### 情報レベル（通常は報告しない）

- その日の最初のエントリでファイルを新規作成した
- 保存先フォルダを新規作成した

---

## Gotchas（既知の注意点）

- **日付はエントリのたびに取り直す**。キャッシュすると日跨ぎで前日のファイルに書き続ける
- **日時は [[obsidian-config]] の優先順で取得する**。暗算しない。node 経路では深夜 0 時台の `24` を `00` に読み替える。
  シェルが塞がれている環境では、その環境が用意した手段を規約で確認する。無ければ機械が記録した
  タイムスタンプを根拠にし、根拠をエントリに明記する（→「日時の取得」）
- **連番を付けない**。同名ファイルは「追記対象」であって「衝突」ではない（[[obsidian-config]] の既定と逆）
- **frontmatter は新規作成時のみ**。追記のたびに書き換えたり重複させたりしない
- **既存エントリは不可侵**。修正が必要なら「訂正」として新しいエントリを追記する（ログは事実の蓄積であり、書き換えると監査価値が消える）
- 時刻見出しは `HH:mm`。`time_format`（既定 `HHmm`）はファイル名用の設定であり、ここでは使わない
- ファイル名にタイトルを付けない。タイトルはエントリ見出しに置く（**原則必須**・1行）
- **集約・要約はしない**。「今日は結局こうなった」というまとめが要るなら、ログとは別の成果物として生成する
- 追記前の末尾改行を忘れると、直前のエントリと見出しが繋がって Markdown が壊れる
