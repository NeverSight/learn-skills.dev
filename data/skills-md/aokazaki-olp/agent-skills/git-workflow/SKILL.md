# git-workflow スキル

git・GitHub 操作の運用規約。「どうコミットし、どう枝を切り、どうマージするか」を規定する。コードの設計・実装・レビューはしない。

このスキルは3層で構成する。読み違えないこと:

- **不変条項（HARD）** — 常に守る。事故防止だけが目的で、判断は要らない。
- **運用モデル（MODEL）** — 「地図」。こう動いているという説明であって、逐一の縛りではない。
- **判断が要るとき** — ビジネス判断。**エージェントは勝手に決めず、指示に従う / 確認する**。

---

## 不変条項（HARD・常に守る）

判断不要・コストほぼゼロで常に守れるものだけ。事故防止。

- **勝手に commit / push しない**。commit・push は依頼されたときだけ。
- default ブランチ（main 等）上で作業していたら、commit の前に**まずブランチを切る**（初期コミットは例外。default 上で行う）。これは main への誤コミットを防ぐ安全分岐であり、トレイン確定（どのリリースに乗せるか）は伴わない。
- コミットメッセージは **日本語・体言止め・prefix なし・句点なし・1行**（詳細は下記）。
- マージは **`--no-ff`**。ファストフォワードで潰さない。**squash / rebase は使わない**。
- **AI 固有のマーカーを一切付けない**: `Co-Authored-By` フッター・PR 本文の「🤖 Generated with Claude Code」等・`claude/` 接頭のブランチ名、いずれも不可。コミット / PR / ブランチは人間と同じ規約で書く。
- **生成物・IDE 設定・秘匿情報をコミットしない**（`.gitignore` / `.git/info/exclude` で除外。`git add .` で入らない前提でも、可能なら明示パス指定を優先）。
- **GO が出るまで機能ブランチを親（ターゲット開発ブランチ）にマージしない**（→ 運用モデルの流動性ガード）。GO ＝ そのトレインに乗せて確定でマージしてよいという人間の承認。エージェントにとっては「マージして」の明示指示を指す。

---

## コミットメッセージ規約

形式は **日本語・体言止め・prefix なし**。Conventional Commits（`feat:` / `fix:` 等）は使わない。

```
<対象>を<動詞>
```

- **動詞（固定語彙・揺らさない）**: 追加 / 修正 / 削除 / 変更 / リファクタリング / 更新
- **対象**: 機能・項目・ドキュメント・依存など。ドキュメントも特別扱いせず同じ動詞で書く
- 末尾に句点（。）を付けない
- **1コミット＝1論理変更**。粒度は意図的に小さく
- 本文（サマリ下の説明）は **基本書かない**（1行で完結）。背景が必要なときのみ箇条書きで補足

### 例

```
住所サジェスト機能を追加
反映ロジックを修正
未使用のヘルパーを削除
READMEを修正
依存を更新
```

### 初期コミット（特別枠）

リポジトリ最初のコミットのみ、固定動詞の対象外。「作品」ではなく**再現可能な基準点（baseline）**として作る。

1コミットの中身:
- scaffold ツールが生成したファイルそのまま（自作コードは足さない）
- `.gitignore` を効かせた状態 = scaffold 標準の除外 + 使う IDE / ツールが吐く成果物（`.idea/` 等）も除外に追加し、**「以降 `git add .` で余計な物が入らない」所まで**整える

メッセージは **何から生成したか（scaffold 元 + バージョン）** を刻む。baseline が再現可能であることの記録。初期コミットは例外的に default（main）ブランチ上で行う。

```
形式: <プロジェクト>を<生成元・バージョン>から新規作成

例:
- laravelプロジェクトをLaravel 12.3から新規作成      （composer create-project laravel/laravel）
- Next.jsアプリをcreate-next-app 15から新規作成
- n8nカスタムノードをn8n-nodes-starterから新規作成
```

**初期化フロー（未 git init のリポジトリ）**: `git init` → `.gitignore` 整備（上記の「効かせた状態」まで）→ 初期コミット（default 上）→ `develop` ブランチ作成 → 必要ならリモート接続。プロジェクトのインフラ（`.agents/` `.claude/` `AGENTS.md` 等の AI 整備物・設定）は「自作コード（プロダクト機能）」ではなく baseline の一部なので、初期コミットに含めてよい。

※ 既にコードがある未 git 化プロジェクトを後から git 化する場合のみ、純 baseline は作れないため、初期コミットは現状まるごと + 由来記録とし、メッセージは「作成」の対象を**プロジェクトではなくリポジトリ**にして区別する（例: `n8nカスタムノードのリポジトリを作成`。「プロジェクトを新規作成」＝手つかず、「リポジトリを作成」＝プロジェクトは既存で repo だけ後付け）。

## 運用モデル（MODEL・地図）

これは「必ずこの形にしろ」ではなく、**こういうモデルで動いているという地図**。リポジトリ規模に応じて、このうち必要な枝だけが実体化する（ターゲットが1つなら develop がそのままターゲット開発ブランチとして振る舞い、下記が縮約される）。

```
main                                    リリース済み・本番
└─ develop                              恒久の統合幹（release 後に main 経由で取り込む）
   ├─ <ターゲット開発ブランチ>          リリース/施策ごとに develop から派生（複数並走）
   │   └─ feature/implement-foo         親機能ブランチ（英語 kebab・長命）
   │        └─ feature/detail-xxx       ローカル子ブランチ。小さいコミットを積む
   └─ <別ターゲット開発ブランチ>
```

- 機能ブランチ名は親子とも `feature/<english-kebab>`。動作語を作業内容に合わせる（`implement-` / `add-` / `fix-` / `refactor-` / `update-` 等）。Git Flow 準拠で必要に応じ `release/` `hotfix/` も使う。
- **図の各層は「役割」であって命名規則ではない**（統合幹 / 派生基準 / 機能 / 子 は role）。本スキルで **"トレイン" はこのターゲット開発ブランチ（リリース/施策ごとの開発ブランチ）を指す**。ターゲット開発ブランチや `release/` の**命名はプロジェクトによる**（固定しない。ターゲット開発ブランチを `feature/` 配下に作ることもある）。
- **基点の選択**: 機能ブランチは、依存対象をすべて含む、develop に最も近いブランチから切る。依存が develop に揃っていれば develop から（可搬性が高い）。先行依存（例: 機能 B が依存する機能 A がまだ develop に無く、進行中のターゲット開発ブランチにしかない）なら、そのターゲット開発ブランチから切るしかない。どのリリース/施策に乗るかは流動的（実装 / 見送り / 前倒し）。

### マージ経路（すべて merge ベース。rebase / squash は使わない）

- **子 → 親**（"子/親" は相対語。子＝直下、親＝直上のブランチ。ここでは `feature/detail-xxx` → 親機能ブランチ `feature/implement-foo`）: **PR なし・ローカル merge**
  - `git merge --no-ff --log <branch>`（`--log` でマージ対象コミットの1行サマリを本文に列挙）
- **親機能ブランチ → ターゲット開発ブランチ**（`feature/implement-foo` → 開発ブランチ）: **PR あり**（merge commit 維持・squash しない。リモート/PR 運用が整うまではローカル `--no-ff` merge で代替）。**PR の宛先を選ぶ行為 = リリース乗り換えの実装**（依存が許す範囲で、通常＝当初狙っていたターゲット開発ブランチ / 先行＝先行開発ブランチ / 先送り＝未来の開発ブランチ）。**基点が develop でも、機能を直接 develop へマージはしない**（develop は release 粒度でのみ統合される。宛先は必ず選んだトレイン）。
- **基点の取り込み（追随）**: 待機中の機能ブランチは、**自分の基点**（切った元のブランチ = develop か、依存で選んだターゲット開発ブランチ）を**適宜 merge で取り込む**。基点からそこまで遅れない状態を保ち、長命ブランチの腐敗を防ぐ。**rebase で載せ替えない**。
- **リリース**: ターゲットごとに QA → **GO ならリリースブランチを作成**（ターゲット開発ブランチから切る）→ リリース → **main へ `--no-ff` マージし、リリース点に注釈付きタグ（`git tag -a`）を打つ**（タグの命名規則＝SemVer / 日付 / ビルド番号等はプロジェクトによる。固定しない） → **main を develop へ戻しマージ**（`git checkout develop && git merge --no-ff main`。released 状態を恒久幹へ還元。develop は per-feature ではなく release 粒度で統合される）→ 兄弟のターゲット開発ブランチへも随時取り込み。
- **hotfix**: 本番障害時は **main から `hotfix/<name>` を切る** → 修正 → **main へ `--no-ff` マージ + タグ** → **develop へは release 同様 main→develop の merge で即還元**（`git checkout develop && git merge --no-ff main`）→ **main 経路を持たない稼働中の兄弟ターゲット開発ブランチへのみ `cherry-pick -x` で伝播**（緊急反映。次リリースの戻しで二重到達しても merge 収束で吸収）。

### 流動性ガード（最重要）

乗り換えの自由度は選ぶものではなく、**依存構造から決まる帰結**。基点が develop（共通祖先）に近いほど可搬性が高く、特定トレインに依存して切る/追随するほど、そのトレイン固有履歴が癒着して他トレインへは道連れ・二重取り込みになる。ただしこの道連れは「B が A に依存している」事実の正しい反映であってバグではない。

**GO が出るまで、親機能ブランチをターゲット開発ブランチにマージしない**。未マージゆえ、**依存が許す範囲で** PR の宛先（＝乗せるトレイン）を変えられる。早まってマージすると cherry-pick / rebase の面倒に転落する。

**機能ブランチは使い捨て前提**。企画変更やドリフトで陳腐化したら、discard（`git branch -D`）や**一から作り直し**は失敗ではなく通常手。stale なブランチを無理に救わない。

## 判断が要るとき（ビジネス判断・人間に委ねる）

以下はビジネス判断であり、エージェントが機械的に決めてよいものではない。**勝手に決めず、指示に従う / 確認する**:

- 機能をどのリリース / 施策に乗せるか（前倒し・見送り・繰り越し）
- 機能ブランチの基点（切る元ブランチ）と PR の宛先の選択（依存構造とトレインの解釈）
- 機能ブランチを discard する / 作り直すか
- リリースブランチをいつ切るか、取り込みをいつ行うか
- 基点の追随 merge の実施タイミングと対象基点（git は「切った元ブランチ」を保持しないため、基点が曖昧ならユーザーに確認）
- release / hotfix をどの兄弟トレインへ伝播するか
- タグ名（命名規則はプロジェクト依存）
- コンフリクトのうち、意味的で自明でない解決（機械的に自明なものは解決してよい）

**メタ規則**: MODEL・HARD いずれに手順が書かれていても、上記の流動的判断が絡む操作はエージェントが自動実行しない。ユーザーの明示指示に従い、無ければ確認する。

エージェントは上記のモデルを**理解した上で**、機械的な作業（**指示された基点での**ブランチ作成・コミット・**自分の基点からの**追随 merge・**指示された宛先への** PR）を行い、流動的判断は人間に渡す。

## いつ使うか（適用条件）

branching model はエンジニアリングの好みではなく、**business の delivery model の git 層への射影**。このモデルは **deferred-commitment（optionality）を最小インフラ（git 規約のみ）で買う**流儀。

- ✅ **最も効く**: マーケ / GTM 協調カレンダーに合わせて機能を "せーの" で launch し（バッチ型 cadence）、かつ投機的に作って捨てる度合いが高い（高 discard）プロダクト。ソシャゲ / ライブサービス / 施策駆動の消費者向けサービス。platform（mobile/web）は問わない。マーケ暦は恒久なので**成熟後も居座れる**。
- ⚠️ **卒業を検討**: flag / CD 基盤を維持できる規模になり、かつ長命ブランチの merge 負債が flag 基盤コストを上回ったとき。同じ optionality を feature flag（ランタイム層）で実装する方が有利になる。
- ❌ **範囲外**: (1) 真の継続デプロイ（trunk-based + feature flag が native）、(2) 多版を並行保守する B2B / 自社ホスト（backport 駆動＝後ろ向きの保守で、このモデルの前向き optionality とは別問題）。

## GitHub / gh CLI

- PR は `gh pr create`（タイトルはコミットと同主旨の日本語）。
- 当面ローカル git 中心で運用する場合、親→開発ブランチの PR もローカル merge で代替しうる。
- gh を使う前に認証（`gh auth login`）とリモート設定を確認する。

## Gotchas（既知の注意点）

- Conventional Commits の prefix（`feat:` 等）は付けない。日本語・体言止め・句点なし。
- マージは `--no-ff`。ff で潰さない。**squash も rebase も使わない**（追随も merge で行う）。
- 子ブランチのマージに PR は使わない（PR は親→開発ブランチの段のみ）。
- 動詞語彙を揺らさない（追加 / 修正 / 削除 / 変更 / リファクタリング / 更新）。
- AI マーカー（`Co-Authored-By`・「🤖 Generated」・`claude/`ブランチ名）を付けない。
- **GO まで親機能ブランチをターゲット開発ブランチにマージしない**（流動性ガードを壊さない）。機能ブランチを "作品" として過剰に守らない。
- 既知リスクとして意識する: ①長命ブランチ × merge-only の**マージ負債** ②**遅延統合**（高 discard 業態では discard が無料になる利点の裏返しで許容） ③複数トレインの**伝播ドリフト**。緩和策: `git config rerere.enabled true`（同一コンフリクト解決の再利用を有効化。`git rerere` コマンド自体は記録の操作用で有効化用ではない）・伝播は `cherry-pick -x`（ただし cherry-pick は同一パッチを別 SHA で複製する。`-x` は出所記録であって重複自体は防がない。トレイン合流時に再解決が要りうるので、恒久統合は最終的に merge 経路一本へ収束させる）・親機能ブランチは極力短命に。
- このリポジトリ固有の除外パス・環境セットアップ（例: 特定ディレクトリの除外、環境変数の読み込み）は、実態に合わせて各リポジトリで確認する。

## 由来

このモデルはソシャゲ開発の実践から創発したもの（トップダウン設計ではなく、マーケ協調 cadence × 高 discard という淘汰圧の中で生き残った運用）。実戦で検証済みかつビジネス整合的。理論的な理想ではなく working practice の抽出である点が信頼の根拠。
