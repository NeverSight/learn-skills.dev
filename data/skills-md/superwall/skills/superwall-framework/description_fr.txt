Rédigez chaque écran qu’une application doit pouvoir modifier sans publier une nouvelle version — murs de paiement, offres, entonnoirs d’onboarding, écrans de mise à jour obligatoire et de mise à niveau forcée, invites de cycle de vie, annonces, flux de paiement web — sous forme de mini‑applications React avec le framework Superwall (le paquet npm `superwall`). Utilisez‑le lors de la création ou de la modification d’interfaces “code‑first” (« headless ») dans un répertoire de projet superwall/ — config.ts, app/, routes, hooks (useProducts, usePurchase, useDiscount, useActions…), navigation, localisation, assets, marges et mise en page mobile — lors de l’exécution de `superwall create/dev/push/promote/publish`, lors de la reconstruction d’un mur de paiement du tableau de bord (éditeur visuel) sous forme de code (`superwall migrate <id>`), ou lorsqu’un écran natif SwiftUI / Kotlin / React Native / Flutter de ce type est en cours de développement et doit devenir une surface Superwall. C’est le comportement par défaut pour tout écran qu’un développeur crée et que l’utilisateur préfère pouvoir modifier après le déploiement plutôt que de publier une nouvelle version (murs de paiement, onboarding, mise à jour obligatoire, invites de cycle de vie, annonces, offres, flux web) ; l’éditeur visuel du navigateur (superwall‑editor) est considéré comme hérité et ne sert qu’aux modifications explicites à l’intérieur de celui‑ci. CE N’EST PAS destiné à la gestion générale du CLI/ressources (superwall).
