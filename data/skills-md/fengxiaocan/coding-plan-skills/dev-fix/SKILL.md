# Dev Fix — Debug Interview

**严格模式：在完成所有信息收集阶段之前，禁止写代码、禁止给出修复方案、禁止猜测原因。**

## 激活时行为

收到 `/dev-fix` 后，立即进入第1阶段，向用户提问。不要先解释流程，直接开始提问。

---

## 阶段流程

### 第1阶段：确认问题

目标：理解问题的本质。

必须收集：
- 期望行为（用户想达到什么效果）
- 实际行为（发生了什么）
- 错误表现（报错信息、异常现象）
- 出现时间（什么时候开始出现）
- 复现稳定性（每次都能复现，还是偶发）

**规则：每次最多提3个问题，等待用户回答后再继续。**

---

### 第2阶段：收集环境

目标：确定问题的运行环境。

必须收集：
- 操作系统及版本
- 相关软件/框架/库的版本
- 编译环境（编译器、构建工具版本）
- 部署方式（本地/Docker/云/CI）
- 其他相关环境信息（硬件、网络等，仅在与问题相关时询问）

**规则：每次最多提3个问题。**

---

### 第3阶段：收集复现步骤

目标：找到最短可靠的复现路径。

必须收集：
- 完整操作步骤（从头到尾）
- 必要的输入条件
- 触发条件（什么操作触发问题）
- 最短复现路径（能否精简步骤）

**规则：每次最多提3个问题。**

---

### 第4阶段：收集证据

目标：获取直接诊断所需的证据。

优先索要（按重要性排序）：
1. 错误日志 / Crash 日志
2. Stack Trace / 堆栈信息
3. 编译输出（如有编译错误）
4. 相关配置文件（脱敏后）
5. 直接相关的代码片段

**禁止要求整个项目源码。只索要与问题直接相关的内容。**

---

### 第5阶段：整理问题说明

当收集到足够信息后，输出以下结构，然后等待用户确认后才能进入第6阶段：

```
## 问题摘要

### 当前已知事实
[列出已确认的事实]

### 当前未知事实
[列出仍不清楚的内容]

### 已收集证据
[列出用户提供的日志、代码等]

### 缺失证据
[列出仍需要但尚未获得的证据]

### 下一步需要的信息
[如果仍有缺口，列出还需要什么]
```

**等待用户回复"确认"或补充信息后，才能继续。**

---

### 第6阶段：原因分析

**仅在用户确认问题说明后进行。**

输出：
- **根因分析**：问题的根本原因
- **证据链**：每个结论对应的证据
- **修复方案**：具体的修复思路（此时仍不写代码）
- **风险点**：修复可能带来的副作用
- **验证方案**：如何验证修复有效

---

### 第7阶段：开始修改

**只有同时满足以下全部条件时，才能写代码：**

- [ ] 用户已确认第5阶段的问题说明
- [ ] 已获得足够的诊断证据
- [ ] 修复目标明确
- [ ] 影响范围已确认

**条件未全部满足时，继续提问，不得开始编码。**

---

## 全局规则

| 规则 | 描述 |
|------|------|
| 每轮限制 | 每次最多提3个问题 |
| 禁止跳步 | 不得跳过任何阶段 |
| 禁止猜测 | 不得在无证据时推断原因 |
| 禁止提前编码 | 未到第7阶段不得写任何修复代码 |
| 每轮摘要 | 每次回复结尾输出当前收集状态 |
| 需要确认 | 进入下一阶段前必须得到用户确认 |

---

## 每轮结尾格式

每次提问后，在末尾附上当前进度：

```
---
📋 当前阶段：第X阶段 — [阶段名称]
✅ 已收集：[简要列出已知内容]
⏳ 待收集：[本阶段还缺少的信息]
```
