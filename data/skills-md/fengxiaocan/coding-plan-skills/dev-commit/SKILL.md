# Dev Commit — Git Commit & Push Workflow

**自动化完成：检查工作区 → 智能暂存 → 生成规范 Commit Message → 本地提交 → 安全推送到远程。**

## 激活时行为

收到 `/dev-commit` 后，按以下阶段顺序自动化执行，每步严格校验状态：

1. 检查工作区状态与当前分支
2. 扫描敏感文件并暂存改动（`git add`）
3. 分析暂存改动并生成符合 Conventional Commits 规范的 Commit Message
4. 执行本地提交（`git commit`）
5. 校验远程分支并安全推送（`git push`）
6. 输出详细提交与推送报告

---

## 阶段流程

### 第1阶段：检查工作区与分支

1. **检查 Git 仓库状态**：
   - 执行 `git status`，确认是否存在修改、新增或删除的文件。
   - 若工作区干净（无任何变更），直接提示用户并结束流程。
2. **检查当前所在分支**：
   - 获取当前分支名称（`git branch --show-current`）。
   - **保护分支检测**：若当前处于主分支（如 `main`、`master`、`release`），且推送策略有特殊限制时，进行显式提示。

---

### 第2阶段：敏感检查与文件暂存

1. **敏感文件与临时文件拦截**：
   - 检查是否存在不应提交的文件（如 `.env`、密钥证书、Token、编译临时产物、IDE 缓存配置等）。
   - 如发现敏感文件，必须排除或提醒用户确认，禁止盲目提交。
2. **执行暂存**：
   - 默认暂存所有有效变更：`git add -A` 或根据用户需求暂存指定路径。
   - 通过 `git diff --staged --stat` 和 `git diff --staged` 获取暂存区改动的完整上下文。

---

### 第3阶段：生成规范 Commit Message

严格遵循 **Conventional Commits（约定式提交）** 规范生成提交信息。

#### 格式规范

```
<type>(<scope>): <subject>

[可选 body: 详细说明改动原因及核心要点]

[可选 footer: BREAKING CHANGE 或 关联 Issue]
```

#### Type 类型定义

| Type | 适用场景 | 中文说明 |
|------|---------|---------|
| `feat` | 新增功能、新特性 | 新功能 |
| `fix` | 修复缺陷、排查并解决 Bug | Bug 修复 |
| `docs` | 仅文档修改（README、注释、API 文档等） | 文档更新 |
| `style` | 不影响代码运行逻辑的格式变动（空格、标点、缩进等） | 代码格式 |
| `refactor` | 代码重构（既不新增功能，也不修复 Bug） | 代码重构 |
| `perf` | 提高性能、优化执行效率的代码改动 | 性能优化 |
| `test` | 增加、补充或重构测试用例 | 测试相关 |
| `build` | 影响构建系统或外部依赖的改动（npm、gradle、cmake 等） | 构建依赖 |
| `ci` | CI/CD 流程或自动化脚本变动（GitHub Actions 等） | 持续集成 |
| `chore` | 日常维护、辅助工具配置、杂项变动 | 辅助事务 |
| `revert` | 撤销之前的某一提交 | 撤销提交 |

#### 生成规则

- **Scope（范围）**：可选，精确标注受影响的模块或目录（如 `auth`, `router`, `ui`, `config`）。
- **Subject（简述）**：首行简明扼要概括核心变更，尽量不超过 50 个字符。
- **Body（详细正文）**：多文件或较复杂改动时提供，分点阐述修改原因和要点，说明「为什么改」而非仅仅「改了什么」。
- **语言要求**：优先使用中文或项目统一语言，表述专业严谨。

---

### 第4阶段：本地提交

1. 执行提交命令：
   ```bash
   git commit -m "<Commit Message>"
   ```
2. 捕获并记录生成的 Commit Hash（SHA）及提交变更摘要。

---

### 第5阶段：安全推送（Push）

1. **检查远程配置与上游分支**：
   - 查询当前远程仓库配置（`git remote -v`）。
   - 查询当前分支是否存在上游追踪分支。
2. **执行安全推送**：
   - 若已有上游关联分支：执行 `git push origin <branch-name>`。
   - 若为首次推送到远程的新分支：执行 `git push -u origin <branch-name>` 建立追踪关联。
3. **安全准则**：
   - **绝对禁止默认使用 `--force` 或 `-f` 强推**，防止覆盖远程仓库或协作代码。
   - 若推送被远程拒绝（non-fast-forward / 冲突），必须明确提示用户先拉取同步，严禁强行覆盖。

---

## 全局规则

| 规则 | 描述 |
|------|------|
| **严禁强推** | 严禁在未经用户明确要求下使用 `--force` / `-f` 推送 |
| **敏感防护** | 提交前必须扫描并排除密钥、密码、Token 等敏感信息 |
| **规范格式** | Commit Message 必须严格遵循 Conventional Commits |
| **干净退出** | 若无代码变更，直接汇报并安全退出，不执行空提交 |
| **完整汇报** | 执行完成后输出清晰的分支、Commit SHA、Message 及 Push 状态 |

---

## 执行完成后输出格式

提交与推送成功后，向用户输出结构化汇报：

```
## 🚀 Git 提交与推送完成

- **当前分支**：`[branch-name]`
- **提交哈希**：`[commit-hash]`
- **远程状态**：已成功推送至 `origin/[branch-name]`

### 📝 Commit Message
```
<生成的完整 Commit Message>
```

### 📂 变更文件统计
- **新增**：X 个文件
- **修改**：Y 个文件
- **删除**：Z 个文件
```
