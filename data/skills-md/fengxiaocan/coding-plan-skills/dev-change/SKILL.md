# Dev Change — Development Change Log

**任务完成后必须生成变更记录文档。**

## 激活时行为

收到 `/dev-change` 后：
1. 分析当前工作目录中本次修改的文件
2. 读取修改内容（通过 git diff 或当前会话上下文）
3. 按下方文档结构生成 CHANGELOG
4. 写入 `docs/CHANGELOG-YYYY-MM-DD.md`
5. 向用户输出摘要

**禁止：编造验证结果、编造已实现内容、输出空模板。**

---

## 输出位置

自动保存到：

```
docs/CHANGELOG-YYYY-MM-DD.md
```

例如：
- `docs/CHANGELOG-2026-06-11.md`

如果当天已存在同名文件：
- `docs/CHANGELOG-2026-06-11-v2.md`
- `docs/CHANGELOG-2026-06-11-v3.md`

---

## 文档结构

### 1. 修改概述

使用 3~10 行描述，让不了解项目的人也能快速理解：
- 本次任务目标
- 解决的问题
- 修改原因

### 2. 需求来源

格式：
```
### 用户需求
[用户原始需求 / Bug描述]

### 目标结果
[期望达到的效果]
```

### 3. 修改范围

格式：

| 文件 | 类型 | 修改内容 |
|------|------|----------|
| [路径] | 新增/修改/删除/重构 | [简要描述] |

### 4. 核心实现说明

```
### 修改前
[原逻辑描述]

### 修改后
[新逻辑描述]

### 为什么这样实现
[方案选择理由]

### 为什么没有采用其他方案
[废弃方案及原因]
```

**重点解释思路，不要简单复制代码。**

### 5. 关键函数说明

仅记录新增函数和重要修改函数：

```
### 函数名
- 作用：
- 输入：
- 输出：
- 调用关系：
- 注意事项：
```

### 6. 配置变更

如果涉及 Gradle / CMake / Manifest / Docker / Nginx / systemd 等：
- 修改前
- 修改后
- 影响原因

如果没有：**明确写「无配置变更」。**

### 7. 影响范围分析

```
### 直接影响
[受影响的模块]

### 间接影响
[潜在影响的模块]

### 风险点
[可能产生的问题]

### 兼容性
[是否影响旧逻辑]
```

### 8. 验证记录

格式：

| 验证项 | 结果 | 说明 |
|--------|------|------|
| 编译通过 | 是/否 | |
| 单元测试通过 | 是/否 | |
| 功能验证通过 | 是/否 | |
| 回归测试通过 | 是/否 | |

**如果验证失败，必须写明原因。禁止省略。**

### 9. 回滚方案

记录：
- 出现问题时应回滚哪些文件
- 应恢复哪些配置
- 回滚风险

### 10. 后续优化建议（可选）

记录：
- 当前未解决问题
- 技术债务
- 后续优化方向

**不允许混入本次交付内容。**

---

## 生成流程

```
1. 获取本次修改的文件列表（git diff --name-status 或上下文）
2. 读取每个修改文件的关键变更（git diff 或 Read）
3. 按文档结构填充内容
4. 检查 docs/ 目录是否存在，不存在则创建
5. 确定最终文件名（避免覆盖）
6. 写入 CHANGELOG 文件
7. 向用户输出摘要
```

---

## 诚信规则

| 规则 | 说明 |
|------|------|
| 禁止编造 | 未验证的内容不得写「通过」 |
| 禁止猜测 | 不确定的内容标记为「无法确定」 |
| 禁止省略 | 失败的验证必须写明原因 |
| 信息不足时 | 标记为 【未验证】/【待确认】/【无法确定】 |

---

## 最终交付输出

任务结束时向用户输出：

```
## 修改总结
[1~3行概括]

## 验证结果
[编译/测试/功能验证结果]

## CHANGELOG文件路径
[完整文件路径]

## 待确认事项
[如有未验证/待确认内容，列出]
```

确保开发人员无需阅读代码即可理解本次变更。
