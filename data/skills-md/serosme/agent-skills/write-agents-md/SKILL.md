# Write AGENTS.md

## 适用场景

### 目标

把项目级 Agent 指令文件（`AGENTS.md`）维护成两类内容：
**必须遵守的约束**，以及**决策点与理由**（为什么用这个、为什么不用那个）。
让 Agent 读完后知道「什么时候用哪个、为什么、违反了会怎样」，
而不是把读一遍代码就能得到的东西再抄一遍。

### 适用

- 新建项目的 `AGENTS.md`。
- 精简、重写已有文件，删掉能从代码读到的内容。
- 补充约束，把踩过的坑固化成可检索的规则。
- 改动或决策后主动维护：完成代码改动、做出取舍或踩到坑之后，先判断本次是否产生了
  新的约束、取舍或环境事实；有则在同一次改动内写入，没有则不写，不等用户提醒。
- 审查 `AGENTS.md`，指出过时、重复、无法判断的内容。

### 不适用

- 写面向人的项目说明、上手文档或 API 参考（那属于 README 或 docs）。
- 编写 Agent Skill 本身（使用 `write-skills`）。
- 未读代码就替用户补写实现细节或架构说明。

## 前置条件

### 必要输入

- 目标文件路径（默认仓库根目录的 `AGENTS.md`）。
- 本次目的：新建、精简、补充约束、主动维护，还是仅审查。

### 可选输入

- 项目校验命令（如 `pnpm lint`、`pnpm typecheck`），文档与代码同时改动时用于验证。
- 必须保留的规则、被外部引用的章节措辞。
- 交付方式：在对话中返回内容，或直接写入文件。

### 参考规范

开始编写前，读取：

- [内容分类与写法规则](references/authoring-rules.md)：判定问句、约束与决策点句式、压缩手法、锚点维护。必读。
- [AGENTS.md 骨架](assets/agents-md-template.md)：新建文件时作为起点。

需要完整案例或边界处理方式时，读取
[精简与反馈示例](references/examples.md)。

### 信息缺失处理

- 目标文件不存在而用户要求精简时，先确认路径，不直接新建。
- 「精简」强度未说明时，默认只保留约束与决策点、删除代码可读内容，并在交付时列出删了什么。
- 某条决策的理由无法从代码、提交记录或用户说明中确认时，询问用户，不臆造理由。
- 文件未纳入 Git 或存在未提交改动时，先提醒可回溯性，再做整段删除。
- 用户分批提供多个文件时，收齐后再统一改写。

## 执行步骤

### 步骤 1：判断本次是否需要维护

- 操作：
  - 触发式入口：当本次任务由代码改动、新的取舍或踩到的坑引起，而不是用户要求改写时，
    先判断是否产生了新的约束、决策点、命令与环境事实。
  - 依据 diff、本次决策与用户说明逐条问「这条以后还能约束别人吗」；
    答案为「否」就留在代码里，不写进本文件。
  - 判定为需要：进入步骤 2，并在同一次改动内完成更新。
  - 判定为不需要：结束本技能，不改文件，在回复中说明「本次无新约束，未改本文件」。
  - 用户明确要求新建、精简、重写或审查时，本步骤直接通过，进入步骤 2。
- 完成标志：
  - 已给出「更新 / 不更新」的判定与理由，没有为了显得有产出而空改文件。

### 步骤 2：盘点现有文件与外部引用

- 操作：
  - 读完整个目标文件，记录行数与字数或字节数。
  - 搜索引用：`AGENTS.md`、`@AGENTS.md`，以及其他文件引用的章节名
    （例如代码注释里的「见 AGENTS.md 的『CPU 限制』」）。
  - 确认文件在 Git 中的状态：是否已提交、能否回溯。
  - 确认同仓库是否还有同类指令文件（子目录 `AGENTS.md`、`CLAUDE.md`、
    `.cursor/rules`、`.github/copilot-instructions.md` 等），记录内容重叠处。
  - 目标文件不存在（新建）时跳过引用盘点，以骨架为起点，
    但仍要先确认项目校验命令、安全边界与部署方式。
- 完成标志：
  - 已列出被外部引用的锚点清单，或确认本次为新建。
  - 已知文件体量、可回溯性，以及本次规则该落在哪一份文件。

### 步骤 3：把每条内容归入保留、改写或删除

- 操作：
  - 按 [内容分类与写法规则](references/authoring-rules.md) 的判定问句逐条分类。
  - 约束、决策点、命令与环境事实保留；能从代码读到的清单与实现描述删除；
    跨章节重复的合并；与文件定位冲突的规则改写。
- 完成标志：
  - 每条内容都有明确归属，没有「说不清属于哪类所以先留着」的条目。

### 步骤 4：改写成可判断的约束与决策点

- 操作：
  - 约束写成必须、禁止或需确认，一条一件事，能判断是否被违反。
  - 决策点写成「选择 A、不用 B 的原因、代价或前提」，
    并附可核对的证据（报错文本、实测数字、平台限制）。
  - 踩过的坑保留可检索的症状，再给应对规则。
  - 与文件定位冲突的规则改写并说明理由。
- 完成标志：
  - 读者能据此判断怎么做，以及为什么不能换别的做法。

### 步骤 5：核验引用与硬性内容

- 操作：
  - 对照步骤 2 的锚点清单确认引用仍成立；措辞变了就同步更新引用处。
  - 确认校验命令、安全边界、提交与部署约定等硬性内容没有遗漏或被弱化。
  - 确认维护责任条款已在文件开头，且写明了触发时机与判定标准。
  - 文档与代码同时改动时，按项目约定运行校验命令。
- 完成标志：
  - 引用不断、硬约束不丢、校验结果已知。

### 步骤 6：验收并交付

- 操作：
  - 逐条核对「输出与验收」中的验收标准。
  - 可自行修正的格式或遗漏，修正后重新检查。
  - 无法确认是否该删除的内容保留，并列为待确认项。
  - 主动维护模式下，在回复中写明本次更新了哪些条目，或为什么判定不需要更新。
- 完成标志：
  - 验收项全部通过，或明确列出未决问题及其影响。

## 约束

### 内容边界

- 只写三类内容：约束、决策点、命令与环境事实；其余删除。
- 不写能从代码读到的内容：功能清单、目录职责逐项说明、表结构、
  API 逐路由要点、组件清单、页面结构。
- 不写与当前代码不符、也无法验证的内容；不臆造决策理由。
- 决策点必须给出备选与代价，不写成「我们用了 X」的单边陈述。
- 具体句式、压缩手法与反例见 [内容分类与写法规则](references/authoring-rules.md)。

### 主动维护

- 改动方负责：完成代码改动或做出取舍的 Agent 在同一次改动内判断并更新，
  不等用户提醒，也不把更新留成待办。
- 触发与条件分开：每次改动后都要判断，但只有新增或改变约束、决策点、
  命令与环境事实时才写入；纯重构、修 bug、加实现而未改变约束时不写。
- 必须把维护责任条款写进目标 `AGENTS.md` 本身：本技能按需加载，不能指望它常驻；
  条款要含触发时机、判定标准与「无变化时不写」。
- 判定由 Agent 自己做，依据 diff、提交记录与本次决策；
  不把「要不要更新」交回用户，只有某条取舍的理由无法确认时才询问。
- 判定为不需要更新时说明理由，不为了显得有产出而追加条目；
  新增条目先查已有条目，能合并就合并，避免文件随维护持续膨胀。

### 语义保留

- 精简不等于放宽：原有校验命令、安全边界、语言与文案约定、提交规范
  不得删除或弱化，除非用户明确要求。
- 与用户既定规则冲突时，说明冲突并请求确认，不静默覆盖。
- 保留被外部引用的章节措辞；确需改名时同步更新所有引用处。

### 操作边界

- 只改用户指定的 `AGENTS.md` 及明确授权的文件，不动其它文档。
- 改写已有文件前先读取其内容；不创建被引用但未交付的附件。
- 整段删除前确认文件可回溯（已提交或有备份），否则先提醒用户。
- 不自动执行提交、推送或安装等操作。
- 用户只要求审查时，输出问题与改法建议，不改文件，等用户确认后再动手。
- 同仓库存在多份同类指令文件时，规则只写在最贴近的一处，其余位置指向它；
  发现重复或冲突先报告，不擅自改另一份文件。

### 异常处理

- 内容归属或删除风险无法判断时，保留并列为待确认项，不擅自删除。
- 文件过大或一次读不完时，分段读取后再分类，不凭片段下结论。
- 校验命令失败时，先判断是否由本次改动引起；与本次无关的既有失败如实报告，
  不宣称通过。
- 引用冲突无法消除时，停止相关部分并给出可选方案，等用户决定。

## 输出与验收

### 交付内容

- 目标文件路径与完整内容，或写入结果。
- 保留、改写、删除的章节清单。
- 前后体量对比（行数、字节或字数）。
- 外部引用锚点的核验结果：哪些仍成立、哪些同步改过。
- 实际运行的校验命令及结果；未运行的说明原因。
- 主动维护模式下：本次判定结论（更新了哪些条目，或为什么判定不需要更新）。
- 仅审查模式下：问题清单（按「必须修 / 建议 / 存疑」分级，附位置）与改法建议，不改文件。

### 验收标准

- 文件只含约束、决策点、命令与环境事实三类内容。
- 每条约束可判断是否被违反；每个决策点都有备选与代价。
- 没有残留的代码可读内容（功能清单、目录职责、表结构、API 逐条说明、组件清单）。
- 更新时机写成「每次改动后判断、只在约束或取舍变化时写入」，
  而不是「改了代码就更新本文件」，也不是「本文件不随代码更新」。
- 维护责任条款已写进目标文件本身，含触发时机、判定标准与「无变化时不写」。
- 主动维护时给出「更新 / 不更新」的判定与理由，没有空改文件。
- 仅审查模式下没有改动任何文件，问题可定位到章节或行。
- 外部引用锚点全部仍存在，或已在引用处同步更新。
- 原有校验命令、安全边界与提交约定无遗漏、无弱化。
- 冲突规则已改写并说明理由，不存在两条互相矛盾的规则。
- 精简类任务给出前后体量对比，且确有下降。
- 未验证部分与待确认项如实列出，未把「读过代码」描述成「跑过测试」。

## 示例

场景一：用户要求把 191 行 / 43.4 KB 的 `AGENTS.md` 精简为约束与决策。

预期行为：

- 删除功能清单（F1–F17）、目录职责、三张表结构、API 逐路由要点、组件清单。
- 保留并重写核心约束；把长段落压成「选择、备选的原因、代价」。
- 新增两条约束：任何代码修改后必须执行项目校验命令；
  模板只能引用 `script` 中出现的标识符（附 vue-tsc 报错文本）。
- 在定位说明里补上维护责任：每次改动后判断，只在约束或取舍变化时写入。
- 核验代码注释引用的「CPU 限制」「菜单分节统一约定」两个锚点仍然存在。
- 交付时给出 43.4 KB → 9.5 KB、191 行 → 103 行的对比与删除清单。

场景二：用户没有提到 `AGENTS.md`，但刚完成一次代码改动。

预期行为：

- 先判断本次是否产生新约束：新增了「重试必须走 `retryFetch`」这类规则才写入。
- 判定为需要时，在同一次改动内更新，并说明新增或改写了哪些条目。
- 判定为不需要时，不改文件，在回复中说明「本次无新约束，未改本文件」。

完整案例、边界处理与反馈写法见
[精简与反馈示例](references/examples.md)。
