Erstelle, prüfe und verwalte den Lebenszyklus von Specs (`SPEC NN`) für ein Feature, bevor auch nur eine Zeile Code geschrieben wird — die bewusst langsame Phase eines spec‑driven Design‑Flows. Stelle sokratische Fragen, um jeden Abschnitt von `templates/SPEC.template.md` zu füllen (Kontext, Ziele, Nicht‑Ziele, Abhängigkeiten, funktionale Anforderungen, Schnittstellen und Verträge, nicht‑funktionale Anforderungen, Randfälle, Akzeptanzkriterien, Risiken, offene Fragen), weise die fortlaufende Nummer `NN` zu, prüfe die Referenzen `Depends on:` und steuere die Statusübergänge Draft → In review → Approved → Implemented → Obsolete (oder deren spanische Entsprechungen — Borrador → En revisión → Aprobado → Implementado → Obsoleto). Nutze diesen Skill, wenn der Nutzer fragt „schreiben wir das Spec für…“, „ich brauche ein Spec für…“, „let's spec out…“, „write a spec for…“, „schicke dieses Spec zur Prüfung“, „ich genehmige SPEC 04“, „approve SPEC 04“, „was sagt SPEC 02?“, „dieses Spec ist veraltet“, oder `specs/SPEC‑NN` explizit erwähnt. Schreibe niemals Anwendungs‑Code und beginne keine Implementierung — das ist Aufgabe von **bambu‑spec‑implement**, das erst startet, wenn das entsprechende Spec den Status Approved erreicht.

Bitte antworte immer in der Sprache des Benutzers.
