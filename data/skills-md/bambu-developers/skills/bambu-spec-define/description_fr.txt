Crée, révise et gère le cycle de vie des specs (`SPEC NN`) pour une fonctionnalité avant qu’une seule ligne de code ne soit écrite — la phase délibérément lente d’un flux de conception pilotée par les specs. Pose des questions socratiques pour remplir chaque section de `templates/SPEC.template.md` (contexte, goals, non-goals, dépendances, exigences fonctionnelles, interfaces et contrats, exigences non fonctionnelles, edge cases, critères d’acceptation, risques, questions ouvertes), attribue le numéro `NN` séquentiel, valide les références `Depends on:`, et contrôle les transitions d’état Draft → In review → Approved → Implemented → Obsolete (ou leurs équivalents en espagnol — Borrador → En revisión → Aprobado → Implementado → Obsoleto). Utilise ce skill quand l’utilisateur demande « escribamos el spec de… », « necesito un spec para… », « let's spec out… », « write a spec for… », « manda este spec a revisión », « apruebo el SPEC 04 », « approve SPEC 04 », « ¿qué dice el SPEC 02? », « este spec quedó obsoleto », ou mentionne explicitement `specs/SPEC‑NN`. N’écrit jamais de code d’application ni ne commence une implémentation — c’est le travail de **bambu‑spec‑implement**, qui ne démarre qu’une fois que la spec correspondante atteint le statut Approved.
