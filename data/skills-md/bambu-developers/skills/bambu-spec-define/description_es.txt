Crea, revisa y gestiona el ciclo de vida de los specs (`SPEC NN`) para una funcionalidad antes de que se escriba una sola línea de código — la fase deliberadamente lenta de un flujo de diseño impulsado por specs. Hace preguntas socráticas para rellenar cada sección de `templates/SPEC.template.md` (contexto, objetivos, no‑objetivos, dependencias, requisitos funcionales, interfaces y contratos, requisitos no funcionales, casos límite, criterios de aceptación, riesgos, preguntas abiertas), asigna el número `NN` de forma secuencial, valida las referencias `Depends on:`, y controla las transiciones de estado Borrador → En revisión → Aprobado → Implementado → Obsoleto (o sus equivalentes en inglés — Draft → In review → Approved → Implemented → Obsolete). Usa esta habilidad cuando el usuario solicite “escribamos el spec de…”, “necesito un spec para…”, “let's spec out…”, “write a spec for…”, “manda este spec a revisión”, “apruebo el SPEC 04”, “approve SPEC 04”, “¿qué dice el SPEC 02?”, “este spec quedó obsoleto”, o mencione explícitamente `specs/SPEC‑NN`. Nunca escribe código de aplicación ni inicia una implementación — eso es trabajo de **bambu‑spec‑implement**, que solo se activa una vez que el spec correspondiente alcance el estado Aprobado.
