# 审查测试设计

黑帆测试官不为凑数升旗：只把能改变执行、覆盖或信心的断点带入复核，并用航海日志中的证据裁决。

复核测试产物的自洽性与证据链，把有依据的文档缺陷消解在交付前。审查聚焦会改变执行、覆盖或信心的问题。

## 交付自校

生成或实质更新完整测试分析、独立模型或用例集时，负责成稿的 Agent 自行复核并修正本轮产物；上层组装尚未完成的中间结果由组装者统一处理。简短澄清、进度和不改变测试含义的文字调整不启动整套复核。用户只要求审查已有文件时只报告；明确要求修改时才修改这些既有文件。

先读取 `test-privateer/references/artifact-routing.md` 的“统一编号与追溯”和“测试术语”，固定当前稿与有效依据，逐项核对本轮定义、引用和规则主张。每个引用能定位到唯一且语义相符的定义，缩写可无歧义还原；每个状态模型使用明确主体和身份判定；结论、模型、测试点与当前安排在同一对象、范围和阶段下相符。发现、缺陷和原因判断遵循术语定义，明确各自的证据。已有规则支持的检查有去向，宣称完成的更新能在实际产物中找到。编号只是定位手段，核对需阅读其对应内容，不依赖固定 Markdown 版式或编号检查脚本。

发现缺陷后，成稿 Agent 查原文和可取得的依据，自行决定修正。错号、失效引用、遗漏的既定内容和未同步的图表直接修正并更新关联位置；缺号先判断是引用写错还是实际少了内容，不为凑齐编号新增测试。语义冲突先区分主体、适用范围、时点、历史版本、实现事实和目标规则；只有同一条件要求相反结果才判冲突，可兼容要求补清边界。

涉及多份资产、状态或决策模型、重要规则变化时，在能力允许的情况下使用独立上下文审阅，提供原任务、有效规则、当前稿及必要依据。审阅者返回证据与意见，不代替成稿 Agent 裁决；已被委派的审阅者直接工作，不再委派。独立审阅不可用时由成稿 Agent 完成自校，如实说明验证方式。

成稿 Agent 根据证据接受、驳回或修正复核意见，无需用户逐项批准文档纠错。同类错误出现时，沿该规则检查其他使用位置，不只复核被点名的编号。修改后重新阅读受影响的定义、引用、模型和结论，确认拆分、合并或重排没有丢掉原有观察点、证据边界和执行限制；仍有可依据现有材料解决的缺陷就继续修正，不把它转成用户待办。没有新证据的重复意见由 Agent 对齐范围后裁决，不反复发起全量审查；范围外建议不阻塞当前交付。收窄完成声明时，已识别但未覆盖的范围仍需保留后续安排或排除理由。

只有现有材料和可自行调查的事实仍不能确定业务规则，或需要用户选择范围、接受风险或扩大授权时，才提出具体决策问题。无法确认的业务预期保留为未知，其他已明确内容继续完成。工具失败或修复尚未完成时报告实际未完成项，不包装成需要用户确认的业务问题或复核通过。

交付的是修正后的产物，附必要的修改摘要和真正待决的业务问题；内部审查分歧按需保留证据，不要求用户逐条审阅。自校完成以当前产物的已发现文档缺陷已修正、关联内容已复读且有效规则未被误改为准；有未知时范围和影响明确。复核不等于产品测试执行或通过。

## 检查分析链

从测试对象追到产品内容、测试点、风险、模型、任务、证据和结论，检查：

- 把 PRD 当测试对象，而不是测试依据之一；
- 默认询问研发、联调、上线等项目治理决定；
- 按职称推断用户权限，或要求用户代替职责之外的负责人制定规则；
- 只看当前需求，遗漏真实业务流程、上下游、接口、数据或状态；
- 按产物路由需要维护的项目 TCO 缺少关键业务链、扫描依据、覆盖节点或取证动作；
- 实际业务与系统证据不足，却声称已完成相应范围分析；仅缺 TCO 文件不构成此项；
- 事实、推断和未知混写；
- 计划内未实现被写成缺陷，或以研发阶段为由遗漏独立的需求问题与现存异常；
- 原因结论没有回应原问题，或把止损、触发条件和局部防护缺陷当成全部原因；
- 以时间先后、复现成功或修复后通过代替机制证据，未交代剩余解释；
- 正文标题和交接内容混用多个译名，或把英文术语直接当作用户可见结论；
- 将用户授权选择方案写成已有成本证据，或将业务规则确认当作风险已接受；
- SFDIPOT 只有摘抄清单，没有具体产品元素、关系和未知，不能支持后续分析；
- 单一 PRD 或单一人员说明被写成完整系统扫描，没有标明证据边界和取证动作；
- MFQ 只有 M/F/Q 名词，没有行为关系和测试点；
- 风险脱离产品内容，或没有改变测试；
- 多个候选测试点未经用户选择、产品风险或新证据筛选，就直接挑熟悉的技术问题建模；
- PPDCS 只有模型标签，没有实际模型、覆盖准则和 TCON；
- TCON 无法追溯到路径、规则、分区、组合或迁移；
- 前置状态、角色、数据分区、动作、观察位置、oracle、关联风险、测试层级或环境不同，却被塞进同一个 TCON；
- 测试任务缺少前置状态、角色、权限、数据、动作、观察位置或 oracle；
- Case 集没有说明已转换、待转换、阻塞和排除范围；
- 含接口、字段、账号、环境或数据占位符，或缺失 oracle 的 Case 被标为可执行；
- 批量常规 Case 使用重复长列表，导致无法快速比较和执行；
- Case 依赖另一条 Case 的执行结果，或混入不同刺激和 oracle；
- 所选数据与观察无法区分正确行为和所防范的错误行为，未满足 designing-test-experiments 的区分力要求；
- 所有 Case 被要求保存同一套重型证据，或并发重复次数没有依据和停止条件；
- 未知政策被写成预期结果；
- 同一规则在结论、模型和测试点中的动作或结果不一致，可能使测试判定相反；
- 用例设计完成被称为可执行，或未核实条件被误报为未实现；
- 下一步没有说明具体对象、动作和产物，导致用户不知是在设计、准备还是执行；
- 接口／页面自动化设计入口声称已提供尚未接入的代码实现能力；
- 测试设计被写成执行证据，或结论强于原始观察；
- 为需求、ticket 或测试轮次另建任务级 TCO，而不是复用项目唯一 `testing/TCO.md`；
- 把单个 Spec 的模型、TCON、用例、实现步骤或逐步证据写入项目 TCO；
- 需求资产不能追溯到其需求来源，或分析、用例、依据存在多个冲突的维护位置；
- 声称内容已升级到 TCO，却不能证明其跨 Spec、共享机制或长期影响；
- 使用项目审批、抽象治理或非测试业务语言，导致用户不知道下一步怎么做；
- 高价值行为还缺模型、TCON、oracle 或可执行测试，却声称测试分析足以支持实施。

检查文档是否把已解决问题保留在待办、旧规则留在有效预期、风险状态无证据更新，或用历史探索主题代替可执行用例。主分析保留全部已识别测试点及安排，用例独立，长依据按需拆分。

## 输出

```markdown
## 审查发现
断裂点 — 资产中的直接证据

## 影响
受影响的执行、覆盖或证据结论

## 最小修正
能够修复断裂的一项可检查改动
```

独立审阅按上述格式把意见返回成稿 Agent；用户只要求审查时直接交付审查结果。成稿交付按“交付自校”修正并简述结果，保留正确内容；不以罗列审查发现代替完成修正。

表格不是目的。只有表达方式妨碍比较、执行或审查时，才把它报告为 finding；单条复杂 Case 使用详细步骤不是缺陷。

用户或既有流程要求判断分析能否支持实施时，给出以下判定；其他审查只说明当前请求的完成程度和下一步：

- **足以支持实施：** 实施计划无需发明产品行为、规则、边界或 oracle。
- **暂不足以支持实施：** 列出阻塞未知、证据来源、应答角色及其测试影响。

**完成条件：** 每个审查发现都有直接证据、实际影响和最小修正；项目基线、模型、TCON 粒度和阶段边界已按范围检查。成稿任务满足“交付自校”的完成条件；仅审查任务返回有依据的意见与核实限制。

交回调用方时附阶段交接：修正后产物路径、发现及处理结果、仍未解决的缺口、已复读的关联文件、是否可进入执行和执行许可。
