# 分析产品风险

产品风险，是威胁产品价值的不确定性，不是 Bug 的同义词。

风险驱动测试，是让风险改变怎么测；不是把所有测试内容改写成风险。

## 分析

接收调用方给出的产品内容、候选测试点、业务与系统上下文和证据状态。先明确用户任务、现状痛点、产品承诺和成功信号。价值锚点缺失，或分析仍停在功能孤岛和 PRD 原句时，先返回需要补齐的产品上下文。

同时检查两类风险：

- **价值未实现：** 功能可以运行，但没有减少工作、改善结果或获得采用。
- **产生伤害：** 错误行为、错误结果或失控条件造成数据、资金、运营、安全、合规或信任损失。

正常研发阶段中，计划内但尚未实现的目标行为是实施状态，不是产品行为风险。分析拟议产品即使按设计实现，仍可能无法兑现什么价值或造成什么伤害。范围遗漏、延期或错误取消确实威胁价值时，记录为项目或交付风险，不冒充产品缺陷。

价值未实现不必包装成故障机制。先说承诺的改善没有发生，再说明出现条件和证据。

每个风险建立完整证据链：

- 对应的用户任务、产品承诺、产品元素、关系或测试点；
- 哪项价值可能没有实现，或在什么状态、角色、数据、顺序、环境或负载下可能产生什么伤害；
- 它如何影响用户结果、工作量、采用、业务流程、数据、运营、集成、安全或合规；
- 支持其发生可能性和后果的事实、历史数据、观察或明确推断；
- 可发现性、可恢复性和仍会改变判断的未知；
- 与其他风险相比为什么更值得先测或深测；
- 哪项新证据会提高、降低或推翻当前排序；
- 它具体改变哪些测试点、顺序、深度、数据、环境、oracle 或投入；
- 下一项分析或测试任务，以及要获得的证据。

没有可信数据时使用定性判断，不编概率和分数。说明排序依据及不确定性，已有授权内按证据推进；重大范围或投入选择才需确认。接受风险由有权负责人决定，不凭职称推断权限。

排序先看是否威胁核心用户任务和产品承诺，再比较影响范围与频率、伤害、可恢复性和证据强弱。罕见但吓人的技术故障，不自动压过普遍发生的价值落空。

“没有省事”可以是完整的价值风险，但必须说明承诺减少的工作、比较基线和观察证据。“幂等不足”“缓存失效”“接口超时”只是机制或诱因；必须说明它威胁哪项价值或造成什么伤害，以及为什么比其他候选更值得投入。

## 让风险发生作用

风险只有改变测试才保留：提前、加深、换环境、加强 oracle、增加恢复或异常测试，或明确降低优先级并记录残余风险。合并重复风险，删除无法追溯到产品内容的通用风险。

风险排序不是行动清单。把判断投影到具体测试点：选择本轮最值得分析或设计的 1～5 项，写清为什么现在、下一产物和启动条件。独立高伤害专题需要不同环境或方法时单列，不因未进本轮而降成低优先级。调用方决定持久化和后续动作。

## 风险生命周期

读取 `test-privateer/references/artifact-routing.md`，按“统一编号与追溯”和风险单一归属记录风险编号、场景与业务影响、当前判断和依据、状态、关联测试、最新证据与判断变化、下一步。

| 状态 | 含义及证据要求 |
| --- | --- |
| 待调查 | 风险假设仍待调查，说明来源和不确定性 |
| 处理中 | 正在调查、控制或验证，记录进展及下一动作 |
| 已控制 | 证据支持指定版本与范围内的控制，保留残余风险和回归要求 |
| 已排除 | 证据证明假设在所述范围不成立；暂不测试不等于风险已排除 |
| 已接受 | 有权负责人明确接受，记录理由、范围、条件和来源 |

用例通过不自动关闭风险，修复不代替验证。每轮按证据提高、降低或修正判断；新变更、失效控制或反证可复开为待调查或处理中，记录原因。原始证据留在来源处，清单只保留当前结论、必要变化摘要和链接。

交回调用方时附 handoff：风险清单路径、当前选中的测试点／TCON、未选范围及理由、阻塞 oracle、下一步建模／设计动作和执行许可。

## 风险记录

```markdown
产品元素／关系
用户任务与产品承诺
价值缺口或伤害及其出现条件
用户、业务或系统影响
证据、推断与未知
可发现性与可恢复性
相对优先理由
改变排序所需证据
改变的测试工作
```

展示暂定排序、理由和改变排序所需证据。选择会实质改变测试范围、投入或环境时，请用户确认；否则可以带着证据边界推进一个安全、最小的高价值测试轮次。未确认的排序不写成既定 P0/P1。其余风险保留，不同时全部展开。

**完成条件：** 每个重要风险都能追溯到用户任务和产品承诺，说明威胁的是价值实现、负面伤害或两者，并有证据链、相对优先理由、改变排序所需证据和具体测试影响；风险判断已落到具体测试点；需要确认的选择已确认或明确保留证据边界。
