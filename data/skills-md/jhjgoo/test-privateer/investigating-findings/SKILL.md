# 异常调查与根因分析

从观察取得证据，用对照检验解释。发现、缺陷和原因判断的含义沿用产物路由的“测试术语”。

核实异常时，交付观察事实、判定依据、影响和待查项；用户要求定位原因时，还需解释原问题的产生机制及证据范围。沿用当前任务的深度，不为普通异常核实强制开展完整根因分析。

沿用原测试项、用例和证据链接；产生新风险或测试项时按 `test-privateer/references/artifact-routing.md` 的编号规则维护，已有缺陷平台编号继续引用。

沿用独立／项目路径：独立任务在对话或指定位置交付；项目任务将观察、调查、缺陷证据和残余风险写入对应测试文档，只有长期或跨 Spec 结论才更新 TCO。

## 调查

1. **界定问题：** 记录原始请求、异常、版本和证据，分开观察与解释，明确要核实或解释的现象。
   用户的问题可能包含多个观察、指标或隐含主张。先逐项列出它们，并标记为已解释、仅有相关性或放大条件、尚未解释，或与其他主张重复／可由其推出。原因结论不得因解释了其中一项就自动覆盖其他主张。
2. **追查链路：** 取得相关输入、输出、状态和近期变化。定位原因时沿异常的产生、传播与反馈追查，区分产生原因、放大条件和防护失效；每段解释指向证据或明确缺口。若问题表现为回归、行为漂移、测试失效或后续工作受阻，继续追溯引入当前条件的变更、计划、决策和验证证据，说明问题为何在该变更中产生、遗漏或被放大。
3. **提出解释：** 从产品、规则、环境、数据、观测或测试设计中选择仍可能成立的原因假设，为重要假设写出可观察预测及反证。
4. **建立对照：** 比较相近的受影响／未受影响、变化前／后对象，或在授权范围内改变一个条件。选择最能区分解释的探查，记录预期区分信号；执行后说明结果支持、排除或仍无法区分什么。
5. **更新判断：** 界定用户、数据、状态、集成、频率和恢复影响，根据证据继续追查或交付。原因结论逐项对应原问题，未解释部分保留下一取证动作及限制。

原因候选过窄、对照难选、输入难缩减或涉及多条件和跨系统事故时，读取 `references/causal-methods.md` 选择方法；不逐项套用。

可自行取得的关键证据仍缺失时继续调查。外部不可观测、证据不可取得或继续调查已不能改变当前措施时，可以交付有限结论，说明调查到哪里及为何停止。止损和预防措施分别说明验证范围；复现现象、回滚恢复或修复后通过，都不自动证明完整因果关系。

调查改变风险判断时，按 analyzing-product-risks 的生命周期更新唯一归属并引用证据；缺陷状态与风险状态分别维护。

## 调查记录

```markdown
## 观察
发生了什么 — 环境／数据／顺序 — 原始证据

## 判定依据
期望行为 — 来源与适用范围；缺失时保留未知，不阻止收集异常证据

## 触发与边界
哪些条件触发／不触发

## 影响
谁或什么受到怎样的影响

## 原因假设与检验
- 假设 — 支持证据／反证 — 可观察预测 — 区分动作 — 实际结果或未执行

## 变化溯源
引入变化 — 变化目标 — 当时验证 — 遗漏或失效环节

## 当前结论与下一步
已解释的现象 — 机制及证据范围 — 尚未解释部分 — 下一取证或验证动作
```

只有证据支持时才称为缺陷。测试错误可修正并重跑；实现偏离已确认需求时，在已有开发／修复授权内衔接修复和回归，否则交付缺陷证据；规则歧义返回澄清，只阻塞相关测试。不能靠删断言、跳过测试或扩大替身范围消除失败。正式缺陷单字段仅在交接流程需要时添加。

**完成条件：** 核实异常已有事实、判断依据和影响边界；原问题中的每个重要观察或主张都有对应的事实证据、解释机制、适用范围和未知或反证边界。原因调查的结论范围不得超过已解释的主张；仅定位到放大或防护问题时，仍需交代异常产生为何已解释或尚未解释。若结论涉及回归、漂移或资产失效，还要说明引入条件的变更及其验证缺口。只解释了部分主张时，交付部分结论并保留剩余主张的下一项区分性取证。局部调查留在需求资产，后续验证针对原现象。

交回调用方时附阶段交接：调查路径、结论及证据、已解释／未解释范围、风险变化、下一项探查或修复回归动作及执行许可。
