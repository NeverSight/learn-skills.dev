# 建立项目测试地图

项目 TCO 是长期测试地图，不是当前需求的分析报告。先看完整产品，再测试局部变化。

## 输入与边界

本 Skill 只用于 `heuristic-testing` 的项目路径。读取 `heuristic-testing/references/artifact-routing.md`，确定项目边界和唯一 `testing/TCO.md`。

输入包括产品目标、用户与业务流程、架构和代码、接口与数据契约、运行环境、历史缺陷、监控和已有测试资产。PRD 只是证据之一。

只写长期项目认知。单个 Spec 的模型、TCON、用例和执行记录留在该 Spec。

## 建图

### 1. 钉住产品价值

用 `clarifying-test-basis` 共同确认：谁使用产品、要完成什么、当前代价是什么、产品承诺改变什么、怎样观察改善。能调查的事实先调查；缺失信息写成未知、负责人和取证动作。

**门槛：** 核心用户任务、产品承诺和关键业务链有权威证据。仅凭代码、架构和需求文档可以生成 TCO 草案；产品价值、真实业务链或成功信号缺少权威证据，且会改变地图或风险重点时，记录取证任务并停在澄清边界。不得用当前 PRD 代替项目上下文。

### 2. 扫描项目

用 `scanning-product-with-sfdipot` 扫描整个项目：

- Structure：组成、存储、配置及关系；
- Function：能力、规则、状态变化、异常与恢复；
- Data：输入、输出、存储、转换、约束和生命周期；
- Interfaces：页面、交互、API、消息、文件和人工交接；
- Platform：设备、服务、基础设施、资源和环境；
- Operations：真实使用、误用、管理、运维和恢复；
- Time：顺序、并发、耗时、超时、重试、过期和恢复窗口。

每个因子必须包含具体项目元素、元素关系和来源；不知道就写未知及取证动作。七个标题填满 PRD 摘录不算扫描。

**门槛：** 关键业务链已跨角色、系统、接口、数据和状态画通；七个因子没有无说明空白。

### 3. 建立顶层 MFQ

用 `analyzing-test-space-with-mfq` 组织：

- M：项目提供的能力和产品内容；
- F：能力之间、人与系统之间、上下游之间的交互；
- Q：利益相关者真正关心的质量特性及失败表现。

为项目覆盖节点分配稳定 ID。MFQ 必须生成可继续调查的具体测试点，不交付缩写清单。

### 4. 标出长期薄弱面

用 `analyzing-product-risks` 识别价值落空和负面伤害。记录长期产品风险、oracle 缺口、不可观测链路、回归保护和自动化薄弱面；风险必须改变测试重点、深度、环境、观察或投入。

## 写入 TCO

读取 `references/project-test-map-template.md`，维护项目摘要与证据索引。SFDIPOT／MFQ 的具体成果按业务与系统组织，详细已有资料直接引用。长期风险使用 analyzing-product-risks 的生命周期，按 artifact-routing 维护唯一归属；需求证据只更新实际支持的项目范围。

旧认知与新证据冲突时保留证据链并修正结论，不另建第二份 TCO。

**完成条件：** TCO 能以权威证据回答谁在何种业务链上使用哪些系统完成什么结果；关键接口、数据、状态、时间和恢复机制有来源或取证动作；SFDIPOT 七因子具体，顶层 MFQ 可用于判断变化影响；长期风险和薄弱面有稳定 ID。否则地图保持草案，说明哪些影响判断尚无依据；只暂停依赖这些未知的结论，不阻止其他证据充分的分析。
