# 设定测试任务

测试任务回答：用户要完成什么，产品承诺改变什么，这次要了解、验证或产出什么，下一步做什么。

## 建立任务

1. 沿用当前请求和已确认上下文中的测试目标。只给测试对象或方法，且分析、设计、执行会产生不同结果时，简述当前理解，问一个决定本轮工作的问题并等待回答；此前只做支撑提问的调查，不扩写完整测试文档。目标已明确或用户要求先自主分析时，按已知范围推进并标明假设。
2. 建立价值锚点：用户任务、现有做法、最费力或最受限之处、产品承诺的改善、可观察的成功信号。指标未知就记录未知，不编阈值。
3. 说明证据的使用者及其需要回答的问题。只有准入、放行、停止或风险接受场景才记录实际决策人与证据门槛。
4. 把需求放回真实业务：参与角色、触发、目标、规则、损失和恢复。
5. 界定测试对象：系统边界、上下游、接口、数据流、共享状态、环境和权限。
6. 区分已知事实、合理推断和未知。缺失信息会改变任务时，调用 `clarifying-test-basis`。
7. 写出当前需要验证的价值问题；只有测试重点、深度或顺序需要它时，才补暂定风险。不用空泛风险替代产品分析。
8. 选择一个最高价值的下一步，说明要获得的证据以及它会改变什么。

下一步可以是澄清、产品分析、风险分析、建模或执行。产品行为和 oracle 尚不清楚时，先补认知，只暂停依赖未知规则的精确预期，继续已明确部分的分析与设计。下一步写明业务对象、具体动作和交付物，区分编写用例、核实执行条件与实际运行。

## 测试任务卡

```markdown
## 测试目的
要了解、验证或产出什么 — 证据使用者

## 工作方式
沿用 heuristic-testing 已确认的独立／项目任务 — 交付位置 — 当前停止阶段

## 业务价值
用户任务 — 现有做法与痛点 — 产品承诺 — 成功信号

## 业务与系统上下文
业务流程 — 参与角色 — 测试对象 — 系统边界 — 上下游 — 接口／数据／状态

## 范围与约束
包含 — 排除 — 环境／权限／时间约束

## 已知、推断与未知
- 内容 — 类型 — 来源／待确认负责人

## 当前关注
- 需要验证的价值或暂定风险 — 依据 — 对测试的影响

## 下一步
行动 — 所需证据 — 会改变什么
```

计划、排期、责任矩阵和准入门槛只在用户或既有流程明确要求时添加。

**完成条件：** 任务卡明确用户任务、产品承诺、成功信号、测试目的、测试对象、范围和一个可执行下一步；未知项如实标注，没有用故障猜测代替业务价值，也没有要求用户代替职责之外的负责人作决定。
