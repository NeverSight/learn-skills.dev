# 调查 Finding

Finding 是值得调查的观察，不等于缺陷，更不等于根因。

沿用独立／项目路径：独立任务在对话或指定位置交付；项目任务将观察、调查、缺陷证据和残余风险写入对应测试文档，只有长期或跨 Spec 结论才更新 TCO。

## 调查

1. 分开记录观察、oracle 和原始证据，不把解释写成事实。
2. 列出仍可能成立的解释：产品缺陷、需求冲突、环境、数据、观测工具或测试设计。
3. 选择能最低成本区分这些解释的安全 probe；只有复现最有区分力时才优先复现。
4. 建立最小对照：变更／未变更、有效／无效、受影响／未受影响。
5. 界定用户、数据、状态、集成、频率、可恢复性和安全影响。
6. 根据结果选择下一项最能排除解释的 probe。

调查改变风险判断时，按 analyzing-product-risks 的生命周期更新唯一归属并引用证据；缺陷状态与风险状态分别维护。

## Finding 记录

```markdown
## 观察
发生了什么 — 环境／数据／顺序 — 原始证据

## Oracle
期望行为 — 权威来源；缺失时明确问题和负责人

## 触发与边界
哪些条件触发／不触发

## 影响
谁或什么受到怎样的影响

## 竞争解释
- 解释 — 支持证据 — 反证

## 下一项 Probe
行动 — 要区分的解释
```

只有证据支持时才称为缺陷。测试错误可修正并重跑；实现偏离已确认需求时，在已有开发／修复授权内衔接修复和回归，否则交付缺陷证据；规则歧义返回澄清，只阻塞相关测试。不能靠删断言、跳过测试或扩大替身范围消除失败。正式缺陷单字段仅在交接流程需要时添加。

**完成条件：** finding 已被证据支持为缺陷，或保留为带竞争解释的观察；影响边界和下一项区分性 probe 明确；局部证据未进入 TCO。
