# 澄清测试依据

与用户共同补齐产品认知。是否能确认规则取决于实际责任和证据，不取决于职称；不要求用户替职责之外的负责人作决定。

## 上下文契约

接收调用方给出的材料、业务与系统上下文及已有未知。关键目标或规则待回答时，不将相关假设固化为完整测试设计；用户明确要求先自主分析时可交付标明假设的草案。返回事实、假设、未知、oracle 和测试变化；调用方决定写入对话、Spec 或 TCO。不另建澄清报告。

## 探索循环

1. **调查：** 汇总 PRD、业务规则、原型、接口契约、架构、代码、配置、数据、日志、历史缺陷、人员说明、TCO 和当前 Spec 测试文档。能自行取得的事实先调查并留下证据。
2. **建模：** 先写出当前事实、推断、假设、未知及来源。确定用户任务、现状痛点、产品承诺和成功信号，再把需求放回真实业务链与系统联动。
3. **生问：** 读取 `references/guideword-cards.md`，让当前最相关的少数引导词碰撞具体对象，生成候选问题。
4. **选问：** 按业务影响、答案会改变的测试范围、问题依赖和取证成本选择主题。共同前提先澄清，可自行查清的事实先调查；同主题内互不依赖的问题成组询问，依赖答案的问题留待后续。答案足以支持当前分析时停止追问，不以清空未知清单为目标。
5. **反馈：** 收到回答后先展示认知变化。每个答案必须落到事实、推断、规则、测试输入、假设或未知，并新增、删除、拆分、合并、改序或延后具体测试工作。
6. **转向：** 用户表示不知道或无法回答时，转为信息收集任务、可推翻假设或测试实验；尚未提问不算问不到。只暂停依赖该答案的部分，推进其他已明确行为。剩余未知不再改变当前选择时，停止提问并开始有界测试；新证据改变模型或选择时重入本循环。

概念问题先给一个具体业务例子或时间序列，再让用户确认或修正；不用未确认的领域模型组织问题。用户表示没看懂或指出理解错误时，立即撤回错误假设，用用户语言重述当前模型，只重问被误解的问题并等待；不要追加新的问题前沿。业务语义稳定后，再单独收集业务链、系统关系和证据源。

只展开当前请求受影响的问题前沿。问题前沿记录依赖、应答角色和测试影响；它用于选择下一问，不要求清空。材料中已有答案、Agent 可自行调查，或答案不会改变当前测试的问题，不打断用户。

从用户动词推断测试目的和交付物。普通“测试分析”直接理解为共同建立上下文、候选测试点和下一步；不询问 PRD 是否可研发、MVP 是否可联调或产品是否可上线。只有用户明确请求准入、放行、停止或风险接受时，才确认对应决定和负责人。

## 保持澄清脉络

开始深入澄清时，简列当前主题、先后理由和状态（已明确／当前处理／待调查／待负责人）。主题从本次需求产生，不套固定章节。每轮说明当前主题；换题说明新证据或依赖为何改变顺序。已交给其他负责人的问题保留风险及影响，不反复追问，也不阻塞无依赖的工作。

推断问题前先验证其业务前提和现有兜底。用户授权选择方案不等于已证明某方案成本最低；推荐、确认规则和已验证事实分开记录。业务规则获确认也不自动表示相关风险已接受。

## 更新有效规则

新确认与 PRD／Spec 冲突时，在测试分析中记录当前规则、确认来源和原文差异；检查相关模型、测试点、用例和行动。已解决问题退出待办，旧预期退出有效内容。回写原需求超出授权时列行动，不擅改原文，不逐轮追加完整问答。

## 证据与权限

记录答案时区分：

- **已知事实：** 材料、系统或观察可以证明；
- **推断：** 由现有事实推演，尚未经证据或负责人确认；
- **已确认规则：** 有权负责人明确确认；
- **测试输入：** 用户提供的经验、现象或历史信息；
- **暂定测试假设：** 为继续分析暂时采用，不能充当 oracle；
- **未知：** 仍需调查或交给对应负责人确认。

用户提出处理办法但其决策权限不明时，只记为暂定测试假设。暂定假设可以支持有限分析，不能充当产品规则或 oracle。

优先索取真实流程、具体例子、反例、历史观察和可访问证据。产品／业务负责人确认规则；研发／系统负责人确认实现边界；运维／安全／发布负责人确认相应约束。用户可提供经验、观察和证据；已有上下文表明其承担相应责任时，直接采用其确认，不重复核验职称。

## 每轮交付

需要用户回答时，用三级标题依次分段：

- `### 🙋 请你确认`：先给完整问题；有明确选项时紧接选项及影响。多个独立问题编号，其他主题的疑点留待对应轮次。
- `### 🔎 判断依据` 或 `### 🔎 当前理解`：只给支持本次判断的事实、具体例子和推荐理由。
- `### ➡️ 确认后做什么`：说明答案将如何影响测试范围、测试重点或交付物，然后等待。

标题已能区分内容时用空行分段；内容较长时可加分隔线。只保留有实质内容的段落。无需用户回答时，按“🔎 本轮发现／📄 交付结果 → ➡️ 下一步”组织；简短进度用普通段落即可。可继续的工作实际推进；完成时附产物路径、关键未决项和必要证据边界。

问题与选项在当前交付中完整可见。按运行环境的可用性及调用规则使用交互提问工具；等待回答期间保持问题为交互焦点。若随后需要文字收尾，该回复也应包含完整问题与选项，用户无需查找上方消息即可作答。

流程说明写给测试参与者：解释这次选择对测试工作的实际影响，结尾交代后续动作。技能条文的引用限于用户追问或运行环境明确要求披露的情况；必要披露简短放在相关说明之后，保持问题与选项突出。

收到回答后说明它改变了哪些认知或测试，不重复整份事实清单。主题表保留当前进度，重大改序时更新，不逐轮复制。用户表示不理解时，用其语言重述具体例子，先处理被误解的问题。

**完成条件：** 当前探索目标已有足以选择下一测试动作的信息，或未知已转为明确取证／实验任务；用户可以直接确认或修正当前具体例子；答案有明确认知或测试变化；没有把未经确认的建议升级为产品规则。问题前沿无需清空。
