# 设计测试自动化

自动化提供持续反馈。选择保留目标行为和判断依据的最小测试范围，不以覆盖率代替价值。

## 接收当前任务

沿用用户目标、选中行为、业务规则及独立／项目路径。项目任务读取相关测试资产，设计写回对应测试文档；独立任务在对话或指定位置交付，不要求 TCO 或 Spec。

先核对预期依据、反馈价值、数据与环境控制、失败定位和维护成本。规则未定只暂停相关精确断言，其他明确部分继续设计。用户已经选定合理层级时直接进入，不另写策略报告。

## 选择入口

| 需要取得的证据 | 入口与交付 |
| --- | --- |
| 稳定业务规则、计算、转换、状态行为 | 单元测试：使用 writing-unit-tests，按请求编写并验证测试 |
| 身份、请求响应、持久化、服务协作 | 接口自动化：交付业务场景、接口依据、身份与数据、动作、预期及观察点 |
| 用户操作、状态反馈、跨页面任务与恢复 | 页面自动化：交付用户任务、前置状态、操作流程、业务结果和体验观察 |

同一业务行为可由不同层级补充证据，不要求三层重复。完全模拟服务的测试不能证明真实集成；浏览器脚本也不能单独证明整体易用性。

## 接口与页面入口的能力边界

这两个入口目前只提供测试设计，自动化框架接入与代码编写尚未实现。用户要求代码或运行时，先说明限制，交付可继续使用的设计及接入所需信息；不安装框架、生成脚本或自行调用技术栈实现流程。已有框架信息可以记录，不能冒充已完成接入。现有测试的获准执行由 running-test-sessions 负责，不受新入口限制。

接口设计围绕业务结果：除响应外，按需要检查数据变化、归属和下游结果；具体状态码与字段预期有契约来源。权限、边界、重复请求、并发和恢复按选中风险展开。

页面设计围绕真实任务：不仅检查点击成功，还检查保存后的业务状态、错误提示、输入保留和恢复。需要人工判断的体验单独说明。实际字段与操作名称保留，未知定位或观察入口标明待核实。

## 交付

给出选中行为及理由、数据与前置条件、动作、预期来源、观察位置、已有测试资产和未决项。设计清楚不表示能立即执行；框架、版本或环境未核实就如实说明。

项目局部设计留在对应测试文档，仅长期反馈保护摘要升级到 TCO。下一步明确是确认规则、准备数据、选择框架、编写单元测试或执行已有测试。

**完成条件：** 当前行为有合适层级及判断依据；接口／页面产物明确为设计；单元测试代码与运行结果按实际证据交付；没有把设计、框架接入或未知条件写成已实现反馈。
