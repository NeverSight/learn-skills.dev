# 设计测试实验

用足以取得可信证据的最轻表达。只具体化当前选择，不重新扫描测试空间。设计交付具体用例、任务或章程；设计完成不代表执行条件具备，也不默认生成自动化代码。

## 输入与轮次

接收调用方选中的候选测试点、TCON 或产品风险，以及业务场景、系统边界和证据目标。一次只展开一个业务结果、一组强相关风险或一批能共同准备和观察的任务。

当前轮次写清：为什么现在测、要学到什么、包含和排除什么、什么证据会结束本轮或改变下一轮。

## 先交代覆盖边界

批量 Case 前列出所有本轮选中内容：

| 测试内容／来源 | 状态 | Case | 原因或下一步 |
| --- | --- | --- | --- |
| <TCON／候选点> | 已转换／待转换／阻塞／排除 | <Case ID 或无> | <依据> |

仍有待转换或阻塞内容时，只能声称本轮 Case 已完成，不能声称整份 PRD 或全部测试已完成。

## 选择表达

- 产品认知仍在变化：探索式测试章程。
- 行为简单：直接测试任务。
- 流程、规则、数据、组合或状态复杂且没有模型：先用 `modeling-tests-with-ppdcs`。
- 需要重复、评审、交接或精确对照：精确测试用例。
- 需要单元测试代码：交给 `writing-unit-tests`。
- 行为与 oracle 稳定且反馈需要重复：自动化候选检查。

测试层级取决于问题可能发生在哪里、结果能从哪里观察，不取决于 PRD 展示在哪一层。

## 选择测试技术

只保留会改变刺激、数据、观察或 oracle 的技术：

| 测试对象 | 优先考虑 |
| --- | --- |
| 能力、规则、转换或禁止行为 | Function |
| 输入、输出、分区、边界或组合 | Domain |
| 容量、长时间、稀缺资源或脆弱依赖 | Stress |
| 端到端链路、顺序、节奏或并发 | Flow |
| 真实角色完成真实任务 | Scenario／User |
| PRD、SLA、提示或隐含承诺 | Claims |
| 已识别问题及征兆 | Risk |
| 需要生成数据、扩大动作或增强观察 | Tool-Supported |

每个任务必须能说明：`来源 → 业务结果或质量关注 → 技术及理由 → 刺激、观察和 oracle`。只写技术名称不算设计。

验证规则、状态或配置差异时，选择能让正确行为与所防范的错误行为产生不同可观察结果的数据和操作。若两者都会得到相同结果，调整样本或观察点。预期依据当前需求确定，不套用其他业务的结果值。

## 表格优先交付 Case

读取 `references/test-cases-template.md`，按 artifact-routing 写入独立用例文件并引用规则来源；实际执行记录写在本文件或证据链接。常规 Case 默认按模块分组，用 Markdown 表格交付：

| ID | 关联风险／依据 | 本轮安排 | 要检查什么 | 场景／前置条件 | 怎么操作 | 预期结果 | 需要保留什么 | 当前条件 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| CASE-001 | <业务影响及风险判断来源> | <执行顺序或准备动作> | <业务关注> | <角色、业务对象、已有状态> | <具体操作> | <可观察结果或待确认规则> | <最小证据> | <当前条件> |

单元格需要多项内容时使用 `<br>`。并发控制、故障注入、长流程、多个观察时点或探索分支无法在一行说清时，保留总表摘要，再展开该 Case 的详细步骤、停止信号和恢复动作。

Case 用业务场景说明目的，用准确动作和观察说明检查方法。手工交接突出操作与预期；实现自动化所必需的字段、接口和控制手段直接保留，避免为简化语言丢失执行信息。

## 收紧可执行门槛

- **可执行：** 已核实测试设计足以开展，指定目标版本、环境、数据与观察手段可用；不表示已获执行授权、已执行或通过。
- **待核实：** 版本或执行条件尚未调查，不能据此断言未实现或环境不可用。
- **待实现：** 测试目标、步骤和 oracle 已明确，但目标行为尚未进入可运行版本。
- **待补环境：** 目标实现存在，但账号、数据、工具、接口或环境尚未准备。
- **待确认规则：** oracle 仍需对应负责人确认。

当前条件写明已知缺口；未调查部分标「待核实」。规则不清时不编精确预期，已知部分继续设计。相同用例可以同时存在规则与环境缺口，不为状态标签重复拆用例。

探索章程可以调查未知：写清探索目标、动作范围、观察及结束／转向信号，不把待探索规则用于通过／失败判定。没有完整精确预期不妨碍获准的信息收集。

## 保持独立、最小

- 每条 Case 自己准备数据；复用时引用已定义的 fixture，不依赖另一条 Case 的结果。
- 不同故障注入点、刺激或 oracle 拆成不同 Case；只有数据取值变化时才参数化。
- 并发重复次数写明采样理由或停止条件，不编固定轮数。
- 每条 Case 只保存证明其 oracle 所需的最小证据；并发时间线和事务日志只用于需要它们的 Case。

关联风险沿用风险分析的结论和依据，不把后果严重程度单独当作风险等级。本轮安排独立决定现在做什么：可执行 Case 使用 P0～P3；其余写明先澄清、准备实现或补齐环境，也可延后，不因受阻就自动优先。

P0 是取得本轮核心结论不可缺少的最小可执行集合；P1 可能改变本轮结论；P2 扩展结论边界；P3 当前增量价值低。每个 P0 说明补齐哪段产品证据链。尚不可执行的 Case 不填写 P0～P3，保留风险判断及准备先后；当前没有可执行测试时明确说明。已有团队采用不同 P0～P3 定义时保留其语义，并另列本轮执行顺序。

## 交付

交付当前范围的用例、任务或章程及依据，分别说明设计完成情况、规则缺口和已核实的执行条件。下一步点名编写什么、准备什么或执行什么；未核实版本和环境时不能把用例草案称为可执行。调用方按已有请求决定持久化与执行。

**完成条件：** 所有本轮选中内容均已列入覆盖边界；常规 Case 可快速扫描，复杂 Case 有必要细节；每条 Case 状态诚实、前置独立、证据最小，并可追溯到候选点或 TCON；P0 与产品价值和核心证据一致；未执行内容没有冒充结果。
