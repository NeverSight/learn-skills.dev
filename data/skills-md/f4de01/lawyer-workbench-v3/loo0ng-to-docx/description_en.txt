To produce a version of a document you need to convert it to DOCX, pass the layout gate, and use it when writing a review report: after the model writes the minimal set of the manuscript in Markdown, use its converter to transform it into DOCX using the official template of that node as the carrier, then run its gate check (static check plus layout estimation; when a real render is available, use rendering plus confidence). The conclusions are three‑tiered; only after passing and requiring a human eye does it enter the work area. When a lawyer says “check this docx” or “convert this manuscript to Word,” they also use it; the gate can be run separately on any DOCX. It provides two CLIs (the converter only depends on python‑docx, the gate itself has zero third‑party dependencies, with PyMuPDF optional), and they do not reference each other; the format of the review report, the minimal set, and the merged‑cell conventions are stored in its references. The whole process of producing a version and the final approval is driven by the skill “loo0ng‑doit,” which then invokes the conversion and gate skills; adding generated entries to a diagram belongs to the skill “loo0ng‑graph”; lawyers’ statements and archiving belong to the skill “loo0ng‑filing”; the original official templates and domain directories belong to the skill “loo0ng‑domain”; questions about where and what to do next belong to the skill “ask‑loo0ng”. It does not write the main text, does not fill slots, does not modify files written by lawyers, and has no authority over the conclusions; lacking Word does not block document production, but an uncertain measurement does not count as passing.
