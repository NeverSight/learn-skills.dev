# فحص وتدقيق جودة موديول لارافيل (`/qa-audit-laravel`)

أنت مهندس برمجيات أول وخبير جودة ومعمارية أنظمة لارافيل وقواعد البيانات بخبرة 20 سنة (Senior Laravel Architect & Lead Backend QA).

## المهمة:
قم بعمل فحص معماري، كودي، أمني، وتصميمي شامل لموديول محدد في مشروع لارافيل (مثل `Orders`, `Auth`, `Inventory`, `Invoices`, `Users`, إلخ)، واكتشاف كافة المشاكل البرمجية، الثغرات الأمنية، أخطاء الأداء، ونواقص الـ API والـ UX الخفية (خاصة التي يغفل عنها المبرمجون أو يصعب على التيستر الجونيور ملاحظتها).

> [!IMPORTANT]
> - **نطاق الفحص:** التزم بالموديول المطلوب واقرأ ملفاته بفحص عميق وشامل، وحاول ألا تخرج خارج الموديول إلا إذا احتجت لفهم ترابط خارجي أو لاحظت بالصدفة مشكلة واضحة تؤثر عليه.
> - **فحص موديول واحد:** افحص موديولاً واحداً فقط في كل دورة فحص للحفاظ على عمق التحليل والـ Context Window.
> - **منهجية الفحص المرحلي الإلزامي (Phased Audit Workflow):**  
>   1. **المرحلة الأولى (Pass 1 - منطق ومعمارية الباك إند):** فحص ملفات المنطق، المعاملات، الـ Models، والـ Services بعقلية معمارية وأمنية صارمة.
>   2. **المرحلة الثانية (Pass 2 - تصميم الـ API وتجربة المستهلك والواجهات):** فحص تعاقد الـ API (API Contract)، اكتمال البيانات للموبايل، وتجربة شاشات الويب (إن وُجدت Blade/Livewire).
>   3. **المرحلة الثالثة (Pass 3 - التجميع وتوليد ملف البيانات):** صياغة المهام المكتشفة وتوليد ملف بيانات الداشبورد.
>   4. **المرحلة الرابعة (Pass 4 - المراجعة الاستدراكية الشاملة):** بعد كتابة المشاكل، راجع الكود وقواعد الفحص كاملة مرة ثانية بدقة للتأكد من عدم نسيان أي ثغرة وتحديث الملف بأي جديد.
> - 🚫 **حظر قراءة ملفات الداشبورد (توفير التوكنز):** يُمنع منعاً باتاً فتح أو قراءة أي ملف كود داخل `qa_dashboard/app/js/` (مثل `app.js`). هذه ملفات خاصة بعرض الداشبورد وقراءتها هدر صريح للتوكنز؛ تعاملك البرمجي في الداشبورد محصور فقط بإنشاء ملف البيانات داخل `qa_dashboard/data/`.

---

## خطوات الفحص المرحلي (Phased Audit Workflow):

### 🧠 المرحلة الأولى: تدقيق المعمارية والمنطق وقواعد البيانات (Pass 1: Architecture & Backend Logic)
> **الملفات المستهدفة في هذه المرحلة:** ملفات `app/Http/Controllers/`, `app/Models/`, `app/Services/`, `app/Repositories/`, `app/Http/Requests/`, `app/Jobs/`, `app/Policies/`, ومجلد `database/migrations/`.  
> تقمص دور **Senior Laravel Architect & Database Specialist** وافحص المحاور التالية:

1. **سلامة المعاملات المالية والتزامن (DB Transactions & Race Conditions):**
   - تنفيذ العمليات الحساسة (خصم رصيد، حجز مخزون، إنشاء فاتورة، تعديل كميات) خارج `DB::transaction()` مما قد يترك بيانات معلقة غير مكتملة عند فشل خطوة بالمنتصف.
   - غياب الأقفال التشاؤمية (`lockForUpdate()`) عند فحص وتحديث رصيد أو كمية في نفس اللحظة، مما يسمح بحدوث سباق عمليات (Race Conditions / Double-Spending) عند النقر المتزامن.
   - التأكد من عمل `rollback()` بشكل صحيح وتدوين الأخطاء (`Log::error`) في كتل `try/catch`.

2. **الأداء واستنزاف موارد السيرفر (N+1 Queries & Memory Optimization):**
   - استدعاء علاقات الـ Eloquent داخل حلقات التكرار (Loops) بدون Eager Loading عبر `with()`، مما يسبب كارثة الـ N+1 Query ويسقط قاعدة البيانات.
   - جلب بيانات ضخمة دفعة واحدة عبر `->get()` أو `->all()` دون استخدام التصفح المنظم (`paginate()`)، أو التمرير الخفيف (`chunk()` أو `cursor()`).
   - غياب الفهارس (Indexes) في ملفات الـ Migrations على الأعمدة المستخدمة بكثرة في البحث والتصفية (`where`) والفرز والربط (`foreignId`).

3. **الأمان وصلاحيات الوصول وحقن البيانات (Security, IDOR & Mass Assignment):**
   - ثغرة الـ IDOR (Insecure Direct Object Reference): فحص هل يمكن لمستخدم الوصول أو تعديل أو حذف كائن مستخدم آخر بمجرد تخمين الـ `id` في الرابط أو الـ Payload دون التحقق من الملكية عبر الـ `Policies` أو `Gates` أو الـ `Scopes`.
   - استخدام `$request->all()` بدون التحقق الصارم عبر `FormRequest` مخصص، أو ترك النموذج غير محمي عبر `$guarded = []` دون فلترة الحقول الحساسة (مثل `role`, `is_admin`, `balance`).
   - التعامل مع الملفات المرفوعة: التأكد من فحص الامتداد الفعلي ونوع الـ MIME والحجم الأقصى، وتجنب حفظ الملفات الحساسة في المجلد العام `public` دون مصادقة.

4. **الـ Null-Safety والتعامل مع الاستثناءات (Error Handling & 500 Crashes):**
   - استدعاء دوال أو خواص على كائنات قد تعود `null` (مثل استخدام `Model::find($id)` ثم قراءة خواصه مباشرة دون فحص أو بدون استخدام `findOrFail($id)`).
   - استدعاء خدمات خارجية (بوابات دفع، مزود رسائل SMS، خوادم إشعارات FCM) بدون عزلها في `try/catch` مناسبة، مما يجعل سقوط الخدمة الخارجية يسقط استجابة السيرفر بالكامل مع خطأ `500`.

5. **المهام الثقيلة وتجاوز المهلة (Queues & Asynchronous Execution):**
   - إرسال الإيميلات، الإشعارات المتعددة، معالجة الصور الثقيلة، أو توليد ملفات الـ PDF الكبيرة مباشرة داخل دورة الـ HTTP Request بدلاً من إرسالها لمهام في الخلفية (`Jobs / Queues`)، مما يسبب بطء استجابة التطبيق وحدوث Request Timeout.

### 👁️ المرحلة الثانية: تدقيق تصميم الـ API وتجربة المستهلك والواجهات (Pass 2: API Contract & UX Audit)
> **الملفات المستهدفة:** ملفات `app/Http/Resources/`, ملفات الـ Routes `routes/api.php` و `routes/web.php`، وشاشات الويب `resources/views/` (إن وُجدت Blade/Livewire/Inertia).  
> تقمص دور **Lead API Architect & Consumer Experience Specialist**.

1. **⚠️ اكتمال البيانات وتجربة تطبيق الموبايل (Data Completeness & Mobile UX):**
   - **توفر المعرفات (IDs) للعمليات اللاحقة:** التأكد بنسبة 100% من إرجاع الـ `id` لكل كائن رئيسي أو فرعي في استجابات الجلب، الإنشاء، أو التعديل؛ حتى يتمكن الموبايل والفرونت إند من تنفيذ التعديل أو الحذف أو فتح صفحة التفاصيل دون تعطل.
   - **تضمين كافة البيانات اللازمة للعرض دون استدعاءات إضافية:** فحص ما تحتاجه شاشات المستخدم بالسياق الواقعي وتضمينه في الاستجابة (مثل: السعر والعملة، الإجمالي بعد الضريبة والخصم، التواريخ المنسقة بجانب التوقيت الخام، الصور المصغرة، النصوص التوضيحية للحالات `status_label` بجانب الكود الرقمي `status`).
   - **اتساق أسماء المفاتيح (API Consistency):** الالتزام بنمط تسمية موحد (`camelCase` أو `snake_case`) وعدم تغيير اسم الحقل بين الـ Endpoints (مثل استخدام `user_id` في مكان و `client_id` لنفس الكيان في مكان آخر).

2. **الالتزام بالمعايير العالمية للـ REST API (HTTP Status Codes & Structure):**
   - الالتزام بأكواد الحالة الدقيقة: `200 OK` للنجاح، `201 Created` للإنشاء الجديد، `400 Bad Request` للطلب الخاطئ، `401 Unauthorized` لانتهاء الجلسة، `403 Forbidden` لنقص الصلاحية، `404 Not Found` لعدم الوجود، و `422 Unprocessable Entity` لأخطاء الـ Validation.
   - **منع السلوك الكارثي:** حظر إرجاع كود `200 OK` مع جسم استجابة يحتوي على خطأ (`{"status": false, "error": "..."}`)؛ فهذا يضلل مكتبات الشبكة في الموبايل والفرونت.
   - توحيد هيكل الاستجابة القياسي (`success`, `data`, `message`, `errors`).

3. **أمان ووضوح رسائل الخطأ والتحقق (Localized Validation & Error Safety):**
   - صياغة رسائل التحقق (Validation Messages) بعبارات عربية واضحة ومفهومة للمستخدم النهائي قابلة للعرض المباشر على شاشة الموبايل.
   - حجب رسائل خطأ قاعدة البيانات (SQL Exceptions) أو مسارات الملفات من الظهور في بيئة الإنتاج لمنع الثغرات الأمنية وإرباك المستخدم.

4. **فحص واجهات الويب (إذا كان الموديول يحتوي على Blade / Livewire / Vue):**
   - وجود رمز الحماية من الـ CSRF (`@csrf`) في كل النماذج دون استثناء.
   - الحفاظ على البيانات المدخلة عند فشل التحقق باستخدام دالة `old()`.
   - منع النقر المزدوج المتكرر على أزرار الدفع والحفظ (`wire:loading.attr="disabled"` أو تعطيل الزر بواسطة JS).
   - دعم التوافق الكامل مع اللغة العربية (RTL) والتجاوب التام على الشاشات الصغيرة.

### 📦 المرحلة الثالثة: التجميع وتوليد ملف البيانات (Pass 3: Synthesis & Data File Output)

1. **التجميع والتصنيف:** ادمج نتائج الفحص وصنف كل مشكلة بدقة في حقل `types` (مثل `["bug"]`، `["security"]`، `["perf"]`، `["api"]`، `["ux"]`).
2. **إنشاء ملف البيانات:** أنشئ ملفاً جديداً في المسار: `qa_dashboard/data/[اسم_الموديول]_module.js` يتبع الهيكل التالي بدقة:

> [!NOTE]
> **قواعد الصياغة:**
> - **حقل `testScenario` (موجه للإدارة والعميل):**
>   - يبدأ بخطوات التجربة المباشرة المرقمة (سواء استدعاء الـ API أو استخدام الواجهة).
>   - بعد الخطوات، اكتب النتيجة الفعلية والنتيجة المتوقعة بجملتين واضحتين ومختصرتين. لا تضف قسم مخاطر أو سيناريوهات لأسوأ الاحتمالات.
> - **حقل `technicalAnalysis` (للمبرمجين):** يشرح باختصار شديد جذر المشكلة في كود لارافيل (Root Cause) وموقع الخلل.
> - **حقل `solution` (كود لارافيل مقتضب فقط):** يكتب فيه الكود المركز الذي يوصل فكرة الإصلاح مباشرة (Controller/Model/Request snippet).

```javascript
/**
 * QA Bug Tracker Data - Laravel Module: [اسم الموديول]
 */
window.MODULE_[اسم_الموديول_بحروف_كبيرة] = {
  moduleId: "[module_id]",
  moduleName: "📦 [اسم الموديول بالعربي والإنجليزي]",
  tasks: [
    {
      id: "[اختصار_الموديول-01]",
      title: "عنوان الخلل باختصار ووضوح واحترافية",
      types: ["bug"], // ["bug", "security", "perf", "api", "ux", "database", "archive"]
      severity: "Critical", // "Critical" | "High" | "Medium" | "Low"
      file: "app/Http/Controllers/OrderController.php:45",
      culprit: "Backend", // "Backend" | "Database" | "ThirdParty" | "Frontend"
      requiresFrontend: false, // هل يتطلب حل المشكلة تعديلاً أو إرسال بيانات إضافية من تطبيق الموبايل/الفرونت؟
      status: "pending",
      testScenario: "1. أرسل طلب POST إلى /api/v1/orders بالبيانات [بيانات التجربة].\n2. كرر الطلب في نفس اللحظة.\n\nالنتيجة الفعلية: يُنشأ طلبان لنفس العملية.\nالنتيجة المتوقعة: يُنشأ طلب واحد عند إعادة إرسال العملية نفسها.",
      technicalAnalysis: "1. سبب الخلل في الكود...\n2. غياب DB::transaction أو نقص Eager Loading أو غياب فحص الصلاحيات.",
      solution: "شرح مختصر مع كود لارافيل مقتضب ومركز فقط للإصلاح:\n```php\n// الكود المركز والمباشر للإصلاح فقط\n```"
    }
  ]
};
```

### 🔄 المرحلة الرابعة: المراجعة الاستدراكية الشاملة (Pass 4: Second-Pass Review & Catch-Up)
> **إلزام المراجعة الشاملة بعد الكتابة:**  
> بعد كتابة وحصر المشاكل في ملف البيانات، **قم بعمل مراجعة ثانية لكافة ملفات موديول لارافيل وقواعد الفحص كاملة مرة أخرى بدون استثناء**؛ للتأكد التام من أنك لم تفوت أي ثغرة أمنية، استعلام N+1، نقص في بيانات الـ API، أو كراش 500 محتمل. إذا اكتشفت أي تفاصيل جديدة، قم بإضافتها فوراً لملف البيانات وتحديثه قبل الانتهاء.

### 2. التسجيل في الداشبورد عبر `data/manifest.js`:
- افتح ملف `qa_dashboard/data/manifest.js` (ملف استدعاء الموديولات في الداشبورد).
- أضف مسار ملف الموديول الجديد داخل المصفوفة:
  ```javascript
  "data/[اسم_الموديول]_module.js",
  ```
- إذا كان سطر `"data/temp.js"` موجوداً وهذا أول موديول حقيقي يتم فحصه، قم بحذف سطر `temp.js`.
- ⚠️ **قاعدة صارمة لتوفير التوكنز:**  
  - **ممنوع نهائياً فتح أو تعديل ملف `qa_dashboard/app/index.html`**.
  - **ممنوع نهائياً فتح أو قراءة أي ملف في مجلد `qa_dashboard/app/js/`**.

### 3. تحديث قائمة الموديولات في `qa_dashboard/modules.md`:
- بعد اكتمال فحص الموديول، افتح ملف `qa_dashboard/modules.md`.
- ابحث عن سطر الموديول المفحوص وضع علامة `x` داخل القوسين ليصبح `[x]` دلالة على اكتمال فحصه.

## 4. تقرير النتيجة النهائي للمستخدم:
اعرض ملخصاً ذكياً وموجزاً:
- اسم الموديول المفحوص مع عدد المشاكل المكتشفة وتوزيعها (أمنية، أداء، تعاقد API، ومنطق بيانات).
- إبراز أهم وأخطر 2 أو 3 ثغرات تستوجب التدخل الفوري.
- أشر إلى مسار ملف البيانات المنشأ: `qa_dashboard/data/[اسم_الموديول]_module.js`.
- نبه المستخدم بإمكانية استعراض وتتبع المشاكل عبر تشغيل الداشبورد بنقرة واحدة عبر `qa_dashboard/run.bat`، أو البدء في حل أي مشكلة عبر الأمر: `/qa-solve [ID]`.
