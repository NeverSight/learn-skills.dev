# ssot-design：按草稿写设计

本块读目标仓库的 `.tmp/ssot-draft/draft.yaml` 与草稿开始时记下的设计基线 `.tmp/ssot-draft/baseline.yaml`，把草稿里的约束写进 `design/`，架构模块与业务单元按草稿的归属一起写；每条约束落在哪里、本轮改动的每个元素为什么存在，记进 `.tmp/ssot-design/` 的台账（共用规则见 `ssot` 总纲第四节）。`ssot draft status <仓库根>` 有错误或没有基线时，`ssot design` 拒绝往下核对：停下，转 `ssot-draft`。

总纲第一节的原则（观察者需要才展开、展开只有一处、规则归持有者、不变量越简单越好、上层状态写成纯函数投影、准入契约与结局分清）在这里直接适用，本块只写落地时的判据。文件布局、VDM-SL 写法范例、索引与未定义、受控文字见 [`references/writing.md`](references/writing.md)；VDM 语法查 [`../ssot/references/vdm/`](../ssot/references/vdm/README.md)。

## 一、每条约束选写法（`ssot design constraints`）

**先用不展开的写法。** 每条约束落地之前，先按 `references/writing.md` 第三节「用不展开的写法守住约束」的次序找写法：身份只比较相等；判定写成不展开的函数放进 `pre`/`post`；事实写成身份之间的映射与集合；结局只列调用方要区分的分支；连接与外部依赖只留签名；数值写进常量或「语义」。前一种能排除违反情形，就不用后一种；六种都排除不了，才展开结构。设计写得越少越好：同样能排除违反情形的两种写法，选元素、字段、分支、参数与合取项更少的那一种。

再按草稿标出的类别选落点，记成台账里 `landing` 的一项：

| 约束类别 | 写法 | `landing.kind` |
|---|---|---|
| 任何时刻都成立的关系（`invariant`） | 先写在持有这份事实的状态的 `inv`，或产生它的操作的 `post`/`pre` 上；只有观察者本来就要按它分支或读字段时，才用类型结构让违反情形构造不出来 | `inv`、`post`、`pre`、`type` |
| 一次调用的准入条件（`admission`） | 操作的 `pre` | `pre` |
| 一次调用前后的关系（`transition`） | 隐式操作的 `post`，`ext` 只列要写的分量；没列进 `ext wr` 的分量调用前后不变 | `post` |
| 生命周期的先后（`lifecycle`） | 显式场景操作，体内每一处先后都对应一条约束 | `scenario` |
| 哪个模块能触达哪个模块 | `imports` 与 `exports` 的方向；它只约束规格里的模块 | `import`、`export` |
| 一条判定 | 函数。判定的内容未定或不归本系统定时，体写 `is not yet specified`，在 `pre`/`post` 里调用它；判定结果本身就是草稿里的约束、且两个独立实现面对同一输入必须得出同一结果时才写显式体；结果用性质刻画、允许多个合格结果或不想绑定算法时只写签名与 `post` | `function` |

最后两行不是草稿的类别，是可以与类别配合的写法：`invariant` 类可以落到导入导出方向与判定函数，`admission`、`transition` 类可以落到判定函数；任何类别都可以把规格写不清的部分落到「语义」（`semantic`）。工具对类别与写法不配的落点给出警告。

```yaml
constraints:                               # .tmp/ssot-design/constraints/*.yaml
  - constraint: C1
    landing:
      - {kind: post, element: "Run`Start"}
      - {kind: import, module: Report, from: Run}
      - {kind: semantic, path: architecture/README.md, line: 17}
    excludes: …                            # 规格里哪个类型或谓词排除了违反情形
```

选完自检：拿草稿里这条约束的违反情形，问“规格里哪个类型或哪条谓词排除了它”，答案写进 `excludes`。指不出来就换写法。导入列表与单条场景排除不了任何情形。工具核对落点存在、真有那一部分（`pre` 落点的操作要写了 `pre`，`inv` 落点要写了 `inv`），对与类别不符的写法给出警告。

约束写在草稿定下的持有者那里，只展开一处；别的模块需要时经导入引用。落点不在草稿归属的层或单元里时，工具给出警告。

失败与场景分两层写：

- **失败结局本身**是一次调用前后的关系：写进结局类型与 `post`。结局并类型只列合法调用方必须区分处理的分支，不逐项列失败原因；可观察的失败分支在说明里写明改走哪个连接恢复（如 `<Unknown>` 一支写明改用 `Status` 找回）。
- **失败之后的恢复次序、生命周期中断**只有草稿里有对应的 `lifecycle` 约束时才写成场景。场景里为了闭合被调连接的结局而写的分支，属于它所服务的那条约束。不为展示正常路径或每种失败另造没有约束来源的场景。
- 涉及集合的约束，由显式纯函数算出全集或候选集合，场景接收单个代表元走通单步调用。

## 二、元素的进入条件（`ssot design elements`）

工具枚举本轮新增或原文改动的类型、字段、函数、操作与场景，以及本轮删掉的元素（与草稿开始时记下的基线 `.tmp/ssot-draft/baseline.yaml` 比较；没动过的旧元素不归本轮草稿解释）。每一项都要答得出：它表达或为之删掉的是草稿里的哪条约束（`constraints`），或者它是哪条约束所需的连接（`connection_for`），并写出理由（`reason`）。新增或改动的答不出，就不写或不改这个元素；删掉的答不出，就恢复它。下面几种情况都属于答不出：

- 为了让一个名字在规格里有落点而造出的元素；
- 没有约束来源、只因为“计算是确定的”而写成显式体的函数（两个实现必须得出同一结果，只决定写法，不构成进入理由）；
- 场景体里有一处先后、分支或挑选，在草稿的约束里找不到。这是在模拟业务怎样运行，删掉。

```yaml
elements:                                  # .tmp/ssot-design/elements/*.yaml
  - {element: "Run`Start", constraints: [C1], connection_for: [], reason: …}
```

`token` 与 `is not yet specified` 只用于不展开的内容，是默认的、合法的终态。草稿里已经定下的约束必须出现在类型、`inv`、`pre` 或 `post` 上，不能藏进不展开的定义里：落点是这类定义时，工具报错，这时把落点改到产生或使用它的操作的 `pre`/`post`、状态的 `inv` 或「语义」，不要为此展开它。本轮新增或改动、却不是最小形式的元素（带结构的类型、状态、字段，有体或有 `pre`/`post` 的操作与函数），`ssot design elements` 都另要 `expansion`：`violation` 写缩回最小形式（退回 `token` / `is not yet specified`、删掉这个字段、分支、参数或合取项）之后，哪条草稿约束的哪种违反情形会重新可以构造；结构还要在 `needed_by` 写出读这份结构、按它分支的别的元素（不能是它自己或它所在的定义）；读者在系统外（例如调用方按结局区分后续处理）时，写 `README.md` 里说明这个读者的那一行。写不出就缩回去。是某条约束的落点不算理由：落点本身也可以选更小的位置。占位不用写理由，所以不展开总是最省事的写法；但系统外的调用方确实要区分的结局，不缩回 `token`。

规格写不清、但确实属于约束的语义，写进 `README.md` 的「语义」；在 README 里展开会遮住架构时，写进它展开的主题文件（开头一段说明展开 README 的哪一节）。落点记成 `semantic` 并给出那一行。一条约束的落点全是「语义」时，工具给出警告，交付时单独列出。「语义」该写哪些内容、怎样写，见 `references/writing.md` 第一、四节。

## 三、落地判据

### 依据与理由

- **依据**写外部世界改变不了的事实、约束、系统级需求与质量要求。每条一句话，写出来源，并接一句“所以……”，说明它让设计多了或少了什么：
  ```markdown
  上游在超时之后仍可能已经开始了运行（来源：上游接口说明，证据见附录 `evidence/upstream-timeout.md`）。所以 ``Run`StartOutcome`` 有结果未知一支，调用方经 ``Run`Status`` 找回运行。
  ```
- **质量要求**写成“在〈环境〉下，〈刺激〉发生时，〈响应〉满足〈度量〉”，并写出来源；数值只在有出处时写。
- 当前实现的目录、调用步骤和偶然行为不是依据；写设计时不参考实现代码。在连接不变时可以替换的做法（底层怎样查找与插入、编码、逐项拒绝原因、保护某条不变量的内部机制）留在实现代码或 `appendix/reference/`。
- **为什么**：每个改变设计形状的决定在 `## 为什么` 中写明理由并引用依据；确实存在可信替代时，写一句为什么不选它（如：“不让调用方自己记下请求号与运行的对应：结果未知时调用方手里没有运行身份，只有提供方能按请求号找回”）。

### 架构模块

- **展开与导出**：观察者需要按状态分支或读字段的，在持有者写出结构并带 `struct` 导出（如 `StartOutcome = Started | <Rejected> | <Unknown>`）；观察者只原样传递的，定义为 `token` 且导出不带 `struct`（如 `RunId = token`）。
- **子模块**：只有当一组元素对外陈述连接、内部决定可对其他模块隐藏、父模块不需要知道其内部细节时，才拆为子模块；拆分理由写进子模块的 `README.md`（如“尝试的记录只追加，所以单独成为子模块：它只用到父模块的 ``Run`RunId``，父模块不需要知道记录怎样保存。”）。模块按抽象划分，不按篇幅或执行步骤切分；并列的底座彼此正交。
- **连接面与状态**：持有 `state` 的模块，状态只放这个连接面要守住的事实，不放冗余信息，也不放观察者不读的内部结构；共享状态的操作共守同一条 `inv`。能由事实算出的性质写成纯函数。
- **生命周期**：一样东西从开始到结束，写清由哪个连接开始、哪个连接结束、嵌套在谁之内、由谁确认（如运行由 `Start` 加入 `live` 开始、由 `Finish` 移出结束；`l subset rng b` 规定活着的运行都嵌套在某个请求之内）。

### 业务单元

- `README.md` 开头写清本单元负责什么、不负责什么。「需求」写必须在问题域中成立、可以被观察到的结果（用户或外部系统看到什么），不是机器的功能列表；每条写出来源，并用双反引号指出兑现它的规格元素。
- 业务单元经导出的连接单向组合（点对点调用一个连接点，或点对面接入一个连接面），不持有持久 `state`。对不带 `struct` 导出的 `token`，只把从连接拿到的值原样传给别的连接，不读结构、不自造。
- 结果在本单元边界收敛：在架构的一般规律内取子集或定细化策略；某处需要同时给多个模块或阶段的来源排优先级时，把不属于本单元的来源拆回各自的模块。常变的业务内容本身留在代码里，不写进规格。

## 四、写不进去时

先判定是哪一种：

- **只是写法不对：** 换一种写法，持有者与含义不变；
- **这项需求不属于本系统承诺：** 回到 `ssot-draft`，把它从约束里移出并写明理由；不为走通系统边界以外的需求扩张架构；
- **对象、关系或归属不成立：** 停下，回到 `ssot-draft` 修改草稿并写明原因，不在落地时改掉归属。

有原始来源设计时，本块同样不读它，也不读代读的概念备忘与答复、不问 `ssot:reader`：草稿说不清的含义，回到 `ssot-draft` 去问。

归业务持有的约束写不进业务时，问业务做判定所需的事实，连接提供了没有。没提供就改连接要提供的内容，不把判定搬进架构。

工具诊断按它反映的设计问题修，不绕过检查，也不为消掉诊断加东西：修法先减后加（`ssot` 总纲第四节）。`ssot check` 报出的确定性反模式（字符串字面量、显式体里的实现、不承诺任何东西的隐式定义、恒真或恒不可满足的约束）随诊断给出修法；`review.py` 的检出是模型按下表各类的判定标准给出的，要逐条看是否真属于那一类，误报不改：

| 诊断 | 反映的设计问题 | 修法 | 不属于这一类的相似写法 |
|---|---|---|---|
| `ssot check` 报某个定义没人用 | 它不需要，或用它的那条连接还没写 | 删掉；只有草稿约束要求那条连接时才写出它。不为消除诊断新增模块、导出、导入或场景 | — |
| QuickCheck 耗时过长、超时或证明义务暴增 | 状态展开了过多嵌套 `map`/`seq` 或观察者不读的内部字段 | 把观察者不读的结构退回 `token`，删掉冗余状态分量 | — |
| `review.py` 报 `stringly` | 用字符串代表身份、一组封闭的取值（状态、种类、角色、结果）或结构化数据 | 规格不需要观察它就写 `token`；要按它分支才写 quote 并类型，要读字段才写记录 | 系统只原样传递或展示给人、不解读的自由文本 |
| `review.py` 报 `bool_stack` | 几个 `bool` 字段一起表示同一样东西互斥的阶段，只有部分组合有意义 | 换成一个 quote 并类型 | 彼此独立、可以任意组合的开关 |
| `review.py` 报 `reasons` | 结局并类型逐项列出了同一种失败或拒绝的具体原因 | 合成一支，原因不写进设计 | 需要调用方分别处理的不同阶段、模式或结局 |
| `review.py` 报 `comment_shape` | 说明只复述了定义已经写出的形状（字段名、类型、参数与结果） | 写它是什么；只有草稿约束要求时才写它承诺什么 | 说明写出了类型结构看不出的含义、承诺或规则 |
| `review.py` 报 `impl_body` | 显式体写成了实现步骤（改状态、循环、缓存、淘汰、造编号、数据结构操作） | 提炼成两个实现必须一致的判定，或移进代码与 `appendix/reference/`；不把函数改写成无状态的隐式操作来绕过检查 | 场景（按次序调用连接）与两个实现必须一致的判定 |
| `review.py` 报 `registry` | 模块只登记了名字：类型与操作没有结构、不变式、`pre`/`post` 或关系，承诺不了任何可核对的东西 | 没有约束来源就删掉这个模块；它是外部依赖或尚未定下的连接的占位、被别的模块用到时，是误报，保留占位，不为它编承诺 | 写出了结构、不变式、结局或 `pre`/`post` 的模块；被用到的外部依赖与未定连接的占位 |
| `review.py` 报 `simulation` | 模块在模拟运行机制：走动的时钟、崩溃与重启的进程、线程、调度 | 这些写进「语义」，不建模 | 规定系统的数据、连接与不变式的模块 |
| `review.py` 报 `business_in_arch` | 架构里混入了只服务单一业务单元的类型、分支或说明 | 移进对应的 `business/<单元>/`，或在架构里退成与业务无关的 `token`；不只是改注释里的字眼 | 对任何业务单元都有意义的通用定义 |
| `review.py` 报 `prose_restates` | 一段文字说的全都能从规格读出（签名、字段、并类型分支、`pre`/`post`/`inv` 已写的内容） | 删掉，或改写成规格说不清的语义 | 写出了规格没有的定时、事务、进程、崩溃、版本、人、理由或来源 |
| `review.py` 报 `coined` | 文字里出现了规格里没有对应物的部件、角色、状态、阶段、产物、锁、队列或机制 | 没有约束来源就删掉这段文字或改用已有的名字；只有草稿约束要求它时才写成规格元素 | 普通词、数值、单位、时间说法，以及“进程”“调用方”“系统”这类通用词 |
| `review.py` 报 `basis` | 「依据」没有来源、只是愿望，或拿当前实现与技术选型当理由 | 写出外部事实、来源与“所以……” | 写明外部事实、来源与它对设计的影响的依据 |
| `review.py` 报 `figure_code` | 图与文法块（```` ```mermaid ````、```` ```ebnf ````、```` ```text ````）里放的是代码：类型、接口、签名或函数体 | 类型、接口与签名写成 ```` ```vdm ```` 规格，实现放进 `appendix/reference/` | 图（Mermaid、ASCII）与文法（EBNF/BNF） |

## 五、步骤与交付

1. **先立框架。** 用 `ssot init`、`ssot module`、`ssot unit` 建好目录，写清每个模块的 `imports`、`exports`、不透明 `token` 与连接签名，运行 `ssot check` 与 `ssot graph`，确认依赖单向无环、类型引用全部闭合。框架阶段不预埋尚未使用的类型、状态字段或 `imports`（VDMJ 对没用到的定义报 `Warning 5000`，`ssot check` 判为错误）；效果还没有约束的连接写成显式 `== is not yet specified`，不为它预先建 `state`；`--` 说明与紧随其后的签名、字段同步。
2. **再填内容。** 按草稿约束填入 `post`、判定函数与场景，只在约束要求时建出最小 `state`、展开占位；补齐各 `README.md` 的「依据」「需求」「为什么」「语义」，写法照 `references/writing.md`。
3. **交付。** 在 omp 的 `eval` 里运行 `review.py`（`%load skill://ssot/scripts/review.py`，`await review("<design>")`），按上表逐条判断报出的反模式，真属于那一类的修掉，误报不改。然后运行 `ssot design status <design>`：它依次跑 `check`（诊断按第四节处理）、`elements` 与 `constraints`。核对无误后用 `--stamp` 盖章；改了规格之后，依据变了的记录会过期，重新核对后改写记录再盖章，或确认不变后 `--stamp <键>` 逐条确认。交付条件是没有错误、警告逐条看过；警告不要求清零，判断保留的照样交付，不为消警告改设计。交付时附上 `constraints` 台账，并单独列出只写进「语义」的约束。

本块不给验证结论，设计交给 `ssot-verify` 验证。验证报出的问题，回到本块或 `ssot-draft` 修改。
