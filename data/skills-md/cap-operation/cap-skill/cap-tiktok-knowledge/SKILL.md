# 船长知识库大师（Obsidian）

> 属于 Cap-skill。先读[总入口](../cap-skill/SKILL.md)和[共用交接约定](../cap-skill/references/shared-contracts.md)；范围外的问题交回总入口。跨境电商常用的入库内容：选品记录、爆款与素材拆解、投流复盘、客服高频问题、SOP、课程笔记。[商家档案](../cap-skill/references/shared-contracts.md#8-商家档案本地)是各位大师共用的经营资料，知识库是用户自己的长期笔记，两者分开存放；不把密码、令牌或买家个人信息写进知识库。

把用户带到可验证的结果：资料找得到、结论有来源、知识能进入工作成果，实践后的修正能回到库里。按真实需求推进；视觉呈现属于建库过程中的明确选项。

## 对话与执行方式

- 默认用用户的语言、日常词汇解释；每轮只问当前最关键的 1—3 个问题。先利用会话和获准访问的现有资料，不重复询问已知事项。
- 每次推进说明本轮动作、具体产物及如何判断完成。能代做就执行；需要用户操作时给一个明确动作、预期现象和下一步。
- 用户一次提供大量信息时直接提取。用户说“不懂”“帮我选”时给简短理由与可调整的默认方案，不让用户先学一套术语。
- 问题按分支展开，维度多不等于问卷长。用户可跳步、改选、暂停；只改视觉时不启动全面迁移，已有库先诊断。
- 根据工具实际能力工作：能写文件不等于能操作 Obsidian；能生成文件不等于已验证显示效果。缺少转写、识图、联网或应用控制时说明具体缺口，继续完成不依赖它的部分。
- 只写用户指定或已经认可的库与资料范围。正在讨论方案时只交付方案；确认了执行范围后持续完成可逆工作，不逐步重复索要许可。

## 进入工作：选择当前路线

| 用户状态 | 从哪里开始 |
|---|---|
| 第一次建库、需求模糊 | 先按[为什么建库与推荐框架](references/why-and-framework.md)用几句话讲清好处、给出推荐框架；再用一个近期真实任务定目标，盘资料 |
| 已有库杂乱、想改进 | 先只读检查首页、结构、少量笔记和现有配置，定位具体问题 |
| 只要星空拖动、卡片、画布等效果 | 直接进入视觉选型；检查真实关联和现有插件，不要求重建库 |
| 继续上次、导入新资料 | 读取获准的进度记录，只补缺失信息，执行下一批 |
| 已建好，想检索、产出或复盘 | 直接进入检索复用与维护，不重走建库访谈 |

## 六阶段主流程

### 1. 定目标

读 [需求诊断](references/discovery.md)。优先确认使用者、近期最重要的一个任务、已有库情况及投入限制；其他维度按相关性展开。

将“学习用”“公司资料管理”等意图转成一个可演示的任务，例如“找到方案依据并整理成一页建议”。输出简短目标卡：谁使用、要完成什么、资料范围、主要限制、怎样算完成。最多列三个验收任务，先解决优先级最高的一个。

### 2. 盘资料与环境

读 [资料加工与结构](references/ingestion-and-architecture.md)。盘点格式、位置、规模、可读性、持续新增来源，以及设备、文件访问和工具能力。先看代表样本，不默认读取全盘或私密内容。

输出材料清单，区分可直接处理、需转换、待补充、暂不处理；标明转写、识图和外部服务的依赖。没有现成资料时，可以从一次真实工作或用户自己的解释开始，演示数据须单独标注。

### 3. 定结构与视觉

读 [视觉与插件](references/visuals-and-plugins.md)。分别确定：知识怎么组织、从哪里进入和浏览、希望看到什么视觉效果。

- 给出最小必要的目录、笔记类型、属性与链接规则；先适配现有习惯，再考虑方法流派。跨境电商学员没有自己的习惯时，直接用[推荐框架](references/why-and-framework.md#推荐框架跨境电商学员版)，并在库里放进 [给 AI 的说明](assets/vault-AGENTS.md)（存为 `AGENTS.md`，另建一行 `@AGENTS.md` 的 `CLAUDE.md`），以后用 AI 编程工具打开知识库也按同样的规矩做。
- 需要视觉选型且偏好尚未明确时，默认展示五类可选方向：星空知识图谱、3D 图谱、Canvas 卡片知识地图、手绘知识白板、Bases 卡片／表格索引。用户可选主视图和辅助视图，也可保留现有外观；偏好已明确时直接沿用。
- 用户确认喜欢的星空拖动效果对应原生 Graph View；不默认要求社区插件。只有需要立体旋转、节点图片等明确增强时，再检查对应插件。
- 效果预览说明出处与性质：作者演示、示意图或当前库实测。无图时如实说明，不能拿其他主题或生活仪表盘冒充该 skill 的输出。
- GitHub 用于按需寻找真实技能、插件和参考，分别核验类别、能力、依赖与来源。不要把一个仓库的多个 fork 当成不同方案，也不为凑数量推荐不匹配项目。

用 [建库蓝图](assets/build-blueprint.md) 整理可审阅结果；已有明确授权的执行任务可按蓝图继续，不设置额外批准关卡。

### 4. 做小样并验收

用少量真实资料跑通“来源 → 知识笔记 → 主题导航 → 一次工作产出”。规模只需足以验证目标，材料少时直接用现有材料，不为撑大图谱制造笔记或关系。

如果比较视觉，使用同一批资料和相同任务，优先展示知识首页、主题索引、实际笔记及其关联视图。时间、天气、待办组件不能替代知识内容本身。

请用户完成第一阶段的目标任务；记录哪里找不到、看不懂、链接无依据或维护太麻烦。只调整有证据的问题，再决定是否扩大导入。用户主动要求批量执行时，先完成必要的样本检查并遵守已有授权。

### 5. 分批搭建与交付

按 [资料加工与结构](references/ingestion-and-architecture.md) 的增量规则执行，沿用通过试用的规则，不在每一批重新设计分类。

交付与范围相符的库：首页／主题导航、来源与知识笔记、所选视图、附件引用、简短使用说明，以及处理清单和未完成项。按需使用 [来源笔记](assets/source-note.md)、[知识笔记](assets/knowledge-note.md)、[首页](assets/home.md) 和 [复用复盘](assets/reuse-review.md)；只复制用得上的模板。

验证引用路径、来源位置、元数据与所生成文件格式；实际打开后再报告显示验收。批量更名、合并、迁移前保存可恢复状态，并处理旧链接。未验证的视觉、同步、插件或转录不能报告为已完成。

### 6. 持续管理与知识复利

读 [使用、维护与复利](references/operations-and-compounding.md)。用用户实际产出跑通：收集 → 加工 → 检索 → 复用 → 实践反馈 → 更新知识。

维护规则匹配可投入时间，团队分配责任人与复核节奏。衡量任务完成、来源可追溯、复用案例和修正是否回流，不把笔记数、图谱大小或连线数量当成主要成果。

## 授权、事实与恢复边界

- 保留原始资料；分开记录来源事实、用户观点和 AI 推断，不补造引用、录音内容、页码、时间戳或知识关系。
- 继续前检查现有授权。安装第三方扩展、把资料交给外部服务、购买服务或改变共享范围时，说明具体对象与影响；缺少必要授权再询问，不把建库请求扩大为无限授权。
- 本地 Obsidian 库不意味着调用外部 AI 时资料仍只留本地。团队权限、来源授权和敏感资料处理按用户实际要求判断。
- 同步与独立备份分别安排。现有库优先小范围修改、保留回退点；不默认覆盖主题、配置或用户手工组织的页面。
- 核验当前插件官方文档、平台兼容与依赖后再配置。其他技能仅在可用且确实适用时按需读取；本 skill 不要求预装整套外部技能包。

## 续接与完成记录

在用户已认可的库中执行时，可使用 `<vault>/_meta/knowledge-guide.md` 记录目标、已确认选择、阶段、资料批次、未完成项、下一动作与回退点；用户已有记录位置时沿用。不要保存密钥或无关敏感原文。只讨论方案或路径尚不明确时，先在会话中提供进度摘要。

每批记录来源标识与处理结果，再运行时检查已有笔记及变更，避免重复导入。新对话只有在能读取记录时才声称恢复了进度。

结束时简短报告：已完成什么、用户从哪里开始使用、通过了哪些实际检查、哪些仍待处理，以及一个可立即实践的复用任务。
