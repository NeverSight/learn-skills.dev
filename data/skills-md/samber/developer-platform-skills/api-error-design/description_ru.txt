Разработайте структуру ошибок публичного API так, чтобы интеграторы могли самостоятельно устранять проблемы — машинно‑читаемая таксономия кодов ошибок (плоский каталог, код/подкод, домен/причина в стиле Google), обёртка problem‑details из RFC 9457 с расширенными полями, пригодные к действию сообщения об ошибках, сигнализация возможности повторных попыток (флаг retryable, Retry‑After) и документация ошибок для каждого эндпоинта с отслеживанием request‑ID. Используйте её каждый раз, когда пользователь упоминает коды ошибок API, таксономию ошибок, RFC 9457, application/problem+json, тела ответов 4xx/5xx или запутанные сообщения об ошибках API — даже если он не говорит явно «дизайн ошибок». НЕ используйте для клиентских механизмов повторных попыток — используйте samber/developer‑platform‑skills@api-idempotency-retry, и не применяйте для коммуникаций о инцидентах и статус‑страницах — используйте samber/developer‑platform‑skills@api-status-communication вместо этого.

Пожалуйста, всегда отвечайте на языке пользователя.
