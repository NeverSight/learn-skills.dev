Concevez la surface d’erreur d’une API publique afin que les intégrateurs puissent se servir eux‑mêmes des correctifs — une taxonomie de codes d’erreur lisible par machine (catalogue plat, code/sous‑code, style Google domaine/raison), l’enveloppe RFC 9457 problem‑details avec des membres d’extension, des messages d’erreur exploitables, un signalement de ré‑essayabilité (drapeau retryable, Retry‑After), et une documentation d’erreurs par point de terminaison avec suivi du request‑ID. Utilisez‑le chaque fois que l’utilisateur mentionne des codes d’erreur d’API, une taxonomie d’erreurs, RFC 9457, application/problem+json, des corps de réponse 4xx/5xx ou des messages d’erreur d’API déroutants — même s’il ne dit jamais « design d’erreur ».
