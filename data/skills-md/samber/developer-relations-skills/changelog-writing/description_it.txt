Trasforma commit grezzi, pull request e ticket in note di rilascio che gli sviluppatori leggono davvero - un record scansionabile di ciò che è stato spedito, cosa significa nella pratica e cosa si rompe. Usalo ogni volta che l’utente menziona un changelog, CHANGELOG.md, note di rilascio, il corpo di un rilascio GitHub per un tag, una pagina “what’s new” ospitata, note di rilascio dell’app‑store, Keep a Changelog o Common Changelog, oppure chiede cosa scrivere per un rilascio appena fatto - anche quando la cronologia dei commit è disordinata e non segue alcuna convenzione di commit. Non è per l’incremento di versione, il tagging o le pipeline di pubblicazione. NON usarlo per una guida completa di aggiornamento con breaking‑change - usa samber/developer-relations-skills@version-migration-guide; per un post narrativo di rilascio usa samber/developer-relations-skills@engineering-blog-post.
