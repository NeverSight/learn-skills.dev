Transforme les commits bruts, les pull requests et les tickets en notes de version que les développeurs lisent réellement – un enregistrement scannable de ce qui a été livré, de ce que cela signifie en pratique et de ce qui casse. Utilisez‑le chaque fois que l’utilisateur mentionne un changelog, CHANGELOG.md, des notes de version, le corps d’une release GitHub pour un tag, une page hébergée « what’s new », les notes de version de l’app‑store, Keep a Changelog ou Common Changelog, ou demande ce qu’il faut écrire pour une version qu’il vient de couper – même lorsque l’historique des commits est désordonné et ne suit aucune convention de commit. Pas pour le bump de version, le taggage ou les pipelines de publication. Ne PAS l’utiliser pour un guide complet de mise à niveau avec changement majeur – utilisez samber/developer-relations-skills@version-migration-guide ; pour un article narratif de release utilisez samber/developer‑relations‑skills@engineering‑blog‑post.
