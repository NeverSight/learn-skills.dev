# Component Contract Design

把「這個畫面該用什麼元件、文字要不要換行、按鈕排在一起會不會重疊」這類決策，從畫面實作期前移到元件庫規格。

**產出**是一份 L3 元件庫規格檔，落在專案的 spec 目錄（L3 指專案元件庫章節；L1 通用原則、L2 語言與框架實作規範，分層見方法論〈分層架構〉）：每個元件的契約欄位表填滿、每個排列關係有容器元件承載。**目的**是讓後續的畫面票只剩「選件與排位」——畫面票寫不成那個形式，就代表契約還有缺口。

## 判準、形狀、程序分屬三處

這三件事各有各的權威來源，本 skill 只是其中之一。把它們搞混會查錯地方，也會把本 skill 當成判準的出處而不去讀方法論。

| 你要找的 | 權威在哪 | 內含 |
|---------|---------|------|
| **判準**——什麼算一個元件、容器為什麼也是元件、契約該有哪些欄位 | 元件庫雙向約束方法論 | 〈元件契約判準〉〈容器亦為元件〉〈命名與通用元件判準〉〈元件文字歸屬〉〈分層架構〉〈形態因素先決〉〈派發語言〉、工程端「禁自製元件」判準、豁免三條件 |
| **形狀**——規格檔長什麼樣、有哪些章節 | `doc` skill 的元件庫規格範本 | 第 1 章形態因素矩陣、第 9 章驗收、檔頭註解的欄位對應表 |
| **程序**——從手上的材料走到契約填滿 | **本 skill** | 下方〈全程〉 |

方法論與範本在本專案的實際路徑見 `references/addresses.md`。與其餘相鄰資產的交界見本檔最後一節，執行時不需要先讀。

|----|--------|------|------|

| 4 | 驗收契約是否齊全（〈契約齊全的定義〉） | `references/step-4-verify-completeness.md` | 齊全判定；未齊全的元件不得被畫面票引用 |

**時序**：本 skill 在 `version-bootstrap` skill 地基波的第 3 塊（UX 審查）之後、第 4 塊（元件庫實作）之前執行，互動反應規格是它的輸入。規劃波前段的 L3 章節得先只含元件清單與禁用對照；契約由本程序補齊，不在規劃波內補。

## 起手

**第一個動作是複製範本**：把 `doc` skill 的元件庫規格範本（地址見 `references/addresses.md`）複製到專案的 spec 目錄，檔名依專案 spec 命名慣例（有編號慣例者用編號，範本檔頭的建議檔名只是預設）。實際填寫的是這份副本，不是範本源檔。

專案已有範本格式的元件庫 spec 者不複製，就地補缺的子節；元件清單散在 design-system spec 或其他 spec 者，新建元件庫 spec 並把原清單改為指向它，清單不雙份維護。

判定「已有範本格式」的依據是章節內容是否符合上表〈判準、形狀、程序分屬三處〉定義的形態因素矩陣與驗收，不是章節編號是否吻合——編號吻合而內容不符不算已有範本格式。

**範例（判定「已有範本格式」的依據是章節內容而非章節編號）**：

輸入：兩份候選既有 spec 的章節清單：

- 候選甲：第 1 章「名稱與概述」、第 2 章「元件目錄」、第 3 章「元件契約」、第 9 章「附錄（僅參考連結）」
- 候選乙：第 1 章「形態因素矩陣」（已填支援形態）、第 2 章「狀態綁定模式」、第 3 章「元件契約」、第 9 章「驗收」（含檢查清單）

產出物（判定表）：

| 候選 | 是否算「已有範本格式」 | 依據 |
|------|----------------------|------|
| 甲 | 否，另行複製範本 | 章節編號 1、9 存在，但內容不是〈判準、形狀、程序分屬三處〉定義的形態因素矩陣與驗收——編號吻合不構成判準 |
| 乙 | 是，就地補缺子節 | 第 1 章即形態因素矩陣、第 9 章即驗收，內容與範本形狀一致 |

驗證（檢驗問句）：

- Q 判定依據是章節「編號」還是章節「內容」？　預期：內容——編號部分吻合不構成「已有範本格式」的理由
- Q 候選甲的第 1、9 章內容是否為形態因素矩陣與驗收？　預期：否 → 不算範本格式
- Q 候選乙的第 1、9 章內容是否為形態因素矩陣與驗收？　預期：是 → 算範本格式

複製之前先確認三項前置。任一項缺料，一律建前置票處理，不在本規格票內把它補出來：

| 前置 | 是什麼 | 缺了怎麼辦 |
|------|--------|-----------|
| design token 層 | 集中定義、程式碼只引用名字的樣式參數；顏色、間距、字級、圓角有具名常數 | 走 `foundation-design` skill 的 UI 維度建前置票，設為本規格票的 blockedBy |
| 形態因素矩陣 | 支援哪些形態的決策表，位於範本第 1 章。形態以使用者操作方式界定而非顯示空間：桌機指標加鍵盤、平板觸控、手機單手觸控各為一個形態；判準見方法論〈形態因素先決〉 | 先填範本第 1 章作為提案送簽核——範本的「預設單一形態」是提案值仍須簽核，支援幾個形態屬用戶簽核，PM 不得自行拍板。簽核回覆前，尺寸契約的「每種尺寸」與操作機制標待決，其餘欄照填 |
| 互動反應規格 | UX 審查的產出，是本程序的第三項輸入 | 建 `ux-design-evaluation` skill 的 UX 審查票。**這一項不擋本規格票**，詳見下表 |

前兩項缺料會擋住本規格票，第三項不會。建了 UX 審查票之後，它擋住的是哪一張：

| 這張票 | 被 UX 審查票擋住嗎 | 這張票該怎麼辦 |
|--------|------------------|--------------|
| 本規格票（你現在做的這一張） | **不擋** | 照跑到底。填契約時把互動反應子節標「待決」即可 |
| 元件票（step 5 才會建） | **擋** | 建票時把 UX 審查票填進它的 blockedBy |

## 判定起點

三種起點互斥，判定結果決定 step 2 走哪一條路徑。

| 起點 | 判定訊號 | step 2 走 |
|------|---------|----------|
| 有規格（狀態矩陣、畫面清單），元件庫尚未建 | spec 有逐畫面狀態表（一張全域狀態清單符合 `references/step-1-pick-starting-point.md`〈全域狀態清單算不算逐畫面狀態表〉者亦算）；元件目錄為空或只有 scaffold 產生的無呼叫端佔位元件。spec 有無元件清單不影響判定——清單無契約在三條路徑都是常態 | 路徑 A 規格推導 |
| 有設計畫布（artboard、wireframe 的統稱，設計稿為其輸出物），無規格或規格未到元件層 | 畫布是主要來源；畫面上的視覺單元尚未有語意名。設計工具的自動命名（如 Frame 123）視同未命名；設計工具內已有具名元件但無程式碼者仍走 B，具名視為候選名並經語意問句驗證 | 路徑 B 畫布拆解 |
| 已有元件程式碼與頁面，無契約或契約不全 | 三訊號任一命中即足：元件目錄非空且有呼叫端；頁面直接用原生佈局排列元件；曾發生重疊、截斷、功能補做 | 路徑 C 程式碼萃取 |

**範例（全域狀態清單是否算「可拆成逐畫面」）**：

輸入：spec 只有一張全域狀態清單（非逐畫面分節），含「畫面」欄；畫面清單：清單頁、詳情頁：

| 狀態列 | 畫面 | 顯示 |
|--------|------|------|
| 清單載入中 | 清單頁 | 骨架卡片 |
| 清單載入失敗 | 清單頁 | 錯誤提示 |
| 詳情載入中 | 詳情頁 | 骨架版面 |

產出物（判定表）：

| 候選 spec | 是否算「可拆成逐畫面」 | 依據 |
|-----------|----------------------|------|
| 上表（含「畫面」欄） | 是，走路徑 A | 每列的畫面欄值（清單頁、詳情頁）逐字等於畫面清單中的畫面名 |
| 假設清單只有「狀態列」「顯示」兩欄、無畫面欄 | 否，A 的訊號不命中；本例無畫布無程式碼，起點判定標待決，建規格補欄票 | 無法從清單本身找出逐字等於畫面名的值 |

驗證（檢驗問句）：

- Q 清單每一列是否都有一欄的值逐字等於畫面清單中的畫面名？　預期：是（依據：「清單每一列都有一欄的值逐字等於畫面清單中的一個畫面名，才算逐畫面狀態表」）
- Q 清單只有「狀態列」「顯示」兩欄、無畫布無程式碼時，起點判定為何？　預期：待決（依據：「起點判定標「待決」，建規格補欄票」）

**判錯的代價高，且錯誤在後續步驟不會自我暴露。** 最貴的一種是該走 C 而走了 A：產出的規格讀起來完好，但它描述的東西與程式碼裡的東西不是同一批，發現時已在實作期。

三種起點各自判錯的後果、多個訊號同時命中時的處置、以及三個不照表判的例外，都在 `references/step-1-pick-starting-point.md`。起點有任何猶豫先讀它，不要靠上表硬判。

## 用詞

| 詞 | 指什麼 |
|----|--------|
| 元件目錄 | 程式碼中實際存在的元件集合 |
| 元件清單 | 規格第 3 章的總表 |
| 元件庫 | 統一匯出入口涵蓋的目錄；入口外的任何 widget 檔皆屬頁面層 |
| 通用元件 | 已存在、語意涵蓋較廣、能以變體吸收差異的那個元件。「能否併入通用元件」的判準見方法論〈命名與通用元件判準〉 |
| 變體（variant） | 同一語意下行為不同的形態，以語意命名（primary／confirm／danger），不以外觀值命名。本套件內 variant 與變體同義，混用不表示兩件事 |
| 形態 | 使用者操作方式的分類（桌機指標加鍵盤／平板觸控／手機單手觸控），不是視窗寬度。同形態內的視窗尺寸差異由容器的排列不變式承載 |
| **本規格票** | **承載本次元件庫規格產出的那張 ticket，不是規格檔本身。** 中間產出物、提案值、待決項一律寫進它的 Problem Analysis。票號由 PM 於派發 prompt 或 Context Bundle 指定；未指定時停手回報，不自行選票 |

## 與相鄰資產的交界

執行時不需要先讀本節。不確定某件事該由本 skill 還是相鄰資產處理時再查。

| 相鄰資產 | 它管什麼 | 交界落在哪 |
|---------|---------|-----------|
| `foundation-design` skill | 地基入口與路由：token 萃取、接手模式的盤點→命名→固化順序、特徵測試閘門、測試基座 | 本 skill 消費 token 名，不自行歸納 token 階；step 2 的路徑 C 沿用其接手順序 |
| `ux-design-evaluation` skill | 畫面級：狀態矩陣、gate、輸入、錯誤恢復、導航；回饋的時間門檻與通知形式由它判斷 | 本 skill 只管元件級契約。同一類失效在這裡寫成契約欄位（內容政策、空間不足策略）而非審查項；回饋契約的通道與狀態集來源由規格撰寫者查形態因素矩陣填寫，不重新判斷時間門檻 |
| 執法工具（Dart 專案為 `dart-style-guardian` skill） | 抓裸值與寫死文字 | 原生元件直用的定義與判定權威在本 skill，不在執法工具——PostEdit hook 含八個 pattern 攔下新增的原生元件直用，但批次掃描腳本不偵測；判定與清點仍由本 skill 的 step-3〈原生元件禁用對照表〉承接。執法工具掃元件層、不掃組合層，所以它全綠仍可能重疊——容器缺件要靠本 skill 的判別問句抓 |
| `version-bootstrap` skill 地基波 | 編排 i18n → design-system → UX 審查 → 元件庫四塊的順序 | 本 skill 落在第三塊之後、第四塊之前；第四塊的前置 checkpoint 是〈契約齊全的定義〉 |
