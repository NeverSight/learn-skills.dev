# 專案分析

接手或協作他人專案時先做的一道工序：盤點對方 repo 的現況，把發現彙整成一份能交給對方、且交付後仍能對帳的工作項表。

本 skill 只管**分析**這一段。分析之後如何導入本框架的個別 skill 協助開發，不在本 skill 範圍。

---

## 模式判定決定走哪一條流程

被操作的專案接下來會不會用本框架開發，決定走哪一條。兩條的工序骨架同源，終點與產物落點不同。

| 判定 | 走哪條 | 終點 | 產物落點 |
|------|-------|------|---------|
| 該專案將納入本框架繼續開發（**吸收**） | `doc` skill 的 Legacy Code 接手處理標準化流程 | 提案、spec 與 UC、版本計畫、父級 ticket | 被操作 repo 的版控內 |
| 該專案不會用本框架開發（**分析**） | 本 skill | 工作項表交付給對方，之後逐次對帳 | 被操作 repo **之外**的外接資料夾 |

**第一道分流（決定走哪條流程）**：這個 repo 有沒有本框架的票庫，且 ticket CLI 可用？

**沒有，就是分析模式。**「無本框架 ticket 系統」不是需要降級處理的邊緣狀況，它就是「這不是本框架專案」的同義詞——真要用本框架開發，ticket 系統本來就會在。

**第二道分流（進入分析模式後，逐筆發現各自判定）**：這筆發現的收件方是誰？收件方指向本框架自身或分析者自己的專案（框架缺陷、自身技術債）時，該筆發現不進工作項表，依原規則在分析者端建票；其餘盤點工作不受影響。射程由收件方決定，不由手邊有無 ticket 系統決定——判準與核對順序見協作專案外接資料夾規格〈適用範圍〉與〈合法性閘門〉。

**Consequence**：把「無 ticket 系統」當成邊緣狀況，就會在每一個建票指令旁各寫一段降級處置。那些降級段各自演進之後，同一個欄位在兩個 skill 會得到不同讀法，而讀者無從判斷哪一個是現行的。

**Action**：模式在流程層宣告一次（下一節），本工序的各步驟不再各自判斷，也不各自寫降級段。

---

## 步驟 1：模式宣告與外接資料夾建立

工序開始前先宣告，全程只宣告一次。三條缺一不可：

| 宣告 | 內容 |
|------|------|
| 專案性質 | 被操作 repo 非本框架專案。本框架的 worklog、票庫與版本編排資產都不會、也不該被建立在對方的 repo |
| 產物落點 | 本工序的全部產物（評估記錄、spec、UC、工作項表）住在被操作 repo 之外的外接資料夾，由分析者持有 |
| 追蹤載體 | 追蹤載體是外接資料夾內的盤點工作項表，不是 ticket |

上表三條是對話層的一次性言明；對應的檔案系統動作在下一節，兩者不重複。

**建票指令怎麼讀**（本 skill 及其路由到的各 skill、各 reference 全程適用）：

> 被操作 repo 無本框架 ticket 系統時，本節的建票指令依
> `.claude/skills/doc/references/external-workspace-spec.md`〈讀法映射〉讀取。

該節（`doc` skill 的協作專案外接資料夾規格〈讀法映射〉）是讀法映射的**單一權威**，本 skill 引用它、不複述——複述即製造第二份會演進的副本。上面那段引文的措辭與路徑由該規格指定，逐字保留：它的〈引用本規格的 skill〉一節是人工維護的雙向表，維護者以字串比對實際引用者來更新該表，措辭改寫後本 skill 不會被自動移除，而是在該表上靜默過期——改動該規格的人據它判斷影響範圍時就會漏掉本 skill。

### 本步驟的操作

1. 依協作專案外接資料夾規格〈適用範圍〉逐條查核：該 repo 有無本框架票庫與可用的 ticket CLI、這次盤點的發現要交給誰。答不出收件方時停手，先向委派方確認收件方歸屬，確認結果寫進第 4 項的對帳票再續行。
2. 依該規格〈外接資料夾結構〉建立資料夾，`docs/` 中間層不可省。`README.md` 依該節 C3 填齊必載欄位（含被操作 repo 的絕對路徑與 commit、對帳責任人、對帳觸發條件）——步驟 6 的對帳要讀其中的觸發條件，只填一部分會讓那一步無據可依。
3. 複製 `doc` skill 的盤點工作項表範本（`.claude/skills/doc/templates/inventory-worksheet-template.md`）到資料夾根層。
4. 在分析者端建立一張本框架 ticket 作為本交付案的對帳載體，並把該規格閘門 G1–G5 的核對結果逐道寫進它的 acceptance。
5. 設定 CLI 執行環境：依該規格 C2，doc CLI 一律從具備本框架 `.claude/` 的 repo 內啟動，並以 `CLAUDE_PROJECT_DIR` 指向外接資料夾。從被操作 repo 啟動會直接被拒。

**產出**：外接資料夾（含 `README.md`、空的工作項表）、分析者端的對帳票。

> 第 4 項不是形式。整份交付只有對帳票被框架強制層覆蓋，規格的各項要求都掛在它的 acceptance 上；不掛上去，那些要求就只有後果敘述而沒有檢查時機。完整論證見該規格〈合法性閘門〉。

## 盤點步驟

依序執行，各步的操作細節取自 `doc` skill 的 Legacy Code 接手處理標準化流程對應章節——本 skill 不複述，只寫分析模式下的差異與產出落點。

| 步驟 | 做什麼 | 操作細節與路由 | 分析模式下的差異 | 產出（全部落在外接資料夾） |
|------|-------|--------------|----------------|------------------------|
| 2. 編譯與建置驗證 | 確認依賴可安裝、專案可編譯建置，排除基礎層級阻礙 | 環境與依賴檢查走 `project-init` skill；問題類型表見接手流程〈編譯與建置驗證〉 | **只記錄不修復**。編譯阻礙是工作項表的一列，不是分析者當場動手的對象 | 建置阻礙清單 |
| 3. 功能實作盤點 | 建立程式碼與規格的對應，釐清已做了什麼、還缺什麼 | 有無 spec 的兩個分支見接手流程〈Spec 標準化與功能實作盤點〉；spec 與 UC 的建立走 `doc` skill 的建立類命令 | **產出不進對方版控**。spec 與 UC 寫入外接資料夾的 `docs/` 之下 | 功能狀態清單、缺失常數清單、偏差清單、spec 與 UC 草案 |
| 4. 測試健康度評估 | 靜態審查加一次性執行分類，取得測試套件的健康狀態 | 掃描與失敗分類見接手流程〈測試健康度評估〉；覆蓋是否真實見 `test-effectiveness` skill；不可靠斷言見 `test-assertion-design` skill | **不做逐 UC 修復**。失敗與 skip 各自成為工作項表的列；該步失敗分類表內的建票指令依步驟 1 的讀法映射讀取 | 測試與 UC 對應表、skip 清單、失敗分類表、健康度摘要 |
| 5. 可觀測性審計 | 找出靜默失敗與盲區，評定成熟度等級 | 審計項目、成熟度矩陣與漸進式指引見接手流程〈可觀測性審計〉；判準來自可觀測性規則（`rules/core` 自動載入層，執行時已在 context 內） | **只評級不改造**。改造路線成為工作項表的列 | 可觀測性審計記錄、成熟度等級判定 |

**跨步驟共通約束**：

- 所有寫入產出的路徑一律帶來源前綴——被操作 repo 的根用 `repo:`，外接資料夾的根用 `ws:`。理由與例外見該規格〈兩種路徑基準〉。
- 外接模式下部分 doc CLI 命令的失敗形態是**成功語氣的空結果**，其輸出不得作為覆蓋率或引用狀況的證據。哪些命令屬此類、各自的正確用法與替代取得方式，以該規格〈目前的工具限制〉為準，使用前先查。**Consequence**：把空結果讀成「確實沒有」，該缺口就不會成為工作項表的一列；交付後沒有任何一方會再查它。

## 步驟 6：彙整工作項表與交付

1. 把盤點步驟的全部發現逐項寫成工作項表的列。必留欄位、順序層推導規則與狀態值域見協作專案外接資料夾規格〈盤點工作項表規格〉。
2. 每項的驗收條件全文、證據與影響檔案清單寫進項目詳情段，表格內只放摘要——表格每格單行是硬要求，理由見該規格〈文件組成〉。
3. 依對方的任務系統選匯入方式（試算表貼上、CSV 匯入、逐項建 Issue、依順序層分段貼文），對照表見該規格〈匯入方式對照〉。
4. 交付。交付當下狀態權威即轉移至對方系統，工作項表降為對照表，逐項狀態欄之後只能由對帳回抄寫入。
5. 依 `README.md` 記載的觸發條件執行對帳，一次對帳新增一列對帳紀錄。未回填外部編號的列計為「未對應」，不得據以宣告終態。

**產出**：可交付的工作項表、首次與後續的對帳紀錄。

> 分析的終點是交付與對帳，不是提案——提案要回答的是「接下來做什麼」，而在分析模式下，決定做不做的是對方。

## 從接手吸收流程剝除了什麼

本 skill 的工序由 `doc` skill 的 Legacy Code 接手處理標準化流程剝除吸收成分而來，不重新發明。剝除的每一項與理由：

| 剝除的項目 | 理由 |
|-----------|------|
| 〈前置步驟：Worklog 結構初始化〉 | 它建立的是本框架的追蹤基礎設施（worklog 三層目錄加票庫）。分析模式的追蹤載體是工作項表，這些目錄不會、也不該被建立在對方的 repo |
| 〈評估報告〉複製進被操作 repo 的 `docs/` | 產物不進對方版控。同一份記錄的落點改為外接資料夾 |
| 〈追蹤整合〉三系統中的 Worklog 與 Ticket 兩項 | 同第一列。核心文件那一項保留，載體改為外接資料夾的工作項表與 `README.md` |
| 〈流程啟動時的回溯盤點〉 | 它的操作是查本框架 ticket 系統中已完成的票。分析模式無此系統，且分析是一次性起點，不存在需要回填的既有本框架工作 |
| 〈提案與標準流程〉 | 提案是本框架決定「接下來做什麼」的入口，前提是後續由本框架繼續開發。分析的終點是把發現交給對方 |
| 〈補充測試並逐 UC 驗證〉 | 寫測試與改程式碼是在對方的 repo 裡開發，已越過分析的邊界。測試缺口在分析模式下是工作項表的一列 |
| 〈Roadmap 規劃與版本計畫〉的版本計畫、版本 worklog、父級 ticket 三項轉換 | 三者全是本框架的編排資產。**只剝除這三項轉換**——它前面的「彙整所有缺口」保留，成為本 skill 的步驟 6 |

該流程的導航性段落（流程總覽、步驟間的依賴關係、適用情境與排除情境、相關文件）由本 skill 自身的結構取代，既非保留亦非剝除。

**留下的盤點步驟為什麼留**：編譯與建置驗證、功能實作盤點、測試健康度評估、可觀測性審計，這些步驟的動作都是讀取與判定，產出都是對現況的描述。它們不預設後續由誰開發，因此與模式無關。

## 範例：入口判定與模式宣告

【輸入】

分析者被要求盤點另一個團隊的服務。已知事實：

- 該 repo 的版控內沒有票庫目錄，命令列也沒有本框架的 ticket 入口
- 對方團隊用自己的任務系統管理工作，盤點結果要交給該團隊的維護者
- 對方沒有表示願意把規格文件收進自己的版控

【產出】

| 判定項 | 值 |
|--------|-----|
| 模式 | 分析（非吸收） |
| 第一道分流依據 | 無票庫且 ticket CLI 不可用 |
| 第二道分流依據 | 收件方是被操作 repo 的維護者，非本框架亦非分析者自己的專案 |
| 產物落點 | 被操作 repo 之外的外接資料夾 |
| 追蹤載體 | 外接資料夾根層的盤點工作項表 |
| 建票指令讀法 | 依協作專案外接資料夾規格〈讀法映射〉 |
| 對帳載體 | 分析者端的一張本框架 ticket，閘門核對結果寫進其 acceptance |

後續各步驟不再重複這組判定，也不各自撰寫「若無 ticket 系統則……」的處置。

【驗證】

| 檢驗問句 | 預期答案 |
|---------|---------|
| 模式判定用的是客觀事實查核，還是「手邊方不方便」？ | 事實查核：查該 repo 有無票庫與 CLI、問這筆發現要交給誰 |
| 收件方是誰答得出來嗎？ | 答得出來（對方團隊的維護者）。答不出來時停手，先向委派方確認 |
| 工序中有幾段「若無 ticket 系統則……」的降級處置？ | 零段。模式已在入口宣告一次；出現第二段即表示有人繞過了步驟 1 |
| 這組判定的產出能被下一個 session 接手嗎？ | 能——外接資料夾的 `README.md` 與對帳票各自留有事實，不依賴對話脈絡 |

**前提相反時判定不同**：若該 repo 的版控內就有本框架票庫且 CLI 可用，模式即為吸收，改走 `doc` skill 的 Legacy Code 接手處理標準化流程。此時改用工作項表視為規避規則。
