# System Design

接到需求之後、開始畫架構之前的設計流程。這支 skill 管的是**範圍與時機**：哪些問題要先問、哪些決定第一版就要定、哪些設計該延後、延後的設計要等什麼指標才引入、變更怎麼安全地上線。它不負責在幾個技術方案中挑一個（那是方案評估的工作），也不負責觸發之後的遷移執行。

適用範圍涵蓋後端、前端與基礎設施。

## 流程

流程由執行這支 skill 的設計者（agent 或工程師）負責，依序走，每一步的產出是下一步的輸入；需求盤點裡的待問題目交給需求方回答。

| 步驟         | 動作                                                         | 產出                                         | 讀                         |
| ------------ | ------------------------------------------------------------ | -------------------------------------------- | -------------------------- |
| 需求盤點     | 逐題問，答案分成已確認、假設、待問                           | 需求清單，待問的題目交給需求方               | `references/requirement-intake.md`  |
| 容量估算     | 從業務事件推估讀取尖峰、寫入、儲存，每個數字附依據           | 估算表，含「依賴它的結論」欄                 | `references/capacity-estimation.md` |
| 決策時機分類 | 列出設計決定，逐項分進定案、先做、延後                       | 決定清單；延後類附早期替代做法與觸發指標     | `references/decision-timing.md`     |
| 觸發指標     | 延後類逐項查觸發訊號與要先量的指標                           | 量測清單（併入「先做」類）                   | `references/escalation-triggers.md` |
| 上線設計     | 判斷要不要功能開關（含後台切換）、A/B 測試、先擴充；對外 API 依消費者的更新能力設計改版與退場；行動 App 另排審核前置時間、強制更新與回退手段；準備上線監控 | 上線計畫與上線監控                           | `references/release-and-rollout.md` |

待問題目還沒有答案時，容量估算照常進行：缺的值用假設值填入估算表，並在那一列標記「假設」。標記的作用是答案回來時找得到要重算的列；沒標記的假設值進入設計之後，就沒有人知道它要被替換。

## 決策時機的分類依據

這是整支 skill 的核心判斷，正文留下分類依據，細節與例子在 `references/decision-timing.md`。

逐項問：**如果之後要改這個決定，改動會碰到已經不在團隊控制範圍內的對象嗎**（已發出去的網址、外部整合方、已寫入的資料）？

- 會 → **定案**：第一版就定，寫明理由。
- 不會，但現在做很便宜、之後補很貴 → **先做**：第一版就做。量測屬於這一類。
- 不會，而且現在做的成本高於之後補的成本 → **延後**：不做，寫下早期替代做法、觸發指標，並確認那個指標現在就在量。

**延後類的成立條件**有三項，缺一不可：寫下早期替代做法、寫下觸發指標、那個指標從現在起就在量。缺任何一項，這一列就還沒分類完成——缺的是觸發指標時，先問它是不是應該分到定案或先做；兩者都不是、也說不出任何會讓它變得必要的情況，就從設計中刪除。理由是沒有指標在量的延後項目，之後沒有任何訊號會讓人回頭想起它，直到相關的問題直接造成故障。

**過度設計的定義是比它的觸發指標先出現的設計。** 審查一份設計時，對每一個擴充性質的設計問「它的觸發指標是什麼、現在到了沒」：還沒到的移到延後類，並照上一段補齊三項。

## 目的不是上線服務的設計另外標記

不是每一份設計都為了上線服務：**原型**驗證需求或技術可不可行、預期會改或丟，**提案 demo** 讓決策者看到效果，**學習或比較**刻意做出某個設計來學一項技術或比較方案（同一個 API 用兩種語言實作、換一個快取伺服器比較）。這三種目的各自標記，並寫下兩件事：這份設計要驗證、展示或學到什麼，以及為了這個目的跳過了哪些上線服務需要的設計。

這些目的不拿來證明規模設計合理，規模判斷也不遷就它們。**目的改變與第一次對外發布時重新走一次決策時機分類**：原型轉成正式服務、demo 被採用直接上線，或原型第一次上架、發 beta、對外開放 API 之前，當初跳過的項目就是缺口，那份「跳過了什麼」的清單是重新分類的起點。細節見 `references/decision-timing.md` 的〈目的不是上線服務的設計〉。

## 產出：設計文件的段落

設計文件依下列段落組織，每一段對應流程的一步：

1. 功能需求與非功能需求（含每條路徑的一致性與延遲目標）
2. 容量估算（值、依據、依賴它的結論）
3. 定案的決定與理由
4. 先做的項目（含要量的指標）
5. 延後的設計（早期替代做法、觸發指標、量測位置）
6. 上線計畫（開關、實驗、擴充與切換、行動 App 的審核與回退，視需要）與上線監控
7. 假設清單與待問清單
8. 開發順序（延後類也都要實作時，例如練習或原型專案）：定案類排最前、量測先於優化，每個延後的設計成為一次有前後對照的實驗

## 範例：一則決定怎麼分類

需求：電商行銷用的短網址服務，訪客點擊後轉址到商品頁。

- 「短碼的格式與短網址用的網域」→ **定案**：網址印進簡訊與廣告之後就收不回來。
- 「轉址回應標記是哪個實例回的」→ **先做**：現在只是一個 header，多實例之後排查全靠它。
- 「用 Bloom filter 擋不存在的短碼」→ **延後**：早期替代做法是快取「不存在」的結果加來源限流；觸發指標是查無資料的請求比例升高、且大多是不重複的短碼；這個比例從第一版開始量。

同一個 Bloom filter，在掃描流量出現後是對的設計；它在那之前出現，就是過度設計。

## 和其他 skill 的分工

| 情境                                                         | 用哪一個                                                         |
| ------------------------------------------------------------ | ---------------------------------------------------------------- |
| 清單上某個決定有多個技術方案要比較、挑一個                   | `design-decision-framework` 或 `wrap-decision`                   |
| 延後項目要設重新評估的條件（觸發指標就是絆腳索）             | `wrap-decision` 的絆腳索                                         |
| 範圍內的需求要寫成可驗收的規格                               | `spec`                                                           |
| 先做類裡屬於專案地基的產物（測試鷹架、migration、可觀測性）  | `foundation-design`                                              |
| 延後的設計被觸發，要擴充設備、遷移或切換                     | 本 skill 的 `references/release-and-rollout.md`〈先擴充才能上線或切換的變更〉 |

表中的 skill 不一定安裝在每個專案；沒有安裝時，情境欄描述的工作仍然要做，改用專案自己的做法。本 skill 的決定清單是那些 skill 的輸入：清單上每一個需要挑方案、設絆腳索、寫規格或建立地基產物的決定，依上表的情境交給對應的 skill。不必等本 skill 全部走完——決策時機分類出現第一個定案項目時，就可以開始為它挑方案。
