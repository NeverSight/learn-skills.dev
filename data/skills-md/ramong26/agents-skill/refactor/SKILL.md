# Refactor

코드의 동작은 유지하면서 읽기 쉽고 관리하기 좋은 구조로 리팩토링한다. 설명은 항상 한국어로, 짧고 직접적으로 작성한다.

## 진행 원칙

- 수정 전에 관련 파일, 호출부, 타입, 테스트와 프로젝트 규칙을 확인한다.
- 기존 API 구조, 외부 동작, 유용한 주석과 프로젝트 스타일을 유지한다.
- 기능 추가, 무관한 버그 수정, 대규모 구조 변경은 요청 범위에 포함하지 않는다.
- 가장 적은 파일과 가장 작은 변경으로 목적을 달성한다.

## 리팩토링 기준

### 가독성

- 함수와 변수 이름만 읽어도 의도가 드러나게 한다.
- 복잡한 조건은 이름 있는 변수나 함수로 분리한다.
- 깊은 중첩은 가능한 경우 early return으로 평탄화한다.
- 매직 넘버와 문자열은 의미 있는 상수로 바꾼다.

### 함수 분리

- 함수 하나는 하나의 책임만 갖게 한다.
- 너무 긴 함수는 실제 책임 경계를 기준으로 나눈다.
- 반복 로직은 진짜 같은 규칙을 공유할 때만 추출한다.

### 중복 제거

- 우연히 비슷해 보이는 코드를 성급하게 공통화하지 않는다.
- 공통화로 변경 이유와 결합도가 늘어나면 작은 중복을 유지한다.

### 타입 안정성

- TypeScript에서 수정 범위 안의 `any`는 가능한 경우 제거한다.
- 유니언 타입과 타입 가드를 우선하고, 프로젝트의 기존 `interface`/`type` 스타일을 따른다.
- 타입 단언이나 임시 땜질로 오류를 숨기지 않는다.
- 관련 없는 전체 타입 시스템 개편은 하지 않는다.

### React

- UI 표현과 비즈니스 로직을 분리한다.
- 재사용과 책임 경계가 분명할 때만 Custom Hook으로 추출한다.
- 컴포넌트를 파일 수만 늘리기 위해 쪼개지 않는다.

## 출력 형식

```md
## 현재 문제

1. 현재 구조의 문제

## 변경 내용

1. 변경한 파일과 핵심 변경

## 변경 설명

각 변경이 동작을 유지하면서 어떤 문제를 해결했는지 설명한다.

## 검증

- 실행한 테스트, 린트 또는 타입 검사
```

- 코드 조각을 직접 받은 경우에는 요청에 맞춰 전체 리팩토링 코드를 제공한다.
- 레포 파일을 수정한 경우에는 변경 파일과 핵심 코드만 보여주고, 변하지 않은 전체 파일을 반복하지 않는다.
- 리팩토링만 요청된 경우 새 기능이나 버그 수정 결과를 끼워 넣지 않는다.
