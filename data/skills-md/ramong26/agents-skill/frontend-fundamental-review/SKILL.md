# Frontend Fundamental Review

토스의 Frontend Fundamentals를 참고한 프론트엔드 기본기 리뷰를 한다. 특정 회사의 공식 심사처럼 말하지 말고, 사용자와 유지보수하는 개발자 관점에서 근거 중심으로 설명한다.

## 진행 원칙

- 리뷰 요청만 있으면 코드를 수정하지 않는다. 수정까지 명시된 경우에만 리뷰와 구현을 분리해 진행한다.
- 먼저 프로젝트의 `AGENTS.md`, 관련 파일, 호출부, 타입, 테스트와 기존 패턴을 확인한다.
- 스타일 취향보다 실제 읽기 어려움, 변경 비용, 오류 가능성, 사용자 영향이 있는 문제를 우선한다.
- 지적마다 파일 경로와 줄 번호, 실제 코드 근거, 문제의 이유, 최소 개선 방향을 제시한다.
- 과한 추상화·파일 분리·리팩토링을 제안하지 않는다. 단순한 중복이 더 예측 가능하면 그대로 둔다.
- 접근성만 요청된 경우에는 `accessibility-review`를 우선 적용하고, 이 스킬에서는 구조·가독성 관점의 문제만 다룬다.

## 확인 기준

### Readability

1. 비교식은 읽는 방향과 자연스러운 순서를 따른다. 예: `min <= value && value <= max`.
2. 복잡한 조건은 의도를 드러내는 이름의 변수나 함수로 분리한다.
3. 인증, 리다이렉트, 로딩 같은 구현 세부사항은 화면의 핵심 흐름과 분리한다.
4. 매직 넘버와 문자열은 의미가 드러나는 상수로 바꾼다.
5. 서로 배타적인 분기와 실행 경로는 한눈에 보이도록 나눈다.
6. 읽기 어려운 중첩 삼항식은 조건문이나 의미 있는 함수로 단순화한다.
7. 하나의 Hook에 여러 책임을 넣지 말고 역할별로 나눈다.
8. 코드를 읽으며 파일과 함수 사이를 불필요하게 오가는지 확인한다. 정책과 핵심 흐름은 가까이 둔다.

### Cohesion

9. 함께 바뀌는 필드와 로직이 한 단위에 모여 있는지 확인한다. 폼 상태와 검증처럼 한 기능의 데이터는 함께 관리한다.
10. 함께 쓰이고 함께 바뀌는 상수는 의미 있는 그룹으로 묶는다.
11. 함께 수정되는 컴포넌트·Hook·타입·스타일이 도메인 기준으로 가까이 있는지 확인한다.

### Coupling

12. 깊은 props drilling은 합성, 적절한 Context, 상태 경계 조정으로 줄일 수 있는지 확인한다.
13. 잘못된 공통화보다 작은 중복을 허용한다. 실제 변경 이유가 다른 코드를 억지로 묶지 않는다.
14. Hook 하나가 여러 책임이나 서로 무관한 상태를 관리하지 않는지 확인한다.

### Predictability

15. 함수 호출만 보고 알기 어려운 상태 변경·네트워크 요청·이벤트 등록 같은 부수 효과를 확인한다.
16. 외부 라이브러리와 충돌하거나 오해를 부르는 모듈 이름을 피하는지 확인한다.
17. 같은 역할을 하는 함수들이 일관된 반환 형태와 오류 처리 방식을 가지는지 확인한다.

## 결과 형식

```md
## 요약

핵심 판단을 1~3문장으로 작성한다.

## Findings

### [P1] [Readability] 조건식의 의도가 드러나지 않음

- 위치: `path/to/file.tsx:42`
- 문제: 실제 코드에서 무엇이 읽기 어려운지 설명한다.
- 이유/영향: 유지보수 비용이나 오류 가능성을 설명한다.
- 개선 방향: 가장 작은 변경 방향을 제안한다.
- 예시: 필요한 경우 짧은 코드만 보여준다.

## 확인 범위

- 확인한 파일과 실행한 검증

## 확인하지 못한 부분

- 실행하지 못한 테스트나 확인이 필요한 런타임 조건
```

- 심각도는 실제 영향 기준으로 `P0`(즉시 대응), `P1`(우선 개선), `P2`(개선 권장)를 사용한다.
- 발견 사항이 없으면 억지로 지적하지 말고 “수정이 필요한 사항을 찾지 못했다”고 명시한다.
- 결과와 설명은 항상 한국어로 작성한다.
