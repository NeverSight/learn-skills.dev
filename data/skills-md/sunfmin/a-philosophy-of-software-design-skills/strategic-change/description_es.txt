Modifica el código existente estratégicamente en lugar de tácticamente. Después del cambio, el sistema debe verse como si hubiera sido diseñado teniendo en cuenta ese cambio desde el principio (A. Ousterhout, “A Philosophy of Software Design”, cap. 3 y 16). Úsalo al añadir una característica o corregir un error en código existente y el usuario quiere mantener el diseño limpio, dice “no lo parchees simplemente”, “¿arreglo rápido o solución adecuada?”, “¿cuál es la forma correcta de añadir esto?” o pregunta antes de confirmar si un cambio empeoró el diseño. No es para módulos nuevos desde cero (design‑it‑twice) o para revisar el PR de otra persona (complexity‑review).
