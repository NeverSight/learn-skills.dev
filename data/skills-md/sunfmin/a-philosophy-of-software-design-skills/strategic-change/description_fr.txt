Modifiez le code existant de manière stratégique plutôt que tactique. Après la modification, le système devrait sembler avoir été conçu dès le départ avec ce changement en tête (« A Philosophy of Software Design » d’Ousterhout, chapitres 3 et 16). Utilisez cela lors de l’ajout d’une fonctionnalité ou de la correction d’un bug dans du code existant et que l’utilisateur veut garder le design propre, dit « ne faites pas juste un patch », « correctif rapide ou correctif complet ? », « quelle est la bonne façon d’ajouter cela », ou demande avant de valider si la modification a détérioré le design. Pas pour les nouveaux modules créés de zéro (design‑it‑twice) ou pour la révision du PR de quelqu’un d’autre (complexity‑review).

Veuillez toujours répondre dans la langue de l’utilisateur.
