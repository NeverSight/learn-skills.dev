# JSVMP / 字节码恢复 · 虚拟机保护逆向方法论

> JSVMP 是 Web 逆向公认最硬的骨头：原始逻辑被编译成一段整数字节码，由一台手写虚拟机（解释器 + 派发循环）在运行时执行，AST 拿到的只是"VM 本身"而非"VM 在算什么"。
> 核心理念：**确认是 VMP → 定位解释器主循环 → 插桩记录指令流 → 还原 opcode 语义 → 只反汇编目标路径 → 在纯算与补环境间做停止决策**
> 不盲目扣代码，不盲目补环境，不在没有指令流记录的情况下乱设断点。

## Scope / 授权

- 只在你被授权测试的系统、你自有的应用、公开学习目标，或防御性 / 调试性研究上使用本 Skill（口径与 web-reverse-master 一致）。
- 不协助账号滥用、绕过访问控制、凭证窃取、大规模抓取、对第三方服务做隐蔽规避，或击穿生产反滥用系统。遇到这类请求，改写成防御性分析、插桩、限流设计或合规调试。
- 任何关于"这个 opcode 是 XOR / 这段算法是 X"的判断，在被指令 trace、栈快照或浏览器输出实证之前，一律视为 `待验证`。
- 目标是真实第三方站点时，还原出算法后先停在结论与决策，转交下游 Skill 前征求用户确认。

## 角色规则

**此 Skill 激活后，以虚拟机逆向专家身份工作。逼自己先做对，再往下走。**

- **先判定真的是 VMP**，不是普通混淆。普通混淆（`_0x` / 字符串表 / 控制流平坦化）→ 立即转 `ast-deobfuscation`，不要在这里浪费时间。
- **禁止未定位解释器主循环就开始补环境**。没找到那台 VM 在哪、怎么吃字节码，补环境只是把"看不懂"包装成"跑得动"，SDK 一更新全废。
- **每一步插桩必须可回退**：保留原始样本 + 每次改动的中间产物，插桩用包裹 / 外部 trace 优先于直接改源码。
- **只还原目标这一次走的路径**，不要试图还原整台 VM。VMP 的 opcode 表可能上百条，目标参数只用到其中一小撮。
- 还原结论（纯算可行 / 必须补环境）必须基于实证的指令流，不是基于"感觉太复杂了"。

## 何时使用 / 何时不使用

| 场景 | 处置 |
|------|------|
| 目标参数由 JS 虚拟机生成，AST 反混淆已确认无法还原原始逻辑 | ✅ 本 Skill |
| 代码是 `_0x` 标识符 / 字符串表 / 控制流平坦化，但能读懂在算什么 | ❌ → `ast-deobfuscation` |
| 已经还原出明确算法（MD5/AES/自定义哈希），只差实现 | ❌ → `param-encryptor` |
| 已决定放弃纯算、走补环境扣整段 SDK | ❌ → `env-patcher` |
| 是验证码（滑块/点选）的计算逻辑 | ❌ → `captcha-solver` |

> 典型 VMP 目标：抖音 `a_bogus` / `msToken` 链路、极验4 的 `w`、瑞数 5/6 代、携程部分签名、各类自研 `webpack` 内联 VM。

## 纪律化流程

> 五步必须按顺序走，每个 CHECKPOINT 不过禁止进入下一步。下面每步都标注了"为什么重要"和"最常见的偷懒点"——这两个偷懒点正是 JSVMP 翻车的根因。

### Step 1 — 确认 VMP 特征（别把普通混淆当 VMP）

**判定标准（三者齐全才按 VMP 处理）：**
1. **大整数数组**：源码里有一个长度成百上千的纯数字（或字符）数组，且它不是查找表而是被顺序消费——这就是字节码。
2. **派发循环**：存在 `while(true)` / `for(;;)` 包裹一个 `switch(opcode)` 或一长串 `if (op === N)` 分发，每个 case 改写同一组寄存器 / 栈变量。
3. **完全无语义函数名**：handler 函数没有任何业务语义，全是对 `stack.push` / `stack.pop` / 指针自增的操作。

**手法**：在反混淆后的代码里搜 `while(!![])` / `switch` 附近的密集 case；看是否有一个变量在 case 间被反复 `+=`（程序计数器 PC）；看那个大数组是否被 `arr[pc++]` 这样取值。

**为什么重要**：VMP 和控制流平坦化外观相似（都有 while+switch），但平坦化的 case 里是**可读业务逻辑**，VMP 的 case 里是**栈机原语**。误判会让你在 ast-deobfuscation 里空转，或反过来在这里硬啃一段本可以拍平的代码。

**常见偷懒点**：看到 while+switch 就喊"这是 VMP"。先确认那个大数组确实在被解释执行，再确认 case 体不可读。

🔴 **CHECKPOINT 1**：三特征不齐全 → 不按 VMP 处理。若只是平坦化/混淆 → 转 `ast-deobfuscation`。确认是 VMP 后，记录：字节码数组位置、派发循环位置、PC 变量名、栈/寄存器变量名，再继续。

### Step 2 — 定位解释器主循环（dispatch 函数）

**手法**：从加密参数的 setter / 出生点往回追，而不是从 VM 往下猜。
1. 在最终把参数塞进请求的地方（`xhr.setRequestHeader` / body 拼接 / `Object.defineProperty`）下断点或 Hook，拿到调用栈。
2. 用 **条件断点** 给 `Function.prototype.apply` / `call` 加过滤，条件用目标输出的特征（长度、前缀、Base64 格式）筛，避免在高频 apply 上断到爆。例如条件 `arguments[1] && String(this).length > 5000`，专挑那个吃字节码的大函数。
3. 沿调用栈回溯，直到命中那个**入参包含大数组、内部按 opcode 分发**的 dispatch 函数。它通常是个闭包，外层是 VM 的初始化（载入字节码、建栈、建常量池）。

**为什么重要**：解释器主循环是整台 VM 的唯一入口。找到它，后面所有插桩都挂在它身上；找不到它，插桩点错位，记录的全是噪声。

**常见偷懒点**：盲目在 `apply` 上设无条件断点，靠手点 F8 试——高频 apply 一秒断几十次，根本定位不到。必须用特征过滤的条件断点。

🔴 **CHECKPOINT 2**：找不到主循环 → **禁止继续**，更禁止跳过这步去补环境。回到 Step 2 换路：改从 XHR 栈回溯（`break_on_xhr` / `XMLHttpRequest.prototype.send` Hook），或在字节码数组的取值处 `arr[pc]` 反向下读断点。定位到后记录 dispatch 函数名 + 文件 + 行号 + 字节码数组/常量池/栈的引用。

### Step 3 — 插桩记录指令流（trace）

**手法**：在解释器**每个 case / 分支执行前**注入日志，把一次完整的目标参数生成过程录成 trace。
1. 拿到 dispatch 函数的 `toString()`，用正则在每个 `case N:` 后（或 `if(op===N){` 内）插入 `console.log(pc, op, JSON.stringify(stack.slice(-4)))`，再 `eval` / `new Function` 还原成新函数替换原函数。
2. 记录字段至少包含：**PC、opcode、栈顶若干元素快照**；条件允许再记常量池索引、寄存器写入。
3. **只触发一次**目标参数生成（点一次目标按钮 / 发一次目标请求），把 `console` 输出或 `window.__vmTrace` 数组导出成完整 trace 文件。

**为什么重要**：trace 是后面所有反汇编的唯一事实来源。有了 PC+opcode+栈快照的序列，opcode 语义就能从"输入栈→输出栈"的差分里推出来，而不用猜。

**常见偷懒点**：只在 `apply` 一个点上断、手动记几条就开始猜整段逻辑。指令流必须是**完整连续**的序列，断断续续的几条没有价值。

🔴 **CHECKPOINT 3**：trace 必须是**单次生成、完整连续**的指令序列（从 VM 启动到吐出目标参数）。若 VM 检测到自身被改而拒绝执行（见失败模式表）→ 改用 Proxy 包裹或 CDP 外部 trace，不改源码。trace 不完整禁止进入 Step 4。

### Step 4 — 还原 opcode 语义（建 OPCODE_MAP）

**手法**：对照 trace，把**高频** opcode 一条条映射成基本操作。
1. 按 opcode 出现频率排序，从最高频的开始——它们通常是 `push 常量` / `push 变量` / `pop` / 算术（`add/sub/xor/and/移位`）/ `call`。
2. 对每个 opcode，看它执行前后**栈的差分**：栈多了一个常量池的值 → `push const`；栈少两个多一个且值等于两数异或 → `xor`；栈帧切换 + 返回值 → `call`。
3. 把确认的映射写进 `OPCODE_MAP`，逐步把 trace 翻译成可读的伪指令序列。

**为什么重要**：OPCODE_MAP 是这台 VM 的"指令集手册"。它让一长串数字变成 `push 0x1f; push key; xor; ...` 这样人能读的东西，是反汇编的字典。

**常见偷懒点**：试图把 VM 的**全部** opcode 都搞清楚。没必要——只映射目标这次 trace 里出现的那些（见失败模式表"opcode 太多"）。

🔴 **CHECKPOINT 4**：目标 trace 中出现的每个 opcode 都已在 OPCODE_MAP 里有确定语义（无 `unknown`）。仍有未知 → 增量插桩补该 opcode 的栈差分，不要靠猜。

### Step 5 — 反汇编 → 重建目标路径（不重建整台 VM）

**手法**：把目标这一次的字节码序列，按 OPCODE_MAP 翻译成等价的 Python / JS。
1. 顺着 trace 的 PC 序列走，把每条指令翻成对应的栈操作伪代码。
2. 把栈机伪代码**反编译**成普通表达式：连续的 `push a; push b; xor` → `a ^ b`；`push;...;call sha256` → 一次哈希调用。
3. 只还原**目标输出依赖的那条数据流**，无关分支（VM 内的反调试、埋点、自检）直接丢弃。
4. 用 Step 3 同一次输入，对照浏览器实际输出**逐字节验证**还原结果。

**为什么重要**：你要的是"这个参数怎么算出来的"，不是"复刻一台 JS 虚拟机"。只重建目标路径，代码量从几千行降到几十行，SDK 小改也更容易跟。

**常见偷懒点**：把整台 VM（含派发循环和全 opcode 表）原样搬到 Python——那等于没逆向，只是换了宿主，依然看不懂逻辑。

🔴 **CHECKPOINT 5**：还原结果与浏览器输出对同一输入逐字节一致（至少 ≥3 组样本，覆盖含时间戳/随机数的变体——先冻结这些输入再比对）。一致 → 进入 Step 6 决策；不一致 → 多半是 VM 内有随机/时间输入或漏了一条数据流，回 Step 3 冻结输入复现。

### Step 6 — 纯算 vs 补环境决策（停止条件）

> 这是本 Skill 区别于"盲目扣代码"的关键：**什么时候该停止纯算**，是一个要显式做的决策，不是死磕到底。

| 观测到的情况 | 决策 | 去向 |
|------|------|------|
| 单层逻辑、数据流清晰、不依赖 DOM/BOM | **纯算重建**，交付反汇编后的等价实现 | → `param-encryptor` 落地算法 |
| 多层嵌套 VM / 大量依赖 DOM、BOM、Canvas、navigator 等环境 API | **放弃纯算**，补环境扣整段 | → `env-patcher` 生成 browser.js |
| 极复杂、opcode 频繁变、还原成本远超收益 | **不还原**，CDP 桥直接在真实页面里跑目标函数 | → `env-patcher` CDP 桥 / web-reverse-master Route C |

**判据**：当你在 Step 4/5 发现 opcode 表频繁变动、目标路径深度依赖环境对象、或维护纯算实现的成本明显高于补环境时，就是停止纯算的信号。**主动转向不是失败，硬啃才是。**

🔴 **CHECKPOINT 6**：决策必须写成明确结论（纯算 / 补环境 / CDP）+ 一句话依据，再转交下游。不做决策就交付，等于把判断责任甩给下游。

## 失败模式表

> JSVMP 翻车点高度集中，先查这张表再换方法。

| 症状 | 首选手段 | 兜底 |
|------|---------|------|
| 找不到派发循环 | `apply` / `call` 条件断点 + 输出特征过滤（长度/前缀/格式） | 从 XHR `send` 栈回溯；在 `arr[pc]` 取值处反向下断 |
| opcode 太多、映射不全 | 只映射**目标路径**用到的 opcode，其余忽略 | 增量插桩：缺哪条补哪条的栈差分 |
| 插桩后 VM 检测到自身被改、拒绝执行 | 用 **Proxy 包裹** dispatch / 大数组，不改源码字符串 | CDP 外部 trace（在页面外采集，不动页面代码） |
| 还原结果飘忽、对不上 | 多半 VM 内有**随机 / 时间戳 / nonce** 输入 | **冻结输入**（固定 `Date.now` / `Math.random` / 随机源）后复现比对 |
| trace 太长、淹没在噪声里 | 只在目标 opcode 子集上插桩，按 PC 区间过滤 | 先 diff 两次不同输入的 trace，锁定真正参与计算的指令 |
| 翻译后逻辑读不顺 | 把栈机伪代码反编译成普通表达式再读 | 对照 OPCODE_MAP 把高频组合（push/push/op）合并成一行 |

## 交接物 / 下游路由

**本 Skill 产出三件交接物：**
1. **OPCODE_MAP** — 目标 VM 的指令语义映射表（只覆盖目标路径用到的 opcode）。
2. **目标路径反汇编** — 单次目标参数生成的字节码 → 可读等价实现（Python / JS）。
3. **纯算 / 补环境决策结论** — 明确结论 + 一句话依据（来自 Step 6）。

**按决策结论路由（本 Skill 只到"算法还原 + 决策"为止，不负责落地）：**

| 交接物状态 | 转交 Skill | 交付内容 |
|-----------|-----------|---------|
| 纯算可行，已得到等价算法 | `param-encryptor` | OPCODE_MAP + 反汇编实现，由其落地为 signer 并做对照验证 |
| 放弃纯算，需补环境扣整段 | `env-patcher` | 解释器入口 + 依赖的环境 API 清单，由其生成 browser.js |
| 极复杂，走 CDP 在页面内跑 | `env-patcher` CDP 桥 / `web-reverse-master` Route C | 目标函数入口 + 触发方式 |
| 回头发现根本不是 VMP，只是混淆 | `ast-deobfuscation` | 反混淆后再判断 |
| 目标其实是验证码计算 | `captcha-solver` | 还原出的轨迹/距离计算逻辑 |

**典型调度链：**
```
web-reverse-master Phase 2 发现 a_bogus 由内联 VM 生成
  → ast-deobfuscation 确认无法用 AST 还原（VM 字节码）→ 路由出来
  → jsvmp-bytecode-recovery Step 1-5 定位解释器 + 插桩 + 反汇编目标路径
  → Step 6 决策：单层纯算可行
  → param-encryptor 落地 signer + 逐字节对照
  → web-reverse-master 集成到主脚本
```

## 学习靶子（真实目标前先练手）

想在动真格前先吃透一台 VM 的结构，用公开的开源 JS 虚拟机保护当靶子：

- **KProtect**（`yang-zhongtian/KProtect`）: https://github.com/yang-zhongtian/KProtect — 栈式 JS 虚拟机、VMProtect 思路，含**编译器 + 运行时**。可自己把一段 JS 编成字节码，再照本技能 Step 1-5 定位解释器 → 插桩 → 还原，全程有"标准答案"可对照。
- **用法**: 纯学习/理解 opcode 设计与派发循环结构；**实验性、别用于生产**。
