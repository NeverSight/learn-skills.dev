**Web and mobile H5 terminology layer** – Convert a user’s vague UI description into a precise requirement that can be sent directly to the Agent, and conveniently point out the term they just described but couldn’t name.

**Applicable to every turn of conversation, not limited to any specific stage**: In any dialogue turn, as soon as the user describes a web page or H5 effect, interaction, state, animation, feel, or bug in plain language (e.g., “the mouse hovers and the color changes”, “clicking does nothing”, “the black bar at the bottom blocks the button”, “the popup can still be scrolled underneath”, “the keyboard covers the input field”, “the content is too long – truncate it”, “it looks a bit cheesy”, “too cramped, not breathable”, “there’s no data at all”, “the page jumps down after the image loads”, “it looks wrong when opened in WeChat”, “this H5 looks weird on a computer”), this skill should be used:

**Do the user’s job as usual**, then naturally include in the progress or result the corresponding term, a plain‑language explanation, and its most common “gotcha”.

- Built‑in local glossary of 128 entries (five volumes covering web · h5 · motion · mp · base; topics include layout, interaction, state, components, forms, animations, feel, accessibility, performance, container platforms, mini‑programs, front‑end fundamentals).  
- Zero network dependency; use `scripts/term.mjs find` to reverse‑lookup **the user’s exact wording** – the search key is “how the user would describe this”, not “what it’s called”, because the inability to name it is precisely the problem to solve.

**Three hard constraints**:  

1. **Every term provided must be traceable to the exact words the user said in this turn** – if you can’t point to the trigger words, don’t mention the term; better to say nothing than to force it.  
2. **H5 pitfalls come in pairs** – the partner listed in the “pairs” entry must be mentioned together (e.g., “sticky bottom ↔ safe area”, “modal ↔ scroll lock”, “input field ↔ keyboard push‑up”, “image ↔ aspect‑ratio placeholder”). Giving only half is a hidden trap.  
3. **Always deliver the task result first, then add terminology** – at most 1–3 terms per response; if the user’s expression is already accurate, provide no teaching.

The skill also works in reverse: when a user posts something said by an Agent or colleague that they don’t understand (e.g., “he wants optimistic updates and error rollbacks”, “he says there’s a CLS issue here”), pick the concept that most affects the next decision, explain precisely what it means in the current task, and highlight a commonly confused boundary.

**Optional output**: `.finesse/lexicon.md` – a terminology alignment table for the project, preventing three different names for the same component across requirements, code, and communication.

Supported action commands: `say · name · explain · check · align · list`.

Trigger phrases: “say it more professionally”, “how to phrase this accurately”, “rephrase as a requirement for the Agent”, “what is this called”, “professional term”, “term”, “I don’t understand what he said”, “H5”, “mobile”, “on phone”, “responsive”, “safe area”, “sticky bottom”, “popup”, “skeleton screen”, “empty state”, “accessibility”, “term alignment”, “/term”.
