# hergy

`hergy` boots a team of AI agents onto herdr from YAML team definitions. It sits one level above herdr: it boots the team from your team definition and hands each member its first prompt, while herdr runs the panes and carries the messages.

The shape of every command and flag lives in `hergy cheat --ai`. Read that before you type one; this file holds only the judgement. `hergy <command> --help` prints one command's page: its flags, each with what it means for that command.

## Choose between hergy and herdr

- Starting a team, adding a worker, closing a team: hergy.
- Reaching a teammate, driving a pane: herdr.
- Whether anyone is waiting on the human, or nobody is working: `hergy status`. A member whose screen has not changed while it works is marked with how long it has stood.

## Team definitions and team names

- A team definition is the directory `teams/<name>/` with its `team.yaml`; `hergy up`, `hergy new` and `hergy show` take a team definition name.
- `team.yaml` must write `description:` — one line saying which case the team is meant for. A definition that writes none, or writes one over more than one line, does not read, and one that still writes the key it replaced is stopped with the sentence that says to write `description:` instead. A description is a note for the person choosing a definition: the web UI's team list and team screen, the start sheet and `hergy show` read it, a team command's header and a running team's tiles do not. It is never part of a member's prompt, and changing only the description leaves nothing for `hergy apply` to put right.
- A team is a running team, named by `hergy up --as` or, without it, by the team definition name; `hergy down`, `hergy status`, `hergy apply`, `hergy refresh`, `hergy reprompt`, `hergy hire`, `hergy focus`, `hergy nudge`, `hergy stop` and `hergy tell` take a team name and find the definition from this machine's launch record. The team's herdr tab is labelled with the team's name alone, so a tab a person sees says the team, not the definition it came from; a team booted by an older hergy still has the definition in its tab's label, and is still found.
- `hergy status` with no team name lists every running team, with its team definition name.

## Before you run one

- Prove the plan with `--dry` before `hergy up`, `hergy down`, `hergy apply`, `hergy refresh` or `hergy hire`. `up --dry` reads no herdr (it names a team definition). `reprompt --dry`, `hire --dry`, `nudge --dry`, `stop --dry` and `tell --dry` also read no herdr, so a team that is not running can be planned for: name it with `--team` (a team name, or a team definition name the launch record does not know), and with no `--team` the one team in this project's launch record is used. `down --dry`, `apply --dry` and `refresh --dry` read the live agents and tabs; `down --dry --json` prints the plan and the leftovers as JSON.
- `hergy apply` is the one operation that puts a changed definition into a running team: hergy compares the saved definition with the prompt each member last read and decides the way for each member — send the prompt again (`resend`, the conversation stays), start it (`start`, the definition has it and no agent is live), restart it (`restart`, its kind or args changed, so the conversation goes), or say it cannot (`cannot`, with the reason). A member that is working or waiting for permission is left, with the reason, and the rest go on; the command answers 1 while one is left, including with --dry or --dry --json. Name the members, or apply every member with drift. After editing a document or a prompt, apply sends the prompt again with a preamble saying what changed; after editing a profile, apply restarts the member.
- `hergy reprompt` and `hergy refresh` stay as the single-purpose tools: `reprompt` sends the bootstrap prompt again (with the preamble when the definition changed), and `refresh` restarts a member, for one that is stuck. `refresh` ends the agent and starts it again, so the conversation starts empty; a member that is no longer running is started again in the pane hergy named after it, when that pane is still at its shell; if the pane is busy, it changes nothing and points at `hergy down` then `hergy up`.
- To add a member to a running team, write it in `team.yaml` and run `hergy apply <member>`: hergy makes it a pane in the team's tab and starts it there, the way `hergy up` starts a member, so it reads the same rules and is handed the same bootstrap prompt. `hergy refresh <member>` refuses a member with no pane and names `hergy apply`. A team that is not running (no tab of its own) is refused, and `hergy up` is named.
- A member cannot `refresh` itself: hergy runs inside a member's pane, and stopping that member would stop hergy before it could start the agent again. Run it from another pane, or as the human.
- `env` is fixed when a pane is made: after changing `env`, run `hergy down` then `hergy up`; apply says so and does not restart the member, and `hergy refresh` keeps the pane and its env.
- `hergy` sets `GY_ACTOR=<herdr name>` in every pane it makes, so an agent's records in gy carry the name herdr knows it by; the bootstrap prompt tells the agent not to change it. A profile that writes `GY_ACTOR` does not win, and `hergy validate` warns when one does.
- The Contact section tells members and workers to check the herdr environment with the exit status of `test "${HERDR_ENV:-}" = 1`. When displaying variables, pass only one name per `printenv` call: on macOS, several names print only the first value, so that output does not show whether the remaining variables are set.
- `hergy down` closes the panes of the team you are in, your own pane included, and that pane last. A pane is closed whether an agent stands in it or not (a member that never started, or whose agent ended, goes too), and a pane hergy did not name is a person's own and stays. A team whose boot stopped before any agent ran is still put away by `hergy down <team>`.
- One worker of a running team is closed alone with `hergy down <worker>`, by its short name or its herdr name (`<team>-<worker>`). Only that worker's pane is closed, and the worker's own tab when that pane was the last one in it; the members and the other workers stay. A name that is both a running team's and a worker's is refused, naming both.
- After closing, `hergy down` lists what the team left in git: the worktrees of the project that came while the team was running (after the worker was hired, for one worker), other than the project root, with their branch, uncommitted changes and commits not in main, and the project's stashes, with the commands that remove them (`git worktree remove <path>`, `git stash list`). An agent keeps its pane in the project root and cds into a worktree for each command, so hergy reads the time from the launch record rather than from the pane's directory; a worktree a closed pane stood in is marked. hergy removes nothing; check a worktree with uncommitted changes or commits not in main before removing it. Temporary documents are not listed: hergy cannot tell which are the team's.
- To read output, add `--lang en`, or use `--dry --json`; the `next:` line names what to type next. `--lang` is the command line's language: the WebUI that serve opens is Japanese whatever `--lang` says.
- `hergy up`, `hergy hire`, `hergy apply` and `hergy refresh` may wait: a new agent can ask a question while it starts (whether to trust this folder, for example). Run them in the background and read their output. The wait begins with a line naming the member, the tab and the pane; tell the person which pane to answer in, and wait for them. Do not answer that question yourself (no `send-keys`), do not write the agent's trust settings, and do not move their focus. If the person stops with Ctrl-C, the last line says how to go on.

## Reaching a member

- `hergy focus <member>` moves herdr's focus to that member's pane, so a person can answer it there.
- `hergy nudge <member> [text]` sends a short push to carry on, only when the member is idle or done: a working or blocked member is refused, and nothing is sent. With no text it sends a short "carry on". The text is headed by who sent it: the member whose pane you type in, else the human.
- `hergy stop <member>` sends esc, ending the member's current turn and keeping its conversation; a member that is not working is left alone, and the command still succeeds. Some agents need esc twice, the first only asking them to interrupt: hergy watches the member's state after each esc and sends a second only while the member is still working, so an agent that stopped on the first is never sent a second. A member still working after two escs is reported as not stopped (exit 1), and `hergy refresh <member>` is named as the next step — the same step a stop that worked names. A member cannot stop itself: hergy runs in that member's pane.
- `hergy tell <member> "<text>" [--from <member>]` sends a message headed by `--from`, else the member whose pane you type in, else the human. It does not read the member's state, so the message reaches an agent in any state. A `--from` name outside the team is refused. A tell is also how a member hands its turn on: it is recorded for the team's watcher, which then knows who opened whose turn (below). `hergy tell human` (`人間`), typed in a member's pane or with `--from`, sends nothing and needs no text: it marks what the member wrote in its pane as the person's, and the watcher does not ask who it is for; from a pane that is no member's it is refused.
- All four take a member by short member name or herdr name, and `--team <team>` picks the team; none needs a herdr-managed pane of its own. `--dry` prints what would be sent, reads no herdr and sends nothing (focus has no `--dry`).

## While you are inside a team

- The lead adds workers within its `workers:` (from, purpose and profile) and gives each a short name. `hergy hire --purpose` must be a purpose the hiring member's `workers:` names, and the profile comes from that entry (a hire does not choose one); a purpose outside it is refused, naming the purposes the member may hire for. With no `--from`, it uses the one member that hires for that purpose (two or more stop the hire and are listed). A worker has one purpose: two purposes are two `workers:` entries, and a purpose with `,` or `、` stops the definition.
- `turns:` says who hands the turn to whom (a member's name, or `human`). Each member and the human hand the turn on to at least one party, and at least one turn reaches the human; a definition that does not say so stops hergy the way a file that does not read does, so `up`, `refresh`, `reprompt`, `hire` and `validate` all stop with the same sentences. Arrows in rules are not parsed or compared with `turns:`.
- `ledger:` says which member may make which write to gy: each entry is `<write> by <member>[, <member>...]`, where `<write>` is the name of a gy write (`req approve`, `decide`, and the like) or `question to human` for a question whose decider is nobody in the team, and `<member>` is a `members[].name` (a worker's name cannot be written). It stops nothing: `hergy validate` warns once for each write a writer of the team (`GY_ACTOR` begins with the team name, or the name the launch record shows) made that the rule gives to other members, and says so in one line when gy cannot be read.
- Members hand the turn on themselves, with `hergy tell <name> "<text>"`, then stop; hergy hands nothing on of its own. hergy's watcher (`hergy turns <team>`, which `hergy up` starts in a strip under the members) records who opened whose turn and acts only when a turn ends unhanded. A turn the outside opened (the person's tell, the start prompt, the watcher's own question) rests when it ends: the reply is the person's, and nothing is sent. A turn another member opened (its tell, or the watcher delivering an answer; a worker's first turn: the member that hired it) that ends with a tell in it was handed on by the member; one with `hergy tell human` in it is the person's: the turn goes to the human, those that waited wait no more, and nothing is asked. A tell that comes while a member works opens its next turn; if the turn rests and no next turn begins within 10 seconds (the harness folded the queued message into the running turn), that rested turn is taken as the answer and the member is asked about it. One that ends without a tell is asked about: the watcher sends the member "who is what you wrote for?" with the names it may answer (those waiting for it, then those the definition's `turns:` name), `human` and `nobody`, and the member's next stop is the answer. One name: the text that waited is delivered to that member (one that is working gets it when it stops, as one message). `human`, `nobody`, no name or several: the turn is the human's, and `hergy status` says why (`turn:`; `awaiting:` lists who waits for whose answer). A member that stops without writing while members wait, one the watcher cannot ask (blocked), or one whose recipient never starts leaves the turn with the human the same way. Members do not use `herdr agent prompt`. The end of a turn is the harness's word first: `hergy up` and `hergy hire` wire each Claude Code member's Stop hook (a settings argument at start), each Codex member's notify (a config override at start; the person's own notify is called afterwards) and each standalone opencode member's plugin (hergy's plugin directory added to the plugins of `OPENCODE_CONFIG_CONTENT`; the person's `~/.config/opencode` is read as before) to `hergy turn-done <team> <member>`, writing nothing into the person's own configuration; the watcher takes those signals before reading herdr and uses the turn's last reply from the signal instead of reading the pane. A member whose profile passes the settings argument or notify itself, whose `OPENCODE_CONFIG_CONTENT` is not JSON, or runs opencode on the shared server (not standalone) gets no signal (`hergy up` says so) and its stops are seen through herdr. The watcher's pane is a four-row strip with a three-line band redrawn in place: each member's state (● working, ○ stopped, ◐ blocked), who holds the turn and who waits, the latest handoffs with their time (→ handed, ✓ to the human, ? asked, ⟲ rested, ✗ not delivered or unclear), and what is being asked. The sentences, one per event with how the end was seen (`[signal: claude]`, `[herdr saw the stop]`, `[no signal within 5 seconds; herdr saw the stop]`, `[as answered]`), go to `$XDG_STATE_HOME/hergy/turns/<team>.log` with the time of each line; `hergy turns <team> --log` prints it. `hergy down` removes the team's turn state, tells and signals, and leaves the log.

## While you write settings from outside

- Write with `hergy new` (it writes into the project's `.hergy/` inside a git repository, and into `~/.config/hergy/` outside one). The members' roles and profile are picked from the role documents and profiles either place already holds; `hergy new` writes no role document and no profile the person did not choose. Only when neither place holds a role document does it write the starter roles, and only when neither defines a profile does it write `claude-default`; otherwise it names the roles and profiles to write in `team.yaml`, and `hergy validate` is the next step. Then edit, `hergy validate`, then show `hergy up --dry` to the person before `hergy up`.
- A role's name is an identifier: `roles/<role>.md` is read by the role name, which matches `[a-z][a-z0-9_-]{0,31}`; the display title comes from the first line of the Markdown document. A role document whose file name is not one is broken: `hergy validate` says so (naming the document, the name and how to fix it — rename it on the roles screen and the save changes the team definitions that read it), and `up` of a team that reads it stops with the same sentence.
- `hergy validate` prints the size of each team definition (the part of its rules that goes into the prompt, plus the words of its templates) and of each role document (the part that goes into the prompt), and warns over the provisional budget (1,200 characters each). It checks a role document once, not once per team that uses it. A warning is not a failure: it names a definition to look at, and the exit code stays 0. When a definition is over, look for rules that are duplicates, that are no longer needed, or that could be read only when they are needed, before cutting the meaning.
- Start in the project's `.hergy/`; ask the person before you change `~/.config/hergy/`.

## Renaming a team definition

In the definition editor, use 名前を変更 to save its name separately. Save or revert its unsaved topology, agreement and YAML first. Stop every team using that file; the server refuses a running or starting team or unreadable herdr state. For a global definition it checks all projects in the connected session, including those not listed in the UI. On macOS and Linux, starts use shared locks and renames use exclusive locks across processes. Concurrent starts are allowed. A start is refused only by a conflicting rename lock; unavailable locking does not stop it. Renames require their locks. Lock files use the absolute team.yaml path as their identity and live in `$XDG_STATE_HOME/hergy/team-locks` (or `~/.local/state/hergy/team-locks`), never in the settings. An unknown launch source refuses a rename only when the definition name matches. A same-place collision, invalid name or changed file is refused. A same name in the other place is allowed and its effect is shown. Launch history keeps the old name and path; the renamed definition has no previous launch until it starts again. Old URLs do not redirect.

## Editing a role while editing a team definition

Open ロールを確認・編集 from the member attributes. This moves to the role’s rules column beside the team agreement. Edit the raw Markdown and save the role document alone; saving refreshes the team checks and prompt while preserving team drafts and selection. The file place and known usages stay visible. Usage is matched to the actual file across registered projects, with the confirmed scope shown; a failed usage read disables saving. A global definition opens the same global role its displayed prompt reads. Missing or unreadable documents explain the problem and link to /roles. Rename, copy, duplicate and delete remain on /roles. The scoped link to /roles carries the team draft like the screen band does.

## Rule definitions and migration

In the team screen’s rules tab, switch to headings and use a heading’s ⋯ menu to choose another team or role, an insertion position, and whether to include child headings. Drag the grip to another column to move; hold Alt (⌥ on Mac) when dropping to copy, or Shift (⇧ on Mac) when starting the drag to include children. The selected text stays unchanged; a missing blank line at the insertion boundary is supplied. Review the drafts and undo before saving. Moves save the destination first; if saving the source fails, the screen says the text remains in both files. Select a document by its name to read and edit it. The rules tab opens with every document of the definition (the team rules and the role documents its members use) side by side at the standard reading width of about 40 Japanese characters per line in 16px text; the role screen uses the same standard width. Use 並べる to choose again which documents stand together, or すべて表示 to bring them all back. Switching documents preserves unsaved edits; each document keeps its own save target. Use Narrow or Wide in a column header, and Equal to reset the widths. Wide expands the selected document beyond the standard reading width. Apart from a column narrowed on purpose, no column is narrower than the standard reading width, and a wide column grows at twice the rate of the others; the board has its own horizontal scrollbar and an explanation when documents do not fit. At narrower widths, two selected documents are stacked. All four screens use the available width for the header and content, with no width limit and at least 40px of space on each side. Below 420px, each side uses at least 16px to leave more room for the content. At 420px and above, the header stays aligned when switching screens. Narrower screens do not reserve space for a scrollbar, so the right side of the header may move when the page length changes. With no focus in an input, the wheel over it scrolls the page; to read inside an input, press it once and then turn the wheel. Ctrl (⌘ on a Mac) with the wheel and pinch stay with the browser's zoom. Switching the display, re-reading, filtering or changing the theme never moves the page; only an act that names its destination (editing the selected attributes, a waiting row, opening a row from a URL) or one whose result would stand off the screen (copy, a new row, a duplicate) brings that destination into view.

Choose Light, Dark, or Follow OS at the top right. The preference stays in the same browser for the same host and port, across all four screens and projects. Different hostnames (including localhost versus 127.0.0.1), ports, and browsers do not share it. If browser storage cannot be read or written, the screens follow the OS and explain why. No hergy configuration file is changed.
