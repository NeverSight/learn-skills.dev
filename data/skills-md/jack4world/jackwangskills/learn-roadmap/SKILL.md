# 白话路线图（Learn Roadmap）

把一份需求拆成一串任务。给新手的拆法有两个额外要求：**每一步做完都要能看见东西**，以及**每一步都要说清楚为什么排在这个位置**。

## 每跑一步，跟一句解释

你每执行一个动作（跑命令、改文件、装依赖、写文件），**紧接着**用一到两句话说清三件事：**刚才干了什么、为什么要干、结果说明什么**。

```
$ npm test
↳ 跑了全部测试，7 个全绿。说明你这次的改动没有把以前做好的功能碰坏。
```

三条约束：

- **不要攒着**。跑五步最后一次性汇报，等于用户全程在看你表演，什么都没跟上。
- **不要只贴输出**。用户看不懂命令输出，那正是他找你的原因。翻译它。
- **一到两句就够**。这是旁白不是讲课，长了会淹掉主线。

## 拆分的核心原则：竖着切，不要横着切

这是整个技能最重要的一句话，也是必须讲给用户听的一句话：

```
🍰 想象一个夹心蛋糕，从上到下是：界面 → 逻辑 → 数据库。

❌ 横着切（新手的本能）：
   第 1 步：把所有界面画完
   第 2 步：把所有逻辑写完
   第 3 步：把数据库全建好
   问题：做完第 1 步，你只有一堆点了没反应的按钮。
   前两周你都不知道自己写的东西到底能不能跑。

✅ 竖着切（工程师的做法）：
   第 1 步：登录这一件事，从界面到数据库全打通
   第 2 步：发帖这一件事，从界面到数据库全打通
   好处：第 1 步做完，你就能真的登录进去，能给人演示。
   出了问题也马上知道是哪一块。
```

每个任务都必须是一根**竖着的针**：窄，但从头扎到底。

## 每个任务的检查标准

<task-rules>

- **做完能演示。** 用一句话说清楚「做完之后你能做什么」，而且这句话里不能有技术词。「能在页面上输入用户名密码点登录，然后看到自己的名字」是合格的；「完成认证模块」不是。
- **一次坐下来能做完。** 大约半天到一天的量。超了就再拆。
- **窄但完整。** 宁可功能少（只支持一种登录方式），不要层次缺（界面做好了但存不进数据库）。
- **顺序有理由。** 每个任务要写清楚「必须先做完哪个才能开始」，以及为什么。

</task-rules>

## 流程

### 1. 先确认需求清楚了

如果 `.learn/需求共识.md` 存在就读它。如果需求还是一团模糊（用户说不清做完是什么样），不要硬拆，告诉用户：「需求还不够清楚，硬拆出来的路线图会是错的。输入 `/jackwangskills:mentor-grill`，我一轮问你一个问题，把它问清楚再回来拆。」然后停下来等，不要自己猜着往下拆。

拆一份没想明白的需求，只会得到一份没想明白的路线图。

### 2. 看一眼现在有什么

已经有代码的话，快速扫一遍：用了什么框架、有没有数据库、已经能跑起来的部分是哪些。第一个任务应该建立在现状之上，而不是假设一切从零开始。

### 3. 排顺序

按这个次序思考：

1. **先让它能跑起来。** 一个空白但能启动、能打开的页面。新手最需要的是先有一个「活着」的东西。
2. **再打通最核心的那一根针。** 这个项目如果只能做一件事，那件事是什么？先做它。
3. **然后一根一根加。** 每根针都依赖前面已经打通的地基。
4. **最后才是打磨。** 样式、边界情况、错误提示，全部排到能用之后。

新手最常见的翻车是把打磨排在前面：花三天调按钮圆角，功能一个没通。你要主动挡住这件事。

### 4. 讲给用户听

用这个格式呈现，一次全部列出来：

```
🗺️ 路线图：<项目名>

━━━ 第 1 步：<白话标题> ━━━
做完之后你能：<一句话，不含技术词>
需要先做完：无，可以立刻开始
大概要多久：<半天 / 一天>
为什么排第一：<一句话理由>

━━━ 第 2 步：<白话标题> ━━━
做完之后你能：<一句话>
需要先做完：第 1 步（因为 <理由>）
大概要多久：<...>
为什么排这里：<一句话理由>

...
```

然后问三个问题，等用户回答：

- 这些步骤的大小合适吗？有没有哪一步看着就头大（那就再拆），或者小到不值得单列（那就合并）？
- 顺序对吗？有没有你更想先做的？
- 有没有哪一步你完全看不懂要干什么？

按反馈改，改到用户点头为止。**不要跳过这一步直接写文件。**

### 5. 落盘

用户确认后，写进 `.learn/路线图.md`，一个任务一段，前面加勾选框：

<roadmap-template>

# <项目名> 路线图

*由 learn-roadmap 生成于 <日期>。做完一步就把 [ ] 改成 [x]。*

## 怎么用这份路线图

一次只做一步。每一步做完，先跑起来看一眼，确认真的能用了，再开始下一步。
卡住了就说「第 N 步卡住了」，我会带你走。

---

## [ ] 第 1 步：<白话标题>

**做完之后你能：** <一句话，用户视角>

**需要先做完：** 无 / 第 N 步

**验收标准（做到这些就算完成）：**

- [ ] <能观察到的具体现象，不是「代码写完了」>
- [ ] <...>

**为什么这样拆：** <一到两句话，讲清楚这一步为什么是独立的一根针>

---

## [ ] 第 2 步：<白话标题>

...

</roadmap-template>

### 6. 交接

写完告诉用户：

「路线图写好了，在 `.learn/路线图.md`。建议从第 1 步开始。想让我把测试写好、留空位给你填的话，输入 `/jackwangskills:learn-tdd`，然后告诉我做第 1 步。」

## 大改造是例外

如果任务是「把所有 `userId` 改成 `accountId`」这种一改就牵动上百个文件的事，不要硬套竖着切。老老实实排成三段，并且讲清楚为什么：

1. **加新的**：新旧两套并存，什么都不坏。
2. **搬过去**：一批一批把调用改到新的上，每批一个任务，每批做完代码都还是能跑的。
3. **删旧的**：确认没人用旧的了，删掉。

告诉用户这叫「扩张 - 收缩」，是专门对付大范围改名的招式，中间任何一步停下来项目都还是活的。
