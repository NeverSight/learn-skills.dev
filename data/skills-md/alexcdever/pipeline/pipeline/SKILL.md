# 编程流程

一份纯流程契约，给两种人用：**人类开发者**（提要求、做裁决）和**具备子代理能力的 agent 软件**（照着它干活）。目的是让 agent 软件开发时**更有效率**——不是让它留更多的记录。

这套流程**按任务收费，和改动大小无关**：一个任务至少要预走一遍验收标准、派两次独立子代理、建一个 worktree、留四个文件、跑一次合并后复验。小到一个 agent 几分钟能写完、自己一眼能验完的活，不要用它——成本大于收益。

它规定主代理、执行子代理、审查子代理怎么协作，什么算完成，什么不算。它不规定用什么模型、什么子代理机制、什么编程语言，也不附带任何脚本；Git 是唯一被指定的工具。

## 硬前提

**宿主必须能派发具备独立上下文的子代理，并且能读写项目文件、运行命令、使用 Git worktree。**

独立上下文的判据（它约束的是审查者）：审查者能看到的东西，全部来自派发时传给它的材料、和它被指到的那棵 worktree；它读不到主代理与执行者的对话历史。审查者还必须**能跑命令、能写 `.pipeline/reviewer.md`**——只能读、不能动的审查者做不了这件事，等于没有审查。

做不到上面这些，本技能不适用——**不要自己给自己降级**：不要让同一个上下文既实现又审查。没有独立审查，这套流程剩下的部分全部失去意义。

## 角色

- **主代理**：面向用户，决定做什么、以及什么算完成。规划、写任务描述、派发子代理、核对结果、合并。**自己不改产品代码**（合并与跑验收命令不算改代码）。
- **执行子代理**：在隔离 worktree 中实现一个任务，遵循测试驱动：先写失败的测试，再写最小实现，然后重构。不动任务描述里的验收标准；标准有问题就报回来，不自行改。
- **审查子代理**：在独立上下文中亲手复验，不采信任何转述，只看代码、测试，和自己跑出来的结果。它不改产品代码、不提交任何东西——复验时留下的临时改动留在工作区，不进提交。
（摸底和会刷屏的活都可以派**一次性子代理**——见「噪声」。**它不是这里列的角色**：不建 worktree、不写 `.pipeline/`、不动产品代码，回到主代理的只有一份结论。）

## 噪声

主代理的上下文用来做决定，不用来通读原始输出。

动手之前先预判：这一步会刷出多少原始输出。按输出性质选处理方式：

- **短输出或结果即结论**：直接保留完整输出。文件读取、小范围搜索、`git status`、`git diff`、版本号、路径和产物检查都属于这一类；输出本身是要判断的结果，不能因为它可能变长就随意隐藏。
- **长输出命令**：完整 stdout/stderr 必须保存到系统临时目录；进入当前上下文的是执行摘要和有限预览，不是完整原始输出。摘要至少包含退出码、是否超时、耗时、输出规模、临时日志路径，以及输出的头部、尾部和可机械识别的错误/失败/警告片段。摘要由执行工具或确定性脚本生成，不要求调用 LLM；宿主不支持自动摘要时，由 agent 主动写临时日志并按需读取。
- **探索性噪声**：全仓搜索、翻目录、追一条跨很多文件的调用链，以及不需要主代理亲自持有原始输出的摸底，可以派一次性子代理。它只回传能直接决定下一步的结论，不回传过程或原始输出。

完整日志是可回查的事实，不是摘要的替代品。摘要不足以判断时，读取日志中的相关范围；失败时优先查 stderr、错误/失败片段及其上下文，仍不能判断再扩大范围或重新执行更窄、机器可读的命令。

- **噪声止于一次性子代理或摘要**。主代理不通读与当前决定无关的原始输出；但执行者、审查者和主代理亲自执行的关键验收命令，必须保留完整长输出到可回查的临时日志。
- **答案的形状在派发时就定死**。摸底那四问（产品定义在哪、术语在哪、测试怎么跑、什么不能碰）就是这个形状；答不上来的，直接说答不上来。
- **决定权不跟着派出去**。它带回的是材料和结论，怎么定仍由主代理做；要产品决策的，按「不可违反的规则」第 9 条问用户。
- **它的结论是规划材料，不是证据**。凡要当判据的事实，仍由主代理亲手走一遍，或由审查者复验；必须主代理亲手做的动作（走验收、合并、主树复验）要保留命令、退出码、执行摘要和必要的后置验证，不要求把完整输出全部放进主代理上下文。

## 执行结果结构

执行层向 agent 返回**统一的通用外壳**，不试图统一不同命令的业务语义。长输出命令的完整 stdout/stderr 保存在系统临时目录；返回给 agent 的 `preview` 是有限预览，不能代替原始日志。所有字段都保留，未知值使用 `null` 或空数组，不省略字段。

推荐结构如下：

```json
{
  "command": "<命令>",
  "cwd": "<工作目录>",
  "status": "completed",
  "exitCode": 0,
  "timedOut": false,
  "durationMs": 18420,
  "error": null,
  "degraded": false,
  "missingFields": [],
  "stdout": {
    "bytes": 1200,
    "lines": 24,
    "previewTruncated": false,
    "preview": "<有限预览>",
    "logAvailable": false,
    "logPath": null
  },
  "stderr": {
    "bytes": 8000,
    "lines": 160,
    "previewTruncated": true,
    "preview": "<有限预览>",
    "logAvailable": true,
    "logPath": "<完整 stderr 日志路径>"
  },
  "postcondition": {
    "checked": false,
    "passed": null,
    "summary": null
  }
}
```

字段含义和约束固定如下：

- `status` 使用 `completed`、`failed`、`timed_out`、`failed_to_start` 或 `terminated`。先判断是否超时：超时使用 `timed_out`，即使之后进程被终止也不使用 `terminated`；未启动成功使用 `failed_to_start`；启动后正常退出时，`exitCode === 0` 使用 `completed`，其他整数退出码使用 `failed`；启动后被外部终止且没有退出码时使用 `terminated`。除 `completed` 和 `failed` 外，`exitCode` 必须为 `null`，并在 `error` 写明原因。`timedOut` 仅在 `status` 为 `timed_out` 时为 `true`。
- `durationMs` 是从执行开始到进程结束、超时或启动失败的毫秒数。`bytes` 按原始输出字节统计；`lines` 按换行符数量统计，若非空输出没有末尾换行则再加一。
- `previewTruncated` 只描述返回给 agent 的预览；`logAvailable` 与 `logPath` 必须保持一致：可回查时为 `true` 和路径，否则为 `false` 和 `null`。长输出命令必须使两路完整日志均可回查；宿主无法做到时将 `degraded` 设为 `true`，把缺失项以 JSON Pointer 字符串（例如 `/stdout/logPath`）写入 `missingFields`，不得宣称满足完整协议。
- `postcondition.checked` 为 `false` 时，`postcondition.passed` 和 `postcondition.summary` 必须为 `null`，表示尚未验证；为 `true` 时，`passed` 必须是布尔值，`summary` 写明验证结论。它由 agent 按验收标准填写，执行层不能猜测。

执行结果结构不承载项目语义。测试数量、失败用例、构建产物和迁移状态由测试工具的机器可读输出、项目适配器或明确的后置验证提供；不能从通用 `preview` 或退出码推断出来。宿主按以下顺序适配：

1. 宿主已有结构化命令执行器时，使用它并映射到本结构。
2. 宿主没有现成执行器但能运行脚本时，在系统临时目录生成 Bash 或 PowerShell 包装脚本，捕获完整 stdout/stderr 并输出本结构；脚本用完即删。
3. 只能直接执行命令时，尽量保存长输出、按上述规则记录可获得的字段并明确标记缺失；关键验收应改用更窄或机器可读的命令，或在能完整保存日志的环境中重跑。

执行层负责通用字段，agent 负责根据验收标准执行后置验证，项目工具负责提供项目特有语义。`执行结果`是规范结构；`执行摘要`只是从它生成、用于节省上下文的有限视图。任何一层都不能用 `postcondition.passed` 代替实际验证。

## 临时文件

**临时文件放在系统临时目录里（`%TEMP%`、`/tmp` 这类），不放进项目。**

- **谁写的都算。** 临时文件是那种用完就该丢、本来不该留在仓库里的东西：为跑一次命令写的脚本、下载下来的数据或工具、跑测试时生成的输入、中间产物——主代理、执行者、审查者、一次性子代理，谁写的都一样。
- **放进项目就不算临时。** 项目里不建 `.tmp/` 这类目录——执行者的 `git add -A` 会把它捡进提交，主树里也会多出与任务无关的文件。
- **要留在仓库里的不在此列。** 交付物、测试代码，和测试要用的夹具与样例数据，照旧进项目；`.pipeline/` 里那四个文件也一样，它们就该待在 worktree 里（见「`.pipeline/`」一节）。分不清就先问一句，别把该留的丢进系统临时目录。
- **这条管新写的文件。** 已经在项目里的文件被临时改过，那是改动，不是临时文件——审查者留下的临时改动照旧留在工作区，不进提交。

## 用户行为

**用户行为：一条从可操作入口开始、到可观察状态变化结束的完整链路。**

- 入口可以是按钮、命令、接口、配置文件；状态变化可以是界面、数据库、文件、日志。
- 「改了三层代码」不是用户行为，「用户点了 X，Y 变了」才是。
- 重构、基建、文档：找出它的可操作入口和可观察状态变化，套进同一个形状（比如一份文档的入口可以是「人照着它做」，状态变化是「他做出来的东西变了」）。套不进去，就把它拆到能套进去为止。

（别的项目文档里叫「功能点」的，在这里一律叫用户行为。）

## 任务

**一个任务是一个或几个用户行为。一个任务 = 一个 worktree = 一次审查 = 一次合并；审查可以来回几轮，重做不另起 worktree。**

几个行为能合成一个任务，**当且仅当它们共用同一条链路**——同一个可操作入口、同一份数据、同一段代码路径。入口或数据不同的，各做各的。

**每个用户行为有一条或多条验收标准**：正常走通是一条，被拒绝、边界、异常各是另一条。一条标准就是一个「做什么操作 → 期待什么状态变化」的序列。

## `.pipeline/`

`.pipeline/` 在子工作树里（`<worktree>/.pipeline/`）—— 进行中的任务，状态都放在这里，**一个任务一份**，寿命就是那个任务的寿命：worktree 被删掉，它随之消失。`<id>` 是这个任务的短标识（kebab-case），同时用作 worktree 目录名和分支名。

四个文件。规则是**一个文件一个写者，且每个文件回答一个别人没回答过的问题**：

- **`task.md`** —— 只有主代理写。上段是任务描述（目标、范围、验收标准），写完不再改；下段是终态，合并后才写（合并提交、主树复验结果、已合并可清场）。**它回答：要做什么。**
- **`progress.md`** —— 只有执行子代理写。**它回答：还剩什么。** 把这次要做的拆成若干步，每步后面写它现在是什么状态——用你自己的话，不规定词表。随时覆盖，永远只反映当前。
- **`executor.md`** —— 只有执行子代理写。**它回答：发生了什么。** 宣布完成时写一次，详略得当，给主代理看。
- **`reviewer.md`** —— 只有审查子代理写。**它回答：复验看到了什么。** 最后写的是它的结论。

四个文件都是散文：没有 schema、没有必填字段、没有机器可读区块。**要加第五个，先回答它解决的是哪个还没人回答的问题**——两个文件回答同一个问题，就说明有一个是多余的。

- **恢复 = `git worktree list`**：`.worktrees/` 下有一个目录，就有一个未关闭的任务。读它里面的 `.pipeline/`：`task.md` 看要做什么，`progress.md` 看还剩什么，`executor.md` 与 `reviewer.md` 看发生过什么。换一次会话、换一个 agent 软件，都一样。（项目怎么跑、什么不能碰这类摸底结论不在里面——那些要重新摸底。）
- **它随 worktree 一起生灭。** 没有独立的「删除 `.pipeline/`」这个动作——清场就是删 worktree。

项目的 `.gitignore` 必须**在创建第一个 worktree 之前**就提交 `/.worktrees/` 与 `/.pipeline/`。前者让主工作树看不见整棵子工作树。后者不是给主工作树用的（主工作树里根本没有 `.pipeline/`）——它是给子工作树自己用的：`.gitignore` 里的 `/` 锚定在它所在的目录，同一个文件检出进 `.worktrees/<id>/` 后，`/.pipeline/` 在那里重新生效；少了它，执行者的 `git add -A` 会把 `.pipeline/` 提交进分支。

## 流程

1. **规划**：先摸底，再定下一个用户行为，给它一个短标识 `<id>`。摸底要读项目自己的约定文件（`AGENTS.md` 之类，如果有），并确定四件事：产品定义在哪、术语在哪、测试怎么跑、什么不能碰。项目里如果还留着旧版技能的东西——根目录有 `pipeline_tools/`，`.pipeline/` 已经被 Git 跟踪，或者 `docs/tasks/` 下还压着旧版任务单（带 `<!-- Task ID: -->` 标记，或写着 `pipeline-contract` 区块）——说明它是从旧版迁过来的（旧版把任务证据提交进 Git，新版不提交）：先读同目录的 `MIGRATION.md`，把该清的文件和理由当面说给用户，得到许可再动；用户说不清理就不清，别问第二次。摸底可以派一次性子代理去做（它有自己的上下文），结论不落盘，**但要装进派发给执行者和审查者的材料里**——他们也不继承你的上下文，不给就每人重建一次。定下来之后，**按你打算写的验收标准亲手走一遍，看它现在是不是已经成立**——不要用 `grep` 的 0 个结果当依据。做完一个直接做下一个，不要每个之间都停下来问用户；只在缺决策、缺授权、或无法自愈时才停。
2. **建 worktree**：先确认项目的 `.gitignore` 已经提交了 `/.worktrees/` 与 `/.pipeline/`（第一次要补上并提交，见「`.pipeline/`」一节），再由主代理从主工作树当前 HEAD 建 `.worktrees/<id>`（`git worktree add -b <id> .worktrees/<id>`）。`.pipeline/` 随之出生。
3. **写任务描述**：写进 `<worktree>/.pipeline/task.md`，含验收标准。写完不再改——要改就重写上段，作废此前的审查结论，**并删掉上一轮的 `executor.md` 与 `reviewer.md`**。
4. **派执行子代理**：传入 worktree 绝对路径、验收标准（任务描述就在它 cwd 的 `.pipeline/task.md` 上段）。它先把这次要做的拆成步骤写进 `.pipeline/progress.md`，然后按测试驱动做：一次一条标准，随时更新那份清单；做完**自检**（自己跑一遍验收、亲手从入口走一遍），自检时记录命令、退出码、执行摘要，并检查验收相关的后置状态——退出码为 0 不等于标准已成立；自检通过后写 `executor.md`，再回来报告完成。
5. **派审查子代理**：主代理先核对执行者的报告与提交——**改动是否只落在任务描述的范围里**，再传入 worktree 绝对路径、同一份任务描述、代码与提交、验收标准。**派发材料里不带执行者的结论。** 审查者亲手复验、亲手逐条标准走一遍入口；长输出命令保留完整日志并按需回查，不能只采信退出码或摘要；**先把自己的结论写进 `.pipeline/reviewer.md`，再读执行者留下的东西**（`progress.md` 与 `executor.md`）对照。
6. **合并**：主代理核对证据后合并到主分支，在主工作树跑一次这个任务的验收（怎么跑由验收标准定）。命令成功后仍检查验收相关的后置状态：测试确实执行且没有被全部跳过，构建产物确实存在，生成的文件或状态确实符合标准；长输出只把执行摘要带入上下文，完整日志保留在系统临时目录，摘要不足时按需回查。**通过了**才把 `task.md` 的终态段写成**已合并、可清场**（连同合并提交与主树复验结果）。
7. **清场**：主代理删除 worktree 与分支——`.pipeline/` 随它一起消失。任务结束时清理成功命令的临时日志；失败日志至少保留到原因确认、修复和复验完成。

审查不通过、合并失败、中途放弃，这几种情况分别怎么办：

- **问题在实现**（跑不通、做错了）→ 原地重做；
- **问题在描述**（标准本身错了）→ 重写任务描述，**并删掉上一轮的 `executor.md` 与 `reviewer.md`**（别让下一轮的人读到作废的结论），重新派执行者与审查者；
- **合并有冲突** → 不要主代理自己解（那等于它改产品代码，而且改完没人审）：退回执行者，让它在自己的 worktree 里把主分支并进来、解冲突、重跑验收，然后重新走第 5、6 步；
- **主树复验不通过**（worktree 通过但主树不通过）→ 这次合并退回去，保留 worktree 与四个文件，按「问题在实现」退回执行者重做——**不许写「可清场」，不许清场**；
- **用户中途说不做了** → 和清场同一个动作：删掉 worktree 与分支，`.pipeline/` 随之消失。

不另起 `<id>`，不留接替痕迹。

## 测试驱动

一次只做一条验收标准。每条标准走这三步，走完再换下一条：

1. **先写测试**：给这条标准写会失败的验收测试。它必须失败，且失败的原因必须是**要做的事还没做**——不是环境坏了、也不是测试写错了。
2. **再写最小实现**：只写让这条测试通过所需的最少代码。**不要顺手把下一条标准也做了**——那是下一轮的事。
3. **然后重构**：在测试保持通过的前提下整理代码。确实没有可重构之处就跳过。

每一步都单独提交——**顺序是可查的事实，不是自我声明**。所以审查者**逐个检出只加测试的提交**，亲手跑一次看它确实失败，**跑完回到原来的分支尖端**，**再**看实现提交的 diff——那是发现测试被偷偷弱化的地方。

## 验收标准

**每条标准写成一个可执行的步骤序列**：做什么操作 → 期待什么状态变化。**不写测试文件名、不写断言实现**——那些会腐烂。

- 一个任务里有几个用户行为、每个行为有几条标准，就写几条，**逐条编号**，不要写成一段。
- 标准由主代理定，必须精确到能被人照着走一遍。
- **每条标准至少一条验收测试**，测试代码由执行者写。标准写在代码之前，所以测试可以先写。
- **判断权在审查者**：它**逐条标准**亲手走一遍入口，再判断对应的测试是否真的证明了那条标准。测试全绿不算通过——「看起来是端到端的、其实中间层全 mock 了」是这类工作里最常见的假通过。

## 证据与恢复

证据是主代理当场获得的事实：命令、退出码、超时状态、执行摘要、按需回查的长输出日志、后置验证结果和审查结论。用途是让主代理知道刚刚发生了什么、下一步该设计成什么样。

- **执行摘要不是语义证明。** 它是低成本、确定性的执行报告，至少说明退出码、是否超时、耗时、输出规模、临时日志路径，以及必要的头部、尾部和错误/失败/警告片段；不要求为每条命令调用 LLM，也不假设它理解了命令语义。
- **完整日志可回查。** 长输出命令的完整 stdout/stderr 放在系统临时目录；摘要不足以判断时，按范围或关键词读取原始日志，必要时重新执行更窄或机器可读的命令。关键验收不能只依赖摘要或退出码。
- **成功也要验证状态。** 命令退出码为 0 后，按验收标准检查实际状态变化；测试、构建、生成和迁移等命令分别确认测试执行、产物存在、文件正确或目标状态产生。
- **临时日志不进任务状态。** `.pipeline/` 只保留四个文件，不新增日志、摘要或 JSON 结果文件；日志路径可以写入 `executor.md` 或 `reviewer.md` 的结论，但不把完整日志复制进去。
- **不承担审计职能。** 任务做完了，结果就在代码里；做失败了，也不必留一份失败档案。
- **不进入 Git。** 它就在被忽略的 `.pipeline/` 里，随时可删。
- **不另建落盘处。** 除了 `.pipeline/` 本身，没有报告目录、没有归档区、没有 JSON 结果文件。

代价说清楚：换机器、重新 clone 都会丢掉 `.pipeline/`；**`git clean -fdx` 会连整个 `.worktrees/` 一起删掉——那里是正在进行的工作，不是缓存。** 它服务的是同一台机器上换一个 agent 软件继续干，不是异地恢复。

## 不可违反的规则

1. 没有独立审查就没做完。自检、自己审自己、主代理替执行者背书，都不算。
2. 先写任务描述再开工；**`task.md` 只有主代理写**。描述改了，此前的审查结论一律作废，**上一轮的 `executor.md` 与 `reviewer.md` 一并删掉**。
3. 一个任务一个 worktree，固定在 `.worktrees/<id>`。不建第二个，不在仓库外建。
4. 测试驱动的顺序不能倒。没有失败的测试，就没有实现。
5. 长输出命令的完整 stdout/stderr 必须保存在系统临时目录；进入上下文的是执行摘要，摘要不足时按需回查原始日志。
6. 退出码为 0 不能替代验收；必须检查验收标准要求的实际状态变化。
7. 合并后必须在主工作树再跑一次验收。worktree 通过 ≠ 主树通过。
8. 做完就清场：删掉 worktree 与分支，`.pipeline/` 随它一起消失。
9. 缺产品决策、协议兼容、外部服务或权限时停下来问用户，不自己定案。
