# Canary Drill：验收网金丝雀演练

## 这是什么，测的是什么

一段代码刚通过验收。本 skill 把"刚验收的 diff"当作突变对象：从验收点切出一次性工作区，由一个与验收流程完全隔离的埋雷者在其中埋入少量伪装良好的 bug，然后让**用户现有的验收流程原样运行**——它不知道有演练。跑完后由判卷者对照预注册的埋雷清单打分：每个 bug 被哪扇门拦住、哪个 bug 漏掉了。

**它测的是网，不是代码。** 演练只有三种合法结局：

1. **网得到校准**——每个 bug 都归因到了具体的门，用户知道自己的安全水平长什么样；
2. **网被证明有洞**——某些 bug 漏掉了。这是有价值的坏消息，报告必须给出明确的补救方向；
3. **演练无效**——锚点 bug 没被拦住，或清单与工作区实际不符。如实报告"演练无效"并说明排查结论，绝不产出一个虚假的"一切正常"。

一个从不说"你的网很好"的演练才是可信的演练。

## 何时运行

以下时机供用户规划演练节奏参考；本 skill 只在用户主动发起时运行，agent 不得据此自动触发或主动提议。

必跑：

- **验收网组成变化后**——增删测试套件、修改 review 指令、更换模型、新增验收剧本。被测对象变了，旧校准作废；
- **某类能力首次落地后**——网第一次面对这类代码，覆盖情况未知；
- **大里程碑/综合验收通过后**——网刚被组装或扩充过，正是校准的时候。

建议跑：

- 把流程托付给更高风险场景之前（真实生产数据、对外开放服务）——先测网的真水平，再决定交不交；
- 心跳：每 10–20 次验收、或每月一次（先到为准），防网的静默衰减（依赖更新让测试失效、模型更新改变 review 习惯，这些都不会通知你）。

不跑：

- 文档/配置类提交、diff 里没有真实行为变化的提交；
- 验证预算超限时（经验标尺：演练开销 ≤ 验证总投入的 10%）。

## 铁律（违反任何一条，演练作废）

1. **只能由用户主动发起。推荐在没有任何工作上下文的新会话中运行**；若当前会话包含被演练代码的实现、评审或验收讨论，不自动终止——在第一阶段向用户说明影响（编排会话的历史特征串会让污染自检的证据强度降级），由用户决定继续或新开会话，继续则在报告证据链中显著标注。对网的隔离不受会话新旧影响：它靠预写模板结构性保证，不靠编排者的记忆空白。
2. **一切改动只发生在一次性 worktree，且 worktree 建在真实仓库之外。** 演练提交永不合并进真实分支，演练结束即销毁 worktree。位置在第一阶段确认：优先持久临时目录（`mktemp -d` / 平台等价物），其次用户确认的项目外目录；**永不默认放入仓库内部**（哪怕 gitignored）——环境所迫必须如此时，只能在第一阶段经用户明确确认。
3. **埋雷清单写在项目外**（默认 `~/.canary/<drill-id>/manifest.md`，沙箱不可写时可用 `CANARY_HOME` 指定等价目录），永不进入仓库、永不被 git 跟踪。
4. **编排者（运行本 skill 的会话）不读清单内容**，只持有路径、SHA256 与数量。原因与万一读了怎么办，见"角色与信息隔离"。
5. **所有 subagent 的提示词使用 `references/prompts/` 里的模板**，编排者只填变量（路径、drill-id、门清单），不得自行措辞。原因：编排者可能偶然读到敏感内容，预制模板保证它知道什么都流不进网里。编排者可附加"环境事实"段落（cwd 行为、依赖与端口状态、无关文件警告、转录解压配方、大 diff 的抽样提示），其中不得出现清单内容、bug 信息或任何要求网提高警惕的措辞。
6. **证据不足一律按"漏掉"计**；锚点 bug 未被拦住、或清单与工作区实际改动不符 → 判"演练无效"。
7. **用户是考官**：可以随时打开清单核对——清单对 agent 隐藏，对用户从不隐藏；唯一纪律是不向验收网的 agent 提及演练的存在。
8. **环境偏离先说明。** 流程分两段：第一阶段完成环境预检与规则确认并取得用户明确许可，第二阶段连续执行、不再打断。执行中遇到第一阶段未预见的限制（权限拒绝、路径不可持久、后台不可用等），停下向用户说明情况并确认处置——禁止静默提权，禁止静默更换已确认的位置或方式。

## 角色与信息隔离

| 角色 | 在哪 | 知道什么 | 绝不知道什么 |
|---|---|---|---|
| 用户 | 演练会话 | 一切（考官） | — |
| 编排者 | 演练会话 | 正在演练；清单路径+哈希+数量 | bug 的位置与内容 |
| 埋雷者 | 新鲜 subagent | bug 是什么、怎么伪装 | 验收网是谁、何时跑 |
| 验收网 | 新鲜 subagent | 和平时验收一模一样的材料 | 有演练这回事 |
| 判卷者 | 网跑完后才生成的全新 subagent | 清单 + 网的全部结果 | （此刻才被允许读清单） |

为什么这样能成立：编排者的知识要想污染演练，只有一条通道——它撰写的验收网提示词。本 skill 把三类 agent 的提示词全部预制在 `references/prompts/` 里，编排者只填路径变量，没有自由发挥的入口；它的上下文里也从头到尾没有 bug 的位置与内容（埋雷者只回传路径+哈希+数量），想泄题都泄不了。判卷阶段会用污染自检验证这一点确实成立（扫描编排会话转录中是否出现过清单特征内容）。

## 执行流程（两段式：先确认，后执行）

### 第一阶段：信息确认（与用户对话，结束时拿到明确许可）

**第 0 步：会话评估、环境预检与规则确认**

0. 会话评估（铁律 1）：检查当前会话是否包含被演练代码的实现、评审或验收讨论。有 → 不自动终止，把影响（污染自检证据强度降级）列入环境约束报告，由用户决定继续或新开会话；与演练对象无关的其他工作上下文不构成障碍。
1. **环境预检**（只探测、不处置，结论进第 4 项的环境约束报告）：
   - 清单主目录 `${CANARY_HOME:-~/.canary}` 是否可写；不可写 → 准备好选项（授权提权 / 改用 `CANARY_HOME`），不自行提权；
   - worktree 候选位置的持久性探测：在候选目录创建标记文件、跨命令验证仍在（沙箱化环境的 `/tmp` 可能每命令独立重建）；候选优先级：持久临时目录（`mktemp -d` / 平台等价物）→ 用户指定的项目外目录；
   - 受限环境补充观察（有异常就记入报告）：后台任务是否可用（不可用则后续一律前台执行）；编排会话转录是否压缩（多帧 zstd 需流式解压，判卷要用，把解压配方记下来）。
2. 与用户确认演练对象，**拆成两个参数**：worktree 切出 commit（默认最近验收提交 / main 顶端）与 diff 基线 commit（"刚验收的代码"指哪段 diff）。两者可相同可不同；用户只给一个提交时，先核实它是否包含真实行为变化，再确认它扮演哪个参数。
3. 与用户确认**网的组成**与**档位**：门的清单从项目的 CLAUDE.md/AGENTS.md、package.json scripts 和用户口述中拼出（如 typecheck → 单元测试 → code-review → 验收剧本），向用户复述确认——它是判卷归因的坐标系。档位：轻（1 锚点 + 1 真实档）/ 标准（1 + 2，默认）/ 加测（1 + 3 + 1 边界探针）。
4. 提交**演练计划**请用户确认：对象两参数、门清单、档位、worktree 位置（含持久性探测结论与备选）、清单主目录，以及**环境约束报告**——哪些预检项受限、将需要什么权限或替代方案。此步骤同时预检 diff：没有真实行为变化（纯文档/配置/几行修补）→ 告诉用户"这次不值得跑"并结束。**用户明确确认前，不进入第二阶段。**

### 第二阶段：执行（确认后连续完成，中途不再打断）

**唯一例外是铁律 8**：遇到第一阶段未预见的限制（权限拒绝、路径不可持久、后台不可用），停下向用户说明情况并确认处置，然后继续。

注意：启动时向用户确认的是**规则**（对象、门、档位），不是答案。数量在最终报告里给出——考前确认一个埋雷者自我报告的数字是掌控的表演，不是掌控。

### 第 1 步：搭建一次性工作区

生成 drill-id（格式 `canary-YYYYMMDD-HHMM`），在第一阶段确认的位置创建 worktree：

```bash
git worktree add <worktree_path> <切出commit>
```

worktree 必须在真实仓库之外（铁律 2）。后续所有角色的操作都限定在这个目录内。

### 第 2 步：埋雷

1. Read `references/bug-menu.md`（错误形态清单与选址规则）。
2. Read `references/prompts/planter.md`，填入变量：{{worktree}}、{{accepted_point}}、{{manifest_path}}（`~/.canary/<drill-id>/manifest.md`）、{{counts}}（按档位）、{{bug_menu}}（上一步读到的清单全文内嵌——subagent 无法自行加载 skill，必须内嵌）。
3. 将填好的全文作为**一个全新 subagent 的完整提示词**执行。
4. 埋雷者只允许返回四行：MANIFEST_PATH / MANIFEST_SHA256 / COUNTS / MECHANICAL。若返回中出现任何 bug 位置或内容描述 → 违规，要求重做并在判卷时标记。

### 第 3 步：登记与机械校验

1. 编排者记录：drill-id、清单路径、SHA256、数量、目标提交、门清单。
2. 编排者独立重跑 worktree 内的 build 与 typecheck（只这两样——机械门的结果不含 bug 位置信息；**不要**预跑测试和 review，那些是网，提前跑污染时序）。
3. 机械门红了 → bug 太浅（语法/类型层），无演练信号。回到第 2 步重新埋雷（告知重埋原因时只说"未通过机械校验"，不说哪扇门红）。

### 第 4 步：放网

1. Read `references/prompts/net-runner.md`，填入变量：{{worktree}}、{{doors}}（第 0 步确认的门清单——每扇门含名称、确切命令或审查程序、判定标准）、{{spec_paths}}（该功能的规格/ticket 路径，若有）、{{results_dir}}（`~/.canary/<drill-id>/results/`）。
2. 作为**全新 subagent** 执行。提示词必须与用户平时的验收流程一字不差——唯一的区别是工作目录指向埋了雷的 worktree。让网真实的关键不是"发生在旧会话"，而是三样东西不变：材料一样、程序一样、它不知道有演练。
3. 网的输出逐门落盘：`{{results_dir}}/door-<序号>-<名称>.log`，review 类发现另写 `door-<序号>-<名称>-findings.md`。

### 第 5 步：判卷

网全部跑完后，Read `references/prompts/judge.md`，填入变量：{{manifest_path}}、{{results_dir}}、{{worktree}}、{{accepted_point}}、{{orchestrator_transcript}}（本会话转录的位置与获取方式；若第一阶段发现转录为多帧 zstd 压缩，一并附流式解压配方）、{{net_composition}}，作为**全新 subagent** 执行。这是全流程中唯一允许读清单的角色。

判卷者职责（细节见其模板）：重算清单哈希 → 逐 bug 做清单↔工作区在场比对 → 扫描编排会话转录做污染自检 → 逐门归因每个 bug（拦截/漏掉/证据不足从严计漏）→ 锚点检查（未拦住 = 演练无效）→ 按 `references/report-format.md` 产出人话报告与行动建议。

### 第 6 步：销毁与报告

1. 判卷报告返回后销毁工作区：`git worktree remove --force /tmp/<drill-id>`。
2. 向用户呈现判卷者的人话报告（以判卷者产出为准，不润色结论、不淡化漏掉）。
3. 报告末尾印出清单路径，注明：考官可随时核对原始答案。

## 无 subagent 能力时的降级

按优先级：

1. **无头 CLI 会话**：对每个角色用 headless 方式执行模板化提示词（如 `claude -p "<填好的提示词>"`），每个角色一个独立进程 = 独立上下文。
2. **人肉三会话**：把三个角色的模板交给用户手动执行——埋雷会话跑第 2 步；用户把 net-runner 模板（不含任何演练信息）带到一个新会话跑第 4 步；判卷会话跑第 5 步。此模式必须额外提醒用户：传话时不要提演练。

架构的本质是"互不知情的有界新鲜上下文"，subagent 只是最顺手的一种实现。

## 交互口径（面向不懂代码或懂得不多的用户）

- 用户在带有工作上下文的会话里提到演练时：若上下文涉及被演练代码，说明影响（污染自检证据降级）并由用户选择继续或新开会话——不自动终止，也不沉默继续；与演练对象无关的工作上下文不构成障碍。
- 全程人话。报告与对话中不出现"突变分数""覆盖率""mutation score"这类术语。
- 启动时确认的是规则与环境（对象两参数、门、档位、worktree 位置、所需权限）；数量在最终报告里给出。考前确认一个埋雷者自我报告的数字不提供任何验证价值——掌控感来自四条证据链，不来自确认仪式。
- 环境受限时（权限不足、路径不可持久、后台不可用），正确口径是说明情况、给出选项（授权 / 换位置 / 改前台 / 放弃）、等用户选择——不静默提权，不静默降级。
- 报告必须包含：每个 bug 的人话判词（被哪扇门拦住/漏掉，及一句"这意味着什么"）、四条证据链状态（锚点拦截 / 清单在场比对 / 哈希一致 / 编排者污染自检）、行动建议（漏掉的 bug 若可测试化 → 建议补什么测试；review 拦住的 → 建议固化为测试；review 漏掉的类 → 建议调整 review 关注点）、清单路径。
- 累计视角：提醒用户"网的能力地图"靠多次演练累积，单次只是抽样；不同里程碑的演练会覆盖不同行为单元，几轮之后这张图才完整。

## 与用户项目约束的衔接

若用户项目的 AGENTS.md/CLAUDE.md 规定"subagent 不能自行加载 skill，委派时必须内嵌方法与约束"——本 skill 的设计已天然满足：三个角色的提示词模板就是为逐字内嵌而写的。编排者内嵌时不得删减纪律段落。
