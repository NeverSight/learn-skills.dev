# AIエージェントのアプリ画面

エージェントの画面は、応答を待つ時間と、途中経過の見せ方で印象が決まる。ここで手を抜くと、固まって見えるか、逆に飾りの多い「AIらしい」画面になる。見た目の一般則は `app-ui-design` にあり、ここではエージェントに固有のことだけを書く。

利用者は「チャットアプリを作って」としか言わないのが普通。応答の流し込み、考え中・ツール実行中の表示、Markdown の表示は、頼まれなくても最初から入れる。逆に、ここに書いていない部品は足さず、要りそうなら1行で提案する。

## 1. 本物で作る

- **LLM の代わりに、定型文を返す偽の実装で画面を作らない。** キーワードの有無で返答を切り替える、テンプレートの文字列を組み立てる、といった「動いているように見えるだけ」の実装は、画面の確認にも使えない。最初から本物のモデルにつなぎ、段階ごとに動かして確かめる
- **偽の実装が要るのは、認証の無い環境で見せるだけ、のような明確な理由があるときに限る。** その場合は、偽物であることを画面か README に書く

## 2. 応答の表示

- **応答の Markdown は描画して見せる。** 見出し、箇条書き、表、強調、コードがそのまま記号で並ぶ `white-space: pre-wrap` の表示で済ませない
- **最初のひと言は、エージェントの発言として1つ置くまで。** 画面の見出しにしない。きらめきの絵文字やロボットの絵を添えない
- **アバターやアイコンで「AIらしさ」を足さない。** 光る球、脳、回路の模様は使わない。応答の中身が主役
- **送信前の空の画面に、使い方の説明や例文のカードを何枚も並べない。** 置くなら入力欄と、最初のひと言だけ

## 3. 待ち時間と途中経過

応答を待つ間に何も動かないと、利用者は固まったと判断する。途中経過は飾りではなく、意味のある動きとして残す。

| 状態 | 見せ方 |
|---|---|
| 考え中（最初のトークンが来るまで） | 「考え中」の文字に、光が左から右へ流れる程度の控えめな動き |
| ツールの実行中 | 何をしているかを1行で。検索ならクエリ、取得なら対象の名前を添える。横に小さな回転の印 |
| ツールの完了 | 同じ行を「完了」の文言とチェックの印に置き換える。行を増やさない |
| 長い生成（数十秒以上） | 回転の印に加え、数秒ごとに入れ替わる短いヒントを1行 |
| 本文の生成中 | 文字が届いた順に描く。末尾にカーソルの印 |

- **同じ状態の行を重ねて出さない。** 進行中の同じ状態があれば追加しない。モデルによっては同じツールの開始を何度も送ってくる
- **本文の文字が届いたら、進行中の状態を全部「完了」へ更新する。** 文字の到着は、その前のツールが終わった合図になる。複数のツールが並行して動いたときも、この1か所でまとめて閉じる
- **ツールの実行中は本文のカーソルを隠す。** カーソルが点滅したまま止まると、固まって見える
- **検索のクエリが変わったら、古い行を消して新しい行を出す。** 同じ「検索中」が何行も並ぶと読めない
- **途中経過の表示は、費用の節約を理由に黙って止めない。** 利用者にとっては、止まった画面と区別がつかない。減らしたいなら案として出す

実装の注意（React）は `references/streaming.md`。

## 4. ログイン画面

デモアプリやエージェントアプリのログインは、入口を2つに絞る。

- **1画面目は2択だけ。** 「Google で続ける」と、メールアドレスの入力欄＋「メールで続ける」
- **パスワードの欄を置かない。** メールの次の画面では「パスキーでログイン」と「メールにコードを送る」を常に並べる
- **パスキーを登録済みかどうかで画面を出し分けない。** 出し分けると、そのメールアドレスが登録されているかを第三者に教えることになる。存在しないアドレスも認証の失敗も、表示は同じ文にそろえる
- **メールのコードでログインした人には、成功の直後に一度だけパスキーの登録を案内する。** ボタンは「パスキーを登録」と「あとで」の2つ。「あとで」なら一定期間（30日など）は再び案内しない
- **コードが届かない人への案内は、コード入力の画面に置く**

## 5. 人前で操作する画面（発表・デモ・画面共有）

人に見せながら操作する画面は、見る人と操作する人が別にいる。2人分の部品を1画面に混ぜない。

- **見せる画面と、操作する部品を分ける。** 見せる画面には、その場で必ず使う操作（終了、やり直し）のボタンだけを置き、それ以外の操作は別のウィンドウへ寄せる。操作ボタンが見せる画面の下に並ぶと、見る人には意味が分からず、操作する人にも手順が読めない
- **操作はマウスだけで完結させる。** キーボードのショートカットと、ボタン横の `Enter` `Esc` のようなキー表示を付けない。キーでしか呼べない操作は、発表中には無いのと同じになる
- **人が操作する番と、自動で進む番をはっきり分ける。** 人の番には押すボタンを1つだけ大きく出し、押すまで進めない。自動で進む番にはボタンを出さない。「一定時間たったら次へ進む」のような自動の進行と、「次へ」のボタンを同じ画面に並べると、押そうとした瞬間に画面が変わる
- **会場の遠い席から読めない大きさの文字を置かない**
- **頼まれていない状態表示を、目に入る場所へ出さない。** 同期中、処理中、接続中のような表示をメニューバーや常時見えるバッジに出すと、画面共有の最中にそのまま相手へ見える。目立たないこと自体が要件になるアプリもある。状態表示が要ると思ったら、実装せずに提案する
- **画面に載せる機能は、依頼者が挙げた範囲に絞る。** 気を利かせて足した機能は、説明の時間を奪う。足したい機能は論点として出す
- **当日は固定の URL で開ける形にしておく。** 現地でサーバーを起動する運用は、失敗の要因を増やす。端末の中でしか動かない部品があるなら、ネットにつないだ直後に1手で起動できる形にし、開く URL と手順を1か所にまとめる
- **直前の修正は、動いていた版を控えてから入れる。** 本番と同じ入力の経路（実際の入力機器や、見る人が使う端末）で自分で通してから反映する。通せない修正は入れない

## 6. 作業の横で動く補助ツール

会議や作業の横で、助言や通知を出し続ける小さな画面の作法。

- **フォーカスを奪わない。** 新しい情報が来ても、利用者が操作している別のアプリから入力を取り上げない
- **新着は上に積む1列にする。** 節に分けない
- **閉じる、既読にする、のような操作を増やさない。** 作業中に手を取らせない
- **通知は色の変化だけにする。** 赤、音、文字のバッジは使わず、画面共有に映っても意味が読み取られない形にする
- **外側を押しても閉じないようにする。** 範囲選択のスクリーンショットを撮るたびに閉じると使えない
