嚴謹且具可辯護性的電子郵件偽造判定與 SPF 供應鏈風險分析，僅根據已發布的 DNS 計算。深入攻擊性 OSINT 武庫中第 16.14 節的記錄層級 SPF/DMARC/DKIM/BIMI/MTA-STS/DNSSEC 抓取配方，補足該節未涉及的推理：依優先順序排列的綜合判定，判斷攻擊者是否真的能將標頭 From 偽造的郵件送入收件匣，以及透過哪種向量（精確域名 vs 子域名）——基於電子郵件安全中最容易被誤解的區別：SPF 驗證的 envelope MAIL FROM 與僅受 DMARC 監管的可見標頭 From:。精確說明為何僅使用 SPF -all/~all 並非防偽的保證，除非有 DMARC 強制，並說明即使在 p=reject pct=100 的情況下，SPF +all 仍會繞過 DMARC。涵蓋 RFC 7208 第 4.6.4 節所列的 10 次 DNS 查詢／2 次空查詢 PermError 失效開放條件，提供可直接執行的僅使用標準函式庫的查詢計數腳本，並說明 SPF‑include 接管供應鏈向量（攻擊者重新註冊已失效的 include，繼承對目標域的 SPF 通過權限），搭配嚴格的瞬時錯誤與 NXDOMAIN 區辨策略，確保暫時的 SERVFAIL 不會被誤判為接管線索。完全被動：僅讀取 DNS TXT，未發送郵件、未執行 RCPT TO 探測、亦不使用 API 金鑰。適用於審核域名的實際防偽能力（不僅是其公布的記錄），向客戶說明「我們有 SPF -all」並不代表已被涵蓋，調查 SPF PermError 或異常長的 include 鏈，評估失效的 SPF include 是否為接管線索，或撰寫可辯護的偽造性發現以供交付。
