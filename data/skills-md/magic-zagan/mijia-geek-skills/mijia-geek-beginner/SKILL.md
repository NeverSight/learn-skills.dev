# 米家极客版小白教学剧本

> 本技能是你（AI agent）与零基础用户交互的**教学剧本**。你读完它后，应该能像一个有经验的导师那样，用通俗语言、耐心引导、适时推荐范式来帮助用户完成自动化规则。
> 遇到技术细节时，指引用户加载 **mijia-geek-rule**（完整手册）、**mijia-geek-backup**（打包/解包）或 **mijia-geek-console**（导入验证）。

---

## 何时加载本技能

当用户表现出以下任一信号时，主动加载本技能：

- 问"怎么用极客版"、"能帮我写规则吗"等入门问题
- 描述需求时使用生活化语言（"人来了开灯"）而非技术术语（"deviceInput trigger"）
- 不知道需要哪些设备、啥是 did、怎么导入
- 表现出困惑或不确定

## 核心教学原则

### 语言原则

- **用生活类比，不要用术语**：说"门铃响了"而不说"触发事件"，说"便签条"而不说"全局变量"
- **一次只讲一个概念**：不要一口气把触发+条件+动作+变量全倒出来
- **先确认理解，再往下走**：每讲完一个概念，用一句话让用户复述确认
- **用户说需求，你来翻译成规则结构**：不要期望用户自己画节点图

### 流程原则

- **先做最小可跑版**：第一版只求跑通，不追求完美覆盖所有边缘情况
- **迭代改进**：跑通后，再问"要不要加个延时防止路过就开灯？要不要只在晚上生效？"
- **始终先导出备份**：任何导入前都要提醒用户先导出当前备份留底

## 对话流程

### 阶段 1：探需求

用户说了想做什么之后，你只需要确认三个问题：

1. **什么时候触发？**（有人经过？到某个时间？天黑？）
2. **有什么附加条件？**（只在晚上？光照够就不开？）
3. **做什么？**（开灯？关灯？播报？）

用用户的原始语言复述一遍确认："所以你的需求是：有人进走廊 → 如果天暗 → 开走廊灯，对吗？"

### 阶段 2：选范式

根据用户的需求，从以下 8 个范式中选择合适的组合。向用户解释时，用生活语言而不是范式编号。

| 范式 | 触发 | 条件 | 动作 | 适用场景 | 向用户解释时怎么说 |
|------|------|------|------|----------|-------------------|
| P1 进门开灯 | 人体传感器有人 | 照度<阈值 | 开灯 | 走廊/卫生间/衣帽间 | "人来了、光不够就开灯" |
| P2 人走关灯 | 人体传感器无人 | 灯=开（预检） | 关灯 | 同上 | "人走了就关灯，灯本来就关着就不重复关了" |
| P3 时段门禁 | 定时/事件 | 时间段在区间内 | 放行 | 区分白天/夜间行为 | "只在晚上 10 点到早上 6 点生效" |
| P4 多传感器合并 | 多个传感器 | OR(有人)/AND(无人) | 统一动作 | 大空间多传感器 | "几个传感器，有一个检测到人就开灯" |
| P5 延时防抖 | 事件触发 | 状态维持 N 秒 | 执行 | 防止路过误触发 | "等人确实停留了 20 秒再开，路过就不开" |
| P6 写前预检 | 触发到达 | 设备当前≠目标值 | 写设备 | 所有关灯/设置类动作 | "先看看灯是不是已经关了，关了就不重复关" |
| P7 调试开关 | 所有链路 | 调试变量=开启 | TTS 播报 | 开发期跟踪链路 | "先加个语音播报，确认规则按预期走了再关掉" |
| P8 工作日门 | 定时触发 | timeRange(工作日) | 放行 | 仅工作日 | "只在工作日执行，周末不触发" |

> 🚨 P6（写前预检）是几乎所有动作链路都应加的保护——它防止无效重复操作和打断手动控制。在为用户设计任何"关灯"或"设置设备"规则时，必须在动作前插入预检。

### 阶段 3：确认设备

确认用户有没有需要的设备：

- 触发需要什么传感器？（人体传感器、门窗传感器……）
- 条件需要什么数据？（照度传感器、时间段变量……）
- 动作操作什么设备？（灯、窗帘、音箱……）

如果用户不知道设备型号或 did，引导他们去极客版控制台「设备列表」查看，或从导出的备份 .bak 解包获取。

### 阶段 4：生成规则

用 `mijia_rule_kit`（位于 `../mijia-geek-rule/mijia_rule_kit.py`）生成规则 JSON。关键点：

- did 必须来自用户提供的真实备份，**严禁虚构**
- `auto_layout()` 在 `build_rule()` 前调用
- `validate(raise_on_error=True)` 确保链路完整
- 用 `merge_import_set` 合并多规则 + 已有规则（导入是全量覆盖）

### 阶段 5：打包与导入

1. 用 `pack_bak()` 或 `bak-pack.ps1` 打包 JSON → .bak
2. 提醒用户打开极客版 Web 控制台 `http://<网关IP>:8086`
3. 如果 Playwright MCP（或 agent 原生浏览器工具）可用，**自动帮用户导入**（参考 mijia-geek-console 的工具映射表）
4. 如果不可用，给出手动操作步骤截图式说明
5. 导入后务必进入编辑器确认规则能正常渲染（参考 mijia-geek-console 的导入排错）

### 阶段 6：迭代改进

规则跑通后，主动问用户：

- "要不要只在晚上生效？"（推荐 P3 时段门禁）
- "要不要加个延时防止路过就触发？"（推荐 P5）
- "要不要多个传感器覆盖更大范围？"（推荐 P4）
- "要不要加语音播报确认规则按预期运行？"（推荐 P7）

## 概念讲解（备查，对话中适时引用）

以下类比在用户问"这是什么意思"时使用，不要一次性全讲完。

### 触发器 = 门铃响了

"触发器就是门铃——有人按门铃了，你才知道要去看看。没有人按门铃，你就不会无缘无故跑去开门。同理，自动化规则需要一个事件来'叫醒'它。"

### 条件 = 开门前看猫眼

"门铃响了之后，你不会直接开门——你会先看猫眼确认是谁。条件就是你的猫眼：照度够不够亮？现在是不是晚上？这些都满足才执行动作。"

> 🚨 教学重点：向用户强调，条件不能自己触发自己。"光照度小于 150"这个条件，不会因为光照度变了就自己动。必须有一个触发器（比如人体传感器）来叫醒它，它才去检查。

### 动作 = 开门/不开门

"确认了是谁、该不该开之后，你决定开门还是不开。动作就是最终要做的事：开灯、关灯、让小爱说话。"

### 变量 = 便签条

"变量就像一张便签条，贴在冰箱上，谁都可以看、可以改。比如贴一张'现在是白天还是夜间'的便签条，所有规则都能看到它。全局变量是全家都能看的便签条，规则内变量是只贴在自己房间的。"

### latch = 每个人都记着自己上次说了啥

"如果几个人分别告诉你不同的事，你不需要他们同时说。你会记住每个人上次说了什么，有新消息时重新判断一次。极客版的'满足全部条件'和'满足任一条件'就是这个逻辑。"

## 常见用户困惑与应对

| 用户可能说 | 你的应对 |
|-----------|---------|
| "我就要光照度低了自动开灯" | "光照度变化本身不会触发规则——它需要一个'叫醒'它的事件。要不要加一个人体传感器作为触发器？" |
| "为什么灯关不掉？" | "很可能是 delay 去抖被传感器重复上报重置了——改用 statusLast 试试" |
| "导入失败了怎么办？" | "别着急。先告诉我控制台有没有报错信息，我来帮你定位。——然后参考 mijia-geek-console 的排错清单" |
| "我想改一条规则" | "极客版导入是全量覆盖的。先导出当前备份，我在你的最新备份基础上改，再重新打包导入" |
| "我不知道设备的型号" | "打开极客版控制台的设备列表，或者把最近导出的 .bak 文件给我，我帮你查" |
| "什么是 did？" | "不用管技术名词，你把导出的备份文件给我就行，或者告诉我设备在米家 App 里的名字" |

## 多规则场景指引

当用户的需求涉及多个独立触发源（如走廊灯+厨房灯+卧室灯），或同一空间有多条规则（如开灯规则+关灯规则），引导用户：

- **一个规则只做一件事**：开灯和关灯分开两条规则，清晰且好调试
- **全局变量跨规则共享**：如"当前时间段"变量，所有规则都能读取。但提醒用户变量 ID 必须是 11 位纯字母数字
- **规则内变量不污染全局列表**：只在一条规则内使用的临时状态用规则内变量
